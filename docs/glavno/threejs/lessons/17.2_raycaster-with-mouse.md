## Concept

The [previous lesson](17.1_raycaster-test-on-each-frame.md) cast a ray per-frame, but the ray's origin and direction were **hardcoded**. This app closes the loop: the ray **follows the mouse**, so hovering the cursor over a moving sphere makes the ray hit it and change its color live.

The key idea is that Three.js will do all the heavy lifting. You give the raycaster the camera and a normalized mouse position, and it works out the ray's world-space origin and direction for you — no manual math on your part.

### Mouse coordinates must be normalized, not in pixels

Mouse events give you pixel positions (`e.clientX`, `e.clientY`) that go from `0` to `window width/height`. But the raycaster's `setFromCamera` expects a **normalized device coordinate (NDC)** — a value from `-1` to `1` on each axis.

The app converts pixel → NDC in the `mousemove` handler:

```ts
mouse.x = (e.clientX / sizes.width) * 2 - 1;  // 0..width  → -1..1
mouse.y = -((e.clientY / sizes.height) * 2 - 1); // 0..height → -1..1 (Y flipped)
```

The `y` is negated because screen space has `+y` going *down* while NDC has `+y` going *up* — the vertical axis is flipped.

The code shows the progression, starting from `0..1`, then `-0.5..0.5`, then the `-1..1` form (which is what `setFromCamera` wants).

### Cast the ray in the tick function, not in the mousemove handler

This is the lesson's **main rule**. The `mousemove` handler fires *far more often* than the animation loop renders a frame. If you called `raycaster.intersectObjects()` inside the handler, you'd be:

1. Doing redundant CPU-side intersection math many times per frame — wasted work.
2. Harming a frame's consistency: the mouse may fire 5 times between two renders, so each render gets a *different, arbitrary* ray position from whichever handler ran last. Raycast results become tied to input frequency, not to the render cadence.
3. Messing up the reset-then-apply color pattern — you'd be resetting and recoloring spheres mid-frame, possibly multiple times between renders.

The solution is to **only record the mouse position** in the handler, and do all the raycasting + coloring inside `tick()`, once per frame.

```ts
// mousemove handler — just store the position
window.addEventListener('mousemove', (e) => {
	mouse.x = (e.clientX / sizes.width) * 2 - 1;
	mouse.y = -((e.clientY / sizes.height) * 2 - 1);
});

// tick() — the raycaster runs once per rendered frame
function tick(timestamp: number) {
	// other per-frame updates (sphere motion)...

	// orient the ray from the camera through the mouse's NDC point
	raycaster.setFromCamera(mouse, camera);

	const intersections = raycaster.intersectObjects(objectsToTest);

	// reset-then-apply colors...
	renderer.render(scene, camera);
}
```

### `setFromCamera` — the mouse-picking raycaster method

Where `raycaster.set(origin, direction)` takes explicit world-space values, `setFromCamera(pointerNDC, camera)` derives them from the camera. It builds a ray that starts at the camera's position and travels *through* the normalized point on the camera's view plane — i.e. through whatever world-space point is under the cursor.

Because `setFromCamera` handles origin and direction for you, you never touch `rayDirection` or worry about keeping it unit-length. The two `// EXPLAIN:` comments in the code hint at this: no need to construct `rayOrigin`/`rayDirection` anymore since they're recomputed from the mouse coordinates.

### The read-frame feedback pattern

All three spheres share the same color value but each gets **its own** `MeshStandardMaterial` instance (same pattern as lesson 17.1). Each tick:

1. Reset every sphere back to the base `#e6cbe8`.
2. Darken (`#344e70`) the spheres whose `intersection.object` is a `THREE.Mesh` and that appear in `intersections`.
3. Render.

The spheres keep bobbing (three `Math.sin` frequencies), so as they sweep past the mouse-pointed ray you see the hovered spheres flash dark while they overlap it — then return to pink as they drift away.

## Code

in repo — `apps/17_2_raycaster_with_mouse`

```ts
import * as THREE from 'three/webgpu';
import { OrbitControls } from 'three/addons/controls/OrbitControls.js';

const scene = new THREE.Scene();
const renderer = new THREE.WebGPURenderer({ canvas });
await renderer.init();

const camera = new THREE.PerspectiveCamera(75, sizes.width / sizes.height, 0.1, 100);
camera.position.set(0, 0, 4);
scene.add(camera);

const orbitControls = new OrbitControls(camera, canvas);

// Three spheres, each with its OWN material so we can color them independently
const sphereColor = '#e6cbe8';
const sphere1 = new THREE.Mesh(geo, new THREE.MeshStandardMaterial({ color: sphereColor, roughness: 0.4, metalness: 0.3 }));
const sphere2 = new THREE.Mesh(geo, new THREE.MeshStandardMaterial({ color: sphereColor, roughness: 0.4, metalness: 0.3 }));
const sphere3 = new THREE.Mesh(geo, new THREE.MeshStandardMaterial({ color: sphereColor, roughness: 0.4, metalness: 0.3 }));
sphere1.position.x = -2;
sphere3.position.x = 2;
const objectsToTest = [sphere1, sphere2, sphere3];
scene.add(...objectsToTest);

const raycaster = new THREE.Raycaster();
const mouse = new THREE.Vector2(0, 0); // normalized device coords, -1..1

// mousemove: only RECORD the position — don't raycast here
window.addEventListener('mousemove', (e) => {
	mouse.x = (e.clientX / sizes.width) * 2 - 1;
	mouse.y = -((e.clientY / sizes.height) * 2 - 1);
});

const timer = new THREE.Timer();
renderer.setAnimationLoop((timestamp) => {
	timer.update(timestamp);
	const elapsed = timer.getElapsed();

	sphere1.position.y = Math.sin(elapsed * 0.3) * 1.5;
	sphere2.position.y = Math.sin(elapsed * 0.8) * 1.5;
	sphere3.position.y = Math.sin(elapsed * 1.4) * 1.5;

	// orient the ray through the mouse's NDC point, once per frame
	raycaster.setFromCamera(mouse, camera);

	const intersections = raycaster.intersectObjects(objectsToTest);

	// reset-then-apply: everything back to pink, then darken what's hit
	objectsToTest.forEach((ob) => ob.material.color.set(sphereColor));
	intersections.forEach((item) => {
		if (item.object instanceof THREE.Mesh) {
			item.object.material.color.set('#344e70');
		}
	});

	orbitControls.update();
	renderer.render(scene, camera);
});
```

## Gotchas

- **Don't raycast inside the `mousemove` handler.** It fires more times than the render loop draws frames, doing redundant intersection math and tying the raycast results to input frequency rather than frame cadence. Record the position in the handler; raycast once in `tick()`. The `// EXPLAIN:` comments in the code ask what problems would arise — this is the answer.
- **NDC vs pixel coordinates.** `setFromCamera` wants `-1..1` on each axis, but mouse events give you `0..width` / `0..height`. Forgetting to normalize makes the ray wildly off-screen. Remember the Y flip: screen `+y` is *down*, NDC `+y` is *up*.
- **Reset-then-apply, or colors stick.** Only *hit* objects appear in `intersections`. If you darken hits but never reset non-hits, the first sphere ever hit stays dark forever. Reset all to the base color first, then apply the hit color — same `// EXPLAIN:` lesson as 17.1.
- **Per-object colors need per-object materials.** Three meshes sharing one `MeshStandardMaterial` means changing one's color changes all three. Each sphere here gets its own material instance (same color *value*).
- **`setFromCamera` means you don't manage the direction.** The ray's origin and direction are derived from the camera, so you don't compute or normalize `rayDirection` by hand. If you had a manual `raycaster.set(...)` left over from 17.0/17.1 and also call `setFromCamera`, the manual set would be overridden each frame.
- **TypeScript wants a narrowing guard.** `intersection.object` is `Object3D` (no `.material`); `if (item.object instanceof THREE.Mesh)` narrows it to `Mesh`, which has one.

## Revisit

- **`setFromCamera` internals** — worth reading how it builds the ray (origin/camera position, direction through the view plane point) to fully internalize why you don't manage the vector by hand.
- **Why per-frame even when the ray follows the mouse** — the spheres here are animated, so per-frame is the minimum. For a fully *static* scene you could raycast on demand (`.onClick`) instead. The three.js `Raycaster` checks bounding spheres internally, but you still control what you feed it.
- **GPU-side picking** — when a per-frame CPU raycast over *thousands* of objects gets too slow, GPU picking (render IDs into an offscreen target, read a pixel) is the alternative. See the linked forum thread.
- **A helper worth revisiting** — the `RaycasterHelper` from `@gsimone/three-raycaster-helper` is imported in the code but commented out (line 4). Wiring it up (`raycasterHelper.hits = intersections; raycasterHelper.update();`) draws the ray and hit markers in the scene — a good way to *see* the mouse ray reaching out to the spheres.

## Outdated

approach is valid

> 🚀 This project already runs on the **WebGPU** renderer (`three/webgpu` + `WebGPURenderer`). The `Raycaster` is renderer-agnostic — it does CPU-side math against object geometries — so mouse-driven per-frame picking works identically on WebGL and WebGPU. If you ever need *GPU*-side picking (faster for scenes with thousands of objects), the WebGPU path offers async render-target pixel reads (`readRenderTargetPixelsAsync`), but here CPU raycasting is correct, portable, and fast.
