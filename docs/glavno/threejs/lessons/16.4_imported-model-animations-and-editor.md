## Concept

In [16.3_draco](16.3_draco.md) we loaded models that were completely **static** — a Duck, a Flight Helmet. Even when you printed the loaded glTF object, its `animations` array was empty. This lesson finally plays something: the **Fox** model from the [glTF-Sample-Models](https://github.com/KhronosGroup/glTF-Sample-Models) repo, loaded from `/models/Fox/glTF/Fox.gltf`. And as a side quest, the README asks us to learn what the **Three.js editor** is and how it can help test models.

### glTF carries animations natively

glTF is not just a geometry dump — the format **specifies how animations are stored** ([glTF 2.0 animations spec](https://github.com/KhronosGroup/glTF/tree/master/specification/2.0#animations)): node transforms (translation / rotation / scale, and more) are sampled over time as keyframes targeting specific nodes in the scene graph. That means an animated model you export from Blender, Maya or Mixamo arrives at Three.js **with its animation data intact** — no manual reconstruction. All you have to do is *read* that data and tell the scene to play it.

The Fox model's own README notes it demonstrates **animated rigging with three animation cycles: Survey, Walk, and Run**, all driving the same joints. Because they drive the same joints, **only one animation should be active at a time** — the client (us) decides which. glTF deliberately leaves *which* animation to play as a client-side choice.

### The animation pipeline: four objects

When you log `foxModel`, you see — next to `scene` — an **`animations` property: an array of `AnimationClip` instances**. Three.js parses every animation stored in the glTF file into its own `AnimationClip` (the log in the app shows exactly three, one per cycle). From there the pipeline is three more objects:

1. **`AnimationClip`** — a reusable "recording", a named set of keyframes. The keyframes are stored as **`KeyframeTrack`s**: `name` (e.g. `.bones[...]`, `position`, `quaternion`, `scale`), a `times` array (the moments in seconds when the value changes) and a `values` array (the actual animated values — 3 values per key for position/scale, 4 per key for a quaternion). A clip doesn't *do* anything by itself; it's just data.
2. **`AnimationMixer`** — the player. It's "like a player associated with an object that can contain one or many `AnimationClip` instances". You create it *bound to the object* whose properties will be animated:

```ts
const mixer = new THREE.AnimationMixer(foxModel.scene);
```

3. **`AnimationAction`** — a "take". A mixer can have the same clip playing several times with different settings (looping, speed, weight, fade times). Each of those configured plays is an `AnimationAction`, obtained via `mixer.clipAction(clip)`:

```ts
const action1 = mixer.clipAction(foxModel.animations[0]); // Survey
const action2 = mixer.clipAction(foxModel.animations[1]); // Walk
const action3 = mixer.clipAction(foxModel.animations[2]); // Run
```

4. The **animation loop** — the frame-by-frame `mixer.update(delta)` call that actually advances the clips. **Without this, nothing plays.**

This is a layer-cake over "just running" a model, and the README is honest about it: *"how to handle animations; well it is a lot of work; it is not that hard but it is a lot of work"*. The payoff is the expressive potential — a character that runs, blends into a gun-hold/gun-aim clip, holsters, etc. This lesson gets the gears turning; cross-clip **mixing** is a later chapter.

### Playing an animation takes exactly three steps

1. Create the mixer bound to the animated object: `new THREE.AnimationMixer(foxModel.scene)`.
2. Pull out an action from a clip and call `.play()`: `mixer.clipAction(foxModel.animations[1]).play()`.
3. Advance the mixer each frame with the **delta** time: `mixer.update(timer.getDelta())` inside the animation loop.

Step 3 is the `// EXPLAIN:` comment's warning — *"it won't play if you just do this"* (referring to `.play()` alone). `.play()` merely arms the action; the mixer only moves a clip forward when you feed it time. The app runs on a `THREE.Timer` (from the [3.3_animation-timer](3.3_animation-timer.md) lesson) and passes its per-frame delta into `mixer.update(delta)` — using the *delta*, not an accumulated elapsed time, because the mixer must know how far to advance the keyframes **per step**, not where to jump the playhead to (though an absolute time via `mixer.setTime()` exists too).

Why does "which animation" work the way it does here? The action the app arms is `animations[1]` (Walk). The Fox's README stresses the three cycles drive the **same joints**, so running two at once would fight over the same keyframe tracks — that's why only one should be active. In Three.js you *can* blend clips (that's what `AnimationAction.weight`/fade methods are for), but it only makes sense when the tracks actually differ.

### Keyframes — what the glTF was actually storing

The README explicitly asks to explain the `AnimationClip` "keyframes". In Three.js terms a clip is a container of **`KeyframeTrack`** objects, each keyed by a property path. A `VectorKeyframeTrack` for position looks like:

| `times` (s) | `values` (x,y,z) |
|---|---|
| 0 | (0, 0, 0) |
| 0.5 | (0, 1, 0) |
| 1 | (0, 2, 0) |

Animated on the **property** `.../position`, the mixer interpolates between those sampled values each `update(delta)`. Rotations are stored as **quaternion** tracks (`QuaternionKeyframeTrack`, 4 values per key) to avoid the gimbal-lock problems of Euler angles; scale uses `VectorKeyframeTrack` with 3 values per key. The Fox's rig animates bones, so its tracks target paths like `.../bones[...]` — but the mechanics are identical.

### Scaling a big model

The Fox ships huge (the README's `// EXPLAIN:` comment echoes it: "model is huge"), so the app scales the whole loaded scene **before adding it**:

```ts
foxModel.scene.scale.setScalar(0.025);
```

Scaling the `scene` node is deliberate — it's the *root* of the glTF. You scale the root once and every child (including the animating bones) inherits the scale, which is much better than "messing with the scale of the children" (the comment): touching individual meshes in a rigged model risks breaking the animation hierarchy, and doing it in the model file / export is the wrong place too. The comment's advice — "scale the loaded scene and add it directly to our scene" — is the safe pattern for imported glTF: **operate on the root, then `scene.add(gltf.scene)`**.

### Draco stays wired, silently

Note the loader setup: `gltfLoader.setDRACOLoader(dracoLoader)` is present, yet the Fox is loaded from `glTF/` (plain flavor). The `// EXPLAIN:` comment calls this out — with Draco attached, glTF still loads the **default format** for models that don't declare `KHR_draco_mesh_compression`. The decoder is invoked *only when a mesh needs it* ([16.3_draco](16.3_draco.md)); there's no need to disable Draco to load a plain model. Also worth noticing: a `LoadingManager` with `onStart` / `onProgress` / `onLoad` / `onError` logs, so loading progress can be followed in the console.

### The Three.js editor

The README's second focus — [threejs.org/editor](https://threejs.org/editor/):

- It's a **tiny online 3D tool** — like a miniature Blender: a viewport, a scene-tree panel, a properties panel, a `index.html` script panel. You *won't* do Blender- or Maya-scale work there, but it's a fun, frictionless sandbox for quick tests.
- **A good way to test models**: drag-and-drop a glTF file into the viewport to inspect it without any code.
- **Only single-file models work** — the editor loads via a single-file path, so you want the **binary `glTF-Binary` (`.glb`)** flavor (assembly of the whole model into one file). That's why the README's exercise is to drop the *Duck*.glb (or the Fox's `glTF-Binary/Fox.glb`) — a multi-file glTF (`.gltf` + `.bin` + textures) won't drag-and-drop the same way.
- The README notes on dropping the Duck: **a mesh is present, the previously-studied camera works, and light is already there** — so a PBR material is visible immediately (a black duck under no light is gone; in older editor versions there wasn't a default light, apparently).
- Beyond models you can add built-in Three.js primitive geometries and lights from the editor's menus, save the scene, and export/publish — handy for quick non-hand-written experiments.

The editor is a *viewing/testing* tool, not a content tool — the hand-written code in this monorepo stays the source of truth; the editor is for inspecting what an exporter produced.

## Code

in repo — `apps/16_4_imported_models_animations`

```ts
// --------- Model + animation ---------
const foxModel = await gltfLoader.loadAsync('/models/Fox/glTF/Fox.gltf');

// The Fox is huge — scale the loaded scene root (never the children)
foxModel.scene.scale.setScalar(0.025);

// `foxModel.animations` holds 3 AnimationClip instances
// (Survey, Walk, Run) parsed out of the glTF
const mixer = new THREE.AnimationMixer(foxModel.scene);

// Get a playable AnimationAction from a clip and arm it
const action = mixer.clipAction(foxModel.animations[1]); // Walk
action.play();

scene.add(foxModel.scene);

// --------- Animation loop ---------
const timer = new THREE.Timer();

renderer.setAnimationLoop(tick);

function tick(timestamp: number) {
	timer.update(timestamp);

	// Feed the elapsed time *between frames* to the mixer
	// — without this, `.play()` alone does nothing
	mixer.update(timer.getDelta());

	renderer.render(scene, camera);
}
```

> 🗒️ The rest of the app is familiar scaffolding from [16.3_draco](16.3_draco.md) and [16.2_multi-mesh-scene-graph](16.2_multi-mesh-scene-graph.md): `WebGPURenderer` (`three/webgpu`), four switchable cube environment maps (`scene.environment`), ambient + directional light with full shadow GUI, a `receiveShadow` floor, `OrbitControls` with damping, plus the `h`-key GUI toggle / resize / fullscreen handlers.

## Gotchas

- **`.play()` alone does nothing.** An `AnimationAction` must be driven frame-by-frame by `mixer.update(delta)` in the animation loop. The code comment's exact warning: *"it won't play if you just do this"*. Forgetting the `mixer.update()` call produces a frozen, posed-but-motionless model — the most common first mistake.
- **`mixer.update()` takes *delta*, not elapsed time.** Passing `timer.getElapsed()` will jump the playhead to the absolute position each frame — the animation appears stuck (or teleports) instead of advancing. The mixer consumes per-step elapsed time; that's exactly why the `THREE.Timer` (delta) idiom from [3.3_animation-timer](3.3_animation-timer.md) is used here rather than the absolute elapsed.
- **One mixer per animated object**, created *bound to that object*. `new THREE.AnimationMixer(foxModel.scene)` must reference the scene that owns the rig; a mixer created against a different group won't know the bone tracks' targets. When you later have several animated models, each needs its own mixer (each also updated per frame).
- **Don't scale the rig's children.** The `// EXPLAIN:` comment is blunt — *"it is not good idea to mess with the scale of the children"*. Scaling bone/mesh children of an imported rig can fight the animation tracks. Scale the **glTF scene root** (`foxModel.scene.scale.setScalar(...)`) once, then add the root to your scene.
- **The Three.js editor is single-file-only.** Drag-and-drop works with `.glb` (binary glTF bundles everything into one file). A `.gltf` + `.bin` + texture set won't drop as a single unit — use `glTF-Binary/` assets for editor inspection.
- **Same-joint clips don't mix well.** The Fox's Survey/Walk/Run all drive the same joints — run two `AnimationAction`s simultaneously and they fight over the same tracks. Blend only clips whose tracks actually differ (see Revisit).

## Revisit

- **Cross-clip mixing** — the README's big open promise: a character that *runs*, blends into an aim pose, holsters a gun, and so on. That's `AnimationAction.weight`, `.fadeIn()`, `.fadeOut()`, `mixer.clipAction` reuse — the natural next lesson. The Fox (same-joint clips) is a *bad* test subject for blending; pick a model with independent tracks.
- **`AnimationAction` settings** — the app never touches loop behavior, speed, or timeScale. `setLoop()` / clamping, `repetitions`, `timeScale`, `.paused`, `.enabled` are all unexplored knobs.
- **`timer.getDelta()` vs the `Clock`** ([3.2_animation-clock](3.2_animation-clock.md)) — the codebase now uses `THREE.Timer` uniformly; worthwhile to re-verify what, if anything, `Clock` still offers and when the `Timer` API changes.
- **Other animation sources** — animation can also be authored at runtime (keyframe tracks assembled from code) rather than imported. That's how scripted object animations fit beside rig animations.
- **The Three.js editor's export/publish path** — the README only touches *testing* models in the editor. Its save/share/export flow is worth a separate look.

## Outdated

approach is valid

> 🗒️ Rendered with the **WebGPU** renderer (`three/webgpu` + `WebGPURenderer`) — this project is already on WebGPU rather than WebGL, the current and forward-looking path in Three.js. 🚀 The animation system (`AnimationMixer` / `AnimationClip` / `AnimationAction`) is renderer-agnostic: it mutates object property values (keyframe tracks), and both renderers read the same updated matrices each frame.
