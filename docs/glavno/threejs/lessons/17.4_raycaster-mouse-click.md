# 17.4 raycaster mouse click

## Concept

The [previous lesson](17.3_raycaster-hover-enter-leave.md) built `mouseenter` / `mouseleave` out of the raycaster by keeping a `currentIntersect` variable that snaps to whatever the ray last pierced. This lesson answers the follow-up: **how do I do something when the user clicks on an object?**

### Why a plain DOM `click` listener is enough

The raycaster already runs **every frame** inside `setAnimationLoop`. That means the line

```ts
currentIntersect = intersections[0] ?? null;
```

is executed ~60 times per second, so `currentIntersect` is *always* "the object under the mouse as of the last rendered frame". A click is not a continuous state — it's a *momentary* event. So the click handler doesn't need to raycast anything; it just reads the variable that's already being kept fresh for hover:

```ts
window.addEventListener('click', () => {
  if (currentIntersect) {
    // do something with the intersected object
  }
});
```

This is the whole trick: **one shared piece of state, two consumers**. The animation loop writes it (via raycast), the click handler reads it. No duplicate raycasting, no per-event math.

### Branching on `currentIntersect.object` with a `switch`

The `// EXPLAIN:` comment points straight at this: *we can test what object is being clicked on*. Because `intersection.object` holds a **reference to the live mesh**, you can `switch` on it and compare **by object identity**. Each mesh in the app reacts differently:

```ts
switch (currentIntersect.object) {
  case sphereMesh1:
    currentIntersect.object.position.x += 0.04;        // slide sideways
    break;
  case boxMesh2:
    currentIntersect.object.rotation.y += Math.PI / 3; // rotate ~60°
    break;
  case sphereMesh3:
    currentIntersect.object.position.z += 0.04;        // slide toward camera
    break;
  default:
    break;
}
```

With `case` matching on object references, order doesn't matter and you get the exact mesh you clicked. The `default` case swallows clicks on anything else — and there is nothing else, because the floor is `visible = false` and excluded from the raycast entirely, so clicking the floor hits the `null` guard instead.

One naming trap worth knowing (per the `// EXPLAIN: made this to be box for the sake of practice` comment): `boxMesh2` is actually a `BoxGeometry` even though its name says "sphere". Geometry per mesh is just a constructor argument — the click logic doesn't care about the shape, only about the object reference.

### The two consumers of each frame's intersection data

This app runs the per-frame coloring *and* the `currentIntersect` state side by side (unlike 17.3, where transitions replaced the loop). Each tick:

1. **reset-then-apply coloring** (from [17.2](17.2_raycaster-with-mouse.md)): set every material back to pink `#e6cbe8`, then darken to `#344e70` whatever `intersections[0]` is;
2. **state tracking** (from [17.3](17.3_raycaster-hover-enter-leave.md)): store `intersections[0] ?? null` into `currentIntersect`.

The click handler reuses what step 2 produces — no new math. The mouse NDC normalization and `raycaster.setFromCamera(mouse, camera)` remain exactly as in 17.2 / 17.3.

### The timing subtlety

The `click` event fires from the browser **between frames**; `currentIntersect` was computed at the last rendered frame. That's accurate enough because a click usually happens with the mouse at rest, and the meshes only bob a small `sin` distance between frames. The pattern holds as long as you accept "last frame's hit" as the definition of "what I clicked".

## Code

in repo — `apps/17_4_raycaster_mouse_click`

```ts
import * as THREE from 'three/webgpu';

// ... scene, WebGPURenderer, camera, OrbitControls, lights,
// three meshes each with its OWN material, as in 17.2 / 17.3 ...

const mouse = new THREE.Vector2(0, 0);
const raycaster = new THREE.Raycaster();
let currentIntersect: THREE.Intersection | null = null;

const objectsToTest = [sphereMesh1, boxMesh2, sphereMesh3];

window.addEventListener('mousemove', (e) => {
  mouse.x = (e.clientX / sizes.width) * 2 - 1;
  mouse.y = -((e.clientY / sizes.height) * 2 - 1);
});

renderer.setAnimationLoop((timestamp) => {
  timer.update(timestamp);
  const elapsed = timer.getElapsed();
  // bob the meshes so the ray passes different shapes each frame ...
  sphereMesh1.position.y = Math.sin(elapsed * 0.3) * 1.5;
  boxMesh2.position.y = Math.sin(elapsed * 0.8) * 1.5;
  sphereMesh3.position.y = Math.sin(elapsed * 1.4) * 1.5;

  raycaster.setFromCamera(mouse, camera);
  const hits = raycaster.intersectObjects(objectsToTest);
  currentIntersect = hits[0] ?? null; // kept fresh every frame

  orbitControls.update();
  renderer.render(scene, camera);
});

// no raycasting in here — just read the state the loop keeps warm
window.addEventListener('click', () => {
  if (!currentIntersect) return; // clicked empty space → nothing

  switch (currentIntersect.object) { // reference equality with live meshes
    case sphereMesh1:
      currentIntersect.object.position.x += 0.04;
      break;
    case boxMesh2:
      currentIntersect.object.rotation.y += Math.PI / 3;
      break;
    case sphereMesh3:
      currentIntersect.object.position.z += 0.04;
      break;
    default:
      break;
  }
});
```

## Gotchas

- **`currentIntersect` is last-frame knowledge, not click-moment truth.** The click handler reads a raycast that ran *before* the click. For slow-bobbing meshes and a pointer at rest that's indistinguishable; for fast-moving objects, or a camera swing just before the click (e.g. ending an OrbitControls drag over an object), the hit can be stale. For pixel-exact clicks, raycast inside the handler from `e.clientX / e.clientY` (see Revisit).
- **Object identity, not `distance`.** `switch (currentIntersect.object)` matches by reference. If you ever clone or re-create meshes between the raycast and the click, the `case` won't match and the object stops being "clickable". Same reason `scene.add` must add the same instance you compare against.
- **Guard the `null`.** With no meshes hit, `currentIntersect` is `null`; `if (currentIntersect)` is the guard that makes clicking empty space a no-op instead of a crash. The `?? null` in the loop is what makes that `null` appear at all — an empty array would give `undefined`.
- **Closest hit wins.** `intersections[0]` is the nearest pierced object — if two meshes overlap under the cursor, the further one never gets the click. Same caveat as 17.3's single `currentIntersect` slot.
- **`intersection.object` is an `Object3D`, no `.material`.** Touching `.material` needs `instanceof THREE.Mesh` narrowing. The per-frame coloring loop already uses `if (item.object instanceof THREE.Mesh)` — a cleaner pattern than the `@ts-expect-error` used for the hover transitions in 17.3.
- **Each mesh needs its own material** if you color per mesh. One shared `MeshStandardMaterial` → the pink reset in the loop recolors them all, and the click highlight hits all of them too. Carried over from 17.2 / 17.3.

## Revisit

- **Stateless alternative:** raycast fresh inside the click handler from `e.clientX / e.clientY` instead of trusting the loop's last frame. Compare the two: stateful (shared `currentIntersect`, zero cost per click) vs fresh-query (exact at the event moment, but you must re-apply the NDC normalization and camera transform). Good exercise: make the box miss clicks when the bobbing meshes "snap" between frames.
- **Show the ray.** The `RaycasterHelper` import is still commented out (as of 17.2 / 17.3). `raycasterHelper.hits = intersections; raycasterHelper.update()` turns the invisible math into a visible line with hit markers — debugging the click moment becomes much easier.
- **Animate the click reactions.** `gsap` is installed but commented. `position.x += 0.04` is instant; `gsap.to()` would let the click "push" the sphere with slight easing — the standard game-feel upgrade.
- **Click-after-drag:** OrbitControls ends a drag with a synthetic `click`. If you don't want a drag to count as a click, track `pointerdown` / `pointerup` positions or a movement threshold — the Three.js Journey course handles this in a later lesson.

## Outdated

approach is valid

> 🚀 This project already runs on the **WebGPU** renderer (`three/webgpu` + `WebGPURenderer`, no legacy import). CPU-side per-frame raycasting is the right tool for a handful of objects; the click-reads-`currentIntersect` pattern is pure logic on top of that and is renderer-agnostic (identical behavior on WebGL). If object counts grow to thousands, GPU picking (render object IDs, read one pixel) replaces the per-frame raycast — but the shared-state-then-read pattern stays exactly the same.
