## Concept

### Why build an environment map in Blender at all?

[Poly Haven](https://polyhaven.com/) has thousands of free HDRIs, and for most scenes one of them is enough. But sometimes you need something very specific — a studio key light with colored fill, a particular sun angle, a product-shot look — that no generic landscape HDRI gives you. **Blender lets you build an environment map from scratch**: instead of capturing a real world, you light a 3D scene and render it as an *equirectangular* HDR image. That image then becomes your `scene.environment` (image-based lighting) and/or `scene.background`. Making one is mostly a matter of knowing what to press in Blender — the rendering engine does the hard part.

The full pipeline in one sentence:

> Build a simple scene in Blender → set the camera to *Panoramic / Equirectangular* → render with **Cycles** → save as **.hdr (Radiance)** → load it in three.js with the **HDRLoader** → assign to `scene.environment`.

### What an equirectangular HDR contains

An equirectangular (latitude/longitude) image maps the whole sphere around a point onto a 2:1 rectangle: longitude 360° along X, latitude 180° along Y. The `.hdr` files Blender writes are **Radiance HDR** images, which store pixels as **RGBE** — three color floats plus one shared exponent — so individual texels can hold values far above `1.0`. That's exactly what image-based lighting needs: the sun/area-light texels carry real light **intensity**, not just color, and `MeshStandardMaterial`/`MeshPhysicalMaterial` use those values as actual illumination (through PMREM downsampling, done internally by the renderer).

### The three.js side of this lesson

This is the third part of the environment-map series — [[19.0_environment-map-intro-with-cube-texture-map]] covered cube-texture environment maps, [[19.1_equirectangular-hdri]] covered loading a ready-made equirect HDRI from [Poly Haven](https://polyhaven.com/), and now *we build the HDRI ourselves* in Blender.

The app loads **three** different HDRIs that were built in Blender (`blender-one`, `blender-two`, `blender-three`) with the `HDRLoader` from `three/addons/loaders/HDRLoader.js` (this works under `three/webgpu` / `WebGPURenderer`):

```ts
const hdriLoader = new HDRLoader();
const environmentMapBlenderOne = await hdriLoader.loadAsync(
	'/textures/environmentMaps/blender-one-2K.hdr',
);
```

The one step that is easy to forget and makes everything look wrong if skipped:

```ts
environmentMapBlenderOne.mapping = THREE.EquirectangularReflectionMapping;
```

Without the mapping, three.js doesn't know the texture is a spherical panorama and the lighting/background will be distorted. The app then assigns the HDR to both channels of the scene and tunes their intensity:

```ts
scene.environment = environmentMapBlenderOne; // lights standard materials
scene.background = environmentMapBlenderOne;  // fills the background

scene.environmentIntensity = 1.9;  // light source strength, default 1.0
scene.backgroundIntensity = 2.4;   // background brightness, default 1.0
scene.backgroundBlurriness = 0;    // 0..1, blurs the background
```

A lil-gui folder exposes `scene.environment`, `scene.background`, `environmentIntensity`, `backgroundIntensity` and `backgroundBlurriness`, with the three Blender-built maps as selectable options plus `none` — the fastest way to A/B test which environment suits the scene. The torus knot (metalness/roughness tweakable, `metalness: 1, roughness: 0.1` initially) is the test subject: crank metalness up with a clean studio HDRI and you should see distinct, sharp reflections; with the sun HDRI you see the sun as a highlight.

The models in the scene are chosen to show env-map quality off: the [FlightHelmet](https://github.com/KhronosGroup/glTF-Sample-Models/tree/main/2.0/FlightHelmet) (heavy, realistic, great specular details), plus a low-poly game console the user built in Blender and exported with DRACO compression (see [[16.3_draco]] and [[18.0_blender-exporting-model-and-loading]]). The console model exists *because* they wanted to see how a homemade model looks under every self-made env map.

### The Blender workflow (how the env maps were made)

Both HDRIs were made in **Blender** with the **Cycles** engine.

#### General setup for any env map

1. **Render Properties → Engine: Cycles.** Cycles is a path tracer, so it produces a physically plausible HDR result with light intensities above `1.0`.
2. **Sampling** — `Max Samples` was set to **256** for both viewport and final render, with **denoising** enabled for the final render only. On this machine (AMD Ryzen 7 5700U, 8 cores/16 threads, integrated Radeon GPU, ~15 GB RAM) Cycles will render on the **CPU** — the integrated GPU isn't worth enabling for Cycles. A sensible recipe:
   - Viewport samples: **32–64** (you're iterating, not rendering).
   - Final render: **128–256** with **Denoise** on (OpenImageDenoise). 256 is the right ceiling here — the image is a static 2048×1024 and denoising covers the rest. Beyond that you get diminishing returns that only cost CPU time.
   - If your Blender has **Adaptive Sampling** on (default in modern versions, `Noise Threshold ≈ 0.01`), the renderer stops early where it's clean and "max samples" is just an upper cap — exactly what you want on a CPU.
3. **World Properties → Surface → Background.** Zero out the background *Value* (the V of HSV) — drag the right-hand slider all the way down to **0**. The point: an environment map should contain **only light sources**, not a flat colored fill. A color with `Value = 0` is pure black no matter what hue/saturation you had — Value is brightness, and 0 means "lights off". (If you *want* a colored ambient fill in the panorama, set the color and raise Value — but for light-source-only env maps, keep it black.)
4. **Output Properties → Format → Resolution: 2048 × 1024.** Why 2:1? An equirectangular image that covers the full sphere *is* 360°×180°, which is exactly 2:1 in angular terms — any other aspect either crops part of the sphere or wastes texel density. It's projected by all panorama-consuming software (three.js included) as the standard, and other software expects 2:1. Not strictly *enforced* by three.js, but it's both the mathematical optimum and the convention — good practice. ("2K" here refers to the 2048 width.)
5. Delete the default cube/camera/light; add a few test objects to light and move them around. This is just so you can judge the light.

#### Camera (required for any render)

Since you deleted the default camera, add a new one with:
- **Position** `(0, 0, 0)` and **Rotation** `(90°, 0, 0)` so it looks along +Y. Strictly speaking the camera only needs to sit *somewhere* and the panorama is captured around it, but putting it at the origin with a fixed, known orientation is what makes the light direction in the final map predictable — you're choosing where the sun lands in longitude/latitude instead of guessing.
- **Object Data → Lens → Type: `Panoramic` → Panorama Type: `Equirectangular`.** This is the step that makes Cycles render a full 360° sphere instead of a flat lens. You won't see this projection live in the viewport's Solid/Material modes — it only exists at render time (see Revisit for the question of modern viewport preview).

#### Lights (the fun part)

- **Area Light** set to roughly the sun. In Blender an Area Light is a rectangle you can move/rotate to decide where shadows fall, and scale to change its size. Blender's default power (≈10 W) is far too weak; crank **Power to 1000 W** (in Blender, light power is in physical watts, so it depends on the size of your scene — for a small scene 1000 W is a good start, tune to taste).
- To make the *light* visible to the camera in the render: select it → **Object → Ray Visibility → check Camera**. The light object is only a lamp; without this its quadrilateral won't be seen.
- Render test: `F12` (`fn`+`F12` on this laptop). When it's done, **Image → Save As** (`Alt`+`S`) and pick **`.hdr` (Radiance HDR)** from the format dropdown instead of the default PNG. Name it — the user chose `blender-one-2K.hdr` — and drop it into `public/textures/environmentMaps/`.

That first map is a "sun test": a light source with shadows on simple objects. Rough, but it proves the pipeline and gives you a sun highlight to inspect.

#### Studio lighting (the second and third maps)

A sun test is fine, but for showcasing materials a **studio setup** is nicer: lights only, no geometry. The user deleted everything except the area light and camera, then built three lights:

- One bright **white** light (key) — the original 1000 W.
- A **red** light behind, near the floor (`z ≈ 0.1`) — used in the app, power **500 W**.
- A **blue** light on the other side, angled from below — power **300 W**.

Three lights, three colors: the classic key / rim / fill-from-below trio. A quick render showed it too dim, so a **third** map was made with all three lights at **1000 W** — hence `blender-one`, `blender-two` (colored, dimmer) and `blender-three` (colored, all 1000 W). The app lets you switch between all of them live.

### Why not skip Blender and fake it?

If you ever need a good-looking neutral studio environment *without* a Blender session, three.js ships `RoomEnvironment` (`three/examples/jsm/environments/RoomEnvironment.js`) which generates a probe at runtime and is made for exactly this purpose. But it's generic — the whole point of this lesson is that Blender gives you **exact control** over light direction, color, intensity and shape.

## Code

in repo - `apps/19_2_hdri_from_blender`

```ts
import * as THREE from 'three/webgpu';
import { HDRLoader } from 'three/addons/loaders/HDRLoader.js';

const renderer = new THREE.WebGPURenderer({ canvas });
await renderer.init();

const scene = new THREE.Scene();

// 1. load the .hdr we rendered in Blender
const hdri = await new HDRLoader().loadAsync(
	'/textures/environmentMaps/blender-one-2K.hdr',
);

// 2. REQUIRED: tell three.js this is a spherical panorama
hdri.mapping = THREE.EquirectangularReflectionMapping;

// 3. use it for both lighting and background
scene.environment = hdri; // image-based lighting for standard materials
scene.background = hdri;  // visible background

// 4. intensity controls (defaults are 1.0)
scene.environmentIntensity = 1.9;
scene.backgroundIntensity = 2.4;
scene.backgroundBlurriness = 0;

// then: camera, orbit controls, renderer.setAnimationLoop(tick)...
```

## Gotchas

- **Forgetting `mapping = EquirectangularReflectionMapping`.** This is marked `// EXPLAIN:` in the app code for a reason: without it the environment and background are sampled as a flat texture and everything looks wrong/dark/stretched. Do it for *every* equirect HDR you load. From the `// EXPLAIN:` comment in `main.ts`: "never forget the mapping type, otherwise your env map will not work properly".
- **A Color with HSV Value = 0 is black no matter the hue/saturation** — Value *is* brightness. You can't "hide" a red background by picking red with Value 0; you *can* use Value 0 intentionally so the env map contains nothing but your light sources. If your env map renders fully dark, this is usually why.
- **Blender area lights default to ~10 W.** Ten watts lights almost nothing. Lights in Blender are parameterized in physical watts and scene size matters — for a small test scene start around **1000 W** and scale up/down. The README records three separate renders ending at "all lights 1000 W" because the colored ones looked too dim.
- **The light object won't appear in the render unless you check Ray Visibility → Camera.** A lamp is not geometry; otherwise your "sun" highlight is invisible in the HDR.
- **Don't confuse the two intensity knobs.** `scene.environmentIntensity` scales how strongly the env map *lights materials*; `scene.backgroundIntensity` (and `backgroundBlurriness`) scales/applies to the *visible background*. Raising one does nothing to the other — the app exposes both, which makes the difference obvious live.
- **The .hdr from Blender is RGBE-encoded** (Radiance). If you try to load it as a plain texture, you get garbage; the `HDRLoader` does the RGBE→float decoding for you. (In a WebGL context the equivalent loader is `RGBELoader`; here, under `three/webgpu`, `HDRLoader` is the right import.)
- **`backgroundBlurriness` is only visible when the same texture is used as background**, and only in the background — blurring doesn't soften the *reflections* on material surfaces (that's a roughness/mipmap thing). Big "wow, my metals look sharp" moments in this app generally come from `environmentIntensity`, not background settings.

## Revisit

- **Optimal Cycles settings for this machine.** The README openly asks "you tell me what would be optimal" for a Ryzen 7 5700U. The answer in the lesson above (viewport 32–64 samples, final 128–256 + OpenImageDenoise, keep adaptive sampling) is a solid default, but it's worth re-verifying against [the official Cycles docs](https://docs.blender.org/manual/en/latest/render/cycles/) — especially if you switch to a GPU (e.g. external) or a bigger render size later.
- **2:1 aspect — required or just good practice?** Currently documented as "mathematically what a full-sphere equirect *is*, and the convention other software expects". If you ever hit a tool that wants 4:1 or square, note whether three.js still PMREMs it correctly.
- **Camera at (0,0,0), rotation (90,0,0) — required?** It's convenient, not required: the panorama is captured around the camera position regardless. What it controls is *where* lights land in the spherical map. Revisit if you ever want to move "the sun" in the scene instead of re-rendering.
- **Panoramic preview in the Blender viewport.** The classic claim is that you can't see the equirectangular projection in the viewport — only at render time. Verify whether modern Blender (5.2, per the README) shows it in Rendered viewport mode; if it does, this whole workflow gets much faster to iterate on.
- **The hidden floor mesh and the disabled lights.** `ambientLight`/`directionalLight`/floor are all present but `visible = false` — kept around purely as scene-composition tests. If you revisit the app to "see the shadows" make sure you remember the lights are off by default.
- **`renderer.shadowMap` GUI is present but shadows are disabled** in code (`renderer.shadowMap.enabled` commented out) — the GUI items only "work" (light up) once enabled. Not a bug, a leftover from the shadows lessons.

## Outdated

**approach is valid** — hand-rendering a custom equirectangular HDRI in Blender and loading it as an environment map in three.js is still the standard, current workflow in 2026, and it works on both the WebGL and the **new WebGPU renderer** 🚀 (this app is `three/webgpu` + `WebGPURenderer`, which handles equirect HDRs natively via the `HDRLoader` — no `PMREMGenerator` boilerplate needed, unlike older WebGL examples).

Small notes, not "outdated":
- On the WebGL path you'd use `RGBELoader` + `PMREMGenerator`; the modern `three/webgpu` path used here is the cleaner one. If you ever see old tutorials calling `PMREMGenerator.fromEquirectangular()` by hand, that's the older approach — under WebGPU the renderer does that internally.
- For quick throwaway studio IBL, `RoomEnvironment` from `three/examples/jsm/environments/RoomEnvironment.js` generates a decent probe in code with zero assets — good when you need "some studio light" but no Blender session.
- Blender 5.x renamed a couple of panels vs. older tutorials (Render settings layout in particular) — the concepts above map under any name, but paths may differ slightly from 3.x-era videos.
