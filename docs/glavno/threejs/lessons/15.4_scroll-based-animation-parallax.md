# 15.4 Scroll Based Animation — Parallax

This lesson continues from `15.3_scroll-animation-proportion-camera` and lives in `apps/15_4_scroll_based_animation_four`. In 15.3 the **camera descended with the scroll**. Here we keep that, and add a **parallax** layer on top: the camera (wrapped in a group) also drifts horizontally and vertically in response to the **mouse position**, so the toon shapes feel like they have depth as you move the pointer around.

## Concept

### What parallax is

**Parallax** is the action of *seeing one object through different observation points*. Your two eyes naturally do this — each sees the same object from a slightly different angle, and your brain fuses those two views into depth. That is literally how we *feel* the depth of things.

To fake it in Three.js you move the **camera** (the observation point) as the input changes — here, as the `cursor` moves — while the objects stay put. Because perspective projects differently from a moving viewpoint, near and far shapes appear to shift against each other, producing a sense of depth without actually moving the meshes.

> This is the *same* technique that the classic Three.js Journey **scroll-based animations** lesson demonstrates (each object at a different depth + a camera that reacts to the pointer). It's how the site feels "3D" even though the meshes never translate.

### The setup this app uses

Everything is wired so that **scroll** drives the camera down through the three sections (see 15.3), while **mouse** adds a parallax offset. Two different inputs, two different jobs — the scroll is mapped to `camera.position.y` directly, and the mouse parallax is applied to a **`cameraGroup`** that wraps the camera:

```ts
const cameraGroup = new THREE.Group();
cameraGroup.add(camera);
scene.add(cameraGroup);
```

### Parallax from the cursor — step by step

The cursor values come from the mouse position on screen. Three steps happen in the `mousemove` listener (`src/main.ts`), and each `// EXPLAIN:` comment marks one purpose:

```ts
const cursor = { x: 0, y: 0 };
window.addEventListener('mousemove', (ev) => {
	// first make values go from 0 to 1
	cursor.x = ev.clientX / sizes.width;
	cursor.y = ev.clientY / sizes.height;
});
```

1. **`ev.clientX / sizes.width`** maps the pixel X (0..viewport-width) into **`0..1`** — a unit fraction across the screen.
2. Subtracting `0.5` then maps that fraction into **`-0.5..0.5`** — centered on zero, so the middle of the screen is the "resting" position and the pointer can push the camera in *either* direction.
3. In `tick`, those normalized values become the parallax and are applied to the **group**, not the camera:

```ts
const parallaxX = cursor.x;
const parallaxY = -cursor.y;   // minus: see Gotchas

cameraGroup.position.y = parallaxY;
cameraGroup.position.x = parallaxX;
```

Because moving the *group* translates the camera (it's a child), you get the mouse-driven drift automatically. The two `// EXPLAIN:` comments in `main.ts` around lines `380`–`396` spell out why a group is used here.

### Why a group instead of moving the camera directly?

This is the deliberate design decision in the lesson (`main.ts` `// EXPLAIN:` for the camera-group). The scroll logic already writes to `camera.position.y` (the 15.3 proportion). If you *also* wrote the parallax to `camera.position.y`, the two would **fight** for the same axis — scroll and mouse both clamping one value. By putting the parallax on the wrapping `cameraGroup.position` instead, each input owns a separate property:

- **scroll → `camera.position.y`**
- **mouse parallax → `cameraGroup.position.x` / `cameraGroup.position.y`**

Clean separation, no coupling, and it respects the offset you already set. (The `// EXPLAIN:` in `tick` also notes you *could* do it with `+=` on `camera.position.y`, but the group is the cleaner, more scalable option — and the user flagged it as an open question worth revisiting.)

## Code

in repo — `apps/15_4_scroll_based_animation_four`

```ts
import * as THREE from 'three/webgpu';

const canvas = /* your canvas#tride */;
const sizes = { width: window.innerWidth, height: window.innerHeight };

// --- scroll (from 15.3) --------------------------------------------------
let scrollY = window.scrollY;
window.addEventListener('scroll', () => (scrollY = window.scrollY));

// --- cursor parallax -----------------------------------------------------
const cursor = { x: 0, y: 0 };
window.addEventListener('mousemove', (ev) => {
	cursor.x = ev.clientX / sizes.width - 0.5;   // normalize to -0.5..0.5
	cursor.y = ev.clientY / sizes.height - 0.5;
});

// --- scene / meshes at -objectsDistance * 0..2 (torus, cone, knot) -------
const scene = new THREE.Scene();
const camera = new THREE.PerspectiveCamera(75, sizes.width / sizes.height, 0.1, 100);
camera.position.z = 3;

// --- camera group: parallax lives here so it never collides with scroll --
const cameraGroup = new THREE.Group();
cameraGroup.add(camera);
scene.add(cameraGroup);

const renderer = new THREE.WebGPURenderer({ canvas });
await renderer.init();
renderer.setSize(sizes.width, sizes.height);

const timer = new THREE.Timer();
renderer.setAnimationLoop(tick);

function tick(timestamp: number) {
	timer.update(timestamp);
	const elapsedTime = timer.getElapsed();

	// scroll -> camera Y (proportion, see 15.3)
	camera.position.y = -(scrollY * debugObject.objectsDistance) / sizes.height;

	// parallax -> cameraGroup, centered on screen
	const parallaxX = cursor.x;
	const parallaxY = -cursor.y; // sign: see Gotchas
	cameraGroup.position.x = parallaxX;
	cameraGroup.position.y = parallaxY;

	for (const mesh of selectionMeshes) {
		mesh.rotation.x = elapsedTime * 0.1;
		mesh.rotation.y = elapsedTime * 0.12;
	}

	renderer.render(scene, camera);
}
```

## Gotchas

- **The parallax sign flip on `y`.** `cursor.y = clientY/height - 0.5` grows *downward* (as the pointer goes down, `cursor.y` increases). Moving the camera `+y` moves the view *up*. So `parallaxY = -cursor.y` is needed to keep the visual direction intuitive — push the mouse up, the camera-group drifts up. The `main.ts` comment flags exactly this: *"prefixed with minus so as we move cursor camera moves up and not down."* (X has no flip because `clientX` already grows in the *same* direction the world expects.)
- **Don't write scroll and pen both to `camera.position.y`.** That's the whole reason for the group. If you `+=` parallax onto the scroll value you'll fight over one axis and the effect glues.
- **Scroll needs `overflow` enabled** (the commented-out `overflow: hidden` in `style.css` must stay off), otherwise the page can't scroll and there's nothing to parallax against.
- **Forget the `-` in the proportion** and the camera scrolls backwards — the meshes live at negative Y (`-objectsDistance * 0..2`).

## Revisit

- **The open question from the code**: is moving the `cameraGroup` genuinely better than writing `camera.position.y += parallaxY` directly? Toggle between the two approaches and watch for coupling with the scroll value; form your own opinion.
