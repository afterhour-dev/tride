# 20.1 Realistic Render — Directional Light & Shadows

> _Using `WebGL` instead `WebGPU` because of the problem we discovered in [[20.2_realistic-render-textures-and-color-space]]_
## Concept

The previous lesson (`20.0`) made the render realistic through **tone mapping** and **antialiasing**. This lesson adds the next piece: **shadows** — specifically a directional light that casts them.

Same scene as before: the Flight Helmet, the Blender-made gaming console (both Draco-compressed glTF), the `abandoned_garage` HDR environment map, and a lil-gui panel with everything tweakable.

### Environment maps can't cast shadows

An environment map gives you **lighting and reflections** but **no shadows** — there is no geometry in the map to occlude light. The scene would look flat and floaty: objects brightly lit by the HDRI yet with nothing anchoring them to the floor.

The fix: add a **real light source** that roughly matches the main light of the HDRI (the garage's "sun" / brightest direction) and let *that* light cast shadows. So:

1. Place a `DirectionalLight` roughly where the environment map's light comes from (`position.set(6, 10, 6)` — high and to the front-right).
2. Enable shadows globally on the renderer.
3. Set `castShadow` / `receiveShadow` on lights and meshes.
4. Tune light position, intensity and shadow camera values in the GUI until the shadow direction "agrees" with the HDRI lighting.

The light's intensity is set to `Math.PI` — since Three.js `r165+` uses **physical light units** by default (`useLegacyLights = false`), directional intensities live in lux and small constants are normal. Don't over-think the number: tweak it in the GUI until the scene reads correctly. (`// EXPLAIN:` the whole point of putting light position/intensity/shadow-camera into the GUI is that you *adopt* good values by tweaking, not by guessing in code.)

Also note `scene.environmentIntensity = 1.6` (instead of the default `1.0`) — the environment is intentionally dimmed a touch so the directional light's shadow is easier to see.

### Enabling shadows — the three switches

```ts
// 1. Renderer: turn shadow mapping on, pick a soft algorithm
renderer.shadowMap.enabled = true;
renderer.shadowMap.type = THREE.PCFSoftShadowMap;

// 2. Light: it must cast
directionalLight.castShadow = true;

// 3. Mesh: each mesh decides to cast and/or receive
mesh.castShadow = true;
mesh.receiveShadow = true;
```

The floor is also set up to receive shadows (`floorMesh.receiveShadow = true`), placed at `y = -2` to sit under both models.

### `castShadow` vs `receiveShadow` — what they cost

- `castShadow` = the mesh is **rendered again** into the light's shadow map (a second pass). Cost scales with the mesh's triangle count.
- `receiveShadow` = the receiving material computes **per-pixel shadow** when it's drawn. Cost is paid by the surface that receives.

**The strategy this app uses** (answering the README's question): traverse every loaded model and enable *both* on every mesh whose material can be shadowed. The guard matters:

```ts
model.scene.traverse((child) => {
    if (child.isMesh && child.material.isMeshStandardMaterial) {
        child.castShadow = true;
        child.receiveShadow = true;
    }
});
```

Only `MeshStandardMaterial` (and physical/lambert/phong) respond to lights, so checking `isMeshStandardMaterial` avoids enabling shadows on things that can't cast them.

**When would you split cast/receive for a complex model?** In a production scene:
- **Receive-only** is a great default for the **ground/floor** — it should get shadows, but casting a huge flat plane into the shadow map wastes resolution. (This app keeps `castShadow` off the floor.)
- **Cast-only** suits objects that are *behind* the camera or never in the lit region — they'd still throw shadows onto what you see without paying for their own receive shading. Rarely needed for correctness though.
- The honest truth: for scenes this size, enabling both on everything is fine. The real budget is the **shadow camera frustum size × map resolution** — keep the frustum tight around the action and the resolution moderate (see below), and you'll barely feel the cost.

### The directional light target — the real lesson

A `DirectionalLight` shines **from its position toward its `target`** — the direction is `target.position − light.position`. The default target sits at `(0, 0, 0)`, which would aim the light at the Flight Helmet's *base*. We lift the aim to the helmet's middle:

```ts
directionalLight.target.position.set(0, 3, 0);
```

And here's the trap the README spends most of its time on: **changing `target.position` alone often does nothing.**

**Why.** Three.js stores transforms as `position` / `rotation` / `scale`, then compiles them into matrices — `matrix` (local) and `matrixWorld` (world). That compilation happens automatically **right before the object is rendered, and only for objects that are part of the scene graph**. The target is a plain `Object3D` held as a property of the light — **it is not in the scene** — so nothing ever recompiles its matrix when you change its position. The shadow code reads `target.matrixWorld`, which stays stale (identity → looking at `(0,0,0)`).

**Solutions, from what the README discovered:**

1. **Add the target to the scene** — then it gets auto-updated every frame like any scene object. The README chose *not* to (and was right not to, for this lesson's purposes): it pollutes the scene graph with an invisible object that gets matrix work done for it forever, and it makes the "fix" implicit rather than something you understand and control.

2. **Update the matrix manually** — what the app does:
   ```ts
   directionalLight.target.updateWorldMatrix(true, false);
   directionalLightHelper.update(); // in the GUI onChange
   ```

3. **Updating the `DirectionalLightHelper` also fixes the target** — a lucky discovery in the README: `DirectionalLightHelper.update()` internally calls `this.light.target.updateMatrixWorld()`, so touching the helper re-freshes the target too. Useful, but fragile as your only mechanism — if you remove the helper in production (who ships debug helpers?) you lose the fix, and in an animated scene you'd have to remember to update it every frame.

**The three matrix functions the README asks about:**

| Function | What it does |
|---|---|
| `updateMatrix()` | Recomputes **only the local `matrix`** from `position/rotation/scale`. Does *not* touch `matrixWorld`. Called automatically for scene objects during render. |
| `updateMatrixWorld(force?)` | Recursively updates `matrixWorld` for this object **and its children** (`matrixWorld = parent.matrixWorld × matrix`), using the local matrix. Called automatically during render traversal for scene objects. |
| `updateWorldMatrix(updateParents, updateChildren)` | First walks **up** to the root updating every ancestor's world matrix (only if `updateParents` is `true`), then updates this object, then (if `updateChildren`) its descendants. |

So `updateWorldMatrix(true, false)` means: *make sure my parents' world matrices are fresh, then recompute mine — but leave children alone.* The `(true, false)` here is correct: the target has no children, and it does need its (non-existent) parent chain skipped properly. `updateWorldMatrix` is the safer manual call when the object might be nested — it cures the whole chain from the root down before computing the target's world matrix.

**Why does the `tick()` function need none of this?** Because nothing moves per frame. The light itself *is* in the scene, so `renderer.render()` updates its matrices every frame; the shadow code places the shadow camera at the (fresh) light position. And the target's matrix was forced valid once at setup (`updateWorldMatrix(true, false)` right after `target.position.set(...)`) and only changes via the GUI's `onChange` — which re-applies the manual update. Both are static, so neither needs a per-frame update. **If you animated the light** (e.g. a planet with a moving sun), you'd need to update the target's matrix every frame — precisely the case where "update the helper in GUI-only" breaks down and you need the manual call (in `tick`) or the target added to the scene.

The README's other question — *"some tutorial's target change didn't work, but mine did"* — the difference: the tutorial changed `target.position` and *didn't* force a matrix update (or its version rendered before anything re-read the matrix); here the manual `updateWorldMatrix(true, false)` right after the `set()` is what makes it work. This behavior is version-dependent, not a WebGL-vs-WebGPU thing — the manual update is the reliable, explicit fix in any backend.

### The shadow map and its camera

The directionals' shadow is rendered by an **orthographic shadow camera** (`DirectionalLightShadow.camera`) whose frustum bounds *what* gets into the shadow map:

```ts
directionalLight.shadow.mapSize.setScalar(512);          // the shadow map resolution
directionalLight.shadow.camera.near = 1;
directionalLight.shadow.camera.far = 25;
directionalLight.shadow.camera.top = 7;    // right = 7, bottom = -7, left = -7
```

- **`mapSize`** — the shadow map's resolution. The README lowers it to **512×512**. Answering its question: doubling resolution *quadruples* shadow-map memory and the shadow pass cost. 512 is a fine budget choice when the scene is dense (small texel-to-pixel ratio hides the softness); go **1024** if shadows look noticeably blocky/soft and you have headroom; 2048 only for a large, hero area. Since it's in the GUI, flip it live and decide by eye. Keep width and height **equal** (a rectangular map wastes memory for no benefit).
- **`shadow.camera` frustum** — must *tightly* enclose the scene: too big → each texel covers a lot of world space → blurry/pixellated shadows and wasted resolution; too small → shadows get **clipped** at the frustum edges. These values (`±7`, `far 25`) fit the two models comfortably. When you change any camera property in the GUI, you must call `directionalLight.shadow.camera.updateProjectionMatrix()` (and refresh the `CameraHelper`) — the code does this in every `onChange`.
- **`shadow.bias`** — a tiny offset (`0.0002`) pushing the shadow-surface comparison away from geometry to fight **shadow acne** (dark speckle stripes) while avoiding **peter-panning** (shadow detaching from the object). Gui range `±0.0002` in small steps is right.
- **`shadow.radius`** — a blur radius to soften hard PCF shadows. **It does nothing with `PCFSoftShadowMap`** (which already softens); it only affects the plain `PCFShadowMap`. The GUI even labels this so you don't chase it.
- **`shadow.intensity`** — how dark the shadow is (`0..1`); `1` = full black.

Both helpers are added to the scene so you can see what you're tuning: `DirectionalLightHelper` (the light position/direction line) and `CameraHelper(directionalLight.shadow.camera)` (the shadow frustum box). The frustum helper **only works while `renderer.shadowMap.enabled === true`** — also labeled in the GUI.

### Why the light's `rotation` is commented out

A `DirectionalLight`'s direction is fully determined by **position → target**. Rotating the light object itself changes nothing about where the light shines (the shadow camera is placed at the light position and oriented to look at the target). Hence the README's discovery: "rotation isn't doing anything" — correct, and the code comments it out. Move the light or the target; don't rotate.

## Code

in repo - `apps/20_1_realistic_render_shadows`

```ts
import * as THREE from 'three/webgpu';

// renderer — enable shadow mapping, pick a soft algorithm
renderer.shadowMap.enabled = true;
renderer.shadowMap.type = THREE.PCFSoftShadowMap;

// the light — position it where the environment map's light comes from
const directionalLight = new THREE.DirectionalLight(0xffffff);
directionalLight.intensity = Math.PI; // physical units: tweak in GUI
directionalLight.position.set(6, 10, 6);
directionalLight.castShadow = true;

// aim it at the middle of the model, not (0,0,0)
directionalLight.target.position.set(0, 3, 0);
// target is NOT in the scene → its matrix is never auto-updated → force it
directionalLight.target.updateWorldMatrix(true, false);
scene.add(directionalLight);

// shadow map resolution + shadow camera frustum (tight around the scene!)
directionalLight.shadow.mapSize.setScalar(512);
directionalLight.shadow.camera.near = 1;
directionalLight.shadow.camera.far = 25;
directionalLight.shadow.camera.left = -7;   // right = 7, top = 7, bottom = -7
directionalLight.shadow.bias = 0.0002;

// meshes — only MeshStandardMaterial can be shadowed; enable both flags
model.scene.traverse((child) => {
    if (child.isMesh && child.material.isMeshStandardMaterial) {
        child.castShadow = true;
        child.receiveShadow = true;
    }
});

// GUI: any shadow.camera change must re-project...
gui.add(light.shadow.camera, 'far')
    .onChange(() => {
        light.shadow.camera.updateProjectionMatrix();
        helper.update();
    });
// ...and any target.position change must re-write the world matrix
gui.add(light.target.position, 'y')
    .onChange(() => {
        light.target.updateWorldMatrix(true, false);
        lightHelper.update();
    });
```

## Gotchas

- **`shadow.radius` silently does nothing with `PCFSoftShadowMap`.** It's a blur for the plain `PCFShadowMap` only. If shadows look right but `radius` isn't blurring — that's why.
- **The shadow-camera helper won't render unless `renderer.shadowMap.enabled === true`.** The `CameraHelper` reads the shadow map state; with shadows off it shows nothing (the GUI labels this).
- **`target.position` changes only take effect if you force the matrix.** The target is not in the scene graph, so its `matrixWorld` is never auto-updated. Either call `target.updateWorldMatrix(true, false)` (or `updateMatrixWorld()`) after every change, or add the target to the scene. This is the single most confusing part of the lesson.
- **Off-by-one on mapSize:** keep `shadow.mapSize.width === height`. A rectangular shadow map wastes GPU memory for zero benefit.
- **Any `shadow.camera.near/far/top/bottom/left/right` change requires `updateProjectionMatrix()`** — otherwise the GUI slider moves a number nobody reads (the shadow cam keeps its old projection), and the helper shows the stale frustum. Every `onChange` in the code does this deliberately.
- **A shadow camera frustum too small clips shadows at its edges**; too big bloats the texel size and softens/blurs everything. Tighten `±top/right/bottom/left` and `far` to the action.
- **Rotating a `DirectionalLight` changes nothing.** Direction = `target − position`. Move the light or the target. (Commented out in the GUI for exactly this reason.)
- **Only lit materials can carry shadows.** The `traverse` guard `child.material.isMeshStandardMaterial` matters: `MeshBasicMaterial`/`MeshNormalMaterial`/etc. ignore lights, so enabling `castShadow` on them would waste work.
- **Physical light units:** with default `useLegacyLights`, `intensity = Math.PI` is a sane starting point — don't port old `0.4`-style WebGL values without re-checking, and tune in the GUI anyway.
- **`updateWorldMatrix(true, false)` is correct here** even though the target has no children: the `true` makes the parent chain safe, the `false` just skips descendants it doesn't have. Using `updateMatrix()` alone would *not* fix the world matrix — that's the local-matrix-only one.

## Revisit

- **The three matrix functions — deepen the mental model.** `updateMatrix` (local only) vs `updateMatrixWorld` (self + children, automatic for scene objects) vs `updateWorldMatrix(parents, children)` (whole chain). Playing with an animated light (moving sun → per-frame `updateWorldMatrix` in `tick`) is the best way to make the difference stick.
- **The "tutorial didn't work" mystery.** The README asks whether WebGL mattes. It doesn't — the behavior is about whether the matrix is force-updated before being read, which varies by three.js version and render-call order. If it ever "stops working", suspect a missing manual update, not the backend.
- **`updateWorldMatrix` are those two booleans** — `updateParents` walking to the root vs `updateChildren` walking down. Revisit why a nested target would *need* the parent walk.
- **More GUI time will produce a better render.** The README's closing note: everything is set up but the values are a starting point — spend a session flipping light position, intensity, `environmentIntensity`, and shadow camera bounds to land the "final" look, then bake those numbers back into code.
- **`VSMShadowMap`** — the variance shadow map algorithm is selectable in the GUI (`renderer.shadowMap.type`). Try it against `PCFSoftShadowMap`: softer, smoother shadow edges — the trade-offs (light bleeding artifacts) are worth knowing.
- **Baking shadows** — for completely static scenes `13.5` bakes shadows into textures and skips runtime shadow maps entirely; the realistic-render path here is the runtime, dynamic alternative.
