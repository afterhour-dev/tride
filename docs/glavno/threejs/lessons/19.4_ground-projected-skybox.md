# 19.4 Ground Projected Skybox

## Concept

When we use an environment map as the `background`, objects in the scene look like they are *flying* — the image behind them has no relation to their position. A common hack is placing a plane underneath the objects, but unless the plane matches the environment map's horizon perfectly, it looks wrong. A much better solution is the **Ground Projected Skybox**.

The idea: take the environment map sphere, and only draw the *top half* of it, flattened so that the horizon of the HDR image lands exactly on a ground plane at a height we choose. The result is a full sky dome with a proper floor that visually "belongs" to the same environment — objects now sit on an infinite ground instead of floating over a picture.

### What the code does differently from a plain env-map setup

1. **`environment`, not `background`** — the HDR equirectangular map is assigned only to `scene.environment` (lighting/reflections), never to `scene.background`. The sky we see comes from the `GroundedSkybox` mesh itself, not from a background texture.
   ```ts
   scene.environment = environmentMap;
   // scene.background = environmentMap; // NOT set
   ```
2. **`scene.environmentIntensity = 1.0`** — kept at its default. This controls how strongly the environment contributes to lighting; here the ground-projected skybox supplies the visual background, so the intensity only affects how bright the light from the environment feels.
3. **`GroundedSkybox`** — the addon that does the work. It replaces the older `GroundProjectedSkybox` (three r150-ish), which had issues (e.g. seams, wrong look) and was renamed. So the current import is:
   ```ts
   import { GroundedSkybox } from 'three/addons/objects/GroundedSkybox.js';
   ```
4. **Positioning** — the skybox must be placed at the height where you want the horizon/floor:
   ```ts
   const skybox = new GroundedSkybox(environmentMap, skyboxHeight, skyboxRadius);
   skybox.position.y = skyboxHeight;
   ```
   The `position.y` is set to the same value as the `height` passed to the constructor: the dome is drawn from `y = height` *downward* to the ground level `y = 0`, so the horizon sits exactly at `skyboxHeight`. If you skip this line, the whole dome shifts and the horizon detaches from your intended ground level.

### How the math works (briefly)

A `GroundedSkybox` is a big sphere (radius `radius`) whose fragment shader samples the environment map, but only for fragments whose direction is at or below the horizontal plane through `y = height`. Everything above that plane is discarded (the top cap is "sliced off"), so you see a dome — sky up high, and the lower part of the HDR projected onto the "ground". Because it's a sphere centered at the origin with `position.y = height`, the ground reads as an infinitely large flat surface at `y = 0`. The `height` is also what the camera should see as the horizon line.

Takeaway: `height` controls where the horizon sits vertically; `radius` controls the size of the dome around the scene.

## Code

in repo - `apps/19_4_ground_projected_env_map`

```ts
import * as THREE from 'three/webgpu';
import { GroundedSkybox } from 'three/addons/objects/GroundedSkybox.js';
import { HDRLoader } from 'three/addons/loaders/HDRLoader.js';

const scene = new THREE.Scene();
const renderer = new THREE.WebGPURenderer({ canvas });
await renderer.init();

// 1. load the HDR
const environmentMap = await new HDRLoader().loadAsync(
	'/textures/environmentMaps/meadow_2_2k.hdr',
);
environmentMap.mapping = THREE.EquirectangularReflectionMapping;

// 2. env map is ONLY for lighting, not the background
scene.environment = environmentMap;
scene.environmentIntensity = 1.0;

// 3. build the ground projected skybox
const skyboxHeight = 15;
const skyboxRadius = 100;

const skybox = new GroundedSkybox(environmentMap, skyboxHeight, skyboxRadius);
skybox.position.y = skyboxHeight; // horizon lands at y = skyboxHeight
scene.add(skybox);

// 4. camera far must comfortably exceed the skybox radius,
//    otherwise the skybox's far side gets clipped
const camera = new THREE.PerspectiveCamera(
	75,
	window.innerWidth / window.innerHeight,
	0.1,
	skyboxRadius * 3,
);

// 5. keep the camera inside the dome when zooming
const controls = new OrbitControls(camera, renderer.domElement);
controls.maxDistance = skyboxRadius * 0.9;

renderer.setAnimationLoop(() => {
	controls.update();
	renderer.render(scene, camera);
});
```

## Gotchas

- **Camera `far` vs skybox `radius` — the black orb.** If the camera `far` is equal to (or smaller than) the skybox radius, the far plane of the frustum can intersect the skybox sphere. Then the far side of the dome is clipped away and you see the *inside* of the sphere as a black orb around the scene — worst when zooming out and looking around. The fix used here: make `far` comfortably bigger than the radius (`skyboxRadius * 3`). There's nothing sacred about `3×` — the real requirement is `far > distance from camera to the far side of the dome`, i.e. roughly `far > radius + |camera position|`. Whatever margin you use, keep it a few times the radius so you never clip the dome no matter where the camera goes.
- **`maxDistance` only stops zoom.** `orbitControls.maxDistance = skyboxRadius * 0.9` prevents dollying past the sphere, so zooming can't put the camera outside the orb. But OrbitControls' `maxDistance` only constrains *dolly* — while panning, the camera can still travel horizontally right out the side of the dome. To truly cage the camera you'd need to clamp the camera position each frame (e.g. in the `tick` loop: if `camera.position.length() > skyboxRadius - margin`, normalize and rescale).
- **`skybox.position.y` must equal the `height` argument.** The constructor's `height` is the horizon height relative to the dome's origin; the mesh itself still needs `position.y = height` so the dome is actually "grounded" in the scene. Skip it and the horizon floats off.
- **`height` vs `radius` — no fixed ratio.** There's no magic rule like "height must be N% of radius". `radius` is about how big the dome is around your scene; `height` is about where the horizon line sits in the image. The practical constraint: the camera should stay *below* the horizon (i.e. `camera.position.y < skyboxHeight`) and inside the sphere — then the projection looks correct. Tweak both until the horizon sits where you want it.
- **The trick doesn't work everywhere.** Ground-projected skyboxes assume the environment map's horizon is (approximately) flat and that the ground plane is what's "down" in the image. If your HDR is a scene with objects around the center — e.g. a building at the equirectangular center, or a panorama where the vertical center isn't the horizon — the projection distorts and "floaty" artifacts appear. This is also why old plant-model test scenes with a sphere-mapped dome look wrong. Use an HDR with a clean, flat horizon (like `meadow_2_2k.hdr`).
- **WebGPU renderer needed.** `GroundedSkybox`'s shader is written for the WebGPU path. With a WebGL renderer (or the older `GroundProjectedSkybox`), results differ or break. This app uses `THREE.WebGPURenderer` and `three/webgpu` — see `19.0` for how that works.

## Revisit

- **Is `far = radius * 3` too much?** The README asks whether `3×` is overkill. `far` on a perspective camera only affects depth precision *within* the frustum — a larger `far` with a fixed `near` (0.1) reduces depth-buffer precision across the scene and can cause z-fighting on small objects far from the camera. With `near = 0.1` and `far = 300` the ratio is already 3000:1, so precision is tight but generally fine for this scene. If you notice z-fighting on the helmet or console, solve it by raising `near` (e.g. `0.5`–`1`) rather than shrinking `far`, or re-derive the exact needed far via `camera.position.length() + radius`.
- **Panning out of the orb.** `maxDistance` handles zoom only. Worth revisiting: clamping `camera.position` to a sphere of radius `skyboxRadius - margin` inside the animation loop, or disabling pan entirely (`orbitControls.enablePan = false`). Decide based on whether you want to inspect the models up close or let the user roam.
- **Is the floor always at `y = 0` of the scene?** The ground of the skybox lands at `y = 0` *because the scene origin is at the skybox height* — but the objects are positioned relative to the scene origin, not the skybox. If you move the whole scene (`scene.position.y = something`), the ground moves with it. The "ground is at 0" assumption is really "the horizon of the env map is at `skyboxHeight` above the skybox origin".
- **The `gamingConsole` model** (built in Blender, Draco-compressed) is loaded to compare how different env-map settings look on a custom model vs. the Flight Helmet and torus knot — revisit this comparison when exploring other environment settings from earlier lessons (`19.0`–`19.3`).

## Outdated

approach is valid

> ⚠️ **Not WebGL — this one is inherently WebGPU.** `GroundedSkybox` ships its shader for the WebGPU pipeline, and this app runs on `THREE.WebGPURenderer`. Earlier, the same effect on WebGL was the `GroundProjectedSkybox` addon (three r150-era) — it was renamed/buggy and is superseded. So if you ever need this look in a WebGL project, that old addon still exists in `three/examples/jsm/objects/GroundProjectedSkybox.js`, but it's the legacy path and won't get fixes. Prefer a WebGPU setup.
