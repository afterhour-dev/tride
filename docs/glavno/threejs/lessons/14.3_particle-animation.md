# 14.3 — Animating Particles

## Concept

In [14.0 particles webgl intro](14.0_particles-webgl-intro.md), [14.1 particles custom geometry](14.1_particles-custom-geometry.md), and [14.2 map alpha map colors blending](14.2_map-alpha-map-colors-blending.md) we built a particle cloud that just *sat there* — the positions were written once and never touched again. This lesson makes the cloud **move**. And the real subject of the lesson is not the motion itself, it's **how many different ways there are to animate a particle system**, and which ones are cheap and which ones will quietly kill your frame rate.

The lesson demonstrates **two** fundamentally different approaches, both live in the tick loop:

---

### Approach one — animate the `Points` as an `Object3D`

`THREE.Points` is not just a cloud of points. It inherits from `THREE.Object3D`, which means it has the same `position`, `rotation`, and `scale` as any other object in the scene. You can move, spin, and scale the **whole cloud** as one unit — exactly like moving a `Mesh`.

```ts
// inside the animation loop:
particles.rotation.y = elapsedTime * 0.2;   // spin the whole cloud
particles.position.y = Math.cos(elapsedTime * 0.2); // bob it up and down
```

This is the **cheap** way to animate. You are not touching a single vertex — you are just updating the object's transform, which every rendered frame already knows how to apply. The GPU re-renders the same vertices through a rotated camera transform. Literally one matrix per frame, no matter how many particles you have.

The GUI in the app (`pointsTweaks` folder) exposes `particles.position.x/y/z` as live sliders — so you can grab the whole cloud and push it around by hand to build intuition for this mode.

> 💡 The commented-out lines at the top of `tick()` show exactly this approach — `particles.rotation.y` and `particles.position.y`. Switch those on (and comment out the loop below) and the cloud will spin and bob as a rigid whole.

### Approach 2 — walk the position buffer 3 numbers at a time

The other way is to reach *inside* the geometry and rewrite the actual per-particle positions, frame by frame.

```js
for (let i = 0; i < count; i++) {
	const i3 = i * 3; // every particle owns 3 consecutive floats: x, y, z

	const x = particlesGreometry.attributes.position.array[i3];
	const z = particlesGreometry.attributes.position.array[i3 + 2];

	// animate the y of this one particle as a wave of its x and z
	particlesGreometry.attributes.position.array[i3 + 1] =
		Math.sin(elapsedTime + x) * 0.3 +
		Math.cos(elapsedTime + z) * 0.6;

	// tell the geometry the buffer changed
	particlesGreometry.attributes.position.needsUpdate = true;
}
```

The mental model here is the `count * 3` layout we met in [14.1 particles custom geometry](14.1_particles-custom-geometry.md). One particle is **three consecutive floats** in the `Float32Array`. To animate just the particle's height we step in triples (`i3`), read its existing `x` and `z`, and overwrite its `y` with a value that waves in time *and* in space. Because the wave is a function of `x` and `z`, different particles in different spots move differently — that's what makes it read as a living, surging cloud rather than a rigid spin.

### The two stars: `needsUpdate` and the cost

Two things about Approach 2 matter more than the math.

**1. `needsUpdate` is what actually tells the GPU to re-upload.**

Writing into `array` alone does nothing. The GPU is rendering the *previous* uploaded snapshot of the buffer. You must flag the attribute dirty:

```ts
particlesGreometry.attributes.position.needsUpdate = true;
```

That flag is the signal that says "this buffer changed, re-upload it before the next draw." Forgetting it is the single most common invisible bug — the loop runs, the array changes, and the screen shows nothing move. No error, just a cloud that pretends to be static.

The commented-out `particlesGreometry;` line is a leftover no-op — a reminder that a bare expression without a mutation or a flag does nothing. What actually matters is the `needsUpdate` write.

**2. Why the README calls this approach "a bad idea" — and the cost truth.**

Rewriting the whole `position` array and re-uploading it **every single frame** is genuinely expensive. In this app there are `20,000` particles, so `count * 3` = `60,000` floats that get rewritten and re-uploaded each frame. At 60 Hz that is ~3.6 million float writes per second just to move the cloud — and most of that upload goes absolutely nowhere useful, because each particle's `y` only changes by a tiny wave amount.

The README literally asks the driving question of this lesson:

> "I guess this is done less costly with vertex shader? Am I right?"

**Answer: yes, you are right.** The professional way to animate particles is not to touch the CPU buffer at all — it's to move the *wave math* into the **vertex shader** (TSL, Three.js Shading Language), so the GPU computes each particle's position *inside* the shader using the elapsed time. The CPU stays idle, the buffer is uploaded once, and the cost of animation drops to effectively zero. That is exactly the path this learning plan takes you on when the shader lessons arrive. This app deliberately does the CPU-side version so you can *feel* the ceiling it bumps into — the whole point is to build the intuition of why "move it in the shader" is the better answer.

That's the lesson-within-the-lesson: **know the cheap path (Object3D) and the expensive path (per-attribute), and know the *right* path for real particle systems is neither — it's the shader.**

## Code

in repo - `apps/14_3_paticles_animation`

```ts
import * as THREE from 'three';

const canvas = document.querySelector('canvas#tride')!;
const scene = new THREE.Scene();
const renderer = new THREE.WebGLRenderer({ canvas });

// -- geometry: 20k random positions + per-vertex colors --------------------
const count = 20000;
const positions = new Float32Array(count * 3);
const colors = new Float32Array(count * 3);
for (let i = 0; i < count * 3; i++) {
	positions[i] = (Math.random() - 0.5) * 10;
	colors[i] = Math.random();
}

const geometry = new THREE.BufferGeometry();
geometry.setAttribute('position', new THREE.BufferAttribute(positions, 3));
geometry.setAttribute('color', new THREE.BufferAttribute(colors, 3));

// -- PointsMaterial: alpha-shaped points, additive glow ----------------------
const material = new THREE.PointsMaterial();
material.vertexColors = true;
material.size = 0.1;
material.sizeAttenuation = true;
material.transparent = true;
material.alphaMap = textureLoader.load('/textures/particles/circle_04.png');
material.depthWrite = false;
material.blending = THREE.AdditiveBlending;

const particles = new THREE.Points(geometry, material);
scene.add(particles);

const camera = new THREE.PerspectiveCamera(75, innerWidth / innerHeight, 0.1, 100);
camera.position.z = 3;
scene.add(camera);

renderer.setPixelRatio(Math.min(devicePixelRatio, 2));
renderer.setSize(innerWidth, innerHeight);
renderer.setClearColor(0x000000, 1);

// -- animation loop ----------------------------------------------------------
const timer = new THREE.Timer();
renderer.setAnimationLoop((timestamp) => {
	timer.update(timestamp);
	const t = timer.getElapsed();

	// (A) cheap: treat Points as an Object3D
	// particles.rotation.y = t * 0.2;
	// particles.position.y = Math.cos(t * 0.2);

	// (B) expensive: rewrite every particle's buffer, frame after frame
	for (let i = 0; i < count; i++) {
		const i3 = i * 3;
		const x = geometry.attributes.position.array[i3];
		const z = geometry.attributes.position.array[i3 + 2];
		geometry.attributes.position.array[i3 + 1] =
			Math.sin(t + x) * 0.3 + Math.cos(t + z) * 0.6;
		geometry.attributes.position.needsUpdate = true; // re-upload the buffer!
	}

	renderer.render(scene, camera);
});
```

## Gotchas

- **`needsUpdate = true` is mandatory — and easy to skip.** Writing into `attributes.position.array` does nothing visible by itself. That flag is the only thing that tells Three to re-upload the buffer into the GPU. Leave it off and you get a perfectly executed math loop that renders a motionless cloud. No error, no hint.
- **The buffer is uploaded once.** Because it is, changing values in the array does not change the picture until you set `needsUpdate`. Watch yourself if your first instinct is "I mutated the array, surely it'll update" — that's the silent failure.
- **Approach 2 is a memory + upload throughput loop, not a "particles" problem.** At `count = 20,000` you're touching 60k floats and re-uploading them every single frame. That is the expensive path regardless of how cheap your math is. The README's cursor question — "isn't the shader cheaper?" — is the correct diagnosis.
- **Approach 1 (Object3D) is not an alternative for *individual* particle motion.** `Points.rotation.y`, `position.y`, `scale` move the **entire swarm** rigidly. If you want each point to drift independently, Object3D can't do it — that's the point at which you're back to the attribute walk (or the shader).
- **The `count * 3` triple-step is easy to hollow.** The loop reads `i3` (start of particle `i`), reads `[i3]` and `[i3+2]` (x and z), writes `[i3+1]` (y). If you index wrongly (e.g. `i` instead of `i*3`) you'll write across particle boundaries and get garbage motion or memory stomp.

## Outdated

approach is valid — the WebGL `Points` + `BufferGeometry` particle here is standard and works everywhere WebGL runs. The CPU-side animation loop itself is intentionally "the slow way," but as a learning instrument it is valid.

To actually *move* a large particle system at scale, though, rewriting the buffer every frame is **not** the professional answer. The up-to-date move is to put the motion in the **vertex shader** — animate `position` inside the shader using elapsed time so the CPU never re-uploads. That's the WebGPU + **TSL** (Three.js Shading Language) future this learning plan is building toward. So the shader-workout is best done with the WebGPU renderer:

> 💡 More up to date alternative: [TSL (Three.js Shading Language) docs](https://threejs.org/docs/TSL.html) — `🤖 suggested` — a vertex shader moves particles on the GPU, no per-frame CPU buffer rewrite; runs in WebGL **and** WebGPU. Replace the tight attribute loop with a node-graph shader that reads an elapsed-time uniform, and pass particle colors/sizes the same way.
> 💡 More up to date alternative: https://threejs.org/examples/ — the official examples under "particles" / "points" show shader-driven particle systems that animate without per-frame buffer churn.

## Revisit

- **The two animation modes, side by side.** Rewrite the loop so the Object3D path is alive (comment out the attribute loop) and feel how cheap and how *rigid* it is. Then swap back. The contrast is the lesson.
- **Per-attribute isn't the only buffer write.** Now that you've seen `needsUpdate`, try mutating the `color` buffer each frame too — make the cloud *pulse*. The `needsUpdate` flag applies to any attribute you hand a growing value to.
- **Move the math into a shader.** Rebuild the *same* wave — `y = sin(t+x)*0.3 + cos(t+z)*0.6` — but as a vertex shader over the `position` attribute. The cloud should now be a GPU-cost-less; the CPU does nothing per frame. That's the milestone this entire lesson is steering toward.
- **The count ceiling on the attribute path.** We validated 500k in [14.1 particles custom geometry](14.1_particles-custom-geometry.md) as a *static* cloud. Now do it *animated* via the attribute walk — watch how hard the animated path tops out vs the static one. That measured difference *is* the lesson.
- **`needsUpdate` on other attributes.** Try adding a `size` or `alpha` attribute in the future and watch how the same "set it, then name `needsUpdate`" pattern generalizes.
