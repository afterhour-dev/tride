## Concept

This lesson explores the **shadow map rendering pipeline** for a `DirectionalLight` and the knobs you can turn to optimize the resulting drop shadow's quality and performance. Once you have a working shadow (see [[13.0_shadows-intro]]), the next question is: how good is it, how expensive is it, and what can you tweak?

All the relevant state lives on the light's `shadow` property:

```ts
console.log(directionalLight.shadow);       // DirectionalLightShadow instance
console.log(directionalLight.shadow.camera); // OrthographicCamera instance
```

### The shadow map resolution (`mapSize`)

The shadow map is a render target — a square texture the light uses to "photograph" the scene's depth from its own point of view. Its size is controlled by `shadow.mapSize`, a `Vector2`:

```ts
directionalLight.shadow.mapSize.width = 1024;
directionalLight.shadow.mapSize.height = 1024;
```

**Higher resolution → sharper shadows, more GPU cost.** Lower resolution → softer/blockier shadows, cheaper. The GUI lets you step through 128 → 2048 and watch the trade-off live.

Why must `width` and `height` be the **same and a power of two**? The shadow map texture is often mipmapped, and power-of-two (POT) textures support mipmapping (and larger filter kernels) cleanly; square keeps the texel density uniform across the map so one axis isn't noticeably softer than the other. If they differ, quality is limited by the smaller dimension while you still pay for the larger one.

### The `near` / `far` planes

Like any truncated view, the shadow camera renders depth only between `near` and `far`:

```ts
directionalLight.shadow.camera.near = 1;
directionalLight.shadow.camera.far = 6;
```

Tighten these to just surround your visible shadow-casting geometry. `near`/`far` mostly affect **depth precision**, not throughput — so they won't greatly improve performance, but they do reduce z-fighting / shimmer in the shadow. Pushing `far` out far past your geometry wastes precision.

### Why is `shadow.camera` an `OrthographicCamera`?

A `DirectionalLight` simulates the **sun**: infinitely far away, so all its rays are effectively **parallel**. That's exactly what an orthographic camera represents — parallel projection with no perspective foreshortening. So the light's shadow view is an orthographic frustum.

Because of this, the shadow's coverage is a **box** you size with `top`, `bottom`, `left`, `right` (sometimes called the "amplitude"). The directional light's position matters only as an origin/offset; the *orientation* is what defines the parallel rays, and the box defines how wide that parallel slab is.

```ts
directionalLight.shadow.camera.top = 2;
directionalLight.shadow.camera.right = 2;
directionalLight.shadow.camera.bottom = -2;
directionalLight.shadow.camera.left = -2;
```

### "Amplitude" and why smaller is better

The four box values define how much of the world falls into the light's shadow map. **The shadow texture always has a fixed pixel budget** (your `mapSize`). So the math is:

```
shadow texel / world unit  =  mapSize  /  box extent  (amplitude)
```

If the box (amplitude) is **huge** — say a whole city of buildings — the same fixed texture is stretched across way more world units, so each texel covers more ground and **every shadow is blockier**. If you shrink the box down to just tightly hug your geometry, the fixed resolution is concentrated on the scene, and **shadows get sharper for free — without raising `mapSize`**.

So reducing amplitude is often cheaper (or at least cheaper-feeling) than increasing resolution: it buys quality on a per-shadow basis, not a global GPU cost. That's the core optimization idea of this lesson. Yes — a scene with a huge city would have worse shadow quality (or need a bigger, more expensive shadow map) because a single directional shadow map has to cover all of it.

### The `CameraHelper`

To *see* the shadow camera's frustum box and size it precisely, add a `CameraHelper` fed the shadow camera:

```ts
const helper = new THREE.CameraHelper(directionalLight.shadow.camera);
scene.add(helper);
```

It draws the orthographic box in the viewport so you can watch how `top/right/bottom/left` (and `near/far`) change coverage live.

### `updateProjectionMatrix()` — the trap

Changing `top`, `bottom`, `left`, `right`, `near`, or `far` on a camera does **not** automatically recompute its projection matrix. You must call:

```ts
directionalLight.shadow.camera.updateProjectionMatrix();
```

…which is why the GUI `onChange` callbacks in this app all do it. And because the `CameraHelper` caches the matrix it draws, you must also call `helper.update()` after changing the matrix, or the helper shows a stale box.

## Code

in repo - `apps/13_1_shadow_map_optim_one`

```ts
import * as THREE from 'three/webgpu';
import { OrbitControls } from 'three/addons/controls/OrbitControls.js';
import GUI from 'lil-gui';

const renderer = new THREE.WebGPURenderer({ canvas });
await renderer.init();
renderer.shadowMap.enabled = true;

const scene = new THREE.Scene();

// Ambient + directional light
const ambientLight = new THREE.AmbientLight(0xffffff, 1);
scene.add(ambientLight);

const directionalLight = new THREE.DirectionalLight(0xffffff, 1.5);
directionalLight.position.set(2, 2, -1);
directionalLight.castShadow = true;
scene.add(directionalLight);

// ---- Shadow map tweakables --------------------------------
directionalLight.shadow.mapSize.width = 1024;
directionalLight.shadow.mapSize.height = 1024;

directionalLight.shadow.camera.near = 1;
directionalLight.shadow.camera.far = 6;
directionalLight.shadow.camera.top = 2;
directionalLight.shadow.camera.right = 2;
directionalLight.shadow.camera.bottom = -2;
directionalLight.shadow.camera.left = -2;

// Visualize the shadow camera frustum
const shadowCamHelper = new THREE.CameraHelper(directionalLight.shadow.camera);
scene.add(shadowCamHelper);

// Standard objects
const material = new THREE.MeshStandardMaterial({ roughness: 0.7 });
const sphere = new THREE.Mesh(new THREE.SphereGeometry(0.5, 32, 32), material);
sphere.castShadow = true;

const floor = new THREE.Mesh(new THREE.PlaneGeometry(5, 5), material);
floor.receiveShadow = true;
floor.rotation.x = -Math.PI / 2;
floor.position.y = -0.5;

scene.add(sphere, floor);

// GUI: watch quality vs. cost live
const gui = new GUI();
const shadow = directionalLight.shadow;
gui.add(shadow.mapSize, 'width', [128, 256, 512, 1024, 2048]).name('mapSize.width');
gui.add(shadow.camera, 'near').min(0.5).max(100).onChange(() => {
  shadow.camera.updateProjectionMatrix();
  shadowCamHelper.update();
});
gui.add(shadow.camera, 'top').min(-5).max(5).onChange(() => {
  shadow.camera.updateProjectionMatrix();
  shadowCamHelper.update();
});
// ...same onChange pattern for right / bottom / left / far

const camera = new THREE.PerspectiveCamera(75, innerWidth / innerHeight, 0.1, 100);
camera.position.set(2, 1, 1);
const controls = new OrbitControls(camera, canvas);
controls.enableDamping = true;

renderer.setAnimationLoop(() => {
  controls.update();
  renderer.render(scene, camera);
});
```

## Gotchas

- **`mapSize.width` and `height` should be kept equal and a power of two.** Mismatched or non-POT sizes hurt mipmapping and give uneven sharpness. The GUI enforces this with a shared preset list.
- **You must call `shadow.camera.updateProjectionMatrix()` after changing `top/bottom/left/right/near/far`** — otherwise the frustum changes but the actual projection used for shadows does not.
- **The `CameraHelper` also needs its own `.update()`** after the projection matrix changes, or it keeps drawing the old frustum box. Easy to update the matrix and scratch your head over the helper "not moving".
- **`near`/`far` won't speed anything up** — they mainly affect depth precision and z-fighting. Don't expect a performance win from them.
- **The `ArrowHelper` direction is computed once at creation** and never re-derived from the light's position. Move the light and the arrow stays put. The GUI even warns about this. To be dynamic, recreate or update it each frame.
- **`directionalLight.lookAt(center)` doesn't behave like you'd expect** for rotating the shadow direction — `debugObject.directLookAtCenter` demonstrates this. The shadow frustum orientation is tied to the light's position/target; don't rely on `lookAt` pointing the shadow where you think.
- **`baseColor.clearcoat`, etc.:** not relevant here, but remember `MeshStandardMaterial` in WebGPU also needs `material.needsUpdate = true` when changing flags like `wireframe` (as seen in the GUI) or the material won't recompile.

## Revisit

- **Root a shadow's quality-to-cost trade-off in one number:** the relation `mapSize / amplitude` (texels per world unit). Revisit how you'd reason about a large scene (many buildings) needing either a bigger `mapSize` or separate per-light shadow maps.
- **Investigate `directionalLight.lookAt()`** and how shadow frustum orientation is really derived from position vs. target — the previous lesson flagged this as unresolved.
- The `DirectionalLightHelper` shows where/which way the light points; the `CameraHelper` shows the actual shadow box. Internalize **which helper answers which question**.
- Follow up with later "part two" optimization lessons (PCF filtering, shadow radius / normal bias, CSM / cascaded shadow maps) when they appear.
- The GUI's `onChange` + `updateProjectionMatrix` + `helper.update` trio is a pattern worth re-practicing until it's automatic.

approach is valid

The technique is unchanged across WebGL and WebGPU in Three.js. **This project already runs on `three/webgpu` + `WebGPURenderer` (WebGPU path) ⚡** — that's the modern rendering route with better shadow-related performance potential.
