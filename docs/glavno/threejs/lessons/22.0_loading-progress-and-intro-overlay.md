> This lesson is the beginning of a series about loading progress and intro. It also marks the **first time writing TSL** (Three Shading Language) and the first time making something **always glued to the camera lens** — an overlay.

## Concept

### Why we need a loader and an intro at all

The starter for this project is the realistic-render setup (see `20.x`) with the Flight Helmet (≈ 50 MB) and a Game-Boy-like console model I built in Blender. Everything shows up only once it's ready, which means a long black or empty canvas while the browser downloads and decodes assets. The goal of the series: show a **loading progress**, then reveal the scene nicely with an **intro/fade-out**.

The loader will be a mix of **WebGPU + HTML/CSS**.

### Ways to make a full-screen overlay

There are several ways to put a black overlay over the screen:

1. **Animate the `<canvas>` in CSS** — hide/fade the canvas element itself.
2. **Animate a `<div>` wrapping the `<canvas>`** — same idea one level up the DOM.
3. **Draw a black rectangle in front of the camera** — a plane in 3D that always faces the camera and covers the whole screen.

We go with **option 3**: a black plane that fades out once the models are loaded.

### How to pin a plane in front of the camera

The obvious approach: add the plane as a child of the camera object and move it slightly forward. Because the plane is a child of the camera, it inherits the camera's transforms and follows it everywhere.

We do something different: **keep the plane in the scene**, but position its vertices with a **vertex shader** that throws away all matrix transformations (see `// EXPLAIN:` comments in `src/shaders/index.ts`).

A normal Three.js vertex shader computes:

```glsl
gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0);
```

That pipeline takes the geometry position through the model matrix, the view matrix, and finally the projection matrix — which is exactly why an object in the scene moves on screen when the camera moves.

Our overlay vertex node skips all of it:

```ts
export const vertexNode = vec4(positionGeometry, 1.0);
```

The plane's vertices go **straight into clip space**. After the perspective divide, clip-space `x` and `y` in `[-1, 1]` map exactly onto the screen edges — so the plane is glued to the lens, and the camera can never scroll past it. `positionLocal` (the same position but already through the model matrix) is deliberately *not* used: any transform on the overlay mesh would then break the "always in front" guarantee.

### Plane size matters: 1×1 → 2×2

Clip space `x`/`y` range from `-1` to `1`. A `PlaneGeometry(1, 1)` has vertices at `±0.5` — that only covers a quarter of the screen. To fill the entire screen from corner to corner the plane needs to be **2×2** so its vertices land exactly on `±1`. (This is called out in the README: "instead of 1 x 1 it should be 2 x 2.")

The material is created with `wireframe: true` at first (comment in `main.ts`) specifically to *see* the overlay geometry while tuning its size — flip it off once the size is right.

### First TSL: node-based shaders

This project writes shaders with **TSL** for the first time. TSL (Three Shading Language) is Three.js's node-based shader system — instead of writing a `ShaderMaterial` with raw GLSL strings, you build shaders out of composable node objects in JavaScript (`three/tsl`). Together with node materials, this is the modern way to do custom shaders in Three.js, and it's what you use on the WebGPU path.

In `src/shaders/index.ts`:

```ts
import { positionGeometry, vec3, vec4, uv } from 'three/tsl';

export const vertexNode = vec4(positionGeometry, 1.0); // overrides vertex stage output (clip space position)
export const colorNode = vec3(uv().yx, uv().y);        // overrides final fragment color
```

These are applied to a `MeshBasicNodeMaterial` in `main.ts`:

```ts
overlayMaterial.vertexNode = vertexNode;
overlayMaterial.colorNode = colorNode;
```

Note the two hooks are not the same:

- `material.vertexNode` overrides the **whole vertex output** (what becomes `gl_Position`).
- `material.positionNode` overrides **only the position part** inside the standard vertex pipeline.
- `material.colorNode` plugs into the fragment stage and overrides the final color.

We use `vertexNode` because we want to replace the entire `gl_Position` computation, not just the position input.

The demo `colorNode` (`vec3(uv().yx, uv().y)`) just visualizes the overlay: it turns the UV coordinates into RGB so you can see the plane covering the screen as a smooth gradient.

### LoadingManagers per asset category

To track loading we use `LoadingManager` — one per asset category, each attached to the loader that needs it:

| Manager | Loader | Assets |
|---|---|---|
| `envMapTextureLoadingManager` | `CubeTextureLoader` | environment map (abandoned garage) |
| `textureLoadingManger` | `TextureLoader` | floor & wall textures |
| `modelLoadingManager` | `GLTFLoader` (+ `DRACOLoader`) | helmet + console models |

Three.js loaders accept a `LoadingManager` as their first argument, and the manager fires four callbacks:

- `onStart(fileUrl)` — a load begins
- `onProgress(fileUrl, itemsLoaded, itemsTotal)` — an item finished
- `onLoad()` — everything in this manager is done
- `onError(err)` — something failed

In this lesson the handlers are mostly placeholders (commented out / `console.log`), because it's the beginning of the series — computing actual percentages and fading the overlay out is the next step. The pieces are already in place: the managers exist, the overlay exists, now they need to talk to each other.

One important API detail when loading GLTF models (`// NOTE` in `main.ts`): use `gltfLoader.load(...)`, **not** `loadAsync`, because `load()`'s return value is not the model — the model is available only inside the callback.

## Code

in repo - `apps/22_0_loading_progress_and_intro_overlay`

```ts
import * as THREE from 'three/webgpu';
import { vec3, vec4, uv, positionGeometry } from 'three/tsl';

const renderer = new THREE.WebGPURenderer({ antialias: true });
await renderer.init(); // WebGPU renderer needs async init

const scene = new THREE.Scene();
const camera = new THREE.PerspectiveCamera(75, innerWidth / innerHeight, 0.1, 100);
scene.add(camera);

// ------------------------------------------------------------
// Overlay: a plane pinned to the screen via a custom vertex node.
// 2 x 2 so its vertices land on clip-space ±1 and cover the screen.
// ------------------------------------------------------------
const overlayMaterial = new THREE.MeshBasicNodeMaterial();
overlayMaterial.vertexNode = vec4(positionGeometry, 1.0);
overlayMaterial.colorNode = vec3(uv().yx, uv().y); // gradient to see it

const overlay = new THREE.Mesh(
	new THREE.PlaneGeometry(2, 2, 1, 1),
	overlayMaterial,
);
scene.add(overlay);

// ...rest of the scene, loaders, lights, models...

renderer.setAnimationLoop(() => {
	renderer.render(scene, camera);
});
```

## Gotchas

- **1×1 does not cover the screen.** A `PlaneGeometry(1, 1)` spans `-0.5…0.5`; you need `2×2` to reach clip-space `±1`. Debug with `wireframe: true` on the overlay material until it fills the viewport.
- **Using `positionGeometry` throws away the model matrix.** Any `scale`/`position`/`rotation` you set on the overlay mesh will be ignored — that's the point (the plane is screen space now), but it's surprising if you forget why the overlay "doesn't move."
- **Positioning in direct clip space bypasses matrices — but also depth.** Writing `vec4(position, 1.0)` with a plane at `z = 0` puts depth at the NDC middle (0.5), not at the front. For a fade-out intro it usually reads fine, but a truly bulletproof "always in front" overlay that doesn't intersect the scene may need `depthTest`/`depthWrite` handling — worth keeping in mind for later in the series.
- **`WebGPURenderer` init is async.** `renderer.init()` must resolve before rendering; the app `await`s it inside the `init()` function.
- **`load()` vs `loadAsync()` for GLTF.** `gltfLoader.load(url, callback)` — the model exists only inside the callback. Don't write `const model = gltfLoader.load(...)`, it won't be there.
- **Shadow map notes carried over from the starter:** `PCFSoftShadowMap` is deprecated (use `PCFShadowMap`), and `shadow.radius` (blur) doesn't work with `PCFSoftShadowMap` anyway.
- **Cube map mapping:** setting `EquirectangularReflectionMapping` on a cube texture errors; use `THREE.CubeReflectionMapping`. Equirectangular mapping is for `.hdr`/`.exr` panoramas.
- **The old color-space WebGPU problem:** this starter uses `WebGPU` even though the readme mentions a known issue — related context from [[20.2_realistic-render-textures-and-color-space]].

## Revisit

- **Wire up the progress**: the `onProgress` handlers are currently placeholders. Compute a real percentage and drive something visible with it.
- **Fade the overlay out** when everything is loaded — that's the actual "intro" this series is heading towards. Currently the overlay just sits there as a UV gradient.
- **The HTML/CSS side of the loader**: the README promises a mix of WebGPU and HTML/CSS for the loader; only the WebGPU half exists so far.
- **Depth behavior of the screen-space plane** — check `depthTest`/`depthWrite` so the overlay never pokes through or clips the scene during the fade.
- **Cube texture mapping gotcha** (`CubeReflectionMapping` vs `EquirectangularReflectionMapping`) — easy to re-introduce by mistake.

## Outdated

Approach is valid. The technique — a full-screen plane whose vertex shader skips matrix transforms so it stays glued to the lens — is still the standard way to do camera-attached overlays, and Three.js's own loading-progress examples use a descendant of this idea.

What's worth underlining: this state of the project already runs on the **WebGPU renderer (`THREE.WebGPURenderer`) with TSL node materials instead of WebGL + raw `ShaderMaterial` GLSL — that's the forward-looking path** 🌐 ⚡. If you know the older way (a `ShaderMaterial` with a GLSL string like `void main() { gl_Position = vec4(position, 1.0); }`), that still works, but on the WebGPU side Three.js pushes node-based TSL materials, so it's the better thing to build new shaders on.

> 💡 More up to date alternative: https://threejs.org/examples/?q=webgpu — official WebGPU/TSL examples, the current way to see how overlay/effect shaders are written today.
