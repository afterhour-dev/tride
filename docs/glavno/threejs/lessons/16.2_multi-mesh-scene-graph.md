## Concept

In [16.0_imported-models-intro](16.0_imported-models-intro.md) and [16.1_gltf-flavor-comparison](16.1_gltf-flavor-comparison.md) we loaded the Duck — a toy model whose scene graph is a single `Object3D` holding one mesh (plus an exported camera). This lesson moves to a **real, production-scale model**: the Khronos **Flight Helmet** from [glTF-Sample-Models](https://github.com/KhronosGroup/glTF-Sample-Models), loaded from `public/models/FlightHelmet/`. It teaches us how to handle a model that is **not one mesh** but a whole scene.

### What's inside `/public/models/FlightHelmet/`

The model folder brings three things (this is also what the README's `Šta samo ukratko pomenuti` asks about — what files live in `public/models/FlightHelmet/glTF`):

| Path | Contents |
|---|---|
| `README.md` | provenance + license (donated by Microsoft, **CC0** — no attribution restrictions) + texture-compression notes |
| `screenshot/` | a `.jpg` preview of the model |
| `glTF/` | the default glTF flavor: `FlightHelmet.gltf` (JSON), `FlightHelmet.bin` (geometry), and **15 PNG textures** (5 materials × baseColor/normal/occlusionRoughMetal) |
| `glTF-KTX-BasisU/` | the same model re-exported with **KHR_texture_basisu** — PNGs converted to `.ktx2` (Basis Universal), as described in the README's table |

The `glTF-KTX-BasisU` variant is a great real-world example of **texture optimization** (see [8.4_format-and-optimisation](8.4_format-and-optimisation.md)): the README's table shows the before/after for each texture. Total goes from **43.06 MB → 29.37 MB**, and the color (ETC1S — LDR, visually-lossy) textures shrink dramatically (e.g. LeatherPartsMat_BaseColor 5.22 MB → 483 KB), while normal/roughness maps use **UASTC** (higher quality, RGB, for non-color data) and often even *grow* slightly. The `.ktx2` files are just sitting on disk in this lesson — nothing loads them yet. That's a Revisit item.

### The Flight Helmet's scene graph

This is the key difference from the Duck. Parsing `FlightHelmet.gltf`:

```
scene (Group)
├── node 0 (Hose_low)           → Mesh, material 0 (HoseMat)
├── node 1 (RubberWood_low)     → Mesh, material 1 (RubberWoodMat)
├── node 2 (GlassPlastic_low)   → Mesh, material 2 (GlassPlasticMat)
├── node 3 (MetalParts_low)     → Mesh, material 3 (MetalPartsMat)
├── node 4 (LeatherParts_low)   → Mesh, material 4 (LeatherPartsMat)
└── node 5 (Lenses_low)         → Mesh, material 5 (LensesMat)
```

Six nodes, six meshes, six materials, **one scene with flat children** (no nesting, no animations in this variant). So `flightHelmet.scene.children` is an array of **6 Mesh instances** — the code's `EXPLAIN` comment says "I looked into `scene.children` property and I saw six Mesh instances". `console.log(flightHelmet)` in the app lets you repeat that inspection live.

### The trap: adding only one child

The code first shows the naive approach (commented out):

```ts
scene.add(flightHelmet.scene.children[0]);
```

Because `children[0]` is `Hose_low` (the helmet's air pipe), you get **just one small piece of the helmet** floating in the scene. The intuition from the Duck lesson — "add the first child, done" — breaks the moment a model has more than one child. To add the whole model you must add *all* of them.

### Three ways to add every child

The code walks through three solutions, each `// EXPLAIN:`-commented as a learning path:

**1. Naive `for...of` loop over `children` (broken):**

```ts
for (const item of flightHelmet.scene.children) {
  scene.add(item);  // model is incomplete, parts missing
}
```

Why is it broken? The user's own hypothesis in the comments is correct: **`scene.add(item)` removes `item` from the model's `children` array** (Three.js *re-parents* — an object can only have one parent, so adding it to our scene detaches it from the model's scene). Since `for...of` iterates lazily over the live array by index, each removal shifts the remaining items down by one. The next iteration skips the item that just fell into the vacated slot — so with 6 children, only ~3 ever get added, and *which* ones (the odd/even pattern) is why some people "get different parts on refresh". Not undefined behavior exactly, but order- and timing-dependent missing meshes.

**2. `while` loop on `length` (works, but mutates):**

```ts
while (flightHelmet.scene.children.length) {
  scene.add(flightHelmet.scene.children[0]);
}
```

This is the fix: we always take index 0, and the condition is the *shrinking array's* length — when it hits falsy `0`, we stop. Every item gets added, because index 0 is re-evaluated every iteration. The comment notes "this worked, we added all parts of the model". The side effect: `flightHelmet.scene.children` is left **empty** (we emptied it into the scene).

**3. Copy the array first (works, non-destructive):**

```ts
const items = [...flightHelmet.scene.children];

for (const item of items) {
  scene.add(item);
  item.castShadow = true;  // explicit — children don't inherit shadow flags
}
```

Spreading `children` into a new `items` array breaks the connection to the live model array: `items` holds **object references**, not a live view. Removing an item from the model's scene doesn't alter `items`, so every child is visited exactly once. Bonus (the `EXPLAIN` comment): `scene.add(item)` + `item.castShadow = true` **does produce a proper drop shadow** for the model.

### The winner: just add the whole `flightHelmet.scene`

```ts
scene.add(flightHelmet.scene);
```

`flightHelmet.scene` is a `Group` instance, and adding a `Group` to our scene adds the *entire subtree* in one call — the "simplest solution" the comments mention. This is the approach the app actually runs. It's the same as option 1 from [16.0_imported-models-intro](16.0_imported-models-intro.md) ("add the whole `duckModel.scene`"), deferred twice before and finally exercised here.

Which of the three is "best"? There's no universal answer — that's the open question the comments leave. Correlating with 16.0's list of approaches:

- `scene.add(flightHelmet.scene)` — **simplest, preserves everything** (parent transform, hierarchy, future structure changes). Pick this as the default.
- The array-copy loop — needed only when you want to **filter or post-process** children (set shadows per-mesh, swap materials, prune nodes), or when adding the whole scene would drag along unwanted cameras/lights.
- The other two are learning artifacts: the for-loop is a bug to recognize, the `while` loop is a mutation trick to know but not prefer.

### Everything else is familiar

The rest of the scene setup repeats known patterns: `WebGPURenderer`, four cube environment maps with `scene.environment` **switched live from the GUI** (studio default), `AmbientLight` + `DirectionalLight` with shadow config (see [13.3_particle-animation](../lessons/13.3_particle-animation.md) — or rather the shadow lessons [13.x](../lessons/13.0_shadows-intro.md)), a floor mesh with `receiveShadow`, `OrbitControls` with damping, and the `h`-key GUI toggle plus resize/fullscreen handlers. The notable additions worth mentioning only briefly:

- Three **helpers** behind toggles: `DirectionalLightHelper`, `ArrowHelper` (direction of the directional light), `CameraHelper` (the shadow camera frustum), plus a colored `AxesHelper`.
- The GUI's `Directional Light Shadow tweaks` folder reproduces the full shadow-camera / `mapSize` / `bias` / `radius` toolbox from [13.1_shadow-map-optimization-part-one](13.1_shadow-map-optimization-part-one.md), including the note that `shadow.radius` (blur) **doesn't work** with `PCFSoftShadowMap`.

## Code

in repo — `apps/16_2_imported_models_complex_model`

```ts
import * as THREE from 'three/webgpu';
import { OrbitControls } from 'three/addons/controls/OrbitControls.js';
import { GLTFLoader } from 'three/addons/loaders/GLTFLoader.js';
import GUI from 'lil-gui';
import { getRequiredElement } from './util';

const cubeTextureLoader = new THREE.CubeTextureLoader(new THREE.LoadingManager());
const modelLoadingManager = new THREE.LoadingManager();
const gltfLoader = new GLTFLoader(modelLoadingManager);

modelLoadingManager.onProgress = (filePaths: string) => console.log('progess ', filePaths);
modelLoadingManager.onLoad = () => console.log('model/s loaded');
modelLoadingManager.onError = (e) => console.error(e);
modelLoadingManager.onStart = (filePath) => console.log('loading started ', filePath);

const canvas = getRequiredElement<HTMLCanvasElement>('canvas#tride');
const sizes = { width: window.innerWidth, height: window.innerHeight };

async function init() {
  const scene = new THREE.Scene();
  const renderer = new THREE.WebGPURenderer({ canvas });
  await renderer.init();

  // Four cube environment maps to switch from the GUI
  const environmentMapTextureStudio = await cubeTextureLoader
    .setPath('/textures/environmentMaps/studio/')
    .loadAsync(['px.png', 'nx.png', 'py.png', 'ny.png', 'pz.png', 'nz.png']);
  scene.environment = environmentMapTextureStudio;

  // Load the complex model — 6 meshes, 6 materials, flat scene
  const flightHelmet = await gltfLoader.loadAsync(
    '/models/FlightHelmet/glTF/FlightHelmet.gltf',
  );
  console.log(flightHelmet); // scene.children = six Mesh instances

  // ✳️ The three ways (alphabetically): broken for-loop / while-loop / copy
  // The app runs the simplest one:
  scene.add(flightHelmet.scene); // flightHelmet.scene is a Group — whole subtree added

  renderer.shadowMap.enabled = true;
  renderer.shadowMap.type = THREE.PCFSoftShadowMap;

  const ambientLight = new THREE.AmbientLight(0xffffff, 2.1);
  scene.add(ambientLight);

  const directionalLight = new THREE.DirectionalLight(0xffffff, 0.4 * Math.PI);
  directionalLight.position.set(5, 5, 5);
  directionalLight.castShadow = true;
  directionalLight.shadow.mapSize.setScalar(1024);
  directionalLight.shadow.camera.far = 15;
  directionalLight.shadow.camera.top = 7;
  directionalLight.shadow.camera.right = 7;
  directionalLight.shadow.camera.bottom = -7;
  directionalLight.shadow.camera.left = -7;
  scene.add(directionalLight);

  const floor = new THREE.Mesh(
    new THREE.PlaneGeometry(10, 10),
    new THREE.MeshStandardMaterial({
      roughness: 0.4,
      metalness: 0.3,
      color: new THREE.Color('#928192'),
    }),
  );
  floor.rotation.x = -Math.PI / 2;
  floor.receiveShadow = true;
  scene.add(floor);

  const camera = new THREE.PerspectiveCamera(75, sizes.width / sizes.height, 0.1, 100);
  camera.position.set(-0.5, 1, 0.6);
  scene.add(camera);

  const orbitControls = new OrbitControls(camera, canvas);
  orbitControls.enableDamping = true;

  renderer.setPixelRatio(Math.min(window.devicePixelRatio, 2));
  renderer.setSize(sizes.width, sizes.height);

  const timer = new THREE.Timer();
  renderer.setAnimationLoop(tick);

  function tick(timestamp: number) {
    timer.update(timestamp);
    orbitControls.update();
    renderer.render(scene, camera);
  }
}

await init();
```

## Gotchas

- **`scene.add(item)` *removes* `item` from the model's `children`.** Three.js re-parents: an `Object3D` can have only one parent, so adding it to your scene detaches it from the loader's `Group`.
- **A `for...of` loop over `children` while adding them skips items.** Because `for...of` iterates the *live* array by index and every `add` shifts the rest down, alternates get skipped. The silhouette is missing pieces, and *which* ones can vary between refreshes. Recognize this exact bug on sight.
- **The fix is index 0 + `length`, or a copied array.** `while (children.length) add(children[0])` works but **empties** the model's `children`. `[...children].forEach(add)` keeps the model's array intact and lets you set `castShadow` per mesh.
- **`castShadow` is per-mesh, not inherited.** Adding the whole `flightHelmet.scene` does **not** give the model a shadow just because `directionalLight.castShadow = true`. Solid meshes that should shadow need `mesh.castShadow = true` explicitly — hence the copy-loop trick setting it on each child. (The model **does** cast a shadow in the app only because of that.)
- **`directionalLight.shadow.radius` (blur) doesn't work with `THREE.PCFSoftShadowMap`** — the GUI disables that knob with a note. Use `PCFShadowMap` if you want the radius blur, or bake softness (see [13.5_baking-shadows](13.5_baking-shadows.md)).
- **`ArrowHelper` direction is computed once at creation.** The GUI's own note says the arrow stays put if you move the directional light; you'd have to recreate/update it per frame.
- **`Documentation` of shadow helpers needs `renderer.shadowMap.enabled === true`** for the shadow camera helper to visualize correctly — the GUI prints this warning inline.
- **A complex PBR model needs light *and* environment.** Without `scene.environment` (or lights) the helmet renders black — same rule as the Duck, but with 15 textures it's easier to mistake a lighting problem for a texture-loading problem.

## Revisit

- **The `glTF-KTX-BasisU` variant is on disk but unused.** The `.ktx2` textures need `KTX2Loader` (`gltfLoader.setKTX2Loader(...)`) — a natural next experiment comparing load times / visual quality vs the PNG variant, right in line with the README's 43.06 → 29.37 MB table. `🤖 suggested`
- **"Which way to add the model is best?"** — the open `EXPLAIN` question in the code stays open here. When you hit a model whose scene tree is *nested* (Groups inside Groups) or that ships cameras/lights/animations, re-evaluate: whole-scene add vs array-copy post-processing.
- **The `while (children.length)` mutation empties the loader's group.** Easy to forget that you've consumed the array; a later `console.log(flightHelmet.scene.children)` returns `[]` and looks like a loading failure.
- **Embedded and Draco flavors** of the helmet (as with the Duck in 16.1) — the scenario where you'd want `KTX2Loader` + `DRACOLoader` combined on one model.
- **Traversing for materials** (`flightHelmet.scene.traverse(...)`) — how you'd visit all 6 meshes in one pass (e.g. to set shadows) without the copy loop.
