## Concept

This lesson builds on the perspective camera from [[4.2_camera-perspective]] by adding interactivity — the camera follows the mouse cursor.

The core idea is simple: capture `mousemove` events on the window, normalize the cursor's screen coordinates into a usable range, and apply those values to `camera.position.x` and `camera.position.y` every frame.

### Cursor normalization

When the mouse moves across the canvas, `ev.clientX` and `ev.clientY` give raw pixel coordinates. To make these useful for camera movement, we need to normalize them:

**Raw to 0–1 range:**

```ts
ev.clientX / sizes.width   // left edge → 0, right edge → 1
ev.clientY / sizes.height  // top edge → 0, bottom edge → 1
```

**0–1 to Cartesian range (centered on canvas):**

```ts
cursor.x = ev.clientX / sizes.width - 0.5;    // range: -0.5 … 0.5
cursor.y = 0.5 - ev.clientY / sizes.height;    // range: -0.5 … 0.5
```

This maps the canvas into a small Cartesian coordinate system where `(0, 0)` is the center. Moving the mouse to the left side of the canvas gives negative `x`, moving up gives positive `y`.

### Applying to the camera

Each frame in the render loop, the cursor values are assigned directly to the camera position:

```ts
camera.position.x = cursor.x;
camera.position.y = cursor.y;
```

Since `cursor.x` and `cursor.y` are already in world units (roughly -0.5 to 0.5), the camera moves within a small range around the origin. The box at `(-0.5, 0, 0.5)` stays fixed while the camera drifts based on mouse position.

If you also want the camera to always face the mesh, uncomment `camera.lookAt(mesh.position)` — but the lesson works fine without it, demonstrating that camera position and look direction are independent.

## Code

in repo — `apps/4_camera_mousemove`

```ts
const cursor = { x: 0, y: 0 };

window.addEventListener('mousemove', (ev) => {
  cursor.x = ev.clientX / sizes.width - 0.5;
  cursor.y = 0.5 - ev.clientY / sizes.height;
});

// inside render loop:
camera.position.x = cursor.x;
camera.position.y = cursor.y;
```

## Gotchas

- **Cursor values are set on the window, not the canvas.** If you move the mouse outside the canvas, `clientX`/`clientY` can exceed canvas dimensions, pushing the camera beyond the normalized range. This doesn't break anything (the box just leaves the frame), but it's worth knowing why the camera drifts unexpectedly.

- **The Y axis is flipped.** Raw `clientY` increases downward, but Three.js Y increases upward. The `0.5 - ev.clientY / sizes.height` expression accounts for this inversion — flipping the sign would make the camera move in the opposite direction from the mouse.

- **Canvas size is hardcoded to 800×600.** The normalization uses fixed `sizes.width` and `sizes.height` rather than the actual canvas or window dimensions. If the canvas is resized (e.g., via CSS), the mapping breaks. For production code, use `canvas.clientWidth` / `canvas.clientHeight` or `window.innerWidth` / `window.innerHeight`.

## Revisit

- Try adding `camera.lookAt(mesh.position)` to see the difference between moving the camera and moving the camera's look target.
- Replace the fixed `800×600` sizes with actual canvas dimensions to handle dynamic resizing.
- Explore what happens with a `PerspectiveCamera` at different field-of-view values — the same cursor range produces very different visual results at 50° vs 90°.
- Consider using `THREE.Vector2` for the cursor instead of a plain object — it comes with built-in math methods.
