# 17.5 raycaster with models

## Concept

The previous lessons ([17.2](17.2_raycaster-with-mouse.md), [17.3](17.3_raycaster-hover-enter-leave.md), [17.4](17.4_raycaster-mouse-click.md)) raycast against hand-made primitive meshes. This lesson answers the more realistic question: **how do I raycast against a loaded model?** Everything from before — NDC mouse normalization, `raycaster.setFromCamera(mouse, camera)` every frame, per-frame hover state — stays exactly the same. The only new idea is *what object we hand to the raycaster*. Instead of a list of `Mesh`es, we hand it **the loaded model's root scene, a `Group`**, and the raycaster figures out the meshes for us.

### Loading the model

The app imports the Duck from the [Khronos glTF-Sample-Models](https://github.com/KhronosGroup/glTF-Sample-Models) repo (`2.0/Duck`), in the **glTF-Binary (`.glb`)** flavor. Loading uses the same pipeline as [16.1](16.1_gltf-flavor-comparison.md) / [16.3](16.3_draco.md): a `LoadingManager`, a [`GLTFLoader`](https://threejs.org/docs/#api/en/loaders/GLTFLoader), and a `DRACOLoader` with its decoder path wired in:

```ts
const gltfLoader = new GLTFLoader(loadingManager);
const dracoLoader = new DRACOLoader();
dracoLoader.setDecoderPath('/draco/');
gltfLoader.setDRACOLoader(dracoLoader);

const duckModel = await gltfLoader.loadAsync('/models/Duck/glTF-Binary/Duck.glb');
duckModel.scene.position.y = -2.4;
scene.add(duckModel.scene);
```

The `// EXPLAIN:` comments in `src/main.ts` highlight exactly these two points: *instatiating the gltf loader* and *here is our duck model, we are loading binary*.

**Why is the model's root a `Group` and not a `Mesh`?** A glTF file is a scene graph. `duckModel.scene` (the `.scene` property of the loaded `GLTF` object) is the root of that graph, and under it sit the actual `Mesh` nodes. In this simple model the root also holds a camera node that came along inside the glTF hierarchy — you can log `duckModel` to see the structure. We don't care about that camera; we only care that the thing we add to the scene and test against is the `Group`. For a flat model, `scene.add(duckModel.scene)` is all you need. The point of the raycaster approach used here is precisely that **it doesn't just work for flat models**: whether the root contains one mesh or ten thousand nested meshes, you still test a single object, the parent.

### The intersect test on the model

The raycaster is already re-set from the mouse at the top of the tick (from the previous lessons). Right after that — before the sphere/box test — the model is tested with **`intersectObject`, singular** this time:

```ts
raycaster.setFromCamera(mouse, camera);

const modelIntersects = raycaster.intersectObject(duckModel.scene);
```

The variable is named `modelIntersect` in the README — a *separate* variable from `intersects`, so it never conflicts with the primitive objects' test.

**Why singular, and why it's weird that it returns an array.** `intersectObject` recurses through the object's children by default. The `Group` itself has no geometry — it's "nothing" in space — but its meshes are somewhere, and the raycaster walks down into them automatically (children, and children of children, and so on). That recursion is why:

- one call on the parent tests every mesh in the model, and
- the return value is **still an array of `Intersection`s**, even though we passed a single object.

There can be multiple entries in that array for two reasons: recursion can hit multiple meshes, and a single ray can pierce *one* mesh multiple times if it enters and exits it twice (a torus, or — easier to test here — pointing the ray at the duck's head from above so it goes **through the head and also hits the tail**, see Revisit).

### Hover → scale, recomputed every frame

The per-frame test drives a read-as-state hover exactly like 17.3, but simpler because we only want enter/leave, not enter/leave events:

```ts
if (modelIntersects.length) {
  duckModel.scene.scale.setScalar(1.4);
} else {
  duckModel.scene.scale.setScalar(1);
}
```

When the cursor is over the duck the array is non-empty → scale up to `1.4`; otherwise reset to `1`. Because the `if/else` reruns every frame, "hovering" and "hovering is over" are just *this frame's* boolean — no event bookkeeping needed, and resetting to `1` each non-hover frame makes the revert automatic.

### The rest is unchanged

The two other raycast consumers from the previous lessons keep running alongside: `intersectObjects(objectsToTest)` for the coloring of the primitives and the `currentIntersect` state used by the click handler. The ray driven by the `mousemove` event, the per-frame `setFromCamera`, and the `Renderer`'s animation loop are all exactly as in 17.2–17.4.

## Code

in repo — `apps/17_5_raycasting_with_models`

```ts
import * as THREE from 'three/webgpu';
import { GLTFLoader } from 'three/addons/loaders/GLTFLoader.js';

// ... scene, WebGPURenderer, camera, OrbitControls, lights,
// three primitives + floor, as in 17.2 / 17.3 ...

const mouse = new THREE.Vector2(0, 0);
const raycaster = new THREE.Raycaster();

// --- model loading: awaited, so the scene is guaranteed ready ---
const duckModel = await gltfLoader.loadAsync('/models/Duck/glTF-Binary/Duck.glb');
duckModel.scene.position.y = -2.4;
scene.add(duckModel.scene);

window.addEventListener('mousemove', (e) => {
  mouse.x = (e.clientX / sizes.width) * 2 - 1;
  mouse.y = -((e.clientY / sizes.height) * 2 - 1);
});

renderer.setAnimationLoop((timestamp) => {
  timer.update(timestamp);
  // ... bob the primitives ...

  raycaster.setFromCamera(mouse, camera);

  // singular, recursive: tests the Group's whole mesh hierarchy
  const modelIntersects = raycaster.intersectObject(duckModel.scene);
  if (modelIntersects.length) {
    duckModel.scene.scale.setScalar(1.4); // cursor over the model
  } else {
    duckModel.scene.scale.setScalar(1);   // cursor elsewhere
  }

  // ... the primitives' intersectObjects / hover-coloring /
  // click-state blocks from 17.2–17.4, unchanged ...

  orbitControls.update();
  renderer.render(scene, camera);
});
```

## Gotchas

- **`intersectObject` on a `Group` only works because recursion is on by default.** The group has no geometry of its own; the raycaster descends into children automatically. The second argument, `false`, disables that recursion:
  ```ts
  raycaster.intersectObject(duckModel.scene, false);
  ```
  With `false`, the group — having no renderable geometry itself — will *never* report a hit. Reset to `true` (the default) to keep model picking working.
- **The result is an array even though you asked about one object.** Recursion can hit many meshes, and one ray can enter and exit a single mesh twice. Always treat the return value as a list (`modelIntersects.length`), never as a single hit.
- **The model isn't there the moment you start.** Loading takes time (model + network). The two interaction bugs this causes:
  - if you animate or raycast the model before it's loaded, you hit `null` (if you used a `null`-initialized variable) — this app avoids that by `await`-ing inside an `async` `init()`: once the code after `await` runs, `duckModel.scene` provably exists, so `tick` never needs a null guard;
  - `await` **blocks** — everything after it (including the first `renderer.render`) is postponed until the model arrives. A big model on a slow network means a black screen meanwhile.
- **The incoming camera node is harmless.** The duck's glTF root contains a `PerspectiveCamera` from the model hierarchy; it has no geometry, so it never shows up in intersections and you don't have to remove it.
- **Keep the model variable in the right scope.** `duckModel` is created inside the `async init()`; `tick` closes over it. That only compiles cleanly because of the `await` guarantee — with `load()` (no await) you'd need `duckModel` outside and a null guard in the loop (see Revisit for the trade-off).
- **Don't forget the old consumers share the same ray.** `setFromCamera` runs once per frame; the model test and the `objectsToTest` test both read that same ray. Changing `mouse` affects both, which is what you want, but it also means the primitives keep reacting while you hover the duck.

## Revisit

- **The `load()` vs `loadAsync()` question you left open in the README.** You noted: with `load()` the model starts `null` and `tick` must handle null until it arrives; with `loadAsync` + `await` you block everything after it, postponing the first render. There's no single right answer — `loadAsync` is fine for exactly this layout *because* the model has nothing to do until init completes, but try rewriting the app with `load()` + a null guard in `tick` and compare: you trade guaranteed-not-null for a non-blocking first render. If you want to guarantee *both*, keep the `await` but consider moving the model load into a separate promise started earlier.
- **Pierce-through test.** Point the ray at the duck's head from above so it goes through the head and out the tail — `modelIntersects` should hold more than one entry for the same mesh. Uncomment the `console.log(raycaster.intersectObject(duckModel.scene))` line and watch for multiply-pierced intersections.
- **Show the ray.** The `@gsimone/three-raycaster-helper` dependency and its import are still commented out. `raycasterHelper.hits = intersections; raycasterHelper.update()` turns the invisible math into an origin→near→far line with hit markers — great for seeing *which* mesh and *how many times* the ray pierces.
- **Animate the scale instead of snapping it.** `gsap` is installed but commented. `scale.setScalar(1.4)` is instant; `gsap.to(duckModel.scene.scale, { x: 1.4, y: 1.4, z: 1.4 })` on enter and a tween back on leave gives the hover a game-feel glide instead of a jump.

## Outdated

approach is valid

> 🚀 This project already runs on the **WebGPU** renderer (`three/webgpu` + `WebGPURenderer` with an `await renderer.init()`), and the raycast-against-loaded-group pattern is renderer-agnostic — it behaves identically on WebGL, so nothing here is tied to a legacy pipeline. One idea to carry forward: the per-frame CPU raycast is trivially cheap for a handful of meshes, but if models grow to thousands of objects, GPU picking (render object IDs to an offscreen target, read one pixel) is the scaling path — and the "test the root group recursively" idea is exactly what that replaces.
