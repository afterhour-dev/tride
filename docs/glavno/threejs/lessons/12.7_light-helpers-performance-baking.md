# 12.7 Light Helpers, Performance, and Baking

After learning individual light types, this lesson covers three practical topics: **visual debugging** with helpers, **performance budgeting** with lights, and **baking** as an alternative to runtime lighting.

The app also serves as a reference tool — every light type has organized GUI controls so you can return to it, toggle lights on/off, tweak parameters, and re-learn what you forgot.

---

## Concept

### Light Helpers

Helpers are wireframe visualizations that make invisible lights visible in the 3D viewport. They are added to the scene just like meshes:

```ts
scene.add(lightHelper);
```

| Light | Helper | What It Shows |
|-------|--------|---------------|
| `AmbientLight` | None needed | Ambient light has no position or shape |
| `HemisphereLight` | `HemisphereLightHelper` | Two half-spheres showing sky/ground colors |
| `DirectionalLight` | `DirectionalLightHelper` | A plane showing the light's position + orientation |
| `DirectionalLight` | `ArrowHelper` (optional) | An arrow pointing in the direction of the light |
| `PointLight` | `PointLightHelper` | A wireframe sphere at the light's position |
| `SpotLight` | `SpotLightHelper` | A cone showing angle, distance, and orientation |
| `RectAreaLight` | `RectAreaLightHelper` | A rectangle showing width, height, and orientation |

Each helper is created with the light instance and optionally a size parameter (except `SpotLightHelper` and `RectAreaLightHelper`, which don't need one):

```ts
const helper = new THREE.HemisphereLightHelper(hemisphereLight, 0.2);
const helper = new THREE.PointLightHelper(pointLight, 0.2);
```

#### RectAreaLightHelper — Separate Import

Unlike other helpers, `RectAreaLightHelper` is **not** available on the base `THREE` namespace. It must be imported from the examples/addons:

```ts
import { RectAreaLightHelper } from 'three/addons/helpers/RectAreaLightHelper.js';
```

This is because `RectAreaLight` is itself a newer, more specialized light type and its helper lives outside Three.js core.

#### SpotLightHelper — Must Update Every Frame

`SpotLightHelper` draws a cone **based on the current state** of the `SpotLight`. If the light moves, or its `angle` / `penumbra` / `target` changes, the helper's cone wireframe becomes stale — it still shows the old state.

Because Three.js has no built-in "helper dirty flag," you must call `spotLightHelper.update()` manually in your animation loop:

```ts
function tick() {
  spotLightHelper.update(); // keeps the wireframe cone in sync
  renderer.render(scene, camera);
}
```

Without this call, the helper will **not** reflect changes to the light's angle, penumbra, or target position.

#### RectAreaLightHelper — Cannot Be Updated

`RectAreaLightHelper` does **not** have an `update()` method. It reads the light's world matrix (position, rotation, scale) every frame, which the renderer already updates. Since a `RectAreaLight` is just a flat rectangle without a complex shape like a cone, there's nothing to recalculate.

Attempting to call `rectAreaLightHelper.update()` will throw an error — the method simply doesn't exist.

#### DirectionalLight + ArrowHelper

The app also adds an `ArrowHelper` to visualize the direction of the `DirectionalLight`:

```ts
const arrowHelper = new THREE.ArrowHelper(
  directionalLight.position.clone().normalize(),
  new THREE.Vector3(0, 0, 0),
  1,
  0xffffff,
);
```

> ⚠️ The arrow direction is computed **once** at creation and never updated. If you move the directional light, the arrow stays where it was. For a dynamic arrow, you'd need to recreate or manually update it each frame.

### Performance and Light Costs

Not all lights are equal. Each light type performs a different amount of calculation per pixel:

| Cost | Light Types | Why |
|------|-------------|-----|
| **Minimal** | `AmbientLight`, `HemisphereLight` | No position/direction calculations — just constant or two-hemisphere color |
| **Moderate** | `DirectionalLight`, `PointLight` | Directional needs dot-product with surface normals; PointLight also computes distance falloff |
| **High** | `SpotLight`, `RectAreaLight` | SpotLight calculates cone angle + penumbra falloff + distance; RectAreaLight computes a full hemisphere integral per pixel |

**How many lights can you have?**

There is no hard limit, but the answer depends on your hardware, resolution, and scene complexity. A mobile GPU might struggle with 4 spot lights. A desktop GPU might handle 16. The key is to profile with your target hardware.

**Best practices:**
- Use as few lights as possible
- Prefer cheaper light types for fill/ambient roles
- Use `AmbientLight` + one `DirectionalLight` for simple scenes rather than many point lights
- Test on the lowest-powered target device early

### Baking

Baking is the technique of pre-computing lighting into textures (usually light maps) inside a 3D application like **Blender**, then loading those textures in Three.js at runtime.

**How it works:**
1. Set up your scene in Blender with all the lights you want
2. "Bake" the light information onto the object's UV textures
3. Export the model with its baked textures
4. Load the model in Three.js without real lights — the lighting is already in the texture

**Pros:**
- Huge performance gain — zero runtime lighting calculations
- Can achieve complex global illumination effects that would be expensive in real-time

**Cons:**
- Lights cannot move — the lighting is "frozen" into the texture
- Requires large texture files
- Objects with baked lighting can't dynamically react to the scene
- Requires knowledge of a 3D application (Blender, Maya, etc.)

### SpotLight Target Mechanics (Extended)

The `SpotLight` has a special `target` property that controls where the cone points. Understanding this is essential for working with spot lights.

**Default behavior:**
```ts
const spotLight = new THREE.SpotLight();
// spotLight.target is an empty Object3D at (0, 0, 0)
// This Object3D is NOT automatically added to the scene
scene.add(spotLight); // but NOT spotLight.target
```

**Making the spotlight point at an object:**
```ts
spotLight.target = sphereMesh; // any Object3D works
// sphereMesh is already in the scene, so the spotlight now targets it
```

**Using an independent target:**
```ts
// Create a target at a specific position
const target = new THREE.Object3D();
target.position.set(2, 0, 0);
spotLight.target = target;
scene.add(target); // REQUIRED — target must be in the scene!
```

**Why the target must be in the scene:** Three.js computes the light's direction by looking at the target's **world position** (its position multiplied through the scene graph hierarchy). If the target isn't in the scene, its `matrixWorld` isn't updated, and the spotlight falls back to the origin.

**The difference between `lookAt` and `target`:**
- `SpotLight.target` — Three.js handles orientation automatically every frame based on the target's world position. Move the target → cone follows.
- `RectAreaLight.lookAt()` — Sets orientation once based on Euler angles. If the target moves, the light does **not** follow — you must call `lookAt()` again every frame in the animation loop.
- `DirectionalLight.target` — Same mechanism as SpotLight. Three.js handles it per frame.

---

### RectAreaLight.lookAt to Follow Objects

From the app's concerns: "In order for `RectAreaLight` to follow some `Object3D`, we need to call `rectAreaLight.lookAt` with that object's position in the animation loop?"

**Yes, that's correct.** `lookAt()` is a one-time rotation. To make it follow a moving object:

```ts
function tick() {
  rectAreaLight.lookAt(sphereMesh.position); // called every frame
  renderer.render(scene, camera);
}
```

This is in contrast to `SpotLight.target`, where reassigning the target object handles following automatically. The app's GUI buttons (`rectLookAtSphere`, `rectLookAtBox`, etc.) demonstrate this — they call `lookAt` once when clicked, but the light won't follow subsequent movement.

### Setting Up All Light Helpers

```ts
import * as THREE from 'three/webgpu';
import { RectAreaLightHelper } from 'three/addons/helpers/RectAreaLightHelper.js';

// Hemisphere
const hemisphereLightHelper = new THREE.HemisphereLightHelper(hemisphereLight, 0.2);
scene.add(hemisphereLightHelper);

// Directional — helper + arrow
const directionalLightHelper = new THREE.DirectionalLightHelper(directionalLight, 0.2);
scene.add(directionalLightHelper);

const arrowHelper = new THREE.ArrowHelper(
  directionalLight.position.clone().normalize(),
  new THREE.Vector3(0, 0, 0),
  1,
  0xffffff,
);
scene.add(arrowHelper);

// Point
const pointLightHelper = new THREE.PointLightHelper(pointLight, 0.2);
scene.add(pointLightHelper);

// Spot — needs .update() every frame
const spotLightHelper = new THREE.SpotLightHelper(spotLight);
scene.add(spotLightHelper);

// RectArea — imported separately, no .update() needed
const rectAreaLightHelper = new RectAreaLightHelper(rectAreaLight);
scene.add(rectAreaLightHelper);
```

### SpotLight Target Swapping (from the app)

```ts
// Button 1: target = sphereMesh
debugObject.makeSphereTarget = () => {
  spotLight.target = sphereMesh;
  // sphereMesh is already in the scene — OK
};

// Button 2: target = an empty Object3D at a specific position
const initialSpotLightTarget = spotLight.target;
debugObject.makeRandomTarget = () => {
  spotLight.target = initialSpotLightTarget;
  scene.add(spotLight.target); // MUST add target to scene
};

// Button 3: reset/remove target
debugObject.removeTarget = () => {
  if (spotLight.target === sphereMesh) {
    spotLight.target = initialSpotLightTarget;
    scene.remove(initialSpotLightTarget);
  }
  if (spotLight.target === initialSpotLightTarget) {
    scene.remove(initialSpotLightTarget);
  }
};
```

When using `WebGPURenderer`, `RectAreaLight` needs LTC (Linearly Transformed Cosines) textures initialized:

```ts
import { RectAreaLightTexturesLib } from 'three/addons/lights/RectAreaLightTexturesLib.js';

const renderer = new THREE.WebGPURenderer({ canvas });
await renderer.init();

// Required for RectAreaLight to work with WebGPU
THREE.RectAreaLightNode.setLTC(RectAreaLightTexturesLib.init());
```

## Gotchas

1. **SpotLightHelper must be updated every frame** — Without `spotLightHelper.update()` in the animation loop, the helper wireframe will not reflect changes to angle, penumbra, or target position. The light itself works fine; only the helper visualization is stale.

2. **RectAreaLightHelper has no `update()` method** — Unlike other helpers, there is no `update()` to call. Attempting `rectAreaLightHelper.update()` throws an error. The helper reads the light's world transform automatically.

3. **RectAreaLightHelper needs a separate import** — Forgetting to import `RectAreaLightHelper` from `three/addons/helpers/RectAreaLightHelper.js` is a common mistake. Other helpers are on `THREE.*` directly.

4. **RectAreaLight with WebGPU requires LTC texture init** — `RectAreaLightTexturesLib.init()` must be called and assigned via `THREE.RectAreaLightNode.setLTC()` before using `RectAreaLight`. Without this, the light may not render correctly.

5. **SpotLight target must be in the scene** — If you set `spotLight.target = myObject` but `myObject` is not in the scene (via `scene.add()`), the spotlight will not point at it correctly. Three.js needs the target in the scene graph to compute its world position.

6. **RectAreaLight.lookAt is one-shot** — Calling `lookAt()` once makes the light point at that position at that moment. If the target moves, the light stays at its initial orientation. Call `lookAt()` every frame to follow movement.

7. **ArrowHelper for DirectionalLight is static** — The app creates an `ArrowHelper` to show light direction, but it captures the direction only at creation time. If you move the light via GUI, the arrow stays put. This is a limitation of the app's approach, not ArrowHelper itself.

8. **GUI folder interactions with helpers** — If a light's `visible` property is set to `false` but the helper's `visible` is `true`, the helper will still show even though the light contributes nothing. This is useful for debugging (you can see where a disabled light is), but can be confusing if you forget the light itself is hidden.

## Revisit

- **Light-per-scene limits** — Profile your own hardware: start adding point or spot lights to a scene and watch the frame rate drop. Finding the limit on your specific hardware is better than trusting a rule of thumb.

- **RectAreaLight.lookAt practice** — Build a small scene where a RectAreaLight follows an animated object. Compare this with the SpotLight `target` approach to solidify the difference.

- **Baking in Blender** — Try the baking workflow end-to-end: light a scene in Blender, bake to textures, export, load in Three.js. Understanding both approaches (real-time vs baked) helps you choose the right one per project.

- **ArrowHelper + DirectionalLight** — Consider improving the app: make the arrow update when the directional light moves, or research alternative directional visualization patterns.
