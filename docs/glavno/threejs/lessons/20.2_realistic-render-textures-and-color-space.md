# 20.2 Realistic Render — Textures & Color Space

## Concept

The previous two lessons made the render realistic through **tone mapping + antialiasing** (`20.0`) and **directional light + shadows** (`20.1`). This lesson adds the next layer of realism: **textures** — a wood floor, a cracked-concrete back wall, both textured with a proper PBR texture set — and **color space**, the thing that makes raw-looking textures suddenly look washed-out *white* if you forget it.

Same scene as before: the Flight Helmet, the Blender-made gaming console (both Draco glTF), the `abandoned_garage` HDR, a directional light with shadows, and a lil-gui panel where essentially everything is tweakable.

### The "3-texture PBR setup" (the real convention)

Textures come from [Poly Haven](https://polyhaven.com/textures). A PBR texture set usually has more files than you need — this lesson deliberately downloads only **three**:

1. **Diffuse / Albedo** — the base color of the surface. This is the only one that is a "color" in the human-eye sense.
2. **Normal (GL)** — surface bump detail, encoded as an RGB normal-direction map.
3. **ARM** (AO + Roughness + Metal packed) — a single texture whose **red** channel holds ambient occlusion, **green** holds roughness, and **blue** holds metalness.

You wire the ARM file up to *three* material slots at once (`aoMap`, `roughnessMap`, `metalnessMap`) — three.js just reads the right channel of the same texture for each:

```ts
floorMaterial.aoMap = woodFloorARMTexture;        // red channel
floorMaterial.roughnessMap = woodFloorARMTexture; // green channel
floorMaterial.metalnessMap = woodFloorARMTexture; // blue channel
```

**Why this trio and not more:**
- **Displacement is skipped** — it either needs real geometry tessellation (subdividing the mesh) or parallax occlusion mapping (a shader trick). Both are expensive; the normal map already fakes enough surface detail for real-time work. Briefly: if you ever *do* want it, it's `displacementMap` + `displacementScale`, and the mesh must have enough subdivision to actually deform.
- **AO isn't loaded separately** — it's already the red channel of ARM.
- **Roughness isn't loaded separately** — green channel of ARM.
- So: **3 texture fetches instead of 6** (diffuse, AO, roughness, metal, normal, displacement), with only a minor loss in surface realism. That's the performance-conscious part of the convention.

**Why `png` for the normal map and `jpg` for the other two:**
The normal map's RGB channels are *data*, not color — tiny per-channel errors from `jpg`'s lossy compression directly corrupt the surface-direction math and you get visible artifacts. `png` is lossless, so the data survives intact. The albedo and ARM texture can tolerate `jpg`'s compression because the eye is far less sensitive to those errors.

**Which normal convention — GL vs DX:** For three.js (and Blender, OpenGL, "Unix-y" tools) pick **Normal (GL)**: its green channel's Y+ points *up*. **Normal (DX)** is vertically flipped (Y+ down) — the default convention in Unity/Unreal/DirectX pipelines. Grab the wrong one and your surface lighting looks inverted/dimpled.

**The multiplier gotcha:** `metalness` / `roughness` *scalars* act as **multipliers** on the map values. When you supply a map, leave them at `1` — otherwise you're scaling down what the texture says.

One open question from the README: **is 1K resolution enough?** For a floor/wall you're usually standing on the other side of, yes — the texel density per screen pixel is loose, and 1K keeps memory small. This is exactly why the lesson uses `_1k` variants.

### Color space — why everything looked "off-white"

After wiring the textures up, the wall and floor looked **flat white**. The cause is **color space**.

A color space is a way of storing colors that accounts for how the human eye perceives brightness. The eye is far more sensitive to differences in *dark* values than in bright ones, so encoding more precision into the dark end and less into the bright end (that's the "gamma" curve, `sRGB`) stores perceptual quality with fewer bits. The difference:

- **sRGB** — the color space of *displayed* content (what your monitor shows, what PNG/JPG files assume by default, what artists paint in).
- **Linear** — the working space of **lighting math**. Renderers compute lighting in linear space because light adds/multiplies linearly; if you did the math on sRGB values, everything would be wrong (too dark, wrong falloff).

So the pipeline is: texture is stored as sRGB → **decoded to linear** when sampled → lighting math happens in linear → tone mapped → **encoded back to sRGB** for the display.

The white-hot-texture bug happens when a texture that is *meant to be seen* (the albedo) is sampled as linear data: it gets gamma-decoded when it shouldn't, blowing the values out toward white.

**The fix — annotate only the "see" textures:**

```ts
woodFloorAlbedoTexture.colorSpace = THREE.SRGBColorSpace;
crackedConcretAlbedoTexture.colorSpace = THREE.SRGBColorSpace;
```

The default is `THREE.NoColorSpace`, which means "treat as linear data." That's correct for textures that are *data*, not color:

- **Normal, ARM (AO/roughness/metal), height** → keep linear (`NoColorSpace`). They encode directions/surfaces, not colors; their values get used in math directly.
- **Albedo/diffuse** → `THREE.SRGBColorSpace` every time. This is the whole point of the app's `// EXPLAIN:` comments.

### Why the models don't need a color-space change

The `FlightHelmet` and the Blender-made gaming console load with correct colors with zero `colorSpace` code. Why?

For the Flight Helmet — **the answer is baked into the file**: glTF stores which textures are sRGB in its JSON, and three.js's `GLTFLoader` reads that and applies `SRGBColorSpace` to albedo maps automatically. (Three.js r152+ also handles the newer `KHR_texture_basisu`/webp paths; for classic glTF the sRGB flag is in the texture's `sampler`/`source` metadata.)

The README's genuine open question: **is the same true for the Blender-made console, where nothing color-space-specific was set in Blender?** Working answer: Blender exports glTF with the standard sRGB flag on base-color textures *by default* — the exporter knows the renderer convention and flags the textures for you. So yes, the loader handles it. Treat it as "the file tells the loader," not "three.js guessed." (The README marked this as a thing to verify — it's on the Revisit list.)

### Loading textures — a parallel setup to models/HDR

Textures load through their own `THREE.LoadingManager` + `THREE.TextureLoader`, mirroring the model and HDR loaders from earlier lessons. A dedicated manager per asset type means the `onProgress` / `onLoad` / `onError` / `onStart` callbacks tell you exactly which *kind* of asset is loading, and each `loadAsync` call awaits its own promise. The floor and wall share texture sets only when the material slots genuinely need the same data — the floor uses the wood set, the wall uses the concrete set.

### The unsolved problem — shadows vanish on the wall with a normal map

⚠️ This is the README's main investigation, and it's **unresolved** — it's the honest study-topic of the lesson, not a solved gotcha.

Symptom: with **no textures** (or no normal map) on the wall, the directional light's shadow renders fine on it. The moment a **normal map** is applied, the shadow on the wall disappears — while the *same* material on the horizontal floor keeps its shadow.

What was tried and did **not** fix it:
- `normalScale = new THREE.Vector2(0.2, 0.2)` on the wall material (incl. `needsUpdate = true`).
- Shadow map resolution back up to 1024×1024.
- Changing the directional light's angle / position.
- `near` / `far` of the shadow camera.
- `shadow.bias` and `shadow.normalBias` tweaks.
- Rotating and moving the whole group (floor + wall + models).

Peculiar observations from the README:
- Moving the light or its target around, the **floor** occasionally gets a sharp illumination where shadows suddenly work, then darkens again and loses them. A "sweet spot" that can't be found for the wall at all.
- Rotating the wall toward horizontal makes the shadow appear — pointing at something about **grazing light + normal-mapped surfaces**, not about light presence.
- The tutorial being followed uses WebGL, not WebGPU — but the environment map difference was judged irrelevant (and it can't cast shadows anyway — env maps light and reflect, they never occlude).

What this smells like (working hypotheses to test, not conclusions):
- **Shadow acne fighting the normal map.** With a normal map, the shadow-comparison happens against perturbed surface normals; `bias`/`normalBias` interact with those per-pixel normals differently per light angle. A grazing light on a normal-mapped vertical surface is the classic worst case.
- **Shadow-map texel resolution vs. wall angle.** The shadow camera frustum is set for the *horizontal* layout (`top/right/bottom/left = ±9`, near 2, far 20); a vertical wall at grazing incidence spans few shadow-map texels — the shadow may be there but sub-pixel and lost in the soft filtering (`PCFSoftShadowMap` with the light 256-wide spread).
- The GUI in the app has a `Textures tweaks` folder whose *only* control removes/adds the wall's normal map — built specifically to confirm the cause-effect live. Flip it yourself and watch the shadow come and go.

## Code

in repo - `apps/20_2_realistic_render_textures_and_color_space`

```ts
import * as THREE from 'three/webgpu';
import { TextureLoader } from 'three';
import { LoadingManager } from 'three';

// a dedicated manager for textures, mirroring the HDR/model managers
const textureLoadingManager = new LoadingManager();
textureLoadingManager.onLoad = () => console.log('texture loaded');
const textureLoader = new TextureLoader(textureLoadingManager);

// load the 3-texture PBR set (albedo jpg, normal png, arm jpg)
const woodFloorAlbedoTexture = await textureLoader.loadAsync(
    '/textures/old_wooden_floor_03_1k/old_wooden_floor_03_diff_1k.jpg',
);
const woodFloorNormalTexture = await textureLoader.loadAsync(
    '/textures/old_wooden_floor_03_1k/old_wooden_floor_03_nor_gl_1k.png',
);
const woodFloorARMTexture = await textureLoader.loadAsync(
    '/textures/old_wooden_floor_03_1k/old_wooden_floor_03_arm_1k.jpg',
);

// COLOR SPACE: the albedo is a "see" texture → mark it sRGB.
// Normals and ARM stay at the default linear (NoColorSpace) — they are data.
woodFloorAlbedoTexture.colorSpace = THREE.SRGBColorSpace;

// build the material — ARM feeds three slots from its three channels
const floorMaterial = new THREE.MeshStandardMaterial();
floorMaterial.map = woodFloorAlbedoTexture;
floorMaterial.normalMap = woodFloorNormalTexture;
floorMaterial.aoMap = woodFloorARMTexture;         // red  channel
floorMaterial.roughnessMap = woodFloorARMTexture;  // green channel
floorMaterial.metalnessMap = woodFloorARMTexture;  // blue channel
// scalar roughness/metalness multiply the map → leave them at 1

const floorMesh = new THREE.Mesh(
    new THREE.PlaneGeometry(8, 8),
    floorMaterial,
);
floorMesh.rotation.x = -Math.PI / 2;
floorMesh.receiveShadow = true;
scene.add(floorMesh);
```

## Gotchas

- **A texture that suddenly looks white/washed-out = the color-space annotation is missing.** Albedo must be `THREE.SRGBColorSpace`, everything else stays linear (`NoColorSpace` is the default — don't "fix" it on normals/ARM by adding sRGB; that double-decodes them and breaks lighting).
- **`metalness`/`roughness` scalars multiply the map.** With a roughness/ARM map supplied, leaving them at `1` preserves the texture's values; lowering them scales the texture down. The `color` property of the material multiplies the albedo the same way.
- **Normal maps must be lossless (`png`), albedo/ARM can be `jpg`.** The normal channel is data; `jpg` artifacts corrupt the direction math. And pick the **GL** variant — DX is vertically flipped and will look inverted on three.js/Blender surfaces.
- **Don't set `colorSpace` on the ARM or normal textures** — "annotate what you see, not what you compute."
- **Only albedo gets sRGB; the environment map is its own case** — the HDR (`abandoned_garage`) is high-dynamic-range linear data (`RGBELoader`/`HDRLoader` territory, `EquirectangularReflectionMapping`), not a `TextureLoader` sRGB texture.
- **Each asset type gets its own `LoadingManager`** — mixing textures and models into one manager makes `onProgress`/`onLoad` ambiguous. The code deliberately keeps HDR, texture, and model managers separate.
- **The wall shadow mystery is unsolved — don't assume your change worked because the README's didn't.** The app's `Textures tweaks` GUI folder (normal map on/off toggle) is the fastest way to reproduce the bug yourself and test hypotheses against it.

## Revisit

- **The wall + normal map shadow bug.** Everything has been tried except a systematic one-variable-at-a-time pass with the GUI: try `shadow.camera` frustum *tighter* around the wall (it's currently sized for the floor layout), try `PCFShadowMap` (non-soft) to see if `PCFSoftShadowMap`'s filtering is hiding a sub-pixel shadow, try a `PointLight` instead of the directional, try a *rotated* wall to confirm the grazing-angle hypothesis. Then bake whatever works.
- **Is 1K resolution enough / when to go 2K/4K?** Learn the rule of thumb: texel density vs. distance from camera and screen size. Poly Haven lets you re-download at higher res cheaply — swap and compare memory vs. close-up quality.
- **The Blender color-space question.** Verify with a test: export the console from Blender with `Color Space: sRGB` explicitly set *and* with defaults, and confirm the glTF JSON carries the flag either way (look for `colorSpace` hints in the gltf/glb). The claim "Blender sets it by default" deserves a first-hand check.
- **Displacement, if you ever want it** — `displacementMap` + `displacementScale`, but only with subdivided geometry. The README deliberately skips it (cost); revisiting it for a hero close-up shot is the way to learn why.
- **Why `scene.environmentIntensity = 1.2`** (this app) vs `1.6` in `20.1` and the defaults — environment intensity interacts with how strongly albedo textures read. Worth a session flipping both against each texture set.

## Outdated

approach is valid

> 💡 **This is a WebGPU lesson, and there is no reason to do it on WebGL.** The renderer is `THREE.WebGPURenderer` from `three/webgpu`; texture loading (`TextureLoader`), color space (`colorSpace`), and material map slots (`map`, `normalMap`, `aoMap`, `roughnessMap`, `metalnessMap`) are API-identical on the classic `WebGLRenderer`. The color-space rules (sRGB for albedo, linear for data maps) are a universal PBR pipeline fact — they apply to WebGL, WebGPU, and any renderer. If you follow a WebGL tutorial for this, only the renderer import line differs.
