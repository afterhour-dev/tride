# Exporting a model from Blender and loading it in Three.js

## Concept

This lesson covers the full asset pipeline for getting a model you built in **Blender** into a Three.js app: exporting it as **glTF 2.0** with the right settings, then loading it in Three.js WebGPU with the **GLTFLoader** (+ **DRACOLoader** when DRACO compression is enabled). The goal: the rendered result should look as close as possible to what you built and lit in Blender.

### The export matters more than you think

When you export from Blender you're not just dumping geometry into a file — you're choosing how that geometry, its materials, textures, vertex colors and transforms get **baked** into a format a web engine understands. Get the settings wrong and you get weird results you'll then try to "fix" in code: double-sided faces, wrong orientation, missing textures, or dark/backwards lighting.

### Blender version note

The user worked in **Blender 5.2** while following tutorials written for older Blender versions. The glTF 2.0 exporter panel looks similar across versions but settings move and rename: always check the current panel against tutorials, and verify what each checkbox does on **your** version rather than trusting a screenshot. See `## Revisit` for version resources.

### Export settings checklist (glTF 2.0, File → Export → glTF 2.0)

Walk through the panel section by section with the settings that worked here:

- **Save location & format**: pick the **`glTF Separate`** format (`.gltf` + `.bin` + textures) when your model has textures. Set the textures folder — the README chose `textures` relative to the model, so textures land next to the model in `public/models/1_game_console/textures/`. Saved to `apps/18_0_blender_exporting_model/public/models/1_game_console/console-for-export.gltf`.

- **`Include`**: check **Limit to: Selected Objects** — only objects you selected get exported. Selection matters: select all meshes (e.g. everything in your game-running Collection); a parent/empty won't pull in children automatically.

- **`Transform`**: check **`+Y Up`** — glTF is Y-up, matching Three.js/WebGPU; Blender is Z-up, so this bakes the axis conversion in at export time.

- **`Geometry (Data → Mesh)`**: keep **Apply Modifiers** checked (bakes modifiers into the mesh), and keep **UVs** and **Normals** checked. UVs are needed because the model has textures; Normals are needed because lighting won't look right without them. (Left unchecked: Tangents, Attributes, Loose Edges, Loose Points, Shared Accessors — fine for this use case unless a model needs them.)

- **`Vertex Colors`**: `Use Vertex Color` = **Material value**. The README left **Export All Vertex Colors** and **Export Active Vertex Color When No Material** checked — that's okay; the material value is what drives the look, the extra checkboxes mostly matter for models that paint per-vertex.

- **`Material (Data → Material)`**: defaults are fine — Materials → Export (dropdown), Images → Automatic format (jpeg/WebP only matter if you want to force a compressed texture), Image quality 75 default, **Unused textures & images** unchecked.

- **`Shape keys`**: unchecked — they're only relevant if your model has animations/pose keys. Not a mistake to leave unchecked for a static model.

- **`Armature` / `Skinning`**: Skinning unchecked (its options gray out when checked), Armature left at default. Both relate to **bones/rigging**, which the model doesn't have — safe to leave as-is for a non-rigged model.

- **`Lighting` → Lighting Mode**: **Standard**. The model doesn't need lights baked from Blender — lights come from Three.js at runtime (ambient + directional in this app). Other values are `Unitless` and `Raw (Deprecated)`.

- **`DRACO compression`**: checked — see `## Gotchas` below for the loader implication.

- **`Animation`**: left unchecked — the Blender model plays video via an **emission material**, which is a Blender-specific render trick that doesn't carry into Three.js; baking it as animation wouldn't help. See `## Revisit`.

### Backface culling (the double-face problem)

When the model appeared with **double faces** in the renderer, the fix was on the **material side, not the export side** — the default material in Blender was rendering both faces of each surface. In Blender: **Material Properties → Settings → Surface → Backface Culling → Camera**. This culls the backface when the surface is seen from the camera, solving the double-face appearance.

The README also checked **Shadow** and **Light Probe Volume** there — those affect how the material interacts with shadow and light-probe helpers, not the backface problem, and are fine to have on.

In the app, the double-face check is manual: traverse the scene graph after load and log `material.side` (2 = `THREE.DoubleSide`) to verify faces are single-sided after the fix — `gamingConsoleModel.scene.traverse(...)` in `### Code` below.

### Loading the model in Three.js WebGPU

The app uses the **WebGPU renderer** and the loader trio:

- `GLTFLoader` — loads `.gltf` (JSON) and referenced `.bin`/textures via a `LoadingManager`.
- `DRACOLoader` — needed **if and only if** the export used DRACO compression; it decodes `.gltf`/`.glb` byte streams. Wired with `setDecoderPath('/draco/')` pointing at the DRACO decoder files, then `gltfLoader.setDRACOLoader(dracoLoader)`.

The whole flow is: create a `LoadingManager` for models, create the GLTFLoader (with its own LoadingManager), `loadAsync('/models/1_game_console/console-for-export.gltf')`, then **`scene.add(gamingConsoleModel.scene)`**. The model scene is scaled up `20×` to match the scene's unit scale.

Model-mesh properties (e.g. `isMesh`, `material.side`) live on the loaded scene's child objects; use `gamingConsoleModel.scene.traverse(...)` to reach every child — useful for both inspection and per-mesh setup like enabling `castShadow = true` on each mesh.

The scene also wires up environment maps (cube textures, `scene.environment`), ambient + directional light (with shadows via `renderer.shadowMap`), a floor mesh, perspective camera with OrbitControls, and lil-gui tweaks for lighting/shadow values.

## Code

in repo - `apps/18_0_blender_exporting_model`

```ts
// Loading a Blender-exported glTF (with DRACO) in Three.js WebGPU
import * as THREE from 'three/webgpu';
import { GLTFLoader } from 'three/addons/loaders/GLTFLoader.js';
import { DRACOLoader } from 'three/addons/loaders/DRACOLoader.js';

// enable DRACO decode and point the DRACO loader at the decoder files
const dracoLoader = new DRACOLoader();
dracoLoader.setDecoderPath('/draco/');

// GLTFLoader resolves resources (textures, bin) through a LoadingManager
const modelLoadingManager = new THREE.LoadingManager();
const gltfLoader = new GLTFLoader(modelLoadingManager);
gltfLoader.setDRACOLoader(dracoLoader);

// load the exported model
const gamingConsoleModel = await gltfLoader.loadAsync(
	'/models/1_game_console/console-for-export.gltf',
);

scene.add(gamingConsoleModel.scene);
gamingConsoleModel.scene.scale.setScalar(20);

// verify the export didn't bring back doubled faces
gamingConsoleModel.scene.traverse((child) => {
	// @ts-expect-error isMesh is a property of Object3D, but TypeScript doesn't know that child is a Mesh
	if (child.isMesh) {
		// @ts-expect-error material is a property of Mesh
		console.log(child.material.side); // 2 = THREE.DoubleSide
		child.castShadow = true; // enable shadows on each mesh
	}
});
```

## Gotchas

- **DRACO-compressed file + plain gltf loader = error.** If you check DRACO compression in the exporter, the file is DRACO-decoded only if a DRACOLoader (with `setDecoderPath` to the decoder files) is registered on the GLTFLoader. Loading a DRACO file with only the gltf loader won't work. The decoder files live under `public/draco/`.
- **Selecting the "parent" does not select children.** You must select all the meshes (e.g. the whole collection) before `Limit to Selected Objects` — otherwise parts won't be exported.
- **`+Y Up` is a transform to remember.** glTF is Y-up; forgetting to check it bakes the model in Blender's Z-up and the model lands rotated in the renderer.
- **Double faces come from the material, not the geometry.** Fix on the Blender material (Settings → Surface → Backface Culling → Camera), then verify via `material.side` after loading — don't fight it in code.
- **UVs / Normals unchecked makes textures and lighting break.** Texture needs UVs; lighting needs Normals. Keep both checked on the exporter.
- **Blender's own lights don't carry over.** Choose `Lighting Mode: Standard` and rely on Three.js lights; baked Blender lights won't help in the app.
- **Emission-material videos don't survive export.** The model's Blender emission-material playback is not a glTF/Three.js feature; leave Animation unchecked and don't expect the video in the app (see Revisit).
- **Vertex-color checkboxes don't break the look.** `Use Vertex Color: Material value` is the important pick; leaving all vertex-color exports checked won't visibly change a material-driven model.

## Revisit

- **Verify version drift.** The exporter panel was driven against older-Blender tutorials. Recheck each setting against Blender 5.2's actual panel and the current exporter docs. 🤖 suggested: [Blender glTF 2.0 exporter docs](https://docs.blender.org/manual/en/latest/addons/import_export/scene_gltf2.html)
- **Texture format choice.** This used `Automatic` image format at quality 75; revisit whether jpeg or WebP with a tuned quality gives noticeably smaller/sharper textures for this model.
- **Backface culling extras.** Shadow and Light Probe Volume were checked alongside Camera — the README asked whether that was a mistake. Verify they don't change shadows on this model and reduce to what's needed. See `## Gotchas`.
- **DRACO value at this scale.** DRACO was enabled here; at one small model the size win may not matter — revisit whether to keep it or export uncompressed gltf for easier debugging.
- **Unused textures & images settings.** Left unchecked (default); if the Blender file accumulates unused materials, revisit whether to tick it.
