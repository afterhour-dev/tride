## Concept

Three.js ships a set of **built-in controls** (`three/examples/jsm/controls/`) that handle common camera interaction patterns — orbiting, panning, flying, dragging objects. These are pre-built solutions you import and configure, not write from scratch. The alternative is **custom controls**: handling mouse/keyboard events yourself and manually updating camera position (like the manual circular motion in the previous lessons).

Built-in controls are almost always the right choice unless you need something very specific. They handle edge cases, cross-browser quirks, and accessibility out of the box.

### OrbitControls — the most common camera control

`OrbitControls` lets the user rotate (orbit) the camera around a target point, zoom in/out, and pan. It's the default control for product viewers, 3D editors, and any scene where you want to explore freely.

**Import and setup:**

```ts
import { OrbitControls } from 'three/examples/jsm/Addons.js';

const orbitControls = new OrbitControls(camera, canvas);
```

Two arguments: the `camera` to control, and the `canvas` (DOM element) that captures the mouse/touch events. Without the canvas, the controls wouldn't know where to listen for input.

**Why you don't add OrbitControls to the scene:**

`OrbitControls` is not a `THREE.Object3D` — it doesn't have position, rotation, or a renderable representation. It's an event handler that modifies the camera's properties directly. You never call `scene.add(orbitControls)`. It just needs the camera and the canvas, and it does its work by listening to DOM events and updating `camera.position`, `camera.rotation`, and `camera.zoom`.

**The `target` property:**

By default, `orbitControls.target` is `(0, 0, 0)` — the world origin. This is the point the camera orbits around. If your scene's subject is offset from the origin, you set the target to match:

```ts
orbitControls.target.set(mesh.position.x, mesh.position.y, mesh.position.z);
```

Without this, the camera would orbit around the origin while the mesh sits off to the side, which feels wrong.

**Damping (inertia):**

```ts
orbitControls.enableDamping = true;
```

When damping is enabled, the camera doesn't stop instantly when the user releases the mouse — it decelerates smoothly, like it has momentum. This makes the interaction feel much more natural and physical.

When you enable damping, you **must** call `orbitControls.update()` every frame in the animation loop. Damping works by interpolating toward the target each tick, so without continuous updates it won't do anything.

```ts
function tick(timestamp: number) {
  orbitControls.update(); // needed for damping to work
  renderer.render(scene, camera);
  requestAnimationFrame(tick);
}
```

> **Should you call `update()` in setup too?** Not unless you change the target or other properties immediately after creating the controls. The first `update()` call in the animation loop will pick up any initial state. If you set `orbitControls.target.y = 1.5` in setup and want it reflected before the first frame, then yes — call `update()` once right after.

**When to call `update()` after property changes:**

If you change `orbitControls.target` or any other property at runtime (not in the animation loop), call `update()` once after the change to apply it immediately. Inside the animation loop, the single `update()` at the top of each frame handles everything.

### Other commonly used OrbitControls properties

| Property | What it does | Default |
|---|---|---|
| `enableDamping` | Smooth inertia after release | `false` |
| `dampingFactor` | How quickly it decelerates (0–1) | `0.05` |
| `enableZoom` | Allow scroll-wheel zoom | `true` |
| `enablePan` | Allow right-click / two-finger pan | `true` |
| `minDistance` / `maxDistance` | Clamp zoom range | `0` / `Infinity` |
| `minPolarAngle` / `maxPolarAngle` | Clamp vertical rotation (0 = top, π = bottom) | `0` / `π` |
| `autoRotate` | Slowly spin the camera when idle | `false` |
| `autoRotateSpeed` | Speed of auto-rotation | `2.0` |

```ts
// to temporarry disable them
orbitControls.enabled = false
```

### Brief overview of other built-in controls

Three.js has several other controls in `three/examples/jsm/controls/`. They'll get their own lesson, but it's worth knowing they exist:

- **TransformControls** — lets the user move/rotate/scale objects directly in the scene (like a 3D editor gizmo). This is an **object control**, not a camera control.
- **DragControls** — drag-and-drop objects on a plane. Also an object control.
- **FlyControls** — fly the camera freely (WASD + mouse look), like a first-person game.
- **PointerLockControls** — locks the mouse pointer for FPS-style camera look. Good for games.
- **TrackballControls** — like OrbitControls but allows rolling (rotating around the view axis), which OrbitControls doesn't.
- **FirstPersonControls** — another FPS-style option, older API.

The distinction: **camera controls** change how you look at the scene; **object controls** change how you interact with objects inside it.

## Code

in repo - `apps/4_camera_controls`

```ts
import * as THREE from 'three/webgpu';
import { OrbitControls } from 'three/examples/jsm/Addons.js';

const canvas = document.querySelector<HTMLCanvasElement>('canvas#tride')!;
const sizes = { width: 800, height: 600 };

async function init() {
  const scene = new THREE.Scene();

  const mesh = new THREE.Mesh(
    new THREE.BoxGeometry(0.5, 0.5, 0.5),
    new THREE.MeshBasicMaterial({ color: 0x4c9892 })
  );
  mesh.position.set(-0.5, 0, 0.5);
  scene.add(mesh);

  const camera = new THREE.PerspectiveCamera(75, sizes.width / sizes.height, 0.1, 100);
  camera.position.set(1, 0, 3);
  scene.add(camera);

  // OrbitControls — takes camera + canvas, NOT added to scene
  const orbitControls = new OrbitControls(camera, canvas);
  orbitControls.enableDamping = true;

  const renderer = new THREE.WebGPURenderer({ canvas });
  await renderer.init();
  renderer.setSize(sizes.width, sizes.height);
  renderer.setClearColor(0x000000, 1);

  const axesHelper = new THREE.AxesHelper(5);
  axesHelper.setColors('red', 'green', 'blue');
  scene.add(axesHelper);

  const timer = new THREE.Timer();
  requestAnimationFrame(tick);

  function tick(timestamp: number) {
    timer.update(timestamp);

    // Must call update every frame for damping to work
    orbitControls.update();

    renderer.render(scene, camera);
    requestAnimationFrame(tick);
  }
}

await init();
```

## Gotchas

- **OrbitControls is not a scene object.** You never `scene.add(orbitControls)`. It's a utility class that modifies the camera directly. Trying to add it to the scene won't cause a crash but it also won't do anything useful.

- **Forgetting `update()` when damping is on.** If `enableDamping = true` but you don't call `update()` in the animation loop, the damping does nothing — the camera moves instantly and stops instantly. The update call is what drives the interpolation.

- **Calling `update()` too often in setup.** Not harmful, just unnecessary. The only time you need an explicit `update()` outside the animation loop is if you change `target` or other properties right after creation and want them applied before the first frame.

- **Wrong canvas reference.** `OrbitControls` needs the DOM element it should listen on. If you pass the wrong element (or `document`), mouse events won't map correctly to the 3D viewport — scrolling might zoom the page instead of the scene, or coordinates might be off.

- **`minPolarAngle` and `maxPolarAngle` use radians.** Common mistake: passing degrees (like `90` instead of `Math.PI / 2`). If the camera stops rotating unexpectedly at a weird angle, check your angle values.

## Revisit

- Try setting `orbitControls.autoRotate = true` and `orbitControls.autoRotateSpeed = 4` to see the auto-rotation feature — useful for product showcases.

- Experiment with `minDistance`, `maxDistance`, `minPolarAngle`, and `maxPolarAngle` to clamp the camera to a specific viewing region. This is common in games and product viewers.

- Look into `TrackballControls` as an alternative when you need camera roll (rotating around the Z axis). It behaves differently from OrbitControls in subtle ways.

- Revisit the manual circular motion from lesson 4.5 — understanding how `sin`/`cos` drive the orbit manually makes what OrbitControls does internally much clearer.
