## Concept

**JUST KNOW THAT Clock is deprecated but you should know about it**

This lesson builds on the primitive animation loop from lesson 3.1 and introduces `THREE.Clock` — Three.js's built-in timer class that replaces manual `Date.now()` tracking. The app creates a wireframe box that rotates and moves in a circular path using `sin`/`cos`, while the camera orbits around it — all driven by `Clock.getElapsedTime()`.

### `THREE.Clock` — why use it instead of `Date.now()`?

In lesson 3.1, we tracked time manually with `Date.now()`. `THREE.Clock` wraps `performance.now()` and handles edge cases automatically:

- **Tab backgrounding** — `Date.now()` keeps ticking when the tab is hidden, causing animation to jump when you return. `Clock` pauses when the tab is inactive (using `requestAnimationFrame` internally).
- **Precision** — `performance.now()` has sub-millisecond precision, while `Date.now()` only gives whole milliseconds.
- **Pausing** — `Clock` can be paused and resumed with `clock.pause()` / `clock.start()`.

**Is `THREE.Clock` deprecated?** The code's `// EXPLAIN:` comment raises this. In TypeScript types, `Clock` is not deprecated — it's a core utility. The Three.js docs still list it as the recommended way to track elapsed time for animations. What *is* deprecated is the older `THREE.AnimationMixer` patterns that use `Clock` differently (e.g., `mixer.update(deltaTime)` with `Clock.getDelta()`). For basic frame-by-frame animation, `Clock` is perfectly fine and current.

### `clock.elapsedTime` vs `clock.getElapsedTime()`

Two ways to read elapsed time, but they're different:

| | `clock.elapsedTime` | `clock.getElapsedTime()` |
|---|---|---|
| **Type** | Property (getter) | Method (function call) |
| **Behavior** | Returns the raw elapsed time since the clock started | Also returns elapsed time, but also **updates the internal state** (calls `getDelta()` internally) |
| **When to use** | When you only need to read it once per frame and don't need delta | When you want both elapsed time and delta in one call |

In practice, both work for simple animations. The difference matters when you also need `getDelta()` for framerate-independent movement — calling `getElapsedTime()` implicitly updates the delta, so you can't call both without getting stale values.

### Trigonometry for circular motion

The app uses `sin` and `cos` to make objects move in circular paths:

```ts
mesh.position.y = Math.sin(elapsedTime);      // up-down oscillation
camera.position.x = Math.cos(elapsedTime);     // left-right oscillation
```

**Why this works:** `Math.sin(t)` and `Math.cos(t)` output values between -1 and 1, repeating every `2π` (about 6.28) seconds. By mapping them to position, the object traces a circle (or an ellipse, depending on the radius).

- `sin(t)` — smooth oscillation, starts at 0, goes to 1, back to 0, then -1
- `cos(t)` — same oscillation but shifted by 90° (π/2) — starts at 1

When you combine them for the same object, you get circular motion. When you use them on different axes (here: mesh Y + camera X), the camera orbits the object while the object also moves up and down.

**Visualization helpers:** The code comments ask for helpers to learn these functions. Good tools for this:
- [Desmos](https://www.desmos.com/calculator) — plot `sin(x)` and `cos(x)` interactively
- [GeoGebra](https://www.geogebra.org/graphing) — visualize the unit circle and how sin/cos relate to it

The rotation multiplier `Math.PI * 0.2` means the object rotates at 0.2π radians per second — roughly 36° per second. Without it, `elapsedTime` alone would rotate at 1 radian per second (~57.3°/s).

### `tick()` vs `window.requestAnimationFrame(tick)` for first invocation

The code asks: should the first call be `tick()` or `window.requestAnimationFrame(tick)`?

- **`tick()`** — calls immediately. The first frame renders right away, with `elapsedTime` starting at 0. This is fine for most cases and is the common pattern.
- **`window.requestAnimationFrame(tick)`** — schedules `tick()` for the next animation frame. The first frame is delayed by ~16ms (one frame). This is slightly more "correct" because it avoids a synchronous block, but the difference is negligible for simple demos.

The code uses `tick()` directly (calling it immediately), which is the standard Three.js pattern.

### `camera.lookAt()` with moving targets

`camera.lookAt(mesh.position)` is called every frame to point the camera at the mesh. This creates an orbit-like camera movement: the camera's X position oscillates with `cos`, while the mesh's Y position oscillates with `sin`, and the camera always faces the mesh.

The camera itself doesn't move in a circle — it only moves left/right (X axis). But because the mesh moves up/down and the camera faces it, the perspective changes as if the camera were orbiting.

## Code

in repo - `apps/3_animation_clock`

```ts
import * as THREE from 'three/webgpu';

const canvas = document.querySelector<HTMLCanvasElement>('canvas#tride');
const sizes = { width: 800, height: 600 };

async function init() {
  const scene = new THREE.Scene();

  const boxGeometry = new THREE.BoxGeometry(0.5, 0.5, 0.5);
  const material = new THREE.MeshBasicMaterial({ color: 0x4c9892, wireframe: true });
  const mesh = new THREE.Mesh(boxGeometry, material);
  mesh.position.x = -0.5;
  mesh.position.z = 0.5;
  scene.add(mesh);

  const camera = new THREE.PerspectiveCamera(75, sizes.width / sizes.height);
  camera.position.z = 3;
  camera.position.y = 0.5;
  camera.position.x = 0.1;
  scene.add(camera);

  const renderer = new THREE.WebGPURenderer({ canvas });
  await renderer.init();
  renderer.setSize(sizes.width, sizes.height);
  renderer.setClearColor(0x000000, 1);
  renderer.render(scene, camera);

  const clock = new THREE.Clock();

  function tick() {
    const elapsedTime = clock.getElapsedTime();

    mesh.rotation.y = elapsedTime * Math.PI * 0.2;
    camera.position.x = Math.cos(elapsedTime);
    mesh.position.y = Math.sin(elapsedTime);

    camera.lookAt(mesh.position);
    renderer.render(scene, camera);
    window.requestAnimationFrame(tick);
  }

  tick();
}

await init();
```

## Gotchas

- **`WebGPURenderer` clear color doesn't default to black in WebGL2 fallback** — when WebGPU isn't available, the renderer falls back to WebGL2, but the clear color may not be opaque black by default. Always call `renderer.setClearColor(0x000000, 1)` explicitly.
- **WebGPU requires a secure context** — `navigator.gpu` returns `null` on `http://` (non-localhost) or plain LAN IPs like `192.168.x.x`. Only `localhost` or `https://` work. If you get "No available adapters," check this first.
- **Chrome on Linux needs flags for WebGPU** — Chrome ships a hardware/driver blocklist for WebGPU on Linux. Set `chrome://flags` → **Force enable WebGPU interop: Enabled** and **Unsafe WebGPU Support: Enabled**, then relaunch. See `Webgpu dev setup.md` in the app for full details.
- **`tick()` as first call vs `requestAnimationFrame`** — both work. `tick()` runs the first frame immediately; `requestAnimationFrame` delays one frame. For simple demos, this difference is negligible. See the Concept section for more.
- **`clock.elapsedTime` vs `clock.getElapsedTime()`** — the property returns raw elapsed time; the method also updates internal state. For most simple animations, both work, but be aware they're not identical in all cases.

## Revisit

- **`THREE.Clock` vs manual timing** — compare this lesson's `Clock` approach with lesson 3.1's `Date.now()` approach. Notice how `Clock` simplifies the animation loop.
- **Sin/cos visualization** — use [Desmos](https://www.desmos.com/calculator) to plot `sin(x)` and `cos(x)` and see how they relate to circular motion. Understanding the unit circle makes these functions intuitive.
- **WebGPU vs WebGL fallback** — test the app with WebGPU flags on vs off to see the fallback behavior. This is important for real users on unflagged browsers.
- **Easing and animation curves** — the rotation uses `elapsedTime * Math.PI * 0.2` for linear speed. Try adding easing functions (ease-in, ease-out) or `THREE.MathUtils.smoothstep()` for more natural motion.

> 💡 More up to date alternative: Use `THREE.Clock` instead of `Date.now()` for all animation loops — it handles tab backgrounding, precision, and pausing automatically.
