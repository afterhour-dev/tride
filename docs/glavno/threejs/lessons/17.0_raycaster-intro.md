## Concept

The **Raycaster** is the workhorse of "picking" in Three.js — asking *"what object is under the mouse?"*, *"is there a wall in front of the player?"*, *"is the spaceship heading towards a planet?"*. You cast a ray from a point into the scene and the raycaster hands you back every geometry it passes through, sorted closest-first, with useful metadata per hit.

The scene in this app is deliberately minimal: three spheres sitting at `x = -2`, `0`, `2` (all with the same geometry and material), and a ray shot from `x = -3` straight along the `+x` axis, which threads through all three spheres in order.

### A ray is `origin + normalized direction`

The mental model from the README is almost right, so let's make it exact. The ray is the set of points:

$$P(t) = \text{origin} + t \cdot \text{direction}, \quad t \ge 0$$

- **`origin`** (a `Vector3`) is where the ray *starts* — the dot at the base.
- **`direction`** (a `Vector3`) is *which way* it points. `P(t)` up to scale — dragging `origin` along the direction line doesn't change what the ray is.

Your guess — *"direction is just a line telling the ray which way to emit"* — is correct. The ray does **not** connect the scene center to the direction vector; the direction vector hangs *off the origin*.

What normalization does is fix the **length** of that direction vector, not its pointing. `direction.normalize()` scales the vector down (or up) until its length is exactly `1`, keeping the direction identical. In the code:

```ts
const rayDirection = new THREE.Vector3(10, 0, 0);
console.log(rayDirection.length()); // 10
rayDirection.normalize();
console.log(rayDirection.length()); // 1
```

Why is the length so important? Because the math in the parametrized form above only gives you **distances in world units when the direction is unit-length**. With `(10, 0, 0)`, the parameter `t` would advance 10 units per step — a point "1 unit" along the ray would actually be 10 world units away. Raycasters ask "how far along the ray does the intersection happen", and they report that as `distance` directly from `t`. Normalize the direction and `t` *is* the distance. Non-normalized directions give wrong (scaled) `distance` and `point` results. This is documented: *"direction — The direction that the ray should take. This must be normalized."*

### Creating and setting the ray

The `Raycaster` constructor itself accepts `(origin, direction, near, far)` — but a cleaner, README-friendly pattern is to construct one and set it later:

```ts
const raycaster = new THREE.Raycaster();          // origin (0,0,0), direction (0,0,-1) by default
raycaster.set(rayOrigin, rayDirection, near?, far?); // near/far are optional distance filters
```

`near` / `far` limit the ray to a distance range — handy when you only care about hits within a few units. With the origin at `(-3, 0, 0)` and direction `(1, 0, 0)`, the ray slices the sphere row from left to right:

- sphere at `x = -2`: hit at its left rim, `distance ≈ 0.5`
- sphere at `x = 0` (center): `distance ≈ 2.5`
- sphere at `x = 2`: `distance ≈ 4.5`

(the exact distances come from the updated world matrices — see Gotchas).

### Casting the ray — one object or many

Two methods, the naming is exactly what you'd hope:

```ts
const singleIntersect = raycaster.intersectObject(sphereMesh3);           // test ONE object
const allIntersects   = raycaster.intersectObjects([mesh1, mesh2, mesh3]); // test a whole array
```

`intersectObjects` takes a flat array of meshes, but by default it recurses into each object's children (`recursive: true`), so passing a `group` catches everything under it. Both return a plain **array** of `Intersection` objects.

### The result — always an array, sorted by distance

Even `intersectObject` returns an array, and it can contain **more than one entry for the same object**. Why? A ray can legally cut through one object multiple times — the README has the perfect example: a **torus**. The ray enters the side of the donut, exits, dips through the hole, re-enters the other side and exits again. Each entry point is its own intersection. The rays in the app hit spheres, which a ray crosses at most twice (front surface, back surface) — only the nearest of those is usually what you want, and Three.js returns them sorted by ascending `distance`, so `intersects[0]` is the closest hit.

Each `Intersection` in the array carries:

- **`distance`** — how far the hit was from the ray origin
- **`point`** — the exact world `Vector3` of the collision
- **`object`** — which mesh was hit
- **`face`** — the triangle (face) of the geometry that was struck
- **`faceIndex`** — index of that face
- **`uv`** — the UV coordinates at the hit point on the geometry (useful to read a texture value there)

The README wondered, rightly, how often `face`/`faceIndex` are used — honestly not that much in picking. `face` becomes relevant for things like *snapping* to a surface or correct *triangle-level* selection in a modeling tool; `uv` is the star for things like placing a decal at the impact point. For "was I clicked / am I under the cursor" use cases, `distance`, `point` and `object` are the ones you'll actually read.

## Code

in repo — `apps/17_0_raycaster`

```ts
const scene = new THREE.Scene();

// Three spheres along the X axis
const sphereGeometry = new THREE.SphereGeometry(0.5, 16, 16);
const sphereMaterial = new THREE.MeshStandardMaterial({ color: '#e6cbe8' });

const sphere1 = new THREE.Mesh(sphereGeometry, sphereMaterial);
const sphere2 = new THREE.Mesh(sphereGeometry, sphereMaterial);
const sphere3 = new THREE.Mesh(sphereGeometry, sphereMaterial);
sphere1.position.x = -2;
sphere3.position.x = 2;
scene.add(sphere1, sphere2, sphere3);

// IMPORTANT: no frame has been rendered yet, so world matrices are stale — see Gotchas
scene.updateMatrixWorld(true);

// Ray from (-3, 0, 0) along +X
const raycaster = new THREE.Raycaster();
const origin = new THREE.Vector3(-3, 0, 0);
const direction = new THREE.Vector3(10, 0, 0).normalize(); // must be unit length!
raycaster.set(origin, direction);

const single = raycaster.intersectObject(sphere1);          // [{}] — one object, nearest hit
const all    = raycaster.intersectObjects([sphere1, sphere2, sphere3]);
// all[0].distance ≈ 0.5, all[1] ≈ 2.5, all[2] ≈ 4.5 — sorted nearest-first
```

## Gotchas

- **Direction must be normalized.** Forgetting `.normalize()` silently corrupts every `distance`/`point`. The raycaster interprets `t` as if the direction were length 1; a `(10, 0, 0)` ray reports distances 10× too large. The code comment calls it out explicitly: *"also you need to normalize direction"*.
- **Stale world matrices → identical distances for everything.** This is the app's own debugging story (see the code comments): before any frame renders, meshes that had `.position` set on the scene graph never pushed it into their `matrixWorld`. `Raycaster` raycasts in **world space**, so a sphere *destined* for `x = 2` was evaluated at `x = 0` — every hit reported `distance ≈ 2.5`, as if all three spheres sat at the center. Calling `scene.updateMatrixWorld(true)` before the intersection flushes the matrices (`true` = force update down the tree), and the distances become the correct `0.5 / 2.5 / 4.5`.
- **Same object can appear multiple times in the result.** The array is per-*entry point*, not per-object. A ray through a torus can hit the same mesh 4 times. Don't assume `intersects[0]` is "the object under the mouse" if your object is concave — check the `object` field on each entry when it matters.
- **`face`/`faceIndex` are triangle-level detail.** Easy to confuse with picking; they're rarely the route to "which mesh was hit".
- **`intersectObjects` recurses into children by default.** Pass a `false` second argument (`raycaster.intersectObjects(objs, false)`) if you want top-level-only hits — the app's flat mesh array makes the flag irrelevant.

## Revisit

- **Mouse picking** — the real-world use is `raycaster.setFromCamera(pointerNDC, camera)` with a normalized `pointer` (from the mouse), cast each frame or on click. The ray here is hardcoded; wiring it to the pointer is the natural next step.
- **`far` / `near` filtering** — the constructor and `.set()` accept them, this app never uses them. A "only hits within 3 units count" budget is a clean exercise.
- **`uv` in practice** — read the texture color at the impact point (e.g. probe a `CanvasTexture` or `DataTexture` at `intersection.uv`) — genuinely useful for terrain painting and decals.
- **Concave picks** — revisit the torus case: how do you pick the *entry* hit vs a ray that grazes the hole? When would you want to `filter` out back faces?

## Outdated

approach is valid

> 🚀 This project already runs on the **WebGPU** renderer (`three/webgpu` + `WebGPURenderer`). The `Raycaster` itself is renderer-agnostic — it does CPU-side math against object geometries — so it works identically on WebGL and WebGPU; picking is unchanged. If you ever need *GPU*-side picking (faster for a scene with thousands of objects), the WebGPU path offers async render-target pixel reads (`readRenderTargetPixelsAsync`), but for this scene CPU raycasting is correct and portable.
