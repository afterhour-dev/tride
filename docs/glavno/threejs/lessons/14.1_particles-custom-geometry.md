# 14.1 — Particles from Custom Geometry

## Concept

In [14.0 particles webgl intro](14.0_particles-webgl-intro.md) we rendered a particle system starting from a built-in `THREE.SphereGeometry` — the points of a sphere were used as particles. This lesson does the same thing, but instead of a ready-made geometry we **build the geometry ourselves** from raw vertex positions. This is the whole point of the lesson: recycling the custom-geometry idea we first met in [6.1 buffer geometry](6.1_buffer-geometry.md) inside a particle context.

When you think about it, a particle cloud is the perfect use case for custom geometry. Particles don't need faces, edges, or UVs — they are just a cloud of points placed in space. So we never need triangle indices or normals; all we need is a big flat array of `x, y, z` positions. Exactly what `BufferGeometry` is designed to hold.

### The `count * 3` mental model

The central idea is that **one vertex is not one array element**. A single 3D point is built from three numbers — its `x`, its `y`, and its `z`. So if you want `count` particles, you need `count * 3` numbers in the array.

```ts
const count = 5000;                       // how many particles we want
const positions = new Float32Array(count * 3); // one x,y,z per particle
```

If you ask for 5000 particles but forget the `* 3`, you end up with a buffer holding only ~1666 valid points (5000 / 3) — the rest reads as garbage or overflows the intended range.

### Filling the buffer

We fill that array with a loop. The `* 3` appears again because every iteration writes `x`, `y`, and `z` — i.e. three consecutive array elements — for one particle.

```ts
for (let i = 0; i < count * 3; i++) {
	// subtract 0.5 so the range is symmetric: -0.5 ... +0.5,
	// then scale by 10 so particles spread across -5 ... +5
	positions[i] = (Math.random() - 0.5) * 10;
}
```

`Math.random()` returns `0 ... 1`. If we used it raw, every coordinate would be positive — the whole cloud would sit in the positive octant of the scene. Subtracting `0.5` shifts the range to `-0.5 ... +0.5` so the cloud is centered on the origin. Multiplying by `10` then spreads it out to `-5 ... +5` on every axis.

### Wrapping the buffer in geometry

A raw `Float32Array` is not yet geometry. We need two wrappers:

1. **`BufferAttribute`** tells Three *how to read* the array — in this case `(positions, 3)` says "every 3 consecutive numbers form one vertex component."
2. **`setAttribute('position', ...)`** tells the geometry *which* attribute this buffer represents.

```ts
const particlesGeom = new THREE.BufferGeometry();
particlesGeom.setAttribute(
	'position',
	new THREE.BufferAttribute(positions, 3),
);
```

### From geometry to a visible particle cloud

A `BufferGeometry` alone renders nothing — it needs a **material** and a **Points** wrapper. `PointsMaterial` knows how to draw individual points instead of a filled surface. The `size` property controls how big each square point is; it defaults quite small, so example bumps it up.

```ts
const particlesMaterial = new THREE.PointsMaterial();
particlesMaterial.size = 0.1;       // bigger points are easier to see
particlesMaterial.sizeAttenuation = true; // smaller when farther away

const particles = new THREE.Points(geometry, particlesMaterial);
scene.add(particles);
```

`PointsMaterial.size` is in world units. `sizeAttenuation` turns on distance-based scaling (like real perspective on the point size), which makes the cloud read as having depth instead of being a flat spray of uniform dots.

### How many particles?

The commented-out lines in [the source](apps/14_1_particles_custom_geo) show the real experiment:

```ts
// const count = 50000;
// const count = 500000;
const count = 5000;
```

We ran **500,000 particles without issues on the dev machine** — with WebGL, not WebGPU. This is worth sitting with: half a million points rendered in real time on the GPU from a single flat buffer. This is the power of using geometry buffers the way the API wants you to — no per-particle meshes, no per-particle draw calls, just one buffer upload and the GPU does the rest. We kept 5000 in the final file to stay comfortable, but the ceiling is far higher.

Because the particles use the **WebGL** renderer (`THREE.WebGLRenderer`), this runs everywhere WebGL runs — no need for special WebGPU hardware. The WebGPU path (`THREE.WebGPURenderer`) is still new and hardware-gated, so WebGL keeps the demo broadly usable.

## Code

in repo - `apps/14_1_particles_custom_geo`

```ts
import * as THREE from 'three';

const canvas = document.querySelector('canvas#tride')!;
const scene = new THREE.Scene();
const renderer = new THREE.WebGLRenderer({ canvas });

// -- custom geometry: a flat buffer of x,y,z positions ------------------
const count = 5000;                    // how many particles
const positions = new Float32Array(count * 3); // one x,y,z per particle

for (let i = 0; i < count * 3; i++) {
	positions[i] = (Math.random() - 0.5) * 10; // spread over -5 .. +5
}

const geometry = new THREE.BufferGeometry();
geometry.setAttribute('position', new THREE.BufferAttribute(positions, 3));

// -- material + Points wrapper -------------------------------------------
const material = new THREE.PointsMaterial();
material.size = 0.1;
material.sizeAttenuation = true;

const particles = new THREE.Points(geometry, material);
scene.add(particles);

// -- camera + render loop ------------------------------------------------
const camera = new THREE.PerspectiveCamera(
	75,
	window.innerWidth / window.innerHeight,
	0.1,
	100,
);
camera.position.z = 3;
scene.add(camera);

renderer.setPixelRatio(Math.min(window.devicePixelRatio, 2));
renderer.setSize(window.innerWidth, window.innerHeight);
renderer.setClearColor(0x000000, 1);
renderer.render(scene, camera);
```

## Gotchas

- **The `* 3` is two different things.** For *allocation* it is "three axes per vertex"; for *the loop* it is "three values written per particle." Forgetting it in one place collapses the cloud into a third of the particles you asked for, or writes past the buffer. Keep them coupled in your head: `count * 3` everywhere.
- **A `Float32Array` is not a geometry.** You must wrap it in `BufferAttribute(positions, 3)` — the `3` is the vertex component size — and assign it to a `BufferGeometry` via `setAttribute('position', ...)`. Skipping either wrapper means Three never sees the data.
- **Points need a `PointsMaterial`, not a surface material.** A `MeshStandardMaterial` on a point buffer will not render points the way `Points` expects. Use `PointsMaterial` together with `THREE.Points`.
- **Point size units.** `PointsMaterial.size` is in world units, not pixels. If points look tiny (or huge) it's a size/scaling issue, not a bug. `sizeAttenuation` changes size with distance — with it off, near and far points are the same size and the depth cue is lost.
- **Commented-out counts are the plan, not the running code.** The 500k experiment is real but the active value is 5000. If you switch to 500000, be ready for the first frame to compile — the point cloud is tiny meanwhile is the shader cache warming, not a hang.

## Outdated

The WebGL path (`THREE.WebGLRenderer`) presented here is valid and is the broadly-compatible choice — still solid for learning particle systems with three.js. `approach is valid`

That said — if you want to push particle counts toward millions with less GPU pressure, the same buffer-geometry technique carries over to WebGPU via `THREE.WebGPURenderer` from `'three/webgpu'`. It is the newer, hardware-accelerated path and is worth leaning into as devices gain WebGPU support.

## Revisit

- **Push the count.** We validated 500k on this machine; try 1,000,000+ and watch for the knee. Keep the camera static and watch frame grap to the renderer's behavior, not GPU cost.
- **Repeat the custom-buffer idea.** This lesson depends on the vertex-layout idea from [6.1 buffer geometry](6.1_buffer-geometry.md). If the `count * 3` / `(positions, 3)` intuition is at all fuzzy, that lesson is the place to rework it.
- **Try points color / per-particle size.** We only set one `PointsMaterial.size` for *all* particles. Since the geometry also ‑can hold a `color` attribute, give each particle a per-vertex color or size and make the cloud we lives.
- **Animate the buffer.** The buffer is uploaded once. Try writing a new `positions` every frame (or a velocity-adding pass) to give the cloud motion — that is the leap from a static scatter to a living particle system.
