# 13.5 Baking Shadows (and an Alternative)

Real-time shadow maps cost performance and can look flat. This lesson explores the other side of the coin: **baking shadows into a texture** — the final tweak in the shadow saga that started in [[13.0_shadows-intro]]. A baked shadow is static and cheap, rendered once in Blender and then just sampled by the material. We also cover the easy alternative: a separate "fake shadow" plane that follows an object and fades with height.

The app is a direct follow-up to [[13.4_shadow-point-light]], so all the light/shadow GUI scaffolding is still there — but for baking **none of it matters anymore**.

---

## Concept

### What "baking" means for shadows

Just like you can bake lighting into a texture to avoid computing it at runtime ([[12.7_light-helpers-performance-baking]]), you can bake **shadows**: compute the shadow once, in Blender (or any offline tool), export it as an image, and apply it as a texture on the surface that receives the shadow — here, the floor.

The moment the shadow lives in a texture, it is **static**. It cannot react to moving objects, which is the whole point and the whole limitation of the technique.

### Step 0: kill runtime shadows

Shadow baking replaces the shadow map pipeline entirely, so we turn it off globally:

```ts
renderer.shadowMap.enabled = false; // was `true` in the previous lessons
```

That single line deactivates **all** runtime shadows. `castShadow`, `receiveShadow` and every `shadow.camera` tweak from the previous lessons become inert — they cost nothing because no shadow pass runs. (You can leave the flags on the meshes, they're simply ignored.)

### Technique 1 — a fully baked shadow texture

This is the "real" baking approach:

1. Bake the shadow in Blender and save it as an image (here: `public/textures/bakedShadow.jpg`).
2. Load it with `TextureLoader` — the same loader you already learned in [[8.0_texture-basics]].
3. Put it on the floor with **`MeshBasicMaterial`** and `map`.
4. That's it — no dynamic shadow, ever.

```ts
const bakedShadowTexture = textureLoader.load('/textures/bakedShadow.jpg');

// MeshBasicMaterial is unlit: it shows the texture's colors as-is,
// which is exactly what we want for a baked shadow.
const floorMaterial = new THREE.MeshBasicMaterial();
floorMaterial.map = bakedShadowTexture;

const floorMesh = new THREE.Mesh(floorGeometry, floorMaterial);
scene.add(floorMesh);
```

Why `MeshBasicMaterial` and not `MeshStandardMaterial`? Because the shadow is **already computed** into the texture — we don't want the material to light it again. An unlit material renders the exact baked result. With a lit material you'd get a muddy interaction between the real lighting and the baked shadow.

**The trade-off:** move the sphere in the GUI (or let the tick animate it) and the baked shadow stays glued to the floor. The floor doesn't know the sphere exists. Static but *basically free* per frame. Ideal for props, ground, and any scene where light and geometry don't move.

### Technique 2 — a simple shadow plane that fakes dynamic shadows

The alternative in this app is a cheap trick to get a *mostly* dynamic shadow:

- A second, small black plane (`SphereShadowMesh`) hovers just above the floor.
- Its material is `MeshBasicMaterial` with `color: 0x000000`, `transparent: true` and an **`alphaMap`** — the `simpleShadow.jpg` texture, where **white = opaque, black = transparent** (a light circle fading out at the edges). The white center renders as visible black shadow; the dark border renders as nothing.
- Every frame, the shadow plane copies the sphere's `x`/`z` position, and only its `opacity` changes with height.

```ts
const sphereShadowMesh = new THREE.Mesh(
  new THREE.PlaneGeometry(1.5, 1.5),
  new THREE.MeshBasicMaterial({
    color: 0x000000,
    transparent: true,
    alphaMap: simplerBakedShadowTexture, // white center → visible, black border → invisible
  }),
);
sphereShadowMesh.rotation.x = -Math.PI / 2;
// nudge just above the floor to avoid z-fighting
sphereShadowMesh.position.y = floorMesh.position.y + 0.01;
```

### The opacity trick: `1 - y`

The core math lives in the animation tick. The sphere bounces with `y = Math.abs(Math.sin(elapsed * 3))`. When the sphere is **high**, the shadow should be **faint**; when it's **low**, the shadow should be **strong**.

If you naively set `opacity = sphereMesh.position.y`, you get it **backwards** — opaque when the sphere is up. Invert it:

```ts
sphereShadowMesh.material.opacity = (1 - sphereMesh.position.y) * 0.9;
```

- `1 - y` flips the relationship so opacity is highest when height is 0.
- `* 0.9` just tones it down because the raw value looks too strong.

### Which technique do you use?

There's no single answer — the README point 3 is the takeaway:

- **Baked shadows** — best image quality for the price when scene is static; budget-friendly; unusable if things move.
- **Simple shadow plane** — dynamic-follow feel, one draw call, quality is limited (a flat blurred blob, no self-shadowing).
- **Real-time shadow maps** — the flexible, expensive option from [[13.1_shadow-map-optimization-part-one]] and [[13.2_shadow-map-optimization-part-two]].

It depends on the project, the performance budget, and what you know. You can also **combine** them — bake the big static AO/shadow and add a moving fake shadow or a real-time shadow map only for dynamic elements.

## Code

in repo - `apps/13_5_baking_shadows`

```ts
import * as THREE from 'three/webgpu';
import { OrbitControls } from 'three/addons/controls/OrbitControls.js';

const textureLoader = new THREE.TextureLoader();

// Technique 1 assets
const bakedShadowTexture = textureLoader.load('/textures/bakedShadow.jpg');
// Technique 2 asset
const simpleShadowTexture = textureLoader.load('/textures/simpleShadow.jpg');

const scene = new THREE.Scene();
const renderer = new THREE.WebGPURenderer({ canvas });
renderer.shadowMap.enabled = false; // kill all runtime shadows
await renderer.init();

// scene...
const sphereMesh = new THREE.Mesh(
	new THREE.SphereGeometry(0.5, 32, 32),
	new THREE.MeshStandardMaterial({ roughness: 0.7 }),
);

const floorMesh = new THREE.Mesh(
	new THREE.PlaneGeometry(5, 5),
	// Technique 1: baked shadow as unlit map
	new THREE.MeshBasicMaterial({ map: bakedShadowTexture }),
);
floorMesh.rotation.x = -Math.PI / 2;
floorMesh.position.y = -0.5;

// Technique 2: fake dynamic shadow plane
const sphereShadowMesh = new THREE.Mesh(
	new THREE.PlaneGeometry(1.5, 1.5),
	new THREE.MeshBasicMaterial({
		color: 0x000000,
		transparent: true,
		alphaMap: simpleShadowTexture,
	}),
);
sphereShadowMesh.rotation.x = -Math.PI / 2;
sphereShadowMesh.position.y = floorMesh.position.y + 0.01; // avoid z-fighting

scene.add(sphereMesh, floorMesh, sphereShadowMesh);

// -- animation loop --
const timer = new THREE.Timer();
renderer.setAnimationLoop((timestamp) => {
	const elapsed = timer.getElapsed();

	sphereMesh.position.x = Math.sin(elapsed) * 1.5;
	sphereMesh.position.z = Math.cos(elapsed) * 1.5;
	sphereMesh.position.y = Math.abs(Math.sin(elapsed * 3)); // bounce up & down

	sphereShadowMesh.position.x = sphereMesh.position.x;
	sphereShadowMesh.position.z = sphereMesh.position.z;
	// strong shadow low, faint shadow high
	sphereShadowMesh.material.opacity = (1 - sphereMesh.position.y) * 0.9;

	renderer.render(scene, camera);
});
```

## Gotchas

- **Runtime shadows must be explicitly disabled.** `renderer.shadowMap.enabled = false` is the step people forget — everything still *looks* fine with a baked texture over real shadows, until geometry moves and the two disagree.
- **A baked shadow never moves.** Rotate the sphere, move it 2 meters away — the floor shadow stays put. That's not a bug, it's the technique. Design scenes around it (static props, official ground).
- **`alphaMap` needs `transparent: true`.** Without it, the alpha texture is applied but the material ignores the alpha channel and renders fully opaque — your shadow turns into a black square.
- **White = visible, black = invisible in an alpha map.** The center of `simpleShadow.jpg` is white → the shadow shows there; the border is black → fades out. Exporting the texture inverted (black where you want shadow) is a classic mistake.
- **Opacity inversion is easy to get backwards.** `opacity = y` makes the shadow strongest when the object is highest. Remember `1 - y` (as the code comment says: "opaque should be when sphere is lower").
- **Nudge the shadow plane off the floor.** `position.y = floorMesh.position.y + 0.01` — exactly on the floor causes **z-fighting** (flickering where the two coplanar surfaces fight for the depth buffer).
- **Three.js reads `alphaMap` from the texture's *green channel*** — the texture's RGB luminance is not what's used. Ink your shadow into green or make sure the map is grayscale-in-all-channels if you hand-craft one. (Present in the docs as: "The green channel of the texture is used for the alpha map.")
- **`MeshBasicMaterial` is unlit — that's a feature here, not a surprise.** It ignores ambient/directional/spot/point light entirely, so the baked shadow renders exactly as painted.

## Revisit

- **Bake in Blender.** This lesson consumed a ready-made texture. Try baking your own `bakedShadow.jpg` from a Blender scene (Cycles render → bake → shadows/AO) and re-tune the `*.jpg` quality + texture size. There's a Blender doc precedent for baking in the vault — extend the docs in `docs/blender/` if you go deeper.
- **Bake the whole lightmap, not just the shadow.** The same principle extends to ambient occlusion and indirect/bounced light — one texture that carries all static lighting + shadows, a standard game-dev optimization.
- **Combine the techniques.** Baked static AO on the floor + a fake shadow plane (or pointlight shadow map) only for moving characters — the app deliberately explores two ends of the same spectrum.
- **`renderer.shadowMap.type = THREE.PCFSoftShadowMap` is still set in the code even with shadows disabled** — it's dead config from prior lessons (see [[13.1_shadow-map-optimization-part-one]] for why the `radius`/blur GUI tweak doesn't work with PCFSoft).
- **Opacity interpolation.** `(1 - y) * 0.9` is linear. A smoothstep or sine-shaped falloff would look more natural — a nice self-study tweak through the GUI.

---

## Outdated

approach is valid — shadow baking is still a mainstream game-dev technique (lightmapping in Unreal/Unity, AO maps in Blender). Runtime shadow maps have gotten better, but baked shadows remain the cheapest way to get high-quality static shadows. The "simple shadow plane" trick is also still widely used in low-poly / mobile-style projects.
