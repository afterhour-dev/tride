## Concept

This lesson is a direct continuation of [[15.4_scroll-based-animation-parallax]]. In that lesson we made the camera move with the mouse cursor (the "parallax" effect), but by snapping the camera straight to the target on every frame, the motion felt *mechanical* and not realistic. This lesson fixes that by adding **easing** (also called **smoothing** or **lerping**) to the camera movement.

The core idea is simple: **don't move the camera all the way to the target on one frame.** Instead, on each frame, move it only a *fraction* (say a 10th, or less) of the remaining distance toward the destination. On the next frame, again another 10th of the *remaining* distance. Then another 10th, and so on. Because the gap keeps shrinking but we never quite close it in one step, the camera glides smoothly toward the target instead of jumping straight there.

This is the classic **linear interpolation ("lerp")** formula, which for each axis looks like:

$$ value_{new} = value_{old} + \left( target - value_{old} \right) \cdot f $$

where `f` is the easing factor between `0` and `1`. When `f = 1`, you jump straight to the target (no smoothing). When `f` is a small number like `0.08`, you move only 8% of the way per frame — smooth and cartoon-like. The smaller the factor, the "floatier" and lazier the movement.

In the code, this is applied to the camera group's position using the mouse-derived parallax values as the *target*:

```ts
cameraGroup.position.x +=
  (parallaxX - cameraGroup.position.x) * 0.08;
cameraGroup.position.y +=
  (parallaxY - cameraGroup.position.y) * 0.08;
```

> 💡 A good mental model: the amount we move is always proportional to how far away we currently are. Far away → move a lot. Close → move a little. That asymmetry from the smoothing/lerp effect.

> 💡 The amplitude was deliberately **halved** near the end of the project (see the code comments): the parallax cursor values are multiplied by `0.5` so the camera window doesn't float off too far. Keep this amplitude in mind when tuning the effect.

### Frame-rate dependence (the important gotcha)

The naive fixed-factor lerp above has a real problem: it is **tied to the display frame rate.** On a high-frequency screen (e.g. 120 Hz or 144 Hz), `tick()` runs many more times per second than on a 60 Hz screen. Because each call moves the camera another 8% closer, the camera on a fast screen travels *much* faster to the target. The result is that the same experience looks different depending on the device. It isn't catastrophic, but it's inaccurate, and it's preferable to have the same result across devices as much as possible.

### Making it frame-rate independent with delta time

To fix that, we multiply the easing factor by the **delta time** — the time spent between the current and previous frame. On a given frame rate, delta is a small number, on the order of `0.016` seconds for a typical 60 fps screen. Since delta time is that small, our easing factor needs to be much bigger than `0.08` to compensate. So we multiply by something like `5`:

```ts
const delta = timer.getDelta();

cameraGroup.position.x +=
  (parallaxX - cameraGroup.position.x) * 5 * delta;
cameraGroup.position.y +=
  (parallaxY - cameraGroup.position.y) * 5 * delta;
```

Now, on a fast or slow screen alike, the *rate* of approach is roughly constant in *real seconds*, so the lerp behaves the same across devices. This is frame-rate-independent animation.

Three.js provides `THREE.Timer` which gives both `elapsedTime` and `getDelta()`. The code comments note that with `Timer` you no longer need to compute delta manually by keeping a `previousTime` variable — `timer.getDelta()` does it for you. You just call `timer.update(timestamp)` once per frame at the top of `tick()`, then read `getDelta()` and `getElapsed()`.

## Code

in repo - `apps/15_5_scroll_based_animation_five`

```ts
// On every frame, lerp the cameraGroup toward the bounce parallax target.
// Multiplying by delta keeps the speed identical across frame rates.

function tick(timestamp: number) {
    timer.update(timestamp);

    const elapsedTime = timer.getElapsed();

    // Vertical scroll drives the whole camera group up/down
    camera.position.y = -(scrollY * debugObject.objectsDistance) / sizes.height;

    // Mouse parallax target (amplitude reduced by 0.5)
    const parallaxX = cursor.x * 0.5;
    const parallaxY = -cursor.y * 0.5;

    const delta = timer.getDelta();

    // Easing: move a fraction of the remaining distance, scaled by delta
    cameraGroup.position.x += (parallaxX - cameraGroup.position.x) * 5 * delta;
    cameraGroup.position.y += (parallaxY - cameraGroup.position.y) * 5 * delta;

    // Rotate the toon meshes over time
    for (const mesh of selectionMeshes) {
        mesh.rotation.x = elapsedTime * 0.1;
        mesh.rotation.y = elapsedTime * 0.12;
    }

    renderer.render(scene, camera);
}
```

This continues the scroll-based animation series that walks the camera along vertically stacked objects (a torus, a cone, and a torus knot, each spaced `objectsDistance` apart using `MeshToonMaterial` with a gradient map), while the mouse parallax smoothly offsets the `cameraGroup`.

## Gotchas

- **Using `=` instead of `+=` kills the smoothing.** If you write `cameraGroup.position.x = parallaxX` you teleport straight to the target every frame — no easing. The smoothing comes *specifically* from accumulating a fraction of the remaining distance (`+=`), never direct assignment.
- **Naive `+= (target - current) * 0.08` is frame-rate dependent.** On a 120 Hz+ screen it moves twice as fast as on 60 Hz. Always scale by `delta` (as described above) to keep the result equivalent across devices.
- **The easing factor must compensate for delta being tiny.** Delta is ~`0.016` at 60 fps, so a `0.08` multiplier is far too small once you multiply by delta. Raise the number (e.g. `* 5`) to get the same feel back. `// GOTCHA:` — forgetting to re-tune this constant is the classic trap.
- **Don't apply parallax easing to the camera by mistake.** The scroll-up/down move belongs on `camera.position.y` (directly along the scroll axis — that's the effect), while the mouse parallax smoothing belongs on the wrapping `cameraGroup.position`. Mixing in the two-level structure (camera inside `cameraGroup`) is what keeps the two motions independent.
- **`magFilter` on the gradient texture** (`NearestFilter`) is set because these textures are intended for crisp toon-look gradient steps; using it wrong produces blurry banding — minor but easy to trip on here.
- **`canvas#tride` is `position: fixed` with the body `overflow` enabled** (`/* overflow: hidden */` is commented out) so the HTML sections can scroll the page while the canvas stays fullscreen behind them. If you accidentally enable `overflow: hidden`, scroll-based animation stops entirely.

## Revisit

- **Understand the lerp math itself.** Play with the easing factor as a floating number; compare `f = 1` (no smoothing) with `f = 0.08` and `f = 5*delta`. Try to reason about how the remaining distance shrinks exponentially frame after frame.
- **Frame-rate independence.** Revisit why multiplying by delta makes the lerp device-independent; think of a 60 Hz vs 120 Hz test on the same code.
- **The `cameraGroup` wrapper.** Re-reading how rotating or positioning the outer group (instead of the camera directly) composes with scroll + parallax + mouse.

## Outdated

`approach is valid` — lerping with delta time to smooth camera movement is still a current, standard technique in Three.js scroll/parallax experiments, though it's also woven into more full-featured libraries (Lenis for smooth scrolling, GSAP for tweens). Nothing here is stale.
