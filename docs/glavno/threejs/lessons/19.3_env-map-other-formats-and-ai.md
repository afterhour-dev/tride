### Where this fits in the series

This is the fourth part of the environment-map series: [[19.0_environment-map-intro-with-cube-texture-map]] covered cube-texture env maps, [[19.1_equirectangular-hdri]] covered ready-made equirect HDRIs, [[19.2_hdri-from-blender]] covered *rendering your own* HDRI in Blender. This lesson asks two new questions:

1. **What other file formats** can carry an environment map — and what does the format actually change?
2. **What other ways** are there to *generate* env maps — specifically AI tools?

The scene is the same test rig as before (FlightHelmet → [[16.3_draco]] / [[18.0_blender-exporting-model-and-loading]] console model, torus knot with live metalness/roughness sliders, gil-gui switcher), so the only new variable is the environment itself.

### The format landscape: HDR vs EXR vs LDR

An environment map is just a *sphere of light* stored as pixels. Formats differ in **how brightness is stored**:

| Format | Extension | How light > 1.0 is stored | Alpha / layers | Typical use |
|---|---|---|---|---|
| Radiance HDR | `.hdr` | RGBE: 8-bit channels + one shared 8-bit exponent | No / no | 19.1, 19.2 — web-friendly, small |
| OpenEXR | `.exr` | Half-float (16-bit) or float (32-bit) per channel | **Yes / yes** | Film & VFX pipeline |
| JPEG / PNG | `.jpg`, `.png` | **None** — capped at 1.0 (8-bit LDR) | PNG: alpha / no | Backgrounds, AI-generated looks |

**`.hdr` (Radiance / RGBE)** — your env maps from [[19.1_equirectangular-hdri]] and [[19.2_hdri-from-blender]] used this. It stores 3 color mantissas plus one shared exponent byte, so a pixel can reach very high brightness, has no alpha channel and no layers, and compresses with RLE. Loader: `HDRLoader`.

**`.exr` (OpenEXR)** — created by Industrial Light & Magic (*Star Wars*, etc.) and now an Academy standard for film post-production. Instead of the RGBE trick it stores **real floating-point values per channel** — half float (16-bit) is typical, full float (32-bit) for masters — which means no quantization loss at high intensities. Two things the README asks about:

- **Alpha channel** — the image can carry transparency/coverage per pixel. Exr is used the same way in three.js regardless — the scene just reads the RGB light — but the alpha is there if your pipeline needs it (e.g. compositing).
- **Layers** — one `.exr` file can hold *several stacked images* as named layers (classically: one layer per light, or a "beauty" pass plus depth/motion/ID passes). For an env map you usually only care about the main RGB layer. Three.js's `EXRLoader` reads the primary image data; reading *specific* layers/passes is a manual/RawTexture affair — revisit material if you ever get handed a multi-layer EXR.

Is EXR *better* than `.hdr`? Honest answer: **not inherently — it depends on the pipeline.** For lighting a three.js scene, both end up as float textures feeding the same IBL path; RGBE's shared exponent is good enough for env maps, and `.hdr` files are lighter. EXR pulls ahead when you need precision without exponent errors, alpha, layers, or interop with a film/compositing toolchain. Switching formats in code is trivial — only the loader changes, the mapping and scene assignment stay identical. `// EXPLAIN:` comment in `main.ts`: "we need EXRLoader" — that's the whole difference.

**JPEG / PNG — LDR (Low Dynamic Range)** — 8 bits per channel, values clamped to 0..1. An LDR image *cannot* store a brightness of 100; it maxes out at 1.0. So as `scene.background` an LDR equirect is fine (it's a picture), but as `scene.environment` (lighting) it's **inherently too dim** — the "sun" can never exceed 1.0. Two things the app does to rescue it:

```ts
ldrTexture.colorSpace = THREE.SRGBColorSpace; // decode sRGB → linear
scene.environmentIntensity = 1.9;             // boost past 1.0
```

The `// EXPLAIN:` comment spells out the first one: "these ones, LDR equirectangular need different colorSpace to look better; without it env map would look washed out". Why: an 8-bit JPEG stores sRGB-**gamma-encoded** values, but the renderer does lighting math in **linear** light. Declaring `SRGBColorSpace` tells three.js to decode the texture on the GPU before it's used as light; without the declaration it's sampled as if already linear and the lighting is wrong. HDR and EXR textures *don't* get this treatment — their float data is already linear — which is why the app sets `colorSpace` only on the five JPEGs, `// EXPLAIN:` makes the distinction explicit.

### Loading them in code

Two loaders, one mapping:

```ts
// EXR
const environmentMapExr = await exrLoader.loadAsync(
	'/textures/environmentMaps/ai-4k.exr',
);

// LDR (JPEG)
const neonCityTexture = await textureLoader.loadAsync(
	'/textures/environmentMaps/ai-images/neon_city.jpg',
);

environmentMapExr.mapping = THREE.EquirectangularReflectionMapping;
neonCityTexture.mapping = THREE.EquirectangularReflectionMapping;
```

Check the app: the EXR is loaded (`ai-4k.exr` — an AI-generated 4K env map) but the initial `scene.environment` assignment is commented out — the app **starts on the neon-city JPEG**, and the GUI (`EXRLoader`-based `myEnvMaps` list) lets you hot-swap between `exr`, the five JPEGs, and `none`. Comparing the same torus knot under all six is the whole lesson in one gesture: the EXR lights materials cleanly at moderate `environmentIntensity`; the JPEGs need the same map plus the SRGB decode and a higher intensity to look comparable.

### Generating env maps with AI (the README's questions, answered)

The README asks for an honest read on the current (2026) AI env-map generation landscape, knowing the constraints: Linux, no subscription on principle. Key facts:

- **The fundamental caveat:** many "AI HDRI" tools output an **8-bit LDR image wrapped in a `.hdr`/`.exr` container**. The file is HDR-*shaped* but the pixels hold no real >1.0 light — fine for background/soft IBL, useless for a physically accurate sun or sharp specular. This is exactly why the five AI JPEGs in this app must be treated as LDR (SRGB decode + intensity boost). Check what a tool actually outputs before trusting the extension.
- **NVIDIA Canvas** — free, Windows + RTX only, so unusable here (the README guessed the "beta for a long time" correctly: the 360° *Panorama* mode landed in Canvas 1.4 in 2023, and NVIDIA still ships the app as a maintained free beta). It exports 4K equirectangular **EXR — but SDR, not HDR**, per NVIDIA's own docs. Nice for sketching environments, not for real IBL light.
- **Skybox by BlockadeLabs** (now owned by Stability AI) — the benchmark: true 32-bit HDRI export, 8K–16K, Unity/API integrations — but paid on a credit model (~$24/mo entry tier). Per the README, not worth it here.
- **Free / pay-as-you-go options worth knowing:**
  - [KenerateAI](https://kenerate.com/) — genuinely free tier, claims true HDR `.exr`/`.hdr` export, 360° env maps/skyboxes with commercial rights.
  - [Poly](https://withpoly.com/) — free tier, focused on HDRI environments + PBR textures.
  - [3DTexel](https://www.3dtexel.com/) — free text-to-HDRI generator.
  - [PanoramaGenerator](https://panoramagenerator.io/) — free trial; be honest with yourself that its "HDRI" wraps an LDR source.
  - [Poly Haven](https://polyhaven.com/) — **not AI**, but the free baseline everyone should compare to: hand-authored CC0 photographic HDRIs, best in class for accurate sun/specular lighting.
  - **Stable Diffusion + panorama LoRAs/ControlNet, self-hosted** (e.g. via ComfyUI on Linux) — the most powerful free route: full control, runs on your machine, no subscription. The cost is engineering: seams, pole distortion, and (again) the output is LDR unless you add HDR post-processing.

**Bottom line for your setup:** for accurate lighting keep using captured/RGBE HDRIs (Poly Haven or your Blender renders from [[19.2_hdri-from-blender]]); for *mood/background* env maps the AI JPEGs are fine and free — and remember the SRGB + `environmentIntensity` recipe from this app.

## Code

in repo - `apps/19_3_env_map_other_formats_and_AI`

```ts
import * as THREE from 'three/webgpu';
import { EXRLoader } from 'three/addons/loaders/EXRLoader.js';

const renderer = new THREE.WebGPURenderer({ canvas });
await renderer.init();

const scene = new THREE.Scene();

// 1. EXR — float channels; real HDR precision
const exrEnv = await new EXRLoader().loadAsync(
	'/textures/environmentMaps/ai-4k.exr',
);

// 2. LDR equirect (JPEG) — max brightness 1.0
const ldrEnv = await new THREE.TextureLoader().loadAsync(
	'/textures/environmentMaps/ai-images/neon_city.jpg',
);

// 3. same mapping for every format
exrEnv.mapping = THREE.EquirectangularReflectionMapping;
ldrEnv.mapping = THREE.EquirectangularReflectionMapping;

// 4. LDR JPEGs are sRGB-encoded → decode to linear
//    (HDR/EXR are already linear — do NOT set this on them)
ldrEnv.colorSpace = THREE.SRGBColorSpace;

// 5. LDR caps out at 1.0 → boost to act like light
scene.environmentIntensity = 1.9;

scene.environment = ldrEnv; // or exrEnv
scene.background = ldrEnv;  // or exrEnv
```

## Gotchas

- **`colorSpace = SRGBColorSpace` on the wrong texture.** Set it on *LDR* JPEG/PNG images (sRGB-encoded) so the renderer decodes them to linear before lighting. **Do not** set it on `.hdr`/`.exr` textures — their data is already linear, and declaring them sRGB double-decodes and darkens them. The `// EXPLAIN:` comment in `main.ts` only assigns it to the five JPEGs, deliberately.
- **Mismatched loaders.** `EXRLoader` for `.exr`, `HDRLoader` for `.hdr`, `TextureLoader` for JPEG/PNG. Loading the wrong container with the wrong loader gives garbage (or grey). Same `// EXPLAIN:` spirit as 19.2's mapping warning: the loader is the format's private key.
- **Forgetting the mapping again.** `EquirectangularReflectionMapping` is still required per texture — the app sets it on all six maps one by one, and the code comment flags it ("also we don't want to forget mapping").
- **"AI HDRI" ≠ HDRI.** Tools that wrap an 8-bit image in `.hdr`/`.exr` are physically LDR. If an AI EXR lights your scene flat/dim when a Poly Haven capture doesn't, check the actual range — the file name lied. Your five JPEGs are the honest version of this: LDR, treated as LDR.
- **Two knobs, again:** `environmentIntensity` scales only *lighting*, `backgroundIntensity` only the *background*. With LDR maps both usually need a push — the app runs 1.9 and 2.4.
- **EXR with layers may not show all passes in three.js.** `EXRLoader` reads the primary image; layered EXRs from film pipelines need channel/layer selection handled manually — see Revisit.

## Revisit

- **Multi-layer / multi-channel EXR.** This app loads a flat `.exr`. Explore what `EXRLoader` does with a layered file (several light passes stacked in one `.exr`) — three.js support for selecting passes is limited, and it's a genuinely different problem from "load an env map".
- **Re-verify the AI tools in a few months.** The README notes it used free env maps without writing prompts; the tool landscape moves fast (BlockadeLabs was acquired by Stability, Canvas's panorama mode is 3+ years old and SDR-only, free tools appear). If you revisit, re-run the research and re-check whether any free tool now outputs *true* 32-bit HDR — that would let AI-generated light actually behave like light.
- **A three-way lighting comparison.** Same scene, same torus knot (metalness = 1): Blender render ([[19.2_hdri-from-blender]]), Poly Haven capture ([[19.1_equirectangular-hdri]]), AI EXR, AI JPEG. Build a small table of which format needs what `environmentIntensity`/`colorSpace` to look right — it's the practical cheat sheet this lesson implies.
- **The commented-out EXR default.** `scene.environment = environmentMapExr;` is commented out and the app boots on `neonCityTexture`. Worth deciding deliberately: for this test rig the LDR start was intentional to show the fix — but an EXR default would be the "correct" lighting baseline.
- **HDRI seam/pole distortion in AI images.** The five JPEGs are AI-drawn equirects; check their zenith/nadir quality (top/bottom of the panorama) and any seam at longitude 0°/360° — the classic AI-panorama failure points from the research.

## Outdated

**approach is valid** — and this is one lesson where the **WebGPU path is the whole point** 🚀: `EXRLoader` + `HDRLoader` run natively under `three/webgpu` / `WebGPURenderer`, loading true float textures with no WebGL-era PMREM boilerplate. The EXR-vs-HDR-vs-LDR reality hasn't changed, and on the loaders side:

- `.hdr`: the older WebGL path used `RGBELoader`; the modern `HDRLoader` (WebGPU) used in [[19.2_hdri-from-blender]] is current. Not outdated.
- `.exr`: `EXRLoader` is the same class on both paths. Not outdated.
- LDR JPEGs: `TextureLoader` unchanged.

> 💡 More up to date alternative: treat AI env-map generation as a *moving target* — re-check [KenerateAI](https://kenerate.com/) and similar free tools before each project; the 2026 "LDR-wrapped-in-HDR-container" state of the art will likely improve. Also: [Poly Haven](https://polyhaven.com/) remains the free non-AI baseline for *physically accurate* env lighting — AI images are for mood, not for measured light.
