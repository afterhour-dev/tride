## Concept

After tuning directional shadows in [[13.1_shadow-map-optimization-part-one]] and [[13.2_shadow-map-optimization-part-two]], and spot-light shadows in [[13.3_shadow-spot-light]], this lesson adds the **point light** to the shadow picture. The point light is the outlier: it shines in **every direction at once**, so a single flat shadow map can't capture it. Three.js answers with a **cube shadow map** — **6 renders per frame**, one per face of an imaginary cube around the light.

### The shadow camera is one `PerspectiveCamera`, reused for all 6 faces

Look at `pointLight.shadow.camera` and you'll find a plain `PerspectiveCamera`:

```ts
// three source — src/lights/PointLightShadow.js
super( new PerspectiveCamera( 90, 1, 0.5, 500 ) );
```

- `fov = 90` — each cube face is a quarter-sphere, so four faces tile the horizon and two more cover top/bottom.
- `aspect = 1` — faces are square.
- `near = 0.5`, `far = 500` — the default depth range of the shadow.

Three.js does **not** create six cameras. At shadow-render time it takes this single camera, places it at the light's position and re-aims it **six times**, once per cube direction:

```ts
// face order: +X, -X, +Y, -Y, +Z, -Z (last face = -Z)
_lookTarget.copy( camera.position );
_lookTarget.add( _cubeDirections[ face ] );   // e.g. (0,0,-1) for the last face
camera.up.copy( _cubeUps[ face ] );
camera.lookAt( _lookTarget );
camera.updateMatrixWorld();
```

This answers the question from the README — *"does three.js render in all 6 directions?"* — **yes, exactly 6**, using one `PerspectiveCamera` that gets re-pointed 6× per frame into a cube map.

### Why the shadow `CameraHelper` looks weird

Because the same camera looks in a **different direction per face**, attaching a `CameraHelper(pointLight.shadow.camera)` only ever shows **one frustum** — the orientation the camera was in when you looked at it. That's why it "seems to face negative Z": the last cube face has direction `(0, 0, -1)`. It also moves around unexpectedly, because its position gets set to the light's position during each shadow render.

**The helper can't be useful for a point light the way it is for a directional/spot light** — you'd need six helpers frozen at the six face orientations to visualize the full capture. In practice, use `PointLightHelper` (position/size) and rely on `near` + `far` thinking instead:

```ts
const pointLightHelper = new THREE.PointLightHelper( pointLight );
scene.add( pointLightHelper );
```

### The real knobs: `near`, `far`, `distance`, `mapSize`

- **`near` / `far`** — the depth range of the shadow capture, set on `pointLight.shadow.camera`.
- **`far` is auto-managed by `light.distance`.** At render time: `const far = light.distance || camera.far;` — so a set `pointLight.distance` overrides whatever you put on `shadow.camera.far`, exactly like the spot light in [[13.3_shadow-spot-light]]. In this app, `pointLight.distance = 10` makes the effective shadow far `10`, silently ignoring the `pointLight.shadow.camera.far = 5` written in the code.
- **`mapSize` is the cube face resolution.** `mapSize.width = 1024; mapSize.height = 1024` is the size of **one face** of the cube map. The actual depth texture totals `6 × width²` texels. Keep `width === height`, powers of two.

### Performance — the honest concern from the README

- **Every shadow-casting point light costs 6 depth passes per frame.** A directional or spot light costs 1. Texture budget is effectively `6 × mapSize`.
- Good practical rules: have **one** shadow-casting point light dominated the scene (as in this app), let the other fill lights skip `castShadow`, keep `mapSize` as small as visually acceptable, and for big scenes prefer a directional key light.
- The GUI shadows in this app intentionally mixes a directional **and** a spot **and** a point light all casting shadows — expect the muddy overlapping shadow result noted since [[13.3_shadow-spot-light]].

### Physical intensity units — candela again

With physically-correct lighting (the default), `pointLight.intensity` is in **candelas**, scaled like `0.4 * Math.PI` here — same story as [[12.4_point-light]] and [[12.6_spot-light]]. `decay = 0.5` gives a gentler falloff than the physical `2`.

## Code

in repo - `apps/13_4_shadow_point_light`

```ts
import * as THREE from 'three/webgpu';

const renderer = new THREE.WebGPURenderer({ canvas });
await renderer.init();
renderer.shadowMap.enabled = true;            // global switch for all shadows
renderer.shadowMap.type = THREE.PCFSoftShadowMap;

const scene = new THREE.Scene();
const camera = new THREE.PerspectiveCamera(75, innerWidth / innerHeight, 0.1, 100);
camera.position.set(2, 1, 1);

// Point light — shines in all directions -> 6 cube shadow faces
const pointLight = new THREE.PointLight(0xffffff);
pointLight.intensity = 0.4 * Math.PI;  // candelas, not 0..1
pointLight.distance = 10;              // ALSO drives shadow.camera.far
pointLight.decay = 0.5;
pointLight.position.set(-1, 1, 0);
pointLight.castShadow = true;          // don't forget!

pointLight.shadow.mapSize.width = 1024;   // per cube face, keep square
pointLight.shadow.mapSize.height = 1024;
pointLight.shadow.camera.near = 0.1;      // default is 0.5
// far is overridden by pointLight.distance at render time

scene.add(pointLight);

// Objects
const material = new THREE.MeshStandardMaterial({ roughness: 0.7 });
const sphere = new THREE.Mesh(new THREE.SphereGeometry(0.5, 32, 32), material);
sphere.castShadow = true;
const floor = new THREE.Mesh(new THREE.PlaneGeometry(5, 5), material);
floor.receiveShadow = true;
floor.rotation.x = -Math.PI / 2;
floor.position.y = -0.5;
scene.add(sphere, floor);

const pointLightHelper = new THREE.PointLightHelper(pointLight);   // position gizmo
scene.add(pointLightHelper);

renderer.setAnimationLoop(() => {
  renderer.render(scene, camera);
});
```

## Gotchas

- **`PointLightShadow` uses a single `PerspectiveCamera`, not six.** It's a `PerspectiveCamera(90, 1, 0.5, 500)` that gets repointed along all 6 cube directions during each shadow render.
- **`CameraHelper(pointLight.shadow.camera)` is basically useless here.** It shows only whichever face orientation the camera was last in — the README observed it "facing negative Z" because the last cube face looks `(0,0,-1)`. Use `PointLightHelper` for position and trust `near`/`far` instead.
- **`pointLight.shadow.camera.far` is overridden by `pointLight.distance`.** If `distance` is set (as in this app, = 10), the five in `far` are ignored. Change `distance` to control shadow range.
- **Not setting `castShadow = true` on the light silently disables all of this.** The scene still lights, only shadows. Setting `sphere.castShadow` / `floor.receiveShadow` without the light flag does nothing.
- **`mapSize` counts per cube face, not total** — real memory is ~6×. Keep `width === height`.
- **PCFSoftShadowMap + `shadow.radius`** — counter to what you'd hoped, the soft shadow map doesn't use the blur radius knob (the app disables the slider and explains this in the "Directional Light Shadow tweaks" panel).
- **Multiple castShadow lights = muddy overlaps** — the scene keeps directional + spot + point all casting. Prefer one dominant shadow source.
- **GUI label bug in the app**: the point-light shadow tweaks folder is named "Spot Light shadow tweaks" — a copy-paste slip in `src/main.ts`; the panels all call the correct `pointLight.shadow.*`.

## Revisit

- **Performance of point light shadows.** 6 depth passes per frame is the most expensive shadow type. Try the same scene with `castShadow` dropped from the directional and spot lights and a bigger `mapSize` on the point light — where does quality stop improving?
- **`far` vs `distance` interaction** — re-read `WebGLShadowMap`/`PointShadowNode.renderShadow()` to internalize `light.distance || camera.far`. If you unset `distance = 0`, the far you set on `shadow.camera` finally governs.
- **Why the cube-map face order matters** (`+X, -X, +Y, -Y, +Z, -Z`) and how the `CameraHelper`, being set to that one orientation, always reads as "facing -Z". Look at `ShadowMap` – `PointShadowNode.js` in `node_modules/three/src/nodes/lighting/`.
- **The 3-light scene result.** Once you've used the GUI to tweak with the directional + spot shadows mute, decide whether "one shadow-casting light" is the house rule for future scenes.

## Outdated

`approach is valid`

Point light cube-shadow maps (`PointLightShadow`, 6 face renders, `PerspectiveCamera(90, 1, 0.5, 500)` and the `far = distance || far` rule) behave identically under WebGL and WebGPU for this version of three (r185 is used here). **This app already runs on `three/webgpu` + `WebGPURenderer` (WebGPU path) ⚡** — no change needed.
