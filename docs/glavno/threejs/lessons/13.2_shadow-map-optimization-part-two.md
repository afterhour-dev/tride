## Concept

This is the second pass at optimising a **directional light** drop shadow (the first was [[13.1_shadow-map-optimization-part-one]]). Part one was about *where* the shadow box sits and how big the shadow map is (`amplitude` and `mapSize`). Part two is about **how the shadow is filtered** — the two knobs that change the softness and cost of the shadow's edges: the blur `radius` on the light, and the shadow map **algorithm** chosen on `renderer.shadowMap.type`.

Three.js lets you pick between a few shadow map filtering algorithms, and separately lets you ask the light to blur the shadow. Understanding which knob works with which algorithm is the heart of this lesson.

### The shadow map algorithm — `renderer.shadowMap.type`

The shadow map is a depth texture rendered from the light's point of view. The "algorithm" decides **how that depth texture is filtered when it's sampled** back in the main render to decide whether a fragment is in shadow. There are four options in three.js:

```ts
renderer.shadowMap.type = THREE.PCFSoftShadowMap;
```

| Type | Performance | Edge quality | Notes |
|------|-------------|--------------|-------|
| `THREE.BasicShadowMap` | ⚡ Very performant | Lousy — hard, jagged edges | No filtering at all — a fragment is either in shadow or not |
| `THREE.PCFShadowMap` | Slower | Smoother edges | Percentage-Closer Filtering — averages a few depth samples **around** the point to soften the edge (the default) |
| `THREE.PCFSoftShadowMap` | Slower | Even softer edges | A larger, optimised sampling pattern for very soft edges |
| `THREE.VSMShadowMap` | Slower, more constraints | Soft, can look wrong | Variance Shadow Maps — filters the depth *moments* instead, can show light-bleeding artifacts |

`PCFSoftShadowMap` is used in this app because it gives the nicest soft edges out of the box. The GUI lets you flip between all four live and watch both the edge quality and the GPU cost change.

### The blur — `shadow.radius`

Independently of the algorithm, a directional light's `shadow` carries a `radius` property:

```ts
directionalLight.shadow.radius = 10;
```

Higher `radius` → blurrier shadow edges. This is a **general and cheap blur** — it does **not** consider the camera-to-object distance or any spatial reasoning; it just spreads the filtering kernel wider. It's cheap precisely because it's a fixed, uniform blur everywhere on the shadow.

**Allowed values:** `radius` is a number, and `0` disables the blur entirely. The GUI in this app sweeps it from `-30` to `30` to explore. Negative values are allowed by the GUI but are a curiosity — you'll want small positive numbers (anywhere from `1` up to a few dozen) for a believable soft shadow; very large values blur the shadow almost completely away. Note that in the newest three.js `radius` also accepts a `NumericValueNode` (three/webgpu) so it can even be animated.

### The trap: `radius` doesn't play with `PCFSoftShadowMap`

The single most important takeaway of this lesson:

> `radius` (blur) has **no effect** with `THREE.PCFSoftShadowMap`.

Why? `PCFSoftShadowMap` already applies its **own fixed kernel** — a hard-coded 9-sample pattern that produces soft edges with a baked-in size. It ignores the `radius` you ask the light for. The radius-based gaussian blur only applies when you use `PCFShadowMap` or `VSMShadowMap`.

So the practical workflow when you want to tune softness:

- **`PCFShadowMap` + a `radius` you control** → you directly dial the edge softness yourself. This is often the sweet spot for "I want soft shadows and I want to choose how soft."
- **`PCFSoftShadowMap`** → soft edges for free, but you lose the `radius` dial; softness is whatever the baked pattern gives.
- **`VSMShadowMap`** → `radius` blurs the shadow map's stored moments, giving smooth soft shadows but with a risk of **light bleeding** (softness leaking into fully-lit areas) and other artifacts.

The GUI in this app spells this out with a disabled label so you see it before you even start dragging the slider.

### How the pieces fit together

Both levers change the *quality/perf* trade-off but do it differently:

- **Algorithm** changes the *filtering strategy* — how many and what kind of samples are taken. More sophisticated algorithms are softer but cost more GPU.
- **`radius`** scales the *blur width* — how far apart those filtered samples are spread. Bigger radius = softer but also more GPU.

Because they work on different axes, you can actually combine a good algorithm *with* a good radius to reach softness neither alone gives you — as long as you pick an algorithm that respects `radius` (so `PCF`/`VSM`, not `PCFSoft`).


## `intensity` and `bias`

In Three.js, `directionalLight.shadow.intensity = 1` sets full shadow darkness (the default value), while `directionalLight.shadow.bias = 0.002` adjusts the shadow map offset to prevent rendering artifacts like shadow acne, though the default bias is typically `0` or negative values (e.g., `-0.0005` / `-0.002`). 

Property Breakdown

- **`intensity`**: Controls the darkness/strength of the shadow map. Valid range is `[0, 1]`, with `1` being fully opaque/dark.

- **`bias`**: Shifts the shadow calculation depth to resolve self-shadowing acne or Peter-panning issues. 

Quick Tips for Configuration

- **Shadow Acne Fix**: If you see striped patterns or dark speckles on surfaces, tweak `bias` closer to small negative values like `-0.0001` or `-0.002` rather than positive numbers.

- **Normal Bias**: Consider using `directionalLight.shadow.normalBias` alongside `bias` to clean up curved or angled geometry artifacts

## Code

in repo - `apps/13_2_shadow_map_optim_two`

```ts
import * as THREE from 'three/webgpu';
import { OrbitControls } from 'three/addons/controls/OrbitControls.js';
import GUI from 'lil-gui';

const renderer = new THREE.WebGPURenderer({ canvas });
await renderer.init();
renderer.shadowMap.enabled = true;
renderer.shadowMap.type = THREE.PCFSoftShadowMap; // pick the algorithm

const scene = new THREE.Scene();
const gui = new GUI();

// Light with shadow tuning
const directionalLight = new THREE.DirectionalLight(0xffffff, 1.5);
directionalLight.position.set(2, 2, -1);
directionalLight.castShadow = true;
scene.add(directionalLight);

directionalLight.shadow.mapSize.width = 1024;
directionalLight.shadow.mapSize.height = 1024;
directionalLight.shadow.camera.near = 1;
directionalLight.shadow.camera.far = 6;
directionalLight.shadow.camera.top = 2;
directionalLight.shadow.camera.right = 2;
directionalLight.shadow.camera.bottom = -2;
directionalLight.shadow.camera.left = -2;

directionalLight.shadow.radius = 10; // blur width (ignored by PCFSoft!)

// Objects
const material = new THREE.MeshStandardMaterial({ roughness: 0.7 });
const sphere = new THREE.Mesh(new THREE.SphereGeometry(0.5, 32, 32), material);
sphere.castShadow = true;
const floor = new THREE.Mesh(new THREE.PlaneGeometry(5, 5), material);
floor.receiveShadow = true;
floor.rotation.x = -Math.PI / 2;
floor.position.y = -0.5;
scene.add(sphere, floor);

// GUI: flip the algorithm and sweep the blur live
gui.add(renderer.shadowMap, 'type', {
  Basic: THREE.BasicShadowMap,
  PCF: THREE.PCFShadowMap,
  PCFSoft: THREE.PCFSoftShadowMap,
  VSM: THREE.VSMShadowMap,
}).name('shadowMap.type');
gui.add(directionalLight.shadow, 'radius').min(-30).max(30).step(0.001)
  .name('shadow.radius (blur)');

// Camera + controls
const camera = new THREE.PerspectiveCamera(75, innerWidth / innerHeight, 0.1, 100);
camera.position.set(2, 1, 1);
const controls = new OrbitControls(camera, canvas);
controls.enableDamping = true;

renderer.setAnimationLoop(() => {
  controls.update();
  renderer.render(scene, camera);
});
```

## Gotchas

- **`radius` has no effect on `PCFSoftShadowMap`.** This is the headline trap. If you set a `radius` and the shadow isn't getting any softer, the first suspect is that `shadowMap.type` is `PCFSoftShadowMap` (this app's default). Switch to `PCF` (or `VSM`) if you want to control the blur width.
- **`radius` is a *blur width*, not the same as `bias`.** `radius` spreads the sampling kernel for soft edges; `bias` is a separate hack that fights shadow-peter-panning / acne by nudging the depth comparison. Don't reach for `radius` expecting it to fix z-fighting.
- **`VSMShadowMap` looks wrong before it looks right.** It smears the shadow map's moments, so you get smooth softness but can see **light bleeding** (softness creeping into fully-lit regions). If VSM looks broken, that's expected — it's the "more constraints, unexpected results" option in the list.
- **`BasicShadowMap` ignores the blur entirely.** It does no filtering, so `radius` does nothing there either — you get hard, jagged drop-shadow edges but the best performance.
- **Try `radius` with `level` too** — `shadow.radius` isn't the only knob; in newer three the shadow API exposes `radius`, `intensity`/`bias` etc. Tune one at a time so you know which knob changed the look.
- From part one, still true here: the GUI's `shadow.camera` tweaks each need `shadow.camera.updateProjectionMatrix()` and `CameraHelper.update()` after change, or the frustum won't actually change in the shadow pass.
- **`directionalLight.lookAt(center)` still doesn't rotate the shadow as you'd expect** — the shadow frustum orientation is pinned to the light's position/target, not an independent rotation. The disabled GUI label calls this out.
- **The `ArrowHelper` direction is computed once at creation.** Move the light and the arrow stays pointing where it was when you created it. Recreate or update it per frame for a dynamic arrow.

## Revisit

- **Learn the WebGPU-native path for `radius`.** The newest `three/webgpu` `LightShadow` accepts a `NumericValueNode` for `radius`, so the blur can be animated or driven by a node graph. Worth revisiting how that differs from the classic hard-coded `number` seen here.
- **Why `PCFSoftShadowMap` ignores `radius`.** Understand the fixed 9-tap kernel inside PCFSoft — once you see it's hard-coded, the "why doesn't my slider work" question answers itself. Dig into how PCFSoft vs PCF really sample the depth texture.
- **Reconsider `VSMShadowMap` for scenes that tolerate light bleeding.** VSM's moment filtering blurs very cheaply and is the common basis for *cascaded* shadow maps (CSM) in large scenes. Revisit whether its artifacts are acceptable for your content.
- **Upcoming:** the README notes the *next* lesson moves away from directionals onto **SpotLight** shadows, still with the same `renderer.shadowMap` knob — expect the spotlight's conical shadow frustum and its own tuning (see [[12.6_spot-light]] for the light itself).
- Refresh the cost/quality model from [[13.1_shadow-map-optimization-part-one]]: `mapSize` / amplitude sets the resolution budget, and this lesson's algorithm + `radius` set the edge softness. Eventually combine per-light tuning with one global algorithm choice.

## Outdated

approach is valid

Filtering via `radius` and the four `shadowMap.type` algorithms exist unchanged in both WebGL and WebGPU. **This app already runs on `three/webgpu` + `WebGPURenderer` (WebGPU path) ⚡** — the modern rendering route. The one forward-looking difference is that in the WebGPU path `radius` can be a `NumericValueNode`, enabling richer/animated blur than the simple static number used here.
