## Concept

In [16.0_imported-models-intro](16.0_imported-models-intro.md) and [16.1_gltf-flavor-comparison](16.1_gltf-flavor-comparison.md) we looked at the different flavors a glTF file can ship in (plain, embedded, binary, quantized). This lesson goes one level deeper into the geometry data itself: **Draco compression**.

### What is Draco?

[Draco](https://google.github.io/draco/) is an **open-source library for compressing and decompressing 3D geometric meshes and point clouds**, developed by Google and released under the **Apache License 2.0**. It is not a model *format* — it is a *codec*. You point it at the buffered geometry data of a mesh and it produces a much smaller byte stream; a matching decoder turns that stream back into positions, normals, colors and UVs at load time.

The sizes speak for themselves. The Duck model's geometry in this repo ([16.1_gltf-flavor-comparison](16.1_gltf-flavor-comparison.md) compared flavors):

| Variant | Geometry bytes |
|---|---|
| glTF (plain `.bin`) | **102,040 B** |
| glTF-Quantized `.bin` | 63,656 B |
| **glTF-Draco `.bin`** | **10,368 B** |

Draco gets the Duck's geometry to roughly **one tenth** of the plain binary — about 6× smaller than quantized. That is the core appeal: smaller download, faster over the network.

### Compression happens on the buffer data — not the whole file

Draco does **not** compress the entire glTF file. It operates on the **buffer data — typically the geometry**. Position, normal, texture-coordinate and index arrays are the expensive part of most models, and that is what gets encoded. Textures, materials, animations, node transforms etc. stay untouched in the `.gltf`/`.bin`/`.glb` as usual.

You can see this if you open `public/models/Duck/glTF-Draco/Duck.gltf` in a text editor: most of the file is a normal glTF JSON (assets, scenes, nodes, cameras, materials, textures), but the mesh primitive carries an extension telling the loader geometry is stored compressed:

```json
"extensions": {
  "KHR_draco_mesh_compression": {
    "bufferView": 0,
    "attributes": {
      "NORMAL": 0,
      "POSITION": 1,
      "TEXCOORD_0": 2
    }
  }
}
```

and at the bottom of the file `"extensionsUsed"` / `"extensionsRequired"` both list `KHR_draco_mesh_compression`. The `extensionsRequired` entry is why loading this file without a Draco decoder **fails** — the format itself declares that a decoder is mandatory.

### Draco vs glTF — not the same thing

A confusion worth clearing up right away:

- **glTF** is a *format* that standardizes how the whole scene is described (JSON scene graph + binary buffer + textures).
- **Draco** is a *compression algorithm* for mesh geometry, that glTF supports via the `KHR_draco_mesh_compression` extension.

Draco is **not exclusive to glTF** — it can compress mesh data outside glTF too — but the two became popular at the same time, and glTF exporters (Khronos, Blender, glTF Transform, etc.) adopted Draco support quickly, which is why the two are so often mentioned together.

### How loading works: GLTFLoader + DRACOLoader + decoder

The default `GLTFLoader` (from earlier lessons) can read plain glTF. To read a Draco-compressed glTF you need to wire three pieces together:

1. **`DRACOLoader`** — the Three.js loader class that knows how to talk to the decoder.
2. **The decoder itself** (`.wasm` + `.js` wrapper) — the actual piece of software that decompresses geometry on the user's machine. Three.js ships it in `node_modules/three/examples/jsm/libs/draco/` — three files per Table 1 of the decoder README:
   - `draco_decoder.js` — Emscripten-compiled decoder (JS), works anywhere;
   - `draco_decoder.wasm` — the **WebAssembly** decoder, faster, for modern browsers/devices;
   - `draco_wasm_wrapper.js` — JS wrapper for the WASM decoder.
   - Each comes in two builds: the stable **default** build, and a **glTF** build (`draco/gltf/`) targeted at the `KHR_draco_mesh_compression` extension. Either variation works with `DRACOLoader`.

   Three.js does not bundle the decoder into your app automatically — the README notes say to **copy the entire `node_modules/three/examples/jsm/libs/draco/` folder into your `public/` folder**, which is exactly what this app does (`public/draco/`). Because it lives in `public/`, Vite serves it statically and the browser can fetch the decoder `.wasm` on demand.

3. **The decoder path** — `DRACOLoader` must be told *where* the decoder files live, via `setDecoderPath()`.

```ts
const dracoLoader = new DRACOLoader();
dracoLoader.setDecoderPath('/draco/');

const gltfLoader = new GLTFLoader(modelLoadingManager);
gltfLoader.setDRACOLoader(dracoLoader);

const duckModel = await gltfLoader.loadAsync('/models/Duck/glTF-Draco/Duck.gltf');
```

Setting the decoder path is optional in the sense that loading *works* (in dev) without it — but **much better to do**: without it the loader falls back to fetching the decoder from unpkg/CDN, which is slower, needs network access, and won't work offline. Point it at your own `/public/draco/` copy.

The `gltfLoader.setDRACOLoader(dracoLoader)` call is the glue — for every mesh whose primitive declares `KHR_draco_mesh_compression`, GLTFLoader hands the `bufferView` to `DRACOLoader`, which invokes the decoder, and only then builds Three.js attributes. The code comment notes you can also assign `gltfLoader.dracoLoader = dracoLoader` directly — both work (the commented-out line) — but `setDRACOLoader()` is the intended API.

### The decoder loads only when needed

A nice property: using `DRACOLoader` does **not** force your whole project to decode everything. Non-compressed glTF files still load with `GLTFLoader` as before — the decoder is **only invoked when a mesh actually declares Draco compression**. Mixed scenes (some Draco, some plain) work with the same loader.

### Draco is not free — when should you use it?

Smaller file size sounds like a win every time, but the README's main warning is that **Draco is not a win-win situation**. The trade-offs, per download:

- **The user has to load extra code**: `DRACOLoader` (a few KB of Three.js) *plus* the decoder (the `.wasm`, about 100–150 KB) even if your model only has one small compressed mesh.
- **Decoding takes time and CPU**: „It also takes time and resources for your computer to decode a compressed file." The decompression happens *on the client*, after download. For small meshes the decode cost can exceed the download savings.
- **Loading is no longer instant-on-parse**: GLTFLoader must wait for the decoder (WASM instantiation) the first time, then for each mesh's decode.

So the practical rule of thumb (and the README's closing question — "in terms of file size, where would you suggest we use Draco?"):

- **Use Draco** mainly when the geometry is the dominant cost of the file — **big, dense meshes** (high-poly models, scanned or CAD-ish assets, point-cloud-like data) where a 10× geometry reduction beats the decoder overhead.
- **Skip it** for tiny or low-poly models where the extra decoder download + decode time outweighs what compression saves.

Adapt per project: measure both file size *and* load behavior (see 16.0's own advice: "question the data you need, the weight of the file, how much time to decompress it").

## Code

in repo — `apps/16_3_imported_models_draco`

```ts
import { GLTFLoader } from 'three/addons/loaders/GLTFLoader.js';
import { DRACOLoader } from 'three/addons/loaders/DRACOLoader.js';

// 1. Instantiate the DRACOLoader
const dracoLoader = new DRACOLoader();

// 2. Point it at your own decoder files (copied from
//    node_modules/three/examples/jsm/libs/draco/ into /public/draco/)
dracoLoader.setDecoderPath('/draco/');

// 3. Hand the DRACOLoader to GLTFLoader
const modelLoadingManager = new THREE.LoadingManager();
const gltfLoader = new GLTFLoader(modelLoadingManager);
gltfLoader.setDRACOLoader(dracoLoader);

// 4. Load the Draco-compressed model — the decoder is fetched and
//    invoked automatically, only because Duck.gltf declares
//    KHR_draco_mesh_compression
const duckModel = await gltfLoader.loadAsync('/models/Duck/glTF-Draco/Duck.gltf');
scene.add(duckModel.scene);
```

> ⚠️ Without `setDRACOLoader()` (or assigning `gltfLoader.dracoLoader = dracoLoader`) loading `Duck.gltf` throws — the file declares `extensionsRequired: ["KHR_draco_mesh_compression"]`, so the loader refuses to guess.

## Gotchas

- **Forgetting the `DRACOLoader` is a hard fail, not a fallback.** A Draco file lists the extension under `extensionsRequired` (not just `extensionsUsed`), so `GLTFLoader` **errors out** if no Draco decoder is attached. The `// EXPLAIN:` comment is explicit: "you would get an error if you wouldn't use DracoLoader".
- **`setDecoderPath()` matters — don't rely on the fallback.** Without it loading may still work in dev because the loader pulls the decoder from a CDN, but that's slow, non-deterministic and offline-hostile. Copy `node_modules/three/examples/jsm/libs/draco/` into `public/` and set `/draco/` yourself (the README's explicit instruction). The trailing slash matters — it's a *folder* path.
- **Draco compresses geometry, not textures.** A Draco `.bin` can be ~10× smaller while the scene is still heavy because of PNG textures. If total file size is the goal, pair Draco with a texture codec (see [16.2_multi-mesh-scene-graph](16.2_multi-mesh-scene-graph.md)'s Revisit about `KTX2Loader` / Basis Universal).
- **Decoding is your user's CPU.** The compressed geometry saves download bytes but the decode happens in the browser after the fetch. On weak devices a giant Draco mesh can *feel* slower than its uncompressed twin despite the smaller file.
- **The installer/wrapper split:** `public/draco/` has both a `.js` and a `.wasm` decoder plus the `draco_wasm_wrapper.js`; the DRACOLoader picks the right one for the browser. Don't delete the wrapper thinking the `.wasm` alone suffices — and note the `draco/gltf/` subfolder holds the glTF-tuned decoder builds, while `draco/` root holds the default/master ones.

## Revisit

- **Draco and KTX2 can be combined on one model** — compress geometry (Draco) *and* textures (Basis Universal / `.ktx2`) — the dual optimization the Flight Helmet folder already hints at (see [16.2_multi-mesh-scene-graph](16.2_multi-mesh-scene-graph.md)). The natural next experiment: same model, plain vs quantized vs Draco, measuring both *file size* and *time-to-first-frame*.
- **The README's open question — "where would you suggest we use Draco?"** — is answered only with the rule of thumb above. To firm it up empirically: load the same Duck from `glTF/`, `glTF-Quantized/` and `glTF-Draco/` (all present in `public/models/Duck/`) in one app, log `performance.now()` deltas for each, and reuse the `modelLoadingManager.onStart/onProgress/onLoad` logs already wired in this app.
- **glTF-Quantized kept quiet** — quantized variants trade a little precision for smaller floats without a decoder. Worth understanding how it stacks against Draco when you care about *precision* (morph targets, authored normals), where lossy Draco can degrade quality.
- **Decoding in a Web Worker** — the README highlights "the decoder is also available in Web Assembly, and it can run in a worker to improve performances significantly". Three.js leaves worker orchestration to you — revisit how to decode off the main thread for big models.
- **`extensionsUsed` vs `extensionsRequired`** — the difference determines whether a loader may *optionally* skip an extension or must reject the file. Easy to forget which is which when authoring/exporting models.
