## Concept

This is the second meaty step in the scroll-based series: it fills the previously empty scene with **distinct 3D objects**, stacks them **vertically** (so each one lines up with an HTML section), and — the new idea — **hooks the scroll value into the animation loop** to drive the camera's `y` position. Rotating the objects permanently while the page scrolls gives the classic "portfolio" feel where 3D content floats behind scrolling text.

### Building the scene: three toon objects

The scene gets green, not a single torus. Three primitive meshes — a **torus**, a **cone**, and a **torus knot** — each with its own `MeshToonMaterial`, its own color, and the shared `gradientMap` (the `three-colors.jpg` gradient used with `magFilter = THREE.NearestFilter` for crisp cartoon bands). Because these materials are **lit**, a `DirectionalLight` is required or they render black:

```ts
const directionalLight = new THREE.DirectionalLight();
directionalLight.intensity = 1 * Math.PI;
scene.add(directionalLight);
```

### Positioning objects so they're equally spaced

The core trick of this lesson is placing three objects along the vertical axis so they are **evenly separated** and each would line up with one of the HTML sections. Instead of hard-coding three magic numbers, the app uses a shared `objectsDistance` value multiplied by an index:

```ts
torusMesh.position.y = -debugObject.objectsDistance * 0; // 0
coneMesh.position.y  = -debugObject.objectsDistance * 1; // -4
knotMesh.position.y  = -debugObject.objectsDistance * 2; // -8
```

With `objectsDistance = 4`, the objects sit at `y = 0`, `y = -4`, and `y = -8`. The torus starts centered in view; the cone and knot hang below the camera's initial sight line. Because the camera later scrolls *down* negative `y`, each object gets scrolled into frame one after another.

Two things make the negative `y` meaningful:

1. **Vertical FOV is preserved.** From lesson 15.1: `PerspectiveCamera.fov` is measured **vertically**. If you stack objects straight down and move the camera straight down, what you see up/down is consistent across screens and resizes — the objects don't "pop" out of view on different viewports. That's exactly why all the movement here is along `y`.
2. **A single knob spaces everything.** Changing `debugObject.objectsDistance` re-spaces all three meshes at once, and this value will be reused in later lessons — that's why it lives in `debugObject`. You can tweak the same `y` values live from the GUI per mesh.

### Getting the scroll value

The browser tracks how far the page has been scrolled in `window.scrollY`. The app captures it in a variable **mutable in the animation loop**, and updates it on any scroll event:

```ts
let scrollY = window.scrollY;

window.addEventListener('scroll', () => {
	scrollY = window.scrollY;
});
```

A regular `let` variable (not `const`) is the point: it's read every frame in `tick()`, so it has to be reassigned by the listener.

### Driving the camera with scroll

The motivating reason to compute scroll is to move the camera in sync with the page. Here it's a **first-pass naive mapping** — deliberately simplistic, explicitly marked `// EXPLAIN` in the code as a stepping-stone to the "final solution" in the next lesson:

```ts
camera.position.y = -scrollY * 0.01;
```

The `0.01` factor (a manually-tuned ratio) is what makes the scroll meaningful. Without some multiplier, **100 pixel of scroll would move the camera by 100 pixels**, which would barely shift the view. By multiplying, `scrollY` in pixels becomes a movement amounts scaled to the scene's units, and the `-` sign makes the camera go **down** as the user scrolls **down**.

### Permanent rotation without a controls update

Because there's **no OrbitControls** (the design principle from 15.0 — the camera is programmatic here), the objects get a constant rotation in the animation loop instead. Each of the three meshes is collected into `selectionMeshes` so one `for...of` handles all of them:

```ts
const selectionMeshes = [torusMesh, coneMesh, knotMesh];

// in tick():
for (const mesh of selectionMeshes) {
	mesh.rotation.x = elapsedTime * 0.1;
	mesh.rotation.y = elapsedTime * 0.12;
}
```

`elapsedTime` comes from the `THREE.Timer()` in the `WebGPURenderer.setAnimationLoop` (the same pattern from the earlier animation lessons), so the rotation is smoothed over real time rather than per-frame. The slightly different rates (`0.1` vs `0.12`) stop the objects from looking like rigidly attached clones.

## Code

```ts
import * as THREE from 'three/webgpu';
import GUI from 'lil-gui';
import { getRequiredElement } from './util';

const canvas = getRequiredElement<HTMLCanvasElement>('canvas#tride');
const gui = new GUI({ width: 250, title: 'Tweaks' });

const debugObject = {
	torusColor: new THREE.Color('#a54841'),
	coneColor: new THREE.Color('#2d3e63'),
	knotColor: new THREE.Color('#a259b3'),
	objectsDistance: 4,
};

const sizes = { width: window.innerWidth, height: window.innerHeight };
let scrollY = window.scrollY;

window.addEventListener('scroll', () => {
	scrollY = window.scrollY;
});

async function init() {
	const scene = new THREE.Scene();

	const renderer = new THREE.WebGPURenderer({ canvas });
	await renderer.init();

	// gradient map for toon shading
	const gradientTexture = new THREE.TextureLoader().load('textures/gradients/three-colors.jpg');
	gradientTexture.magFilter = THREE.NearestFilter; // hard bands

	// light required by MeshToonMaterial
	const light = new THREE.DirectionalLight();
	light.intensity = 1 * Math.PI;
	scene.add(light);

	// three toon objects, spaced by objectsDistance
	const torus = new THREE.Mesh(
		new THREE.TorusGeometry(1, 0.4, 16, 60),
		new THREE.MeshToonMaterial({ color: debugObject.torusColor, gradientMap: gradientTexture }),
	);
	const cone = new THREE.Mesh(
		new THREE.ConeGeometry(1, 2, 32),
		new THREE.MeshToonMaterial({ color: debugObject.coneColor, gradientMap: gradientTexture }),
	);
	const knot = new THREE.Mesh(
		new THREE.TorusKnotGeometry(0.8, 0.35, 100, 16),
		new THREE.MeshToonMaterial({ color: debugObject.knotColor, gradientMap: gradientTexture }),
	);

	torus.position.y = -debugObject.objectsDistance * 0;
	cone.position.y  = -debugObject.objectsDistance * 1;
	knot.position.y  = -debugObject.objectsDistance * 2;
	scene.add(torus, cone, knot);

	const selectionMeshes = [torus, cone, knot];

	const camera = new THREE.PerspectiveCamera(75, sizes.width / sizes.height, 0.1, 100);
	camera.position.z = 3;
	scene.add(camera);

	// per-mesh GUI folders (color + x/y/z sliders)
	// ...

	renderer.setPixelRatio(Math.min(window.devicePixelRatio, 2));
	renderer.setSize(sizes.width, sizes.height);

	const timer = new THREE.Timer();
	renderer.setAnimationLoop(tick);

	function tick(timestamp: number) {
		timer.update(timestamp);
		const elapsedTime = timer.getElapsed();

		camera.position.y = -scrollY * 0.01;   // scroll drives camera

		for (const mesh of selectionMeshes) {
			mesh.rotation.x = elapsedTime * 0.1;
			mesh.rotation.y = elapsedTime * 0.12;
		}

		renderer.render(scene, camera);
	}
}

await init();
```

## Gotchas

- **`window.scrollY` must be a `let`, not `const`** — the scroll listener reassigns it each event, and the animation loop reads the current value every frame. Reading a `const` would freeze the camera.
- **Toon materials need light** — same trap as 15.1: without the `DirectionalLight`, all three meshes render black.
- **Forgetting `NearestFilter`** on the gradient map blurs the toon cells into muddy gradients instead of crisp cartoon bands.
- **The `0.01` multiplier is arbitrary** — it's a tuning constant that couples scroll pixels to scene units. It's a naive first pass, deliberately; the "correct" mapping is the subject of the next lesson. Don't treat it as a magic value.
- **Vertical axis is your friend** — objects are spaced along `y` because the camera (and the scene's vertical FOV) stays consistent with resize. Placing them along `z` would make spacing depend on the window shape.

## Revisit

- The `camera.position.y = -scrollY * 0.01` mapping is explicitly a placeholder. Revisit it in the next lesson where the scroll will map cleanly and proportionally to the total scene height — likely using the size of the scrollable content rather than a hard-coded factor.
- The rotation rates `0.1` and `0.12` were chosen for variety by eye. Try tying rotation rates to something meaningful (e.g. scroll progress) instead of just `elapsedTime`.
- The per-mesh GUI folders (position `x/y/z` + color) duplicate the shared `objectsDistance` logic; reconsider whether to also expose `objectsDistance` directly for live spacing tweaks.
- Compare the `data-attribute`/sections-based approaches for sync scroll vs the naive `scrollY * factor` here once the next lesson shows the cleaner method.

## Outdated

approach is valid

The scroll-driven camera technique is a current, widely used pattern for Three.js portfolio/landing pages. This project uses `three/webgpu` with `WebGPURenderer` (needs `await renderer.init()`), which is the modern WebGPU path. A more robust production alternative for scroll → scene mapping is mapping the scroll to an explicit camera path through the scene's vertical extent with a smoothing factor, and `MeshToonMaterial` + `gradientMap` + `NearestFilter` remains the standard crisp-cartoon look.
