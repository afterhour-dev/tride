## Concept

When using a GUI like lil-gui to tweak geometry parameters (e.g. subdivision count), you might be tempted to recreate geometry on every slider movement. But geometry creation is **expensive** — it allocates vertex buffers, index buffers, and uploads data to the GPU. Doing this continuously as a range slider moves creates and destroys geometry dozens of times per second, causing massive CPU/GPU overhead.

The solution is to use **`onFinishChange`** instead of `onChange`. While `onChange` fires on every slider tick, `onFinishChange` fires only once — when the user releases the slider. This way geometry is recreated only when the final value is settled.

There are also two important cleanup steps:
1. **Dispose the old geometry** before creating the new one. Three.js geometries hold GPU resources; forgetting to `.dispose()` them causes a memory leak.
2. **Reassign the geometry reference** to keep it in sync. Since we use `let boxGeometry` (not `const`), we can reassign `boxGeometry = boxMesh.geometry` after the new geometry is assigned to the mesh, so the variable always points to the active geometry.

### Why `let` instead of `const` for geometry?

The variable holding geometry must be declared with `let` because we reassign it in the `onFinishChange` callback. A `const` reference would prevent reassignment, forcing us to use a separate variable or always reference `boxMesh.geometry` directly.

## Code

in repo - `apps/7_gui_geometry_tweak`

```ts
import * as THREE from 'three/webgpu';
import { OrbitControls } from 'three/examples/jsm/Addons.js';
import GUI from 'lil-gui';

const canvas = document.querySelector<HTMLCanvasElement>('canvas#tride')!;
const gui = new GUI();

const debugObject = { subdivisions: 2 };

let boxGeometry = new THREE.BoxGeometry(1, 1, 1, 2, 2, 2);
const material = new THREE.MeshBasicMaterial({ color: '#7b6fc9', wireframe: true });
const boxMesh = new THREE.Mesh(boxGeometry, material);

gui
  .add(debugObject, 'subdivisions')
  .min(1)
  .max(20)
  .step(1)
  .onFinishChange((subdivs: number) => {
    boxGeometry.dispose();
    boxMesh.geometry = new THREE.BoxGeometry(1, 1, 1, subdivs, subdivs, subdivs);
    boxGeometry = boxMesh.geometry;
  });
```

## Gotchas

- **Forgetting to dispose old geometry** — every time you create a new `BoxGeometry` (or any geometry), the old one holds onto GPU buffers. Without `.dispose()`, those buffers accumulate and eat memory. Always dispose before reassigning.
- **Using `onChange` instead of `onFinishChange`** — `onChange` fires on every slider tick. With a range slider going from 1 to 20, that's potentially 19 geometry disposals + creations per drag. Use `onFinishChange` for expensive operations like geometry recreation.
- **Not reassigning the geometry reference** — after `boxMesh.geometry = new THREE.BoxGeometry(...)`, the `boxGeometry` variable still points to the old (now disposed) geometry. Reassign it to keep the reference valid.

## Revisit

- Memory management patterns in Three.js — `.dispose()` applies to geometries, materials, and textures. Get into the habit of tracking what needs disposal.
- Performance profiling: use the browser's Performance tab or Three.js's built-in `renderer.info` to monitor draw calls and geometry count when tweaking.
- lil-gui's `onChange` vs `onFinishChange` — understand when each is appropriate (cheap updates like position/rotation can use `onChange`; expensive ones like geometry/material recreation should use `onFinishChange`).
