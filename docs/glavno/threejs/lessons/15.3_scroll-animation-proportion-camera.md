# 15.3 Scroll Based Animation — Proportion & Camera Position

This lesson follows up on `15.2_scroll-animation-positions-rotation`. The goal is the same: integrate Three.js properly with HTML content by driving the **camera** from the page's **scroll position**. Everything lives in `apps/15_3_scroll_based_animation_setup3`.

The hardest mental step here isn't the Three.js — it's deciding **which number to multiply the scroll value by** so that the three objects line up with the three HTML sections as you scroll. The whole lesson is the attempt and reasoning behind that proportion, worked out in the comments in `src/main.ts`.

## Concept

### The setup

- `index.html` has **3 `<section class="sekcija">`**, each **`100vh`** tall.
- The `<canvas id="tride">` is `position: fixed`, so it stays glued to the screen while the HTML sections scroll underneath it (`src/style.css`).
- The scene has **3 toon meshes**: a torus, a cone, and a torus knot. They are spaced **one `objectsDistance` apart** (`debugObject.objectsDistance = 4`):

```ts
torusMesh.position.y = -debugObject.objectsDistance * 0; // 0
coneMesh.position.y  = -debugObject.objectsDistance * 1; // -4
knotMesh.position.y  = -debugObject.objectsDistance * 2; // -8
```

- The camera stays more or less pointing forward; it's the **camera's Y position** that moves down through the three objects as the user scrolls.

### The core idea: a proportion, not an absolute number

You want this relationship: **one scroll step is equivalent to one `objectsDistance` step**. The user's own comment spells it out perfectly:

```
scrollY / sizes.height = camera.position.y / debugObject.objectsDistance
```

Read it as: *"how far I've scrolled (in viewport-heights) is proportional to how far the camera should have traveled down (in objectsDistance steps)."* Each section is exactly one viewport tall, and each object is exactly one `objectsDistance` apart — so the two maps share the same scale. Rearranging for `camera.position.y`:

```
camera.position.y = -(scrollY * debugObject.objectsDistance) / sizes.height
```

The leading `-` appears because `scrollY` grows **down** (positive) while the meshes sit at **negative** Y.

### The two candidate solutions (this is what's emphasized in the code)

In `src/main.ts` the user worked through **two** possible formulas and left both commented:

**Solution A — the one picked** (`main.ts`):

```ts
camera.position.y = -(scrollY * debugObject.objectsDistance) / sizes.height;
```

**Solution B — the one given up on** (`main.ts`, commented out):

```ts
camera.position.y =
	-(
		(3 * debugObject.objectsDistance -
			debugObject.objectsDistance) *
		scrollY
	) /
	(document.body.scrollHeight - sizes.height);
```

### Which one is better, and why

Mathematically, for **exactly 3 sections** they produce the **same** result. Proof with `objectsDistance = 4`, page height = `3 * 100vh`:

- Max `scrollY = document.body.scrollHeight - sizes.height = 2 * height` (you can't scroll the last 100vh into view).
- **Solution A** at the bottom: `-(2h * 4)/h = -8`.
- **Solution B** at the bottom: `-((3*4 - 4) * 2h)/(2h) = -(8 * 2h)/(2h) = -8`.

Both land the camera at `y = -8`, exactly on top of the knot. So for this fixed page **neither is "mathematically more correct."** The difference is **generality and readability**:

- **Solution B** is *over-engineered* (the comment at `main.ts` admits: *"for some stupid reason I know that I overcomplicated it in here"*). It hardcodes the number of sections (`3 *`) and the total travel distance (`3*objectsDistance - objectsDistance` = from first torus to last knot). If you ever add a fourth section, this map breaks — it no longer matches the page.
- **Solution A** encodes only the **per-viewport → per-`objectsDistance` proportion**. It doesn't care how many sections exist. Each section is one viewport tall and the camera should travel one `objectsDistance` per section, so the scale is uniform and the number of sections cancels out. That's why it's the *better* choice: **simpler and robust to more content.**

The moral: prefer expressing the **proportion per unit of scroll** over hard-coding the **total travel distance**. Let the page's own section count emerge naturally instead of baking it into the formula.

## Code

in repo — `apps/15_3_scroll_based_animation_setup3`

```ts
// --- capture scroll, in pixels -------------------------------------------------
let scrollY = window.scrollY;
window.addEventListener('scroll', () => {
	scrollY = window.scrollY;
});

// --- in the animation tick -----------------------------------------------------
function tick(timestamp: number) {
	timer.update(timestamp);
	const elapsedTime = timer.getElapsed();

	// the proportional map — the whole lesson
	camera.position.y = -(scrollY * debugObject.objectsDistance) / sizes.height;

	for (const mesh of selectionMeshes) {
		mesh.rotation.x = elapsedTime * 0.1;
		mesh.rotation.y = elapsedTime * 0.12;
	}

	renderer.render(scene, camera);
}

renderer.setAnimationLoop(tick);
```

(Truncated for focus — the full file also builds the meshes, lights, GUI and resize/fullscreen handlers.)

## Gotchas

- **Forget `-` → camera moves the wrong way.** `scrollY` is positive and grows up as you scroll downscreen. The meshes live at negative Y. Without the `-`, the camera travels up into empty space. See `main.ts` + the `//` in `position.y`.
- **The page has to be scrollable at all.** The canvas is `position: fixed`, but the HTML sections still need `overflow` enabled on `html, body`. The commented-out `/* overflow: hidden; */` in `style.css` is asking *why* it must stay commented — because `overflow: hidden` kills the scroll entirely.
- **`document.body.scrollHeight` is a trap as a *parameterized* formula.** It's fine as a *constant end-of-page* check, but if you bake it into the per-frame camera math (solution B), you hard-code the page layout.
- **Don't drive camera Y with a raw fraction of `elapsedTime`.** Keep the *scroll-driven* camera motion separate from the *time-driven* mesh rotation (rotation is `elapsedTime * 0.1`; the camera is `scrollY`-proportional). Two different clocks, two different jobs.
- **`scrollY` must be read fresh on each scroll**, not captured once. The listener reassigns `window.scrollY` on every `scroll` event; the tick reads the latest value.

## Revisit

- **Third solution worth probing**: instead of `scrollY / sizes.height`, some projects divide by `document.body.scrollHeight - sizes.height` to get a **0..1** progress and then multiply by the full travel. Try re-doing the mapping with a normalized progress value and see how it compares to solution A.
- **The next lesson** is the continuation ("Continuation of project will be on next lesson") — likely adding object parallax or scroll triggers.
- Re-spell the proportion **from scratch** without copying, from the plain sentence: *"camera moves one objectsDistance for each viewport scrolled."* See if you still derive the same formula.
- **The canvas is fixed; nothing scrolls with it.** When you later overlay text or other DOM on top of the Three.js content, remember the canvas z-layering vs. the sections.

## Outdated

approach is valid

This project already runs on the modern path — it uses `three/webgpu` and a `WebGPURenderer` (`src/main.ts`), which is the forward-looking replacement for `WebGLRenderer`. No stale WebGL-only approach to flag here. The scroll-proportion concept (mapping scroll to camera translation) is renderer-agnostic and applies unchanged to WebGPU.
