# RectAreaLight

Exploring `RectAreaLight` — the three.js light that behaves like the big soft rectangles you see on a photoshoot set: a large, flat, glowing panel that throws a wide, directionally-influenced wash of light rather than a point or a uniform sun.

## Concept

A `RectAreaLight` is a **planar (flat, rectangle-shaped) area light** — picture a studio softbox or a glowing light panel. It sits at a position in the scene and points in a direction, and its light comes from the whole rectangular surface at once, not from a single point.

Conceptually it's a **mix between a directional light and a diffuse/area light**:

- Like a `DirectionalLight`, it shines **in a specific direction** — it has an orientation you can aim, and the "look direction" matters.
- Unlike a directional light (whose rays are perfectly parallel), it's a **finite, sized surface**, so the light is soft and spread-out, and it **mixes with Diffuse Lambertian shading** on the surfaces it hits. The result is a soft, realistic, area-lit look — exactly what makes product/portrait photoshoot lighting read as "soft."

That combination is what makes it distinctive: you get controlled, directional-but-soft illumination, closer to real-world large light sources than any of the previous light types.

### The constructor and its properties

```ts
new THREE.RectAreaLight(color, intensity, width, height)
```

- **`color`** — the light's color (default `0xffffff`). Here `0x4e00ff`, a purple.
- **`intensity`** — the brightness (default `1`). Here `2`.
- **`width`** — the width of the light's rectangle (default `10`). Here `1`.
- **`height`** — the height of the rectangle (default `10`). Here `1`.

You can pass all four at construction, or create an empty light and assign properties afterwards (as the app does) — convenient when you want to expose them to the lil-gui panel:

```ts
const rectAreaLight = new THREE.RectAreaLight();
rectAreaLight.color = new THREE.Color(0x4e00ff);
rectAreaLight.intensity = 2;
rectAreaLight.width = 1;
rectAreaLight.height = 1;
rectAreaLight.position.set(-1.5, 0, 1.5);
scene.add(rectAreaLight);
```

### What intensity range is allowed?

There is **no hard "allowed" clamp** — `intensity` accepts any non-negative number and the GUI exposure in the app is just `0–10`. What changes is how *much* you need for a good result:

- In **physically-correct lighting** (the default with `WebGPURenderer` / `useLegacyLights = false`), `intensity` is treated as a physical luminous-intensity value and behaves differently from the legacy "multiply by 1" world. Area lights measured this way can need **values well above `1`** to read as bright — that's why this app starts at `intensity = 2` and the GUI lets you go up to `10`.
- In **legacy lights mode** (older setups, `useLegacyLights = true`), intensity was an arbitrary brightness multiplier and `1` already looked sensible.

So: don't reach for a "valid range" from docs — treat the **renderer's light mode** as the real constraint. In the modern WebGPU path, expect to push `intensity` up and tune by eye. This mirrors the behavior you saw with `PointLight` in the previous lesson.

### It only works with standard / physical materials

`RectAreaLight` only illuminates **`MeshStandardMaterial`** and **`MeshPhysicalMaterial`**. It does nothing for the legacy/cheaper materials (`MeshBasicMaterial`, `MeshLambertMaterial`, `MeshPhongMaterial`, `MeshToonMaterial`, etc.). This is because area-light shading is a physically-based technique that plugs into the PBR lighting model — the simple materials don't implement it.

If you point a rect area light at a Lambert or Phong surface and see nothing happen, that's not a bug — it's the documented material restriction.

### Positioning and aiming it

You position it with `position.set(x, y, z)`, same as any other light. To aim it, use **`lookAt(target)`**:

```ts
rectAreaLight.lookAt(new THREE.Vector3());      // aim at the origin
rectAreaLight.lookAt(sphereMesh.position);       // aim at an object
```

Or rotate it directly via its `rotation` (the app exposes `rotation.y` in the GUI).

> **Gotcha: you can `lookAt`, but there's no `.target`.** Unlike `DirectionalLight` and `SpotLight`, `RectAreaLight` has **no `.target` object property**. Calling `.lookAt()` just rotates it once, then the look direction exists only implicitly in its `rotation`/`quaternion`. So a single `lookAt()` is a one-shot aim, not a persistent "always face this object" link. To keep it tracking something during an animation, you must re-call `lookAt()` every frame (see the `tick` loop in the app).

### The WebGPU problem: LTC textures

This is the big one the app documents. Trying to add a `RectAreaLight` to a `WebGPURenderer` scene throws a confusing error:

```txt
THREE.TSL: TypeError: Cannot read properties of null (reading 'LTC_FLOAT_1')
  at RectAreaLightNode.setupDirectRectArea() ...
```

**Why it happens.** Physically-based rect area lights are evaluated on the GPU using a technique called **Linearly Transformed Cosines (LTC)**. That technique depends on a pair of precomputed lookup tables (stored as `DataTexture`s, called `LTC_FLOAT_1` and `LTC_FLOAT_2`) that let the shader approximate the BRDF for arbitrary rectangular emitters. In the WebGL path these tables get wired in for you automatically. But the **WebGPU / TSL path does not bundle them by default** — when `RectAreaLightNode` tries to read `LTC_FLOAT_1`, it's `null`, and `setDirectRectArea()` crashes.

**The fix** is to explicitly supply those textures before the first render (the app does it right after `await renderer.init()`):

```ts
import { RectAreaLightTexturesLib } from 'three/addons/lights/RectAreaLightTexturesLib.js';
import { RectAreaLightNode } from 'three/webgpu';

// somewhere before your first render, e.g. after await renderer.init()
RectAreaLightNode.setLTC(RectAreaLightTexturesLib.init());
```

This does two things: `RectAreaLightTexturesLib.init()` builds/initializes the two LTC textures, and `RectAreaLightNode.setLTC(...)` hands those textures to the `RectAreaLightNode` that performs the area-light shading, so `LTC_FLOAT_1` / `LTC_FLOAT_2` are no longer `null`.

**Is this solution up to date?** Yes — this is exactly the pattern the official three.js WebGPU examples use (`RectAreaLightNode.setLTC( RectAreaLightTexturesLib.init() )`), and it remains the required setup in the current `WebGPURenderer` path. It's neither a hack nor an outdated workaround; it's the supported API for enabling rect area lights under WebGPU. Note the textures are an **addon** (`three/addons/...`), not part of the core `three/webgpu` build, so you must import the addon yourself — that's the root of "it's not there by default."

### Performance notes

Area lights are among the **more expensive** light types — the LTC BRDF evaluation is heavier per fragment than a simple point or directional light, and each one has extra cost at render time. Fine for a few, but keep the count reasonable in scenes that already carry a lot of shading work. (This app also disables the other light types by setting `visible = false` so the rect area light's own contribution is the only thing lighting the `MeshStandardMaterial` surfaces — the same isolation pattern as the other light lessons.)

## Code

in repo - `apps/12_5_rect_area_light`

```ts
import * as THREE from 'three/webgpu';
// EXPLAIN: the LTC texture library — REQUIRED for RectAreaLight under WebGPU
import { RectAreaLightTexturesLib } from 'three/addons/lights/RectAreaLightTexturesLib.js';

const canvas = document.querySelector<HTMLCanvasElement>('canvas#tride')!;

async function init() {
  const scene = new THREE.Scene();

  const renderer = new THREE.WebGPURenderer({ canvas });
  await renderer.init();

  // CRITICAL for WebGPU: give the rect area light its LTC lookup textures
  // before the first render, or you get:
  //   TypeError: Cannot read properties of null (reading 'LTC_FLOAT_1')
  THREE.RectAreaLightNode.setLTC(RectAreaLightTexturesLib.init());

  // RectAreaLight — a flat "softbox" panel. Only lights
  // MeshStandardMaterial / MeshPhysicalMaterial.
  const rectAreaLight = new THREE.RectAreaLight();
  rectAreaLight.color = new THREE.Color(0x4e00ff);
  rectAreaLight.intensity = 2; // physical mode: values above 1 needed
  rectAreaLight.width = 1;
  rectAreaLight.height = 1;
  rectAreaLight.position.set(-1.5, 0, 1.5);
  // rectAreaLight.lookAt(new THREE.Vector3()); // one-shot aim (no .target!)
  scene.add(rectAreaLight);

  const material = new THREE.MeshStandardMaterial();
  material.roughness = 0.4;

  const box = new THREE.Mesh(new THREE.BoxGeometry(0.75, 0.75, 0.75), material);
  const torus = new THREE.Mesh(new THREE.TorusGeometry(0.3, 0.2, 32, 64), material);
  torus.position.x = 1.5;
  const sphere = new THREE.Mesh(new THREE.SphereGeometry(0.5, 32, 32), material);
  sphere.position.x = -1.5;
  const floor = new THREE.Mesh(new THREE.PlaneGeometry(5, 5), material);
  floor.rotation.x = -Math.PI / 2;
  floor.position.y = -0.65;

  scene.add(box, torus, sphere, floor);

  const camera = new THREE.PerspectiveCamera(75, innerWidth / innerHeight, 0.1, 100);
  camera.position.set(2, 1, 1);
  scene.add(camera);

  renderer.setPixelRatio(Math.min(devicePixelRatio, 2));
  renderer.setSize(innerWidth, innerHeight);
  renderer.setAnimationLoop(() => {
    // To keep the light tracking a target every frame you must re-aim it:
    // rectAreaLight.lookAt(sphere.position);
    renderer.render(scene, camera);
  });
}

await init();
```

> Note: in the real app, `intensity`, `color`, `width`, `height`, `position.x/y/z`, `rotation.y`, `visible`, and several `lookAt(...)` buttons are exposed to a lil-gui panel so the effect can be explored live. In the minimal snippet above, only the essentials are kept.

## Gotchas

- **You must call `RectAreaLightNode.setLTC(RectAreaLightTexturesLib.init())` under WebGPU.** Without it, adding a rect area light crashes with `TypeError: Cannot read properties of null (reading 'LTC_FLOAT_1')` (or `LTC_FLOAT_2`). This is the single most common failure with this light type on the WebGPU path. Put it after `await renderer.init()`, before the first render.

- **`RectAreaLightTexturesLib` is an addon import, not part of `three/webgpu`.** You can't use `RectAreaLightTexturesLib` unless you import it: `import { RectAreaLightTexturesLib } from 'three/addons/lights/RectAreaLightTexturesLib.js'`. `RectAreaLightNode` meanwhile comes from `three/webgpu` (it's `THREE.RectAreaLightNode`). Getting the two sources mixed up is a common first stumble.

- **It only lights `MeshStandardMaterial` and `MeshPhysicalMaterial`.** Point it at a basic/lambert/phong/toon material and nothing happens. Use a standard or physical material to see anything.

- **`lookAt` is a one-shot aim — there is no `.target`.** `RectAreaLight` has no target property like a directional/spot light. To keep it following an object, re-call `lookAt()` each frame. Verifying this in the GUI, the app's `lookAt` buttons each do a single aim; repeating it in the animation loop is what produces continuous tracking.

- **Physically-correct `intensity` needs bigger values.** Under WebGPU (`useLegacyLights = false`), don't expect `intensity = 1` to look like the old legacy default. Start higher (`2+`) and tune; the app's GUI goes to `10`. There's no fixed valid range, only the renderer's light mode driving what "1" means.

- **Area lights are relatively expensive.** They're fine in small numbers, but the LTC-based shading adds per-fragment cost. Keep the count modest in heavy scenes.

- **`await renderer.init()` is mandatory for WebGPU.** The `WebGPURenderer` must finish async init before the first render (and, here, before `setLTC` effectively matters), or you get a blank canvas.

## Revisit

- **LTC fundamentals.** The fix works, but the *why* is worth digging into: Linearly Transformed Cosines are how real-time renderers precompute the BRDF integral for a rectangular area emitter. The two lookup textures encode this so the GPU can do a fast approximation per fragment. Revisit the LTC technique to understand what `setLTC` is really feeding the shader.

- **Physical intensity units.** Follow up on exactly how `intensity` maps to luminous intensity / candela in physical mode, and how `width`/`height` interact with energy. Because the light's emitted energy is spread over the rectangle, surface area can affect perceived brightness — this ties into the "why values above 1" curiosity.

- **No shadows.** `RectAreaLight` does **not** cast shadows in three.js. If you want soft, area-ish shadows later, note that this light type can't provide them — come back to this when you reach the shadows lesson.

- **Why only standard/physical materials.** Explore how area light BRDF evaluation is wired into the PBR lighting model but absent from the simpler materials. Understanding the lighting pipeline (why the simple materials skip it) clarifies the whole series.

- **Alternative large soft lights.** For scenes where a rectangle panel isn't the right tool, remember `HemisphereLight` (already covered) and environment maps / indirect light as other ways to get soft, "area-ish" fills without a rect area light's cost.

## Outdated

The approach is **valid and current**. This is a modern WebGPU (`WebGPURenderer`) + TSL setup with PBR (`MeshStandardMaterial`), and `RectAreaLight` remains a supported, documented light type. The `RectAreaLightNode.setLTC(RectAreaLightTexturesLib.init())` requirement is the *official, current* pattern for enabling rect area lights under WebGPU — the `RectAreaLightTexturesLib` addon and `setLTC` API are exactly what the bundled official examples use. Nothing here is obsolete; earlier WebGL-only versions handled LTC textures implicitly, and the explicit WebGPU setup is simply the current required step rather than a workaround.
