## Concept

Creating complex shapes (a character, a car, a house) purely with Three.js geometry primitives and `BufferGeometry` code is impractical. The standard approach is to **model the shape in dedicated 3D software** (Blender, Maya, Cinema 4D...) and **import it into the web app**. This lesson is the introduction to that pipeline: choosing a format, getting a model, and loading it with `GLTFLoader`.

### Model formats

There are many 3D model file formats, and each one is a trade-off between a set of criteria:

- **What data** it can hold — geometry, materials, animations, skeletons, lights, cameras, scene structure...
- **Weight** — how heavy the file is on disk and over the network
- **Compression** — whether the data is compressed (and how much time/decompression effort that costs)
- **Compatibility** — which softwares, engines, and renderers read it
- **Copyright / openness** — proprietary vs open formats

Popular older formats:

- **OBJ** — widely supported, simple, geometry only
- **FBX** — Autodesk exchange format, very common in game pipelines
- **STL** — 3D-printing format, triangles only
- **COLLADA (.dae)** — XML-based, an earlier Khronos standard
- **3DS** — old 3ds Max format
- **PLY** — point clouds and meshes

### glTF — the standard to learn first

**glTF (GL Transmission Format)** is developed by the Khronos Group — the same consortium behind OpenGL, WebGL, Vulkan, and COLLADA, with members like AMD, Nvidia, Google, Nintendo... It has become the de facto standard for real-time 3D on the web: it supports geometries, materials, cameras, lights, scene graphs, animations, skeletons, morphing, and so on, and most 3D software, game engines, and runtimes read it.

> ⚠️ You don't have to use glTF everywhere. The right choice depends on the data you need, the weight you can afford, and how much time decompression takes. Question it per project.

Note that "glTF" is **not one file format — it ships in several flavors**. Open `public/models/Duck/` and you'll see four of them:

| Folder | Extension | Files | Contents | Weight |
|---|---|---|---|---|
| `glTF` (default) | `.gltf` + `.bin` + `.png` | multiple | the `.gltf` is a JSON describing cameras, lights, scenes, materials, object transforms; the `.bin` holds geometry data (vertex positions, UVs, normals, colors); the `.png` is the texture | medium |
| `glTF-Binary` | `.glb` | one | everything in a single binary file | usually lighter |
| `glTF-Draco` | `.gltf` + `.bin` + `.png` | multiple | like default glTF, but the buffer data is compressed with the Draco algorithm | much lighter |
| `glTF-Embedded` | `.gltf` | one | JSON with textures embedded as base64 | heavier |

**Choosing a flavor** is a matter of how you intend to handle the assets:

- You want to **alter/edit** the files → go with default `glTF`
- Loading **multiple files** can be faster (parallel requests)
- You want **one self-contained file** → `glTF-Binary` (`.glb`)
- You need the smallest payload → `glTF-Draco` (more on Draco in a later lesson)
- Do not need to touch the data → binary, it's harder to alter anyway

When we load the default `Duck.gltf`, the referenced `.bin` and `.png` **load automatically** — we only point `GLTFLoader` at the `.gltf`.

### Where to get models

The glTF team provides sample models for testing in the [glTF-Sample-Models](https://github.com/KhronosGroup/glTF-Sample-Models) repository. In this project the `2.0/Duck` sample was downloaded/copied into `public/models/Duck/`.

### How loading works in code

`GLTFLoader` returns a `GLTFParsed` object (when loading through `GLTFLoader.loadAsync`, the parsed `gltf` object is resolved). The key parts:

- `duckModel.scene` — a `Group` (the root of the loaded model's own scene graph)
- `duckModel.scenes` — an array of scenes in the file; usually `[Group]`
- `duckModel.scene.children` — the root children. For the Duck we found **one** `Object3D`, whose children were a **`PerspectiveCamera`** and a **`Mesh`**

So the Duck's structure is:

```
scene (Group)
└── children[0] (Object3D)   ← carries the GLB's node matrix — including scale
    ├── PerspectiveCamera   ← baked into the file by the exporter, not needed by us
    └── Mesh               ← the actual duck
```

**This matters**: the scale transform lives on the parent `Object3D`, not on the mesh itself. If we only grabbed the `Mesh`, the duck would render with the wrong scale/position/rotation. That's why the model's files should be clean (or you clean them yourself in 3D software and re-export).

### Adding the model to the scene

There are several valid approaches; which one you pick depends on the model and the situation:

1. **Add the whole `duckModel.scene`** into our scene — simplest, preserves everything, and some people always do this; we'll practice this in a later lesson.
2. **Add the scene's children** to our scene and ignore the embedded `PerspectiveCamera` — scale preserved, but you take the unwanted camera along.
3. **Filter/traverse children before adding** — find only the meshes; can get awkward when a model changes its structure.
4. **Add only the `Mesh`** — easiest, but you end up with wrong scale/position/rotation, because the scale is applied on the parent.
5. **Open the file in 3D software, clean it, export it again** — the robust production fix.

In this app we chose **option 2 in a minimal form**: `scene.add(duckModel.scene.children[0])` — the whole `Object3D` (which carries the correct scale) goes into our scene, embedded camera and all.

### Why do imported models need lights? (PBR)

Imported models typically use **physically-based rendering (PBR) materials** — `MeshStandardMaterial` / `MeshPhysicalMaterial`. PBR materials don't emit light themselves; their final color is computed from the scene's lights and environment (and the material's roughness/metalness/albedo). If the scene has no lights, a PBR model renders **black**. That's why this app sets up an `AmbientLight` + `DirectionalLight`, and also assigns a cube environment map to `scene.environment` (see `10.10.x_mesh-standard-material-cube-map`) so the duck gets reflections and doesn't look flat even where direct light doesn't reach.

### Environment map loading, `loadAsync` vs `load`, and the LoadingManager

The app also loads four cube environment maps (studio, lumber, creek, glasshouse) with a `CubeTextureLoader` sharing a `LoadingManager`, plus a separate `LoadingManager` for the model loader. This is what the model manager's callbacks log:

- `onStart` — a load started (gives the file path)
- `onProgress` — progress events (note: only the **file path** string is provided here — not a fractional percent, because `loadAsync` doesn't expose granular progress)
- `onLoad` — everything finished
- `onError` — something failed

`GLTFLoader.loadAsync(url)` resolves with the loaded object **outside** the callback, which reads much cleaner than the callback-based `.load(url, onLoad, onProgress, onError)` — inside which you can only reach the model inside the callback. The trade-off: with `loadAsync` you lose the per-file progress callback, which is why the `LoadingManager` is used here to observe progress.

## Code

in repo — `apps/16_0_imported_models`

```ts
import * as THREE from 'three/webgpu';
import { GLTFLoader } from 'three/addons/loaders/GLTFLoader.js';
import { OrbitControls } from 'three/addons/controls/OrbitControls.js';
import GUI from 'lil-gui';
import { getRequiredElement } from './util';

// Two loaders share a LoadingManager so we can observe progress
const cubeTextureLoader = new THREE.CubeTextureLoader(
	new THREE.LoadingManager(),
);
const modelLoadingManager = new THREE.LoadingManager();
const gltfLoader = new GLTFLoader(modelLoadingManager);

modelLoadingManager.onProgress = (filePaths: string) => {
	console.log('progess ', filePaths);
};
modelLoadingManager.onLoad = () => {
	console.log('model/s loaded');
};
modelLoadingManager.onError = (e) => {
	console.error(e);
};
modelLoadingManager.onStart = (filePath) => {
	console.log('loading started ', filePath);
};

const canvas = getRequiredElement<HTMLCanvasElement>('canvas#tride');
const sizes = { width: window.innerWidth, height: window.innerHeight };

async function init() {
	// Renderer
	const scene = new THREE.Scene();
	const renderer = new THREE.WebGPURenderer({ canvas });
	await renderer.init();

	// Environment maps
	const environmentMapTextureStudio = await cubeTextureLoader
		.setPath('/textures/environmentMaps/studio/')
		.loadAsync(['px.png', 'nx.png', 'py.png', 'ny.png', 'pz.png', 'nz.png']);
	scene.environment = environmentMapTextureStudio;

	// Load the model — all referenced .bin/.png load automatically
	const duckModel = await gltfLoader.loadAsync('/models/Duck/glTF/Duck.gltf');

	// Scene graph of the Duck:
	// scene (Group) -> children[0] (Object3D, holds scale) -> [Camera, Mesh]
	// We add the Object3D (option 2) so the bake-in scale is preserved.
	scene.add(duckModel.scene.children[0]);

	// Lights — PBR materials need light to be visible
	const ambientLight = new THREE.AmbientLight(0xffffff, 2.1);
	scene.add(ambientLight);

	const directionalLight = new THREE.DirectionalLight(0xffffff, 0.4 * Math.PI);
	directionalLight.position.set(5, 5, 5);
	scene.add(directionalLight);

	// Floor to catch shadows
	const floor = new THREE.Mesh(
		new THREE.PlaneGeometry(10, 10),
		new THREE.MeshStandardMaterial({
			roughness: 0.4,
			metalness: 0.3,
			color: new THREE.Color('#928192'),
		}),
	);
	floor.rotation.x = -Math.PI / 2;
	floor.receiveShadow = true;
	scene.add(floor);

	// Camera + controls
	const camera = new THREE.PerspectiveCamera(
		75,
		sizes.width / sizes.height,
		0.1,
		100,
	);
	camera.position.set(-3, 3, 3);
	scene.add(camera);

	const orbitControls = new OrbitControls(camera, canvas);
	orbitControls.enableDamping = true;

	renderer.shadowMap.enabled = true;
	renderer.shadowMap.type = THREE.PCFSoftShadowMap;
	renderer.setPixelRatio(Math.min(window.devicePixelRatio, 2));
	renderer.setSize(sizes.width, sizes.height);

	const timer = new THREE.Timer();
	renderer.setAnimationLoop(tick);

	function tick(timestamp: number) {
		timer.update(timestamp);
		orbitControls.update();
		renderer.render(scene, camera);
	}
}

await init();
```

## Gotchas

- **The scale lives on the parent, not the mesh.** In the Duck file, `children[0]` (an `Object3D`) carries the baked-in transform. Adding only the `Mesh` gives you a duck that's tiny, offset, and rotated. Add the parent `Object3D` instead — for this model `scene.add(duckModel.scene.children[0])`.
- **`duckModel.scene.children[0]` is `undefined` afterwards.** Once you `scene.add(...)` it, Three.js re-parents the object, so it's no longer a child of the loading `Group`. Logging it after the add prints `undefined` — grab your reference *before* adding.
- **Imported models may carry their own `PerspectiveCamera`.** The exporter wrote one into the Duck file. Ignore it (or filter the children you add); don't accidentally start rendering from the file's camera.
- **PBR materials render black without light.** Imported models use PBR materials, so if the scene has no lights — or no environment map — you'll see a black duck, not a missing texture. Add at least one light, or set `scene.environment`.
- **`loadAsync` gives no granular progress.** If you need per-file progress percentages, use `LoadingManager` callbacks too, as the code does.
- **When you add the whole `gltf.scene`, you take everything** — including the file's camera and any unwanted transform hierarchy. For a single-mesh toy like the Duck it's trivial, but realistic models need thought about what exactly gets added.
- **OS may hide file extensions.** Some files (`.gltf`, `.bin`) might show without extensions in your file manager. Look at them in your code editor.

## Revisit

- **Draco compression** in depth — the `glTF-Draco` variant exists, and if you want to ship it you need `DRACOLoader` + setting `gltfLoader.setDRACOLoader(...)`. Deferred to a later lesson.
- **Adding the whole `duckModel.scene`** to our scene — the "simplest" approach, explicitly deferred.
- **Traversing children** (`object.traverse()`) to pick out meshes / materials — how it behaves when the model's structure changes between versions.
- **Cleaning models in Blender** before export (applying transforms, removing unwanted cameras/lights) — the production-grade fix for the scale problem.
- **The `duckModel.scene.children[0]` becoming `undefined`** after `add` — an easy thing to forget and a clue about how Three.js `add` re-parents objects.
