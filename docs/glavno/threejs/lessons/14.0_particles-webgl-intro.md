# 14.0 Particles — WebGL Intro

The first stop on the way to a particle system. Particles are the technique behind stars, smoke, rain, dust, fire, snow, sparks, magic effects — anything made of a huge number of small elements. The app itself is deliberately minimal: it renders a cloud of points from a `SphereGeometry` and lets you tweak them, but the real content here is **why this lesson runs on WebGL instead of WebGPU** and what that means for the path forward.

---

## Concept

### What a particle is

A particle looks like a tiny 2D plane — **two triangles** — that is **always facing the camera** (the technical term is *billboarding*). You don't see the plane itself; you see a texture drawn on it (a dot, a star, a snowflake, a flame sprite).

The cheap magic of particles: you can have **thousands of them at a reasonable frame rate**, because they are all drawn in a single draw call. Three.js renders them through the GPU as *points* — one GPU vertex per particle — instead of a full mesh per object. That is why "how many particles" is usually not the bottleneck; a few thousand points is nothing for a modern GPU.

### The three pieces of a particle system

Creating particles is structured exactly like creating a mesh, just with `Points`-prefixed counterparts:

| Mesh | Particles |
|---|---|
| `BufferGeometry` (e.g. `SphereGeometry`) | `BufferGeometry` holds the per-particle positions |
| `MeshBasicMaterial` etc. | `PointsMaterial` |
| `Mesh` | `Points` |

```ts
// 1. the geometry — its vertices define WHERE the particles are
const particleGeometry = new THREE.SphereGeometry(1, 32, 32);

// 2. the material — visual appearance and size
const particleMaterial = new THREE.PointsMaterial();

// 3. the visible object — like a mesh, it has position/rotation/scale
const particles = new THREE.Points(particleGeometry, particleMaterial);

scene.add(particles);
```

A subtle but crucial idea: **each vertex of the geometry becomes one particle.** In this intro the geometry is a `SphereGeometry(1, 32, 32)`, so the particles sit on the surface of a sphere filled with vertices. A real particle system usually uses a hand-built `BufferGeometry` with thousands of random positions instead (that's the next step of the lesson series).

### `PointsMaterial` options — size and sizeAttenuation

Two settings matter for the look:

```ts
const particleMaterial = new THREE.PointsMaterial({
  size: 0.02,           // diameter of each particle, in world units
  sizeAttenuation: true,
});
```

- **`size`** — how big each particle is. In this app it's set after construction: `particlesMaterial.size = 0.02` — small enough that you clearly see the points.
- **`sizeAttenuation`** — controls perspective on particles. When `true` (default), distant particles render smaller than close particles — the size is attenuated by depth. When `false`, every particle stays the same pixel size no matter how far away it is.

> 💡 Play with `size` and `sizeAttenuation` through the GUI (`Tweaks → particles (Points instance)`), and don't be fooled: **if `sizeAttenuation` is `false` and `size` is tiny, you won't see anything** on a close camera — the particles aren't scaled by distance, so they stay a few pixels large.

### Why WebGL and not WebGPU — the actual subject of this lesson

The codebase started as a WebGL-only lesson, but the commit history shows the attempt to switch to `three/webgpu` first — and the decision to go back. The first line of `src/main.ts` documents it:

```ts
// EXPLAIN: using WebGL instead
import * as THREE from 'three';        // ← WebGL path
// import * as THREE from 'three/webgpu';
```

The README explains why. In WebGPU (the renderer on the `three/webgpu` path), `PointsMaterial.sizeAttenuation` **didn't work** — the size wasn't reduced with distance. After research the conclusion was: this option is **not implemented / not working in the WebGPU path of Three.js**, so a real solution requires writing **custom particles with TSL** — Three.js Shading Language — which you can't do without first learning shaders.

That reframes the priorities:

- **Shaders** come later in this learning plan (they are on the table after the classic + intermediate techniques).
- As long as shaders aren't covered, **WebGL with `sizeAttenuation`** is the only way to get correct-depth particles.
- The `WebGPURenderer` path depends on `await renderer.init()` before first render — the WebGL `WebGLRenderer` path doesn't have that, so this app simply skips `.init()`.

So — **yes, it's worth learning particles with WebGL.** The WebGL renderer is still perfectly maintained and capable, the particle principle is identical across both renderers, and the first-class WebGPU way (TSL) needs shaders that you'll learn anyway. What you learn here transfers.

### The GUI for the lesson

`lil-gui` is used for the particle position controls — `position.x/y/z` of the `Points` have their own parent window folder (`particles (Points instance)`). The default camera position is far enough away (`camera.position.z = 3`) to see the particle set.

## Code

in repo - `apps/14_0_particles_webgl_intro`

```ts
import * as THREE from 'three';
import { OrbitControls } from 'three/addons/controls/OrbitControls.js';
import GUI from 'lil-gui';

const canvas = document.querySelector<HTMLCanvasElement>('canvas')!;

const scene = new THREE.Scene();

// particles — vertex per particle
const particleGeometry = new THREE.SphereGeometry(1, 32, 32);
const particleMaterial = new THREE.PointsMaterial({
  size: 0.02,
  sizeAttenuation: true,
});
const particles = new THREE.Points(particleGeometry, particleMaterial);
scene.add(particles);

const camera = new THREE.PerspectiveCamera(75, innerWidth / innerHeight, 0.1, 100);
camera.position.z = 3;
scene.add(camera);

const controls = new OrbitControls(camera, canvas);
controls.enableDamping = true;

// WebGL renderer — no await init(), unlike WebGPURenderer
const renderer = new THREE.WebGLRenderer({ canvas });
renderer.setPixelRatio(Math.min(devicePixelRatio, 2));
renderer.setSize(innerWidth, innerHeight);
renderer.setClearColor(0x000000, 1);

renderer.setAnimationLoop(() => {
  controls.update();
  renderer.render(scene, camera);
});
```

## Gotchas

- **`sizeAttenuation` on the WebGPU path.** This is the exact bug this lesson exists to avoid. In WebGPU (`three/webgpu`), `PointsMaterial` projects the particle size wastefully and the attenuation setting is not honored. It's an intentional fallback, not a code typo.
- **`size`, `sizeAttenuation`, `color` etc. are just settings on the material — set them in the constructor or after, both work.** The app sets `size` and `sizeAttenuation` after construction (`particlesMaterial.size = 0.02`). That's fine — but with many options it's easy to miss one. Doing `new THREE.PointsMaterial({ size: 0.02, sizeAttenuation: true })` in one place is less error-prone.
- **Tiny size + no attenuation = invisible particles.** If `sizeAttenuation: false`, the particle size is a fixed world-space amount; on the view plane it can be smaller than a pixel. With `size: 0.02` and a close camera you may see nothing — grow the size or turn attenuation on.
- **Check the defaults before trusting a material.** `PointsMaterial` defaults to `sizeAttenuation: true`, `size: 1`, `color: 0xffffff`. A size of `1` world unit is huge — if you forget to lower `size`, your "particles" are giant white squares on screen.
- **The vertex count equals particle count.** The geometry decides how many particles you get — no `count` option on `PointsMaterial`. For a particle cloud you hand-build the positions for each particle.
- **Camera and particles interplay.** The three.js `Points` positions are controlled like a regular object (`position.x/y/z`), so the GUI tweaks you do there move the whole cluster — not the individual particles.

## Revisit

- **A custom particle geometry.** The real step toward a practical particle system: create a `BufferGeometry`, fill a `Float32Array` with N random positions, set `geometry.setAttribute('position', new THREE.BufferAttribute(positions, 3))`. The `SphereGeometry` particles in this lesson are a nice static layout, but that's not a cloud of dust.
- **Attenuation — the WebGPU question again.** Come back to this when the shader lessons arrive: learn TSL and re-create particles on `WebGPURenderer` with a `shaderPoint` in `PointsMaterial` (node-based), and verify the attenuation behavior you get.
- **The `sizeAttenuation` math.** It's a depth-dependent size factor. What exactly gets computed on the vertex shader — world distance vs view depth — is worth a second look when reading the docs.
- **Particles as curtains of points.** The README lists possible particle systems (stars, smoke, rain, dust, fire). Pick one and build it with the technique from this lesson — the difference will help you get past the "static sphere" look.

## Outdated

approach is valid — classical Three.js particles via `WebGLRenderer` + `PointsMaterial` are still fully supported and are the right choice until shaders are on the table. The one thing to keep coming back to is the WebGPU alternative.

For a project with `WebGPURenderer`, the classic `PointsMaterial` path is not adequate (as of this lesson, `sizeAttenuation` is not present on the WebGPU path). The modern path is TSL (Three.js Shading Language) — building the material node graph yourself, including the depth-attenuation, which is possible since shaders are now on the table. **WebGPU + TSL is better and more flexible than the classic one — but it assumes you can write shaders.** Start with WebGL for this build, then do the upgrade in the shaders lesson.

> 💡 More up to date alternative: [Three.js — TSL (Three.js Shading Language) docs](https://threejs.org/docs/TSL.html) — the size attenuation a TSL point shader allows runs in WebGL **and** WebGPU — reason: the current WebGPU path doesn't support the classic `PointsMaterial` attenuation; TSL gives you both.
