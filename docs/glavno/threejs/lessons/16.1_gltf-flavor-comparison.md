## Concept

In [16.0_imported-models-intro](16.0_imported-models-intro.md) we loaded the Duck and learned *why* we add `duckModel.scene.children[0]` (the `Object3D` carries the baked-in scale) instead of just the mesh. This lesson is a **practical test**: the same Duck model ships in **five different glTF flavors** inside `public/models/Duck/`, and we try to load each one to see what actually works — and what doesn't. Along the way we also look at the **glTF-Quantized** flavor that we skipped in the previous lesson.

### The five flavors on disk

The Duck folder actually contains **five** variants, not four:

| Folder | Extension | Extra files next to it | What's in the JSON |
|---|---|---|---|
| `glTF` (default) | `.gltf` | `Duck0.bin` + `DuckCM.png` | JSON referencing external `.bin` and texture |
| `glTF-Binary` | `.glb` | none | everything packed into one binary blob |
| `glTF-Draco` | `.gltf` | `Duck.bin` + `DuckCM.png` | JSON, but mesh geometry compressed with **Draco** (`KHR_draco_mesh_compression`) |
| `glTF-Embedded` | `.gltf` | none | JSON with `data:` URIs inline (base64) — big, single file |
| `glTF-Quantized` | `.gltf` | `Duck.bin` + `DuckCM.png` | JSON, mesh **vertex data quantized** (`KHR_mesh_quantization`) |

The folder names in `public/models/Duck/` (`glTF`, `glTF-Binary`, `glTF-Draco`, `glTF-Embedded`, `glTF-Quantized`) are the Khronos sample repository's naming.

### What the experiment showed

- `glTF/Duck.gltf` — **loaded** ✅
- `glTF-Binary/Duck.glb` — **loaded** ✅
- `glTF-Embedded/Duck.gltf` — **loaded** ✅ — and this is the one active in the code
- `glTF-Draco/Duck.gltf` — **did not load** ❌
- `glTF-Quantized/Duck.gltf` — **not tested** in this app (the file sits there but nothing loads it)

Why did Draco fail? Because the Duck's Draco file declares `"extensionsRequired": ["KHR_draco_mesh_compression"]` — the mesh geometry is **only** stored as compressed Draco chunks, there is no uncompressed fallback data. A plain `GLTFLoader` can't decode that; you must register a **`DRACOLoader`**:

```ts
const dracoLoader = new DRACOLoader();
dracoLoader.setDecoderPath('/draco/');
gltfLoader.setDRACOLoader(dracoLoader);
```

That's why the previous lesson deferred Draco to "a later lesson" — it's not a loader difference, it's an **additional decompressor** (`DRACOLoader` decodes the compressed geometry on the CPU before handing it to the renderer). Without it, the loader throws — the try-out in the code comments is exactly that failure.

### glTF-Quantized — what is it?

**Quantization** means storing vertex attributes with fewer bits than the full float precision they nominally use. A typical uncompressed `POSITION` target is three `float32` values (12 bytes per vertex). A quantized accessor might store the same positions as three **`int16`** values (6 bytes per vertex) plus a tiny per-color/per-attribute scale/offset — "dequantizing" back to floats is just `value * scale + offset`. Because vertex positions in any given mesh usually stay within a small box, the precision loss is often invisible in practice, especially once the error is bounded by an extension mechanism.

The Duck's quantized file was produced by **gltfpack**, a command-line tool (part of the `meshoptimizer` project) written in C++ by Zeux. Notice its header: `"generator": "gltfpack 0.13"` — a completely different toolchain from `COLLADA2GLTF` (the exporter that made the other four Duck variants). gltfpack is normal among the *tools* ecosystem, but **quantization itself is still a niche, edge-case choice** compared with the everyday four flavors.

Important security nuance: the Duck's quantized JSON lists `"extensionsRequired": ["KHR_mesh_quantization"]`. **`extensionsRequired` and `extensionsUsed` are not the same thing.** `extensionsUsed` says "some parts of the file *optionally* use this" — engines are allowed to ignore them. `extensionsRequired` says "you MUST support this extension or you can't load the file" — it's a hard contract. The quantized Duck, like the Draco one, is `required`-level.

Is quantization commonly used? **Not in everyday projects.** The user who lists "is this edge case or not?" in the README — the honest answer: it's the right tool when you need aggressive size reduction on CPU-side models and can't/won't use Draco, or when you're already inside the meshoptimizer toolchain. For typical hand-authored Three.js apps, the four flavors from the previous lesson cover 99% of cases. See the **Revisit** section for a real-world benchmark link.

### The exotic embedded string

When the embedded flavor was loaded, the `LoadingManager` `onProgress` callback printed what looked like "a huge base64 or similar formatted huge string". That's exactly what it was — the embedded `.gltf` file itself contains `data:application/octet-stream;base64,...` URIs for its buffers and `data:image/png;base64,...` URIs for its textures. `onProgress` gets a **file path string** (in `GLTFLoader` it's the URL being requested), and for an embedded model there is no separate `.bin`/`.png` request at all — the loader reports the whole inline URI, mega-string and all. Not a bug, not a leak; just the consequence of a single self-contained file.

```
data:application/octet-stream;base64,ObhEvuo/b7+PUpk+yVSBvRR...   ← 102 KB of geometry, raw
data:image/png;base64,iVBORw0KGgoAAAANSUhEUgAAAgAAAAIACAMAAA...    ← the DuckCM texture
```

These same exact bytes are what make the embedded file the heaviest of the five (≈ 163 KB vs ≈ 120 KB for the `.glb`).

### The relation to `.glb`

`glTF-Binary` (`.glb`) and `glTF-Embedded` (`data:` URIs) solve the same problem — *one file, easy to share* — through two opposite paths:

- `.glb` is **binary and compact** — the JSON chunk plus a binary chunk inside one container. The format is the container, so it stays small.
- Embedded `.gltf` is **text and heavy** — it's still a JSON document, so all that binary gets base64-encoded into ASCII (a ~33% size blowup before compression).

If you want to distribute a single-file model, `.glb` is usually the better default; embedded `.gltf` mostly appears when a toolchain exports it that way and you don't re-export.

### PBR + full scene graph matters

Everything you made 16_0 still matters here: PBR Duck needs lights + `scene.environment` (the studio cube map) or it renders black. Because we add `duckModel.scene.children[0]`, the Duck's baked-in scale survives. And because we add a parent object rather than the whole scene, the file's own `PerspectiveCamera` is dragged along too — harmless for a demo, worth remembering when a real model ships one.

## Code

in repo — `apps/16_1_imported_models_gltf`

```ts
import * as THREE from 'three/webgpu';
import { OrbitControls } from 'three/addons/controls/OrbitControls.js';
import { GLTFLoader } from 'three/addons/loaders/GLTFLoader.js';
import GUI from 'lil-gui';
import { getRequiredElement } from './util';

const loadingManager = new THREE.LoadingManager();
const cubeTextureLoader = new THREE.CubeTextureLoader(loadingManager);

// Model loader with its own LoadingManager so we can watch progress
const modelLoadingManager = new THREE.LoadingManager();
const gltfLoader = new GLTFLoader(modelLoadingManager);

modelLoadingManager.onProgress = (filePaths: string) => {
  // with glTF-Embedded this prints the huge base64 data: URI as the "path"
  console.log('progess ', filePaths);
};
modelLoadingManager.onLoad = () => console.log('model/s loaded');
modelLoadingManager.onError = (e) => console.error(e);
modelLoadingManager.onStart = (filePath) =>
  console.log('loading started ', filePath);

const canvas = getRequiredElement<HTMLCanvasElement>('canvas#tride');

const sizes = { width: window.innerWidth, height: window.innerHeight };

async function init() {
  const scene = new THREE.Scene();
  const renderer = new THREE.WebGPURenderer({ canvas });
  await renderer.init();

  // Environment map (studio) — PBR ducks need it or they look black
  const environmentMapTextureStudio = await cubeTextureLoader
    .setPath('/textures/environmentMaps/studio/')
    .loadAsync(['px.png', 'nx.png', 'py.png', 'ny.png', 'pz.png', 'nz.png']);
  scene.environment = environmentMapTextureStudio;

  // ⬇️ switch between the five flavors here
  const duckModel = await gltfLoader.loadAsync(
    // '/models/Duck/glTF/Duck.gltf',          // ✅ loads
    // '/models/Duck/glTF-Binary/Duck.glb',   // ✅ loads
    // '/models/Duck/glTF-Draco/Duck.gltf',   // ❌ needs DRACOLoader
    '/models/Duck/glTF-Embedded/Duck.gltf' // ✅ loads
    // '/models/Duck/glTF-Quantized/Duck.gltf', // ✔️ should load — try it
  );

  console.log(duckModel.scene.children); // [Object3D]
  scene.add(duckModel.scene.children[0]);

  renderer.shadowMap.enabled = true;
  renderer.shadowMap.type = THREE.PCFSoftShadowMap;

  const ambientLight = new THREE.AmbientLight(0xffffff, 2.1);
  scene.add(ambientLight);

  const directionalLight = new THREE.DirectionalLight(0xffffff, 0.4 * Math.PI);
  directionalLight.position.set(5, 5, 5);
  directionalLight.castShadow = true;
  scene.add(directionalLight);

  const floor = new THREE.Mesh(
    new THREE.PlaneGeometry(10, 10),
    new THREE.MeshStandardMaterial({
      roughness: 0.4,
      metalness: 0.3,
      color: new THREE.Color('#928192'),
    })
  );
  floor.rotation.x = -Math.PI / 2;
  floor.receiveShadow = true;
  scene.add(floor);

  const camera = new THREE.PerspectiveCamera(
    75,
    sizes.width / sizes.height,
    0.1,
    100
  );
  camera.position.set(-3, 3, 3);
  scene.add(camera);

  const orbitControls = new OrbitControls(camera, canvas);
  orbitControls.enableDamping = true;

  renderer.setPixelRatio(Math.min(window.devicePixelRatio, 2));
  renderer.setSize(sizes.width, sizes.height);

  const timer = new THREE.Timer();
  renderer.setAnimationLoop(tick);

  function tick(timestamp: number) {
    timer.update(timestamp);
    orbitControls.update();
    renderer.render(scene, camera);
  }
}

await init();
```

## Gotchas

- **Draco files fail with a plain `GLTFLoader`.** `KHR_draco_mesh_compression` is in `extensionsRequired`, meaning *all* the mesh geometry is Draco-compressed and there's no fallback. Until you register `gltfLoader.setDRACOLoader(dracoLoader)` with a `DRACOLoader` (and its decoder path), the load errors.
- **`extensionsRequired` ≠ `extensionsUsed`.** `Used` is optional — engines may ignore it. `Required` is a hard contract: no support, no load. Both Draco and Quantized Ducks are `Required`.
- **`scene.children[0]` becomes `undefined` after `scene.add()`.** Three.js re-parents the object, so once added, indexing into the *old* group's children no longer finds it. Grab the reference before adding.
- **Embedded models print monster strings in `onProgress`.** Because there's no external `.bin`/`.png` to request, the loader's "file path" is the entire `data:...;base64,...` URI. It looks alarming, it's expected.
- **The embedded file is the heaviest** — the base64 encoding bloats the bytes ~33% before it even hits the network compared to the `.glb`. Single-file convenience comes at a cost.
- **The camera the model exports comes with the add.** `duckModel.scene.children[0]` also carries the Duck's own `PerspectiveCamera`. Fine here; remember it when a real model ships a camera you don't want.
- **OS may hide extensions.** The `.gltf`/`.bin` files can appear extensionless in a file manager; check them in the code editor.

## Revisit

- **Draco in-depth** — it was deferred in 16_0 and still isn't wired here. When you get to it: `DRACOLoader`, `setDecoderPath`, and whether to use it on the model that needs it. `🤖 suggested`
- **Quantized-in-practice** — this README only *asked* "is it edge case?" without answering via benchmark. Real numbers: meshoptimizer's own docs show quantized glTF cutting file size roughly in half on their sample set — worth confirming/quantifying yourself before you ever reach for it. `🤖 suggested`
- **The Quantized Duck itself is untested** — it's on disk but nothing loads it. Wire the URL in and confirm `GLTFLoader` + Three.js's built-in `KHR_mesh_quantization` support actually renders it. That's a 2-minute experiment worth doing. `🤖 suggested`
- **Adding the whole `duckModel.scene` vs just `children[0]`** — explicitly deferred in 16_0 and again here. Which behavior do you actually want when the model's structure changes between versions?
- **The `directLookAtCenter` dead-end** in the GUI code — the `directionalLight.lookAt` behavior surprised you there; worth re-examining how lights aim when you revisit helpers.
