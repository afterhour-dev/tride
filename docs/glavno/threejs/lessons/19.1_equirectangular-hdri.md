## Concept

### What is an HDRI?

An **HDRI** (High Dynamic Range Image) is an image whose pixels can store values far beyond the usual 0–255 range of a regular image. The file extension is `.hdr` — where "HDR" stands for "High Dynamic Range", and the "I" stands for "Image".

A regular image (e.g. a JPEG or PNG) clamps its light values into a narrow range — the brightest pixel is 255, period. An HDRI does not clamp: a light bulb, window, or blazing sun in an HDRI can have a value of 10, 100, or 1000+ times brighter than a normal white pixel. This extra range is exactly what makes HDRIs ideal for storing **luminosity data** — the actual brightness of light sources in the real world.

This matters for 3D because when you use an HDRI to light your scene, the material calculations need those extreme values: a bright window in the HDRI will genuinely illuminate the objects near it, not just paint a washed-out white spot on them.

### Equirectangular projection

An environment map of real surroundings is a full **360° view** of a place. There are two common ways to store such a view:

- as **six images** forming a cube (the cube texture map, used in the previous lesson),
- as a **single image** that wraps the whole view around a sphere — an **equirectangular** image.

`Equirectangular` means the image is a rectangular picture where the horizontal axis maps to the full 360° of longitude and the vertical axis maps to the 180° of latitude (from zenith to nadir). If you take such a photo of a room, the same single file contains everything around, above, and below you. Look at the image and you'll see both the sky and, stretched at the bottom, the floor — the stretching is expected: the poles of the sphere are squeezed into the top and bottom edges of the rectangle.

So, unlike a cube texture map (a set of 6 images), an equirectangular HDRI is **one file, one picture** containing roughly a full surrounding 360° view. That single file is then used for the background and, more importantly, for **image-based lighting** — the environment map lights the scene by sampling the HDRI from every direction, with no actual light objects needed.

### What an environment map is used for

In this app (and the previous one) the environment map serves three roles, and all three are visible in the code:

- **background** — `scene.background` = the HDRI texture. The same image you'd see in real life behind the objects.
- **reflection** — a `MeshStandardMaterial` with low roughness and high metalness reflects the environment map instead of just a flat color. The torus knot in this app (`roughness: 0.1, metalness: 1`) is a perfect mirror of the surroundings.
- **lighting (image-based lighting)** — `scene.environment` = the HDRI texture. Three.js treats the HDRI as the light source: every point on the model is lit by the incoming light from the direction of the environment. This is why the ambient and directional lights in the app are created but set to `visible = false` — the lighting you see comes almost entirely from the HDRI.

### The settings used in this app

```ts
scene.environment = environmentMapWoodsTexture;   // lighting
scene.background  = environmentMapWoodsTexture;   // visible background
```

Two independent multipliers control the strength of each role:

```ts
scene.environmentIntensity = 1.9; // default is 1.0 — how strongly the HDRI lights objects
scene.backgroundIntensity  = 2.4; // default is 1.0 — how bright the background image is
```

and the background can also be blurred so it stays as lighting but doesn't distract:

```ts
scene.backgroundBlurriness = 0; // 0 (sharp) to 1 (fully blurred)
```

### Why `EquirectangularReflectionMapping` is required

The code sets the mapping explicitly for every loaded HDRI:

```ts
environmentMapWoodsTexture.mapping = THREE.EquirectangularReflectionMapping;
```

In this app the comment explains the symptom: *without* this line, the backgroundBlurriness didn't apply as value changed, and map looked skewed. The reason is that Three.js needs to know **how the texture is meant to wrap around the scene**. By default a texture's mapping is `UVMapping` (it projects onto surfaces using UV coordinates). An HDRI is not a flat surface texture — it's a panorama of the surroundings. Setting `EquirectangularReflectionMapping` tells Three.js to sample the texture as a 360° equirectangular sphere surrounding the camera. For equirectangular environment maps this mapping is essential; note that since r151 (via `useLegacyLights`) and the modern WebGPU renderer, the mapping detection is automatic in most flows — but seeing it set explicitly (as here) makes the intent clear and protects against a wrong default.

### Downsides

- **Heavier to load and render** — HDRIs store much more data per pixel (half-float/float color channels, no range clamping), so a 2K HDRI loads and decodes more slowly than a comparable regular texture, and costs more memory on the GPU.
- **Mitigation** — use the smallest resolution that still looks good (2K is a common sweet spot), use the HDRI only for lighting (`scene.environment`) and, when it's also the background, blur the background (`scene.backgroundBlurriness`) if a soft backdrop is acceptable — a blurred background hides the low resolution and compression artifacts of a small HDRI while the lighting still looks rich. See the Revisit section — the exact trade-off is worth testing yourself.

## Code

in repo - `apps/19_1_hdri_map`

```ts
import * as THREE from 'three/webgpu';
import { HDRLoader } from 'three/addons/loaders/HDRLoader.js';

// --- minimal loader setup ---
const loadingManager = new THREE.LoadingManager();
loadingManager.onProgress = (url) => console.log('loading', url);
loadingManager.onLoad = () => console.log('hdri loaded');

const hdriLoader = new HDRLoader(loadingManager);

// --- load the equirectangular HDRI ---
const hdriTexture = await hdriLoader.loadAsync('/textures/environmentMaps/studio_kontrast_02_2k.hdr');

// --- REQUIRED for an equirectangular image ---
hdriTexture.mapping = THREE.EquirectangularReflectionMapping;

// --- apply to the scene: lighting + background ---
scene.environment = hdriTexture;   // lights every Standard/Physical material via IBL
scene.background  = hdriTexture;   // visible backdrop

// --- optional strength / blur adjustments (defaults are 1.0 / 0) ---
scene.environmentIntensity = 1.9;
scene.backgroundIntensity  = 2.4;
scene.backgroundBlurriness = 0;
```

To let the user switch between several HDRIs, keep the loaded textures in an object and let lil-gui write the selected one into `scene.environment` / `scene.background` (as done in the app with the `bridge`, `studio`, `woods` maps).

## Gotchas

- **Always set `EquirectangularReflectionMapping` on the loaded `.hdr` texture.** Forgetting makes backgroundBlurriness not working, incorrectly bright/dark, and skewed. The mapping tells Three.js the texture is a 360° panorama of the surroundings, not a UV-mapped flat image.
- **An HDRI is NOT a normal texture.** Its color values are high-dynamic-range floats, which is what makes it a light source — but it also means it can't be treated like a JPEG: values breeze past 1.0, which is exactly why it lights the scene the way it does.
- **Equirectangular stretching at the poles is normal.** The floor/ground and zenith look horizontally stretched at the top and bottom of the image — that's the projection, not a bug.
- **Lights were set to `visible = false` on purpose.** If you re-enable them (or a stray `AmbientLight`), you no longer see pure image-based lighting from the HDRI — the picture is lit by a combination, which makes it harder to judge how the env map behaves.
- **Don't rely on a GUI tweak to prove a property "doesn't apply."** The README notes the trap: `backgroundBlurriness` appeared stuck at 0 with the GUI — because the mapping wasn't correct. Set `EquirectangularReflectionMapping` first (it's on every loaded texture), then adjust blur/intensity; otherwise you'll debug a symptom, not the cause.

## Revisit

- **HDRLoader vs RGBELoader** — this app imports `HDRLoader` from `'three/addons/loaders/HDRLoader.js'`; some older examples in the wild use `RGBELoader`. Both load `.hdr` files. Worth exploring: what the difference is (the Radiance RGBE format vs the general HDR decoder) and whether `RGBELoader` matters for particular encodes or toolchains. In the modern addons repo, `HDRLoader` is the current name.
- **Resolution strategy** — the README question is still open: a 2K HDRI is used here; is the idea to keep resolution low for load/VRAM, use the HDRI only for `scene.environment`, and rely on `backgroundBlurriness` for a soft background? Test with the GUI: raise the resolution and blur the background, then compare quality vs load time.
- **Per-material vs global intensity (carried over from lesson 19.0)** — since mid-2024 you generally do NOT need to touch `material.envMapIntensity` per material. `scene.environmentIntensity` multiplies the global `scene.environment` for all materials at once. `material.envMapIntensity` only matters when a material has its own override texture in `material.envMap`.
- **`scene.backgroundIntensity` allowed range** — from the previous lesson: `backgroundIntensity` is a plain floating-point multiplier that Three.js does not clamp to a fixed range. Experiment a bit above the default to feel the limits in practice.

- **Traverse** — for models, iterating `model.scene.traverse(...)` and checking `child.isMesh` / `child.isMeshStandardMaterial` is handy for per-mesh tweaks, but for env map intensity it's unnecessary — `scene.environmentIntensity` covers all materials globally.

## Outdated

approach is valid

The HDRI + equirectangular approach is still the standard, current way to do image-based lighting in Three.js. The app runs on the modern `three/webgpu` module with `WebGPURenderer` (note the `import * as THREE from 'three/webgpu'` and `await renderer.init()`), so it's already on the up-to-date rendering path — not the legacy WebGL one. 💡 WebGPU is the forward-looking path here, and this app already uses it.

- `HDRLoader` is the current addon; if you meet `RGBELoader` in older material, it's the older name for the same job — see Revisit.
