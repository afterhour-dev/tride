## Concept

An **environment map** is a texture that describes the light coming from all directions around a point. Instead of placing light sources in the scene manually, we capture (or paint) the surroundings of a scene — a studio, a forest, a sky — and feed that image to the materials as light.

In this lesson the environment map is a **cube texture**: 6 square images, one for each face of an imaginary cube (`px nx py ny pz nz` — positive/negative x, y, z). We already touched cube maps in lesson [[10.10.x_mesh-standard-material-cube-map]] (app `apps/10_10x_cube_map`), where the map was applied to a single sphere via the material's `envMap` property. This time we go deeper: the map drives the whole scene.

### Three roles of an environment map

The same cube texture can be used for three different things:

1. **Background** — what you see behind the objects (via `scene.background`).
2. **Reflection** — the texture appears on shiny surfaces (driven by `roughness` and `metalness`).
3. **Lighting / IBL** — the texture *is* the light source; it illuminates objects from all directions (via `scene.environment`).

**IBL** stands for *Image-Based Lighting*: lighting computed from an image rather than from explicit `Light` objects. This is the important one — a background-only skybox does not light anything.

### Where the textures came from

- The 4 environment maps (`studio`, `lumber`, `creek`, `glasshouse`) were downloaded as **HDRI** files from [Poly Haven](https://polyhaven.com/hdris) — a library of free, CC0 HDRIs.
- HDRI is a single panoramic image (equirectangular projection). Three.js wants 6 cube faces, so the user converted each HDRI to 6 PNGs with the online tool [HDRI-to-CubeMap](https://matheowis.github.io/HDRI-to-CubeMap/).

### The "old school" way (what we deliberately did *not* do)

In old video games and early demos the "skybox" was built by hand:

- create a **massive cube** around the whole scene,
- make its faces visible from the **inside** (flip normal / `side: BackSide`),
- apply the sky texture to its material.

In three.js this is `THREE.CubeTextureLoader` and `CubeReflectionMapping` usage. Why it's a bad idea: it only paints the background. It sits in the world like any other mesh — it does **nothing** for lighting, reflections, or shadows. A skybox is decoration; `scene.environment` is actual light. (Correct spherical-skybox alternatives exist, like `BoxGeometry` + `BackSide`, or a `ShaderMaterial` sky — but for lighting you still want IBL.)

> In this lesson the floor mesh is kept in the scene graph but hidden (`floorMesh.visible = false`) — an easy trap: a floor hidden this way still ignores IBL reflections only because it's not rendered at all.

### Loading the cube map in three.js

`CubeTextureLoader` (unlike `TextureLoader`) takes an **array of 6 image paths** — one per face. With `setPath()` you set the folder once, then just name the files. The face order is fixed: `px, nx, py, ny, pz, nz`.

```ts
const cubeTextureLoader = new THREE.CubeTextureLoader(loadingManager);

const envMap = await cubeTextureLoader
  .setPath('/textures/environmentMaps/studio/')
  .loadAsync(['px.png', 'nx.png', 'py.png', 'ny.png', 'pz.png', 'nz.png']);
```

`loadAsync` is used so we can `await` the 6 files before assigning anything — the app loads **all 4** maps up front and lets you switch them at runtime via the GUI.

### Wiring the map into the scene

```ts
scene.environment = envMap; // IBL: reflections + ambient lighting for all PBR materials
scene.background   = envMap; // visible as the backdrop
```

- `scene.environment` — gives **every** `MeshStandardMaterial` / `MeshPhysicalMaterial` in the scene image-based reflections and fill light. This includes materials that come from loaded models (the `FlightHelmet` glTF, the Blender-exported console), not just materials you instantiate.
- `scene.background` — paints the backdrop with the same texture. Rendering the sky as a *background* is cheaper than a skybox mesh.

### The three scene-level sliders

| Property | Default | Meaning |
|---|---|---|
| `scene.environmentIntensity` | `1.0` | Plain float multiplier for the *lighting* contribution of `scene.environment`. Global — affects all materials at once. |
| `scene.backgroundBlurriness` | `0.0` | Blurs the backdrop (0–1). Lifesaver when the env map resolution is low — hides the pixels. Does not touch lighting. |
| `scene.backgroundIntensity` | `1.0` | Brightens/dims the *background only*. Useful when the background should be bright but shouldn't over-drive the scene's lighting. |

### One slider instead of per-material pain — `envMapIntensity` vs `scene.environmentIntensity`

The classic gotcha: to vary reflection strength you used to set `material.envMapIntensity` on **every** material — annoying for a loaded model with 10+ materials, unless you `traverse()` it. Since roughly **mid-2024** (three.js r16x) this split exists:

- `material.envMapIntensity` → scales only `material.envMap` — the per-material *override* texture you assign yourself.
- `scene.environmentIntensity` → scales `scene.environment` — the **global IBL**. One value, affects everything, loaded models included. This is the one used here, exposed on the GUI (`min 0, max 5, step 0.001`), and it works on materials from both hand-made meshes and imported glTFs.

It's just a plain float multiplier — three.js does **not** clamp it. Values above `1.0` over-brighten the scene; that's legal, often desirable.

### `traverse()` — walking the loaded model

`traverse()` exists on every `Object3D` (so also `Group`, `Mesh`, `Scene`). It recursively visits every child and grandchild — exactly what you need when a glTF comes in as one opaque `Group`:

```ts
flightHelmet.scene.traverse((child) => {
  if ((child as THREE.Mesh).isMesh) {
    (child as THREE.Mesh).castShadow = true;
  }
});
```

The booleans `isMesh`, `isMeshStandardMaterial`, `isGroup`… are set by three.js on every class, so you can type-narrow inside the loop without `instanceof`. In this app `traverse` is only used to enable shadows on the imported meshes — **we do not need it for env-map intensity anymore**, since `scene.environmentIntensity` is global. That's the reason it's discussed here rather than used.

### Why roughness & metalness matter so much here

The torus knot uses `MeshStandardMaterial` with `roughness: 0.1` and `metalness: 1`. With lights off, the environment map is *all* the light:

- `metalness = 1` → the material is a mirror for the env map (no diffuse color visible, reflections dominate).
- `roughness` → spreads/blurs the reflected env map. `0.1` = crisp, sharp reflections. Crank roughness to `1` and the reflection turns into diffuse-ish fill light.

Both are on the GUI (`knotTweaks` folder) precisely so you can watch this. In the app, `ambientLight.visible = false` and `directionalLight.visible = false` by default → **complete darkness except for the env map**. Turn the lights on in the GUI to see the env map plus direct lighting combined (note the directional light is tuned with `intensity = 0.4 * Math.PI`, see Gotchas).

## Code

in repo — `apps/19_0_environment_map_intro`

```ts
import * as THREE from 'three/webgpu';

// setup: canvas, WebGPURenderer + await renderer.init()
const scene = new THREE.Scene();
const camera = new THREE.PerspectiveCamera(75, innerWidth / innerHeight, 0.1, 100);
camera.position.set(-7, 9, 6);

// 1 — load all faces of the cube map (px nx py ny pz nz)
const cubeTextureLoader = new THREE.CubeTextureLoader();

const envMap = await cubeTextureLoader
  .setPath('/textures/environmentMaps/studio/')
  .loadAsync(['px.png', 'nx.png', 'py.png', 'ny.png', 'pz.png', 'nz.png']);

// 2 — one texture, two jobs: light the scene + paint the backdrop
scene.environment = envMap;   // IBL for every PBR material
scene.background = envMap;    // visible sky
scene.environmentIntensity = 1.9;  // global lighting multiplier (no clamp)
scene.backgroundBlurriness = 0.2;  // 0..1, softens a low-res backdrop
scene.backgroundIntensity = 2.4;   // brightens background only

// 3 — a mirror-like material to see the reflections
const material = new THREE.MeshStandardMaterial({
  color: 0xaaaaaa,
  roughness: 0.1,
  metalness: 1,
});
const sphere = new THREE.Mesh(new THREE.SphereGeometry(1, 64, 64), material);
scene.add(sphere);

renderer.setAnimationLoop(() => renderer.render(scene, camera));
```

## Gotchas

- **Per-material `envMapIntensity` is not needed for `scene.environment`** anymore (since ~mid-2024). `material.envMapIntensity` only scales `material.envMap` — a per-material override texture you manually assign. For scene-wide IBL, use `scene.environmentIntensity`. Trying to `traverse()` a model to set intensities is dead weight now.
- `scene.environmentIntensity` is a **raw float multiplier — not clamped**. Values look "wrong" (blown out) above ~1.5–2 for mid-tone HDRIs; that's expected, not a bug. The GUI caps it at 5 for usability, not because three.js restricts it.
- `backgroundBlurriness` blurs **only the background**, and it saves low-resolution env maps from looking pixelated. It does *not* blur the lighting. There's no equivalent for `scene.environment` lighting sharpness baked in — you pick that when you generate the map (or via roughness).
- `backgroundIntensity` affects **background only**. If you crush it to 0 you get a black backdrop while reflections stay bright — good trick, and the README's open question is exactly what the sensible range is (see Revisit).
- **CubeTextureLoader expects exactly 6 paths in order** `px, nx, py, ny, pz, nz`. Wrong order = mirrored/inverted sky. The app hardcodes this array 4 times (once per map) — a helper would avoid copy-paste.
- Setting `scene.environment` affects **all** `MeshStandardMaterial`/`MeshPhysicalMaterial` in the scene at once — including the materials of the loaded FlightHelmet and the Draco-compressed blender console. That's a feature of IBL, but it means "switching scene.environment in the GUI" is a global, instant change across models.
- The old "massive cube around the scene" (inverted `BoxGeometry` + `side: THREE.BackSide` …) is **not** the way to get lighting. It gives you a background only. Use `scene.environment` for IBL; use a cube/`SphereGeometry` skybox only for looks.
- **WebGPU renderer lights use physical units** — this app runs on `three/webgpu` and sets `directionalLight.intensity = 0.4 * Math.PI`. If you copy the light setup into a WebGL renderer with intensity `0.4 * Math.PI` (≈ 1.26) it will look brighter than on WebGL's legacy scaling. Read the three.js docs for the lighting unit of the renderer you're on.
- Misc items visible in the GUI but unrelated to env maps, worth remembering: `shadow.radius` (PCF blur) **does nothing with `PCFSoftShadowMap`**; the `ArrowHelper` direction is computed once at creation and never updates.

## Revisit

- **What are the allowed/meaningful ranges of `scene.backgroundIntensity`?** — flagged as an open question in the README. three.js does not clamp it; practically the useful range seems to be roughly `0…~10` with the maps used here, but it would be worth testing extreme values (very large multipliers) and reading the current docs/source for the WebGPU path.
- **Verify the "mid-2024" claim** — the README says: "we don't need to set `material.envMapIntensity` per material since mid 2024." The split `scene.environmentIntensity` vs `material.envMapIntensity` should be checked against the three.js changelog (r16x) and confirmed on the version pinned in `package.json` (`three@^0.185.1`).
- The converter tool (HDRI-to-CubeMap) may be unmaintained — if it breaks or you want sharper results, load the `.hdr` directly:
> 💡 More up to date alternative: load the `.hdr`/`.exr` directly with `RGBELoader` (or `EXRLoader`) and generate the PMREM-blurred environment in three.js with `PMREMGenerator` — no 6-face pre-conversion step, and you control blur levels — see the official envmaps example.

- `traverse()` deserves a follow-up: exercise the `isMeshStandardMaterial` boolean to tweak materials of loaded models (e.g. flip `metalness` of every metal part of the FlightHelmet and watch the IBL respond).
- Try the console model (Blender-exported, Draco-compressed) with each of the 4 env maps in the GUI — good for building an intuition of how a "neutral studio" vs a "warm glasshouse" changes the same model.
- Revisit the physical-lighting difference: this app deliberately hides ambient + directional lights to see pure IBL; re-open them and re-check `scene.environmentIntensity` interplay with real lights (both still apply additively).

## Outdated

`approach is valid` ✅ — cube-texture environment maps with `scene.environment` + `scene.background` is the standard, current way to do IBL in three.js (WebGL and WebGPU alike).

**🚀 This app already runs entirely on WebGPU** (`WebGPURenderer` from `three/webgpu`, `await renderer.init()`) — no WebGL fallback needed, and every concept in this lesson behaves identically there. WebGL-only users would hit the old physical-light unit differences; here you're on the modern path.

The genuinely outdated part is the *workflow*, not the runtime: pre-converting HDRIs into 6 PNG faces with a third-party web tool, and the old giant-cube skybox. Both are superseded (see Revisit for the `RGBELoader` + `PMREMGenerator` alternative).
