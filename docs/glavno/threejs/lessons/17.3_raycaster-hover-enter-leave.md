## Concept

The [previous lesson](17.2_raycaster-with-mouse.md) colored every sphere the ray pierced. This lesson answers the natural next question: **how do I know *when* the cursor starts hovering an object and *when* it stops?** In other words — how to get DOM-style `mouseenter` / `mouseleave` behaviour out of a raycaster.

### Why there is no `mouseenter` / `mouseleave` event here

The DOM's `mouseenter` / `mouseleave` events work on HTML elements because the browser tracks element boundaries. A `THREE.Mesh` is not an HTML element and the raycaster doesn't dispatch events, so you get nothing for free. What you *do* get is a per-frame answer to the question "does the ray pierce anything right now?". That's only a **snapshot**, not a transition. "Mouse entered the sphere" is a *transition between two consecutive snapshots*: before = nothing hit, now = sphere hit. It has to be derived by you.

The app calls these derived transitions `"pierceenter"` and `"pierceleave"` to keep it honest about what's really happening: a ray starting/stopping its pierce through an object.

### The `currentIntersect` pattern — deriving transitions from snapshots

The whole trick is one state variable holding the *currently hovered* object:

```ts
let currentIntersect: THREE.Intersection | null = null;
```

Then, each frame, compare the fresh raycast result against that stored state:

- **`intersections.length > 0` and `currentIntersect` is `null`** → the ray *just started* piercing an object → that's a `"pierceenter"` (your "mouseenter"). Now remember the hovered object.
- **`intersections.length === 0` but `currentIntersect` is set** → the ray *just stopped* piercing the previously hovered object → that's a `"pierceleave"` (your "mouseleave"). Clear the stored state.
- Any other combination → nothing changed, don't fire anything.

```ts
if (intersections.length) {
  if (!currentIntersect) {
    // "pierceenter" happened — ray just started piercing an object
    // (in the real app: color the object, play a sound, show UI, ...)
  }
  currentIntersect = intersections[0]; // remember what we're hovering
} else {
  if (currentIntersect) {
    // "pierceleave" happened — ray stopped piercing the previous object
  }
  currentIntersect = null; // nothing hovered anymore
}
```

That's the entire pattern. The `// EXPLAIN:` comments in `src/main.ts` point straight at it: one variable to hold the currently hovered object, change color only at the transitions.

### Why the enter/leave fires exactly once, not every frame

Because `currentIntersect` latches the state, the `"enter"` branch only runs on the *first* frame the ray pierces, and the `"leave"` branch only runs on the *first* frame it stops. Every subsequent frame while hovering matches neither transition branch, so nothing re-fires. This is what makes it event-like instead of a continuous condition.

### The visual feedback uses only the first hit

The app changes the hovered sphere's color: base pink `#e6cbe8` on leave, dark blue `#344e70` on enter. Note it only reads `intersections[0]` — the **closest** pierced object. If the ray pierces two spheres at once (possible while they bob past each other), only the first is colored. The reset-then-apply loop from lesson [17.2](17.2_raycaster-with-mouse.md) is commented out: with the `currentIntersect` logic the color only needs touching at the two transition points, so the full per-frame reset is no longer necessary.

```ts
// @ts-expect-error material is there
currentIntersect.object.material.color.set('#344e70'); // on enter
// ...
currentIntersect.object.material.color.set('#e6cbe8'); // on leave
```

### The surrounding scene

Everything else is carried over from earlier lessons: three spheres sharing one geometry but each with its **own** `MeshStandardMaterial` (so colors can differ), bobbing on `Math.sin` at three different frequencies via `THREE.Timer`, a `PerspectiveCamera`, `OrbitControls` with damping, and `raycaster.setFromCamera(mouse, camera)` each tick. The `mousemove` handler still only stores the normalized position:

```ts
mouse.x = (e.clientX / sizes.width) * 2 - 1;
mouse.y = -((e.clientY / sizes.height) * 2 - 1);
```

A `RaycasterHelper` from `@gsimone/three-raycaster-helper` is imported but commented out — wiring it up would draw the ray so you can *see* the pierce/leave transitions.

## Code

in repo — `apps/17_3_raycaster_mouse_enter_leave`

```ts
import * as THREE from 'three/webgpu';

// ... scene, renderer, camera, orbitControls, lights, three spheres
// (each with its OWN MeshStandardMaterial), as in 17.2 ...

const raycaster = new THREE.Raycaster();
const mouse = new THREE.Vector2(0, 0);

// the state variable that turns snapshots into transitions
let currentIntersect: THREE.Intersection | null = null;

window.addEventListener('mousemove', (e) => {
  mouse.x = (e.clientX / sizes.width) * 2 - 1;
  mouse.y = -((e.clientY / sizes.height) * 2 - 1);
});

renderer.setAnimationLoop((timestamp) => {
  timer.update(timestamp);
  const elapsed = timer.getElapsed();

  sphere1.position.y = Math.sin(elapsed * 0.3) * 1.5;
  sphere2.position.y = Math.sin(elapsed * 0.8) * 1.5;
  sphere3.position.y = Math.sin(elapsed * 1.4) * 1.5;

  raycaster.setFromCamera(mouse, camera);

  const intersections = raycaster.intersectObjects([sphere1, sphere2, sphere3]);

  if (intersections.length) {
    if (!currentIntersect) {
      // "pierceenter" — ray just started piercing
      currentIntersect.object.material.color.set('#344e70'); // dark
    }
    currentIntersect = intersections[0]; // remember closest hit
  } else {
    if (currentIntersect) {
      // "pierceleave" — ray stopped piercing
      currentIntersect.object.material.color.set('#e6cbe8'); // pink
    }
    currentIntersect = null;
  }

  orbitControls.update();
  renderer.render(scene, camera);
});
```

## Gotchas

- **"mouseenter/mouseleave" is a lie.** There is no such event in WebGL/WebGPU land — the raycaster returns only per-frame intersection *snapshots*. Enter/leave is logic *you* build on top by diffing consecutive frames against a stored `currentIntersect`. Naming it `"pierceenter"`/`"pierceleave"` (as the README does) is a good reminder.
- **Only `intersections[0]` counts.** `intersectObjects` returns hits sorted by distance, and the pattern stores/colors only the first. If the ray pierces two spheres, the further one gets nothing — and if the first moved away *between* frames, that's a leave even though the ray still pierces the second one. If you want per-object enter/leave, you need per-object state, not one `currentIntersect`.
- **Forget to `null` the state on leave, and enter never re-fires.** `currentIntersect` must be reset to `null` in the no-hit branch — otherwise the next pierce sees `currentIntersect` still set and skips the enter branch forever.
- **The color change depends on each sphere having its own material.** Three meshes sharing one `MeshStandardMaterial` would all change colour when one hovers — same lesson as 17.1/17.2.
- **`currentIntersect.object` is an `Object3D`**, which has no `.material` — the `@ts-expect-error` in the code papers over it. A cleaner alternative is `if (currentIntersect.object instanceof THREE.Mesh)` narrowing before touching `.material`.
- **Not raycaster's job to track "previous".** The raycaster is stateless and doesn't "remember" the last frame's hit — *you* hold that memory in `currentIntersect`. Keeping raycasting inside `setAnimationLoop` (once per rendered frame) still applies, per 17.2.

## Revisit

- **Only one `currentIntersect` for the whole scene.** If you wanted independent hover state per object, you'd track `Map<Object3D, boolean>` or mark each mesh… — worth thinking through where the single-slot pattern breaks (the two-spheres-pierced case) and how you'd extend it.
- **The `RaycasterHelper`** from `@gsimone/three-raycaster-helper` (imported, commented out) — enabling it (`raycasterHelper.hits = intersections; raycasterHelper.update();`) draws the ray and hit markers, which makes pierce/leave frames much more visible. Already noted in 17.2's Revisit.
- **GPU-side picking** — per-frame CPU raycasts are fine for a handful of spheres but not for thousands of objects. Revisit GPU picking (render IDs, read a pixel) if/when hover hitches. Also noted in 17.2.
- **The commented-out reset-then-apply loop** — it's still the right mental model for "color everything that's pierced", and the enter/leave pattern is its stateful replacement. Flip between them mentally: one is stateless-per-frame, the other is stateful transitions.

## Outdated

approach is valid

> 🚀 This project already runs on the **WebGPU** renderer (`three/webgpu` + `WebGPURenderer`, so no import from `three` legacy). The enter/leave pattern is pure logic on top of CPU-side `Raycaster` results, which is renderer-agnostic — it behaves identically on WebGL and WebGPU. If you later need GPU-side picking for thousands of objects, the WebGPU renderer offers async render-target pixel reads (`readRenderTargetPixelsAsync`), but the \`currentIntersect\` transition pattern itself stays exactly the same.
