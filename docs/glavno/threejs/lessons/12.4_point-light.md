# Point Light

Exploring `PointLight` — the three.js light that behaves like a bare lightbulb: it starts at an infinitely small point and spreads uniformly in every direction.

## Concept

A `PointLight` is the closest thing to a **lighter** or a naked **lightbulb**. Unlike `DirectionalLight` (which arrives as parallel rays, like the sun) or `HemisphereLight` (which lights from all directions at once), a point light has a **single, specific location in the scene**, and from that exact point it emits light **uniformly in all directions**.

That one property drives everything else:

- **It lives at a position.** Because it fans out from a point, you must place it in the scene: `pointLight.position.set(x, y, z)`. Move it and the whole distribution of light changes.
- **Distance to the surface matters.** A surface close to the light is much brighter than one far away — the light falls off over distance (unlike a directional light, where distance does nothing).
- **Every side of an object near the light picks some light up.** Since it radiates `360°`, surfaces all around the source get hit, though brightness drops with distance and angle.

### The constructor arguments

```ts
new THREE.PointLight(color, intensity, distance, decay)
```

- **`color`** — the light's color (default `0xffffff`). Here `0xff9000`, a warm orange.
- **`intensity`** — the brightness (default `1`). Here `0.5`.
- **`distance`** — (optional) *maximum* range of the light in world units. Light only reaches surfaces within this radius; beyond it, the light contributes nothing. Default `0` means "no limit — light reaches infinitely far" (subject to `decay`).
- **`decay`** — (optional) how quickly the light fades with distance. Default is `-1` in the constructor, which falls back to the renderer's `useLegacyLights` choice; set `2` for physically correct `1/d²` falloff.

You can pass all four at construction, or create an empty light and assign properties afterwards (as the app does) — handy when you want to expose them to a lil-gui panel:

```ts
const pointLight = new THREE.PointLight(0xff9000, 0.5);
pointLight.distance = 10;
pointLight.decay = 2;
pointLight.position.set(1, -0.5, 1);
scene.add(pointLight);
```

### `distance` — the range, and its values

`distance` is the **cutoff radius** in world units:

- `0` → the light has **infinite range** (it only dims via `decay`).
- Any positive number → the light shines up to that many world units, then **stops entirely**, even where it would otherwise still be visibly bright.

So `distance = 10` (as in this app) means the light fully illuminates surfaces within `10` world units and contributes nothing past them. Because the scene here is small (objects sit within a couple of units of the origin), `10` is effectively generous — everything stays lit. Setup objects at the edges of the floor or shrink `distance` in the GUI to see the sphere begin to fade out and then vanish as it crosses the boundary.

### `decay` — how the light fades, and its values

`decay` controls the **mathematical rate of falloff** with distance:

- `0` → **no fade at all**; brightness stays constant regardless of distance (a very unphysical "flat" light).
- `1` → linear falloff.
- `2` → **physically correct** falloff, brightness proportional to `1 / distance²`. This is the right value to emulate a real bulb.

In physically correct mode (`decay = 2`), the light is extremely bright close to the source and drops off quickly as you move away. That's why in the app it's the **side of an object nearest the light that's brightest**, and the far side falls into shadow — a point light gives strong local contrast, perfect for showing off the surfaces near the "bulb."

> 💡 For `decay` and `distance` to behave physically, the renderer must not be in legacy-lights mode. In current Three.js (used here via `WebGPURenderer`) `useLegacyLights` defaults to `false`, so `decay = 2` gives the correct `1/d²` falloff out of the box. If you're ever on an old setup where `renderer.useLegacyLights = true`, decay behaves differently — set it to `false` for realistic falloff.

### Positioning the point light

Because the center is just a point in space, you place it with `position.set(...)`. In this app it's moved to `(1, -0.5, 1)` — slightly to the front-right and a touch below center. Since the object cluster sits around the origin, this placement puts the light close to them, making the near-side brightness / far-side darkness visible. Move `x/y/z` in the GUI and you can watch the "hot spot" travel across the scene in real time.

### Why the other lights are hidden

Like the other lessons in this series, the app also creates `AmbientLight`, `DirectionalLight`, and `HemisphereLight` — but each is set to `visible = false` so the **point light's** own, local contribution is the only thing lighting the `MeshStandardMaterial` surfaces. This isolation is what makes the point light's character (local, fading, omnidirectional) actually readable; with all four on, the point light's effect would be swamped by the ambient fill and directional shading.

## Code

in repo - `apps/12_4_point_light`

```ts
import * as THREE from 'three/webgpu';

const canvas = document.querySelector<HTMLCanvasElement>('canvas#tride')!;

async function init() {
  const scene = new THREE.Scene();

  const renderer = new THREE.WebGPURenderer({ canvas });
  await renderer.init();

  // Other light types exist but are hidden (visible = false)
  // so only the point light's local, fading contribution is visible.

  // Point light — like a lighter: one point, radiating everywhere.
  // default decay (-1) resolves to physical 1/d² falloff in WebGPU.
  const pointLight = new THREE.PointLight(0xff9000, 0.5);
  pointLight.distance = 10; // range in world units (0 = infinite)
  pointLight.decay = 2;     // physically correct 1/distance² falloff
  pointLight.rotation.y = 0;
  pointLight.position.set(1, -0.5, 1); // place the "bulb"
  scene.add(pointLight);

  // MeshStandardMaterial needs light to be visible
  const material = new THREE.MeshStandardMaterial();
  material.roughness = 0.4;

  const box = new THREE.Mesh(new THREE.BoxGeometry(0.75, 0.75, 0.75), material);
  const torus = new THREE.Mesh(new THREE.TorusGeometry(0.3, 0.2, 32, 64), material);
  torus.position.x = 1.5;
  const sphere = new THREE.Mesh(new THREE.SphereGeometry(0.5, 32, 32), material);
  sphere.position.x = -1.5;
  const floor = new THREE.Mesh(new THREE.PlaneGeometry(5, 5), material);
  floor.rotation.x = -Math.PI / 2;
  floor.position.y = -0.65;

  scene.add(box, torus, sphere, floor);

  // Camera
  const camera = new THREE.PerspectiveCamera(75, innerWidth / innerHeight, 0.1, 100);
  camera.position.set(2, 1, 1);
  scene.add(camera);

  // Render loop
  renderer.setPixelRatio(Math.min(devicePixelRatio, 2));
  renderer.setSize(innerWidth, innerHeight);
  renderer.setAnimationLoop(() => {
    renderer.render(scene, camera);
  });
}

await init();
```

> Note: in the minimal snippet above, `pointLight.rotation.y = 0` is a harmless no-op; it is not in the actual app. In the real app, `intensity`, `color`, `position.x/y/z`, `distance`, `decay`, and `visible` are all exposed to a lil-gui panel so the falloff can be explored live.

## Gotchas

- **`distance` is a hard cutoff, not a "fade to here."** It's the max range in world units — beyond it the light contributes *nothing*, even where it would still be clearly visible. `0` means unlimited. If you set `distance` small you get a sharp, artificial edge, not a gentle fade; use `decay` for the smooth falloff and `distance` only for a hard range limit.

- **`decay` and `distance` interact.** With `decay = 2`, brightness scales as `1 / distance²`; with `decay = 0` it does not fade at all. The default constructor `decay` is `-1`, which means "inherit the renderer's legacy-light setting." In modern Three.js (`WebGPURenderer`, `useLegacyLights = false`) that resolves to physically correct `2`; on an old setup with `useLegacyLights = true` it behaves like `1`. If your falloff looks wrong, check this — it's a classic source of confusion.

- **The light is invisible in the scene.** `PointLight` renders nothing itself — only the meshes reveal its effect. To reason about its location, either place a debug mesh at `light.position`, or (as the app does) tweak `position.x/y/z` in the GUI and watch the hot spot move.

- **Both near-side brightness and far-side darkness are expected.** Because a point light fades with distance, the side of an object facing the light is bright and the far side falls dark. This is correct physical behavior, not a bug — it's the whole point of a point light versus an ambient one.

- **`MeshStandardMaterial` renders black without light.** As in the previous lessons, standard/physical materials need at least one visible light source. The app hides the other lights, so if you ever toggle the point light off you'll go dark.

- **`await renderer.init()` is mandatory for WebGPU.** The `WebGPURenderer` must finish async initialization before the first render, or you get a blank canvas.

## Revisit

- **`useLegacyLights` and physical decay.** Dig into how the renderer's `useLegacyLights` flag (and the old `renderer.physicallyCorrectLights`) controls whether `decay`/`intensity` behave physically. In current Three.js the default is already correct, but the history is worth knowing so a legacy snippet doesn't confuse you.

- **Intensity units in physical mode.** When `useLegacyLights = false`, `intensity` behaves in a more physical sense (candela-ish local intensity) and values needed differ from the legacy mode. Experiment with a `PointLight` at `intensity` values above `1` here — in this app's GUI it's clamped to `0–1`, but real scenes often need more.

- **Performance / use across a scene.** A point light is omnidirectional and (in WebGPU) generally cheaper per light than shadow-casting spotlights, but each light still costs. Compare lighting a large scene with many point lights vs. fewer — the falloff + range controls are the main tuning knobs.

- **Shadows.** Point lights *can* cast shadows later, using a shadow camera over all 6 directions (a cube shadow map). Come back to this topic once you reach the shadows lesson.

- **Links/GLSL on GPU.** Intriguing to revisit `1/d²` in terms of what a shader actually computes per fragment — `distance` and `decay` map directly to the attenuation constant in the lighting equation.

## Outdated

Approach is valid — this is a current WebGPU-based Three.js setup using the recommended `WebGPURenderer` and PBR (`MeshStandardMaterial`). `PointLight` remains a standard, supported light type. One older naming worth watching: the constructor argument is `color` (so `new THREE.PointLight(0xff9000, ...)`), and `physicallyCorrectLights` was renamed to `useLegacyLights` — but in the modern WebGPU path the physical default is already on, so nothing here needs updating. No parts are obsolete.
