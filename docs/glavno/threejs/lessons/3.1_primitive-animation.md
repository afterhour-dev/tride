## Concept

This lesson covers the most basic way to animate objects in Three.js: manually updating properties each frame inside a render loop. The app creates a wireframe box, moves it across the screen, rotates it, and has the camera follow it — all driven by a simple `tick()` function called every animation frame.

### The animation loop

Every animation in Three.js (or any game engine) follows the same pattern:

1. **Track time** — read the current time and compute how much time passed since the last frame (delta time).
2. **Update state** — move, rotate, or scale objects based on elapsed time.
3. **Render** — tell the renderer to draw the scene.
4. **Schedule next frame** — use `window.requestAnimationFrame(tick)` so the browser calls `tick()` again before the next repaint.

```ts
let time = Date.now();

function tick() {
  const currentTime = Date.now();
  const deltaTime = currentTime - time;
  time = currentTime;

  // update objects here...

  renderer.render(scene, camera);
  window.requestAnimationFrame(tick);
}

tick();
```

### Why `Date.now()` is called "primitive"

The code uses `Date.now()` to read wall-clock time. This works but isn't the most robust approach — it doesn't account for tab backgrounding or high-precision timing. Three.js's built-in `Clock` class wraps `performance.now()` and handles edge cases automatically. Using `Date.now()` here is fine for learning, but in real projects you'd typically reach for `THREE.Clock`.

### Delta time — making animation framerate-independent

`deltaTime` is the number of milliseconds between the current frame and the previous one. Instead of writing:

```ts
mesh.position.x += 0.01;  // moves at different speed on different machines
```

you write:

```ts
mesh.position.x += deltaTime * 0.001;  // moves at the same speed everywhere
```

Without delta time, a fast machine (144fps) moves the object 144 times per second while a slow machine (30fps) moves it only 30 times — the object travels different distances. Multiplying by `deltaTime` normalizes the movement so it's consistent regardless of framerate.

### Why `camera.lookAt(mesh.position)`

`camera.lookAt()` points the camera's forward direction at a target point. Here it makes the camera always face the moving box, creating a simple tracking shot. The camera itself doesn't move — it just rotates to keep the box in frame.

### Why `window.requestAnimationFrame` instead of recursion

You might wonder why we don't just call `tick()` at the end of `tick()`. Two reasons:

1. **Browser optimization** — `requestAnimationFrame` syncs with the display's refresh rate (typically 60Hz) and pauses when the tab is hidden, saving battery and CPU.
2. **Stack safety** — direct recursion would eventually blow the call stack. `requestAnimationFrame` schedules the next call as a separate event, keeping the stack clean.

### WebGPU renderer

This app uses `WebGPURenderer` (imported from `three/webgpu`) instead of the classic `WebGLRenderer`. WebGPU is the modern successor to WebGL, offering lower-level GPU access and better performance. The renderer requires an `await renderer.init()` call before use — unlike WebGL which initializes synchronously.

## Code

in repo - `apps/3_animation`

```ts
import * as THREE from 'three/webgpu';

// Setup
const scene = new THREE.Scene();
const boxGeometry = new THREE.BoxGeometry(0.5, 0.5, 0.5);
const material = new THREE.MeshBasicMaterial({
  color: 0x4c9892,
  wireframe: true,
});
const mesh = new THREE.Mesh(boxGeometry, material);
mesh.position.x = -0.5;
mesh.position.z = 0.5;
scene.add(mesh);

// Camera — slightly offset for a more 3D perspective
const camera = new THREE.PerspectiveCamera(75, 800 / 600);
camera.position.set(0.1, 0.5, 3);
scene.add(camera);

// Renderer
const renderer = new THREE.WebGPURenderer({ canvas });
await renderer.init();
renderer.setSize(800, 600);
renderer.setClearColor(0x000000, 1);

// Animation loop
let time = Date.now();

function tick() {
  const currentTime = Date.now();
  const deltaTime = currentTime - time;
  time = currentTime;

  mesh.position.x += 0.001;
  mesh.rotation.y += deltaTime * 0.0002;
  camera.lookAt(mesh.position);

  renderer.render(scene, camera);
  window.requestAnimationFrame(tick);
}

tick();
```

## Gotchas

- **Forgetting to call `renderer.render()` inside the loop** — if you only update positions but don't re-render, the screen stays frozen. `render()` must be called every frame.
- **Using raw time instead of delta time** — writing `mesh.rotation.y += 0.001` makes the animation run at different speeds on different machines. Always multiply by `deltaTime` for consistent behavior.
- **Calling `tick()` recursively without `requestAnimationFrame`** — direct recursion will eventually cause a stack overflow. Always schedule the next frame with `requestAnimationFrame`.
- **`WebGPURenderer` needs async init** — unlike `WebGLRenderer`, the WebGPU renderer must be awaited: `await renderer.init()`. Forgetting this leads to silent failures or errors.
- **Camera must be added to the scene for `lookAt` to work** — calling `camera.lookAt()` without adding the camera to the scene tree can produce unexpected results depending on the Three.js version.

## Revisit

- **`Date.now()` vs `THREE.Clock`** — the lesson uses `Date.now()` for simplicity, but `THREE.Clock` is the standard approach. Try replacing `Date.now()` with a `Clock` instance and compare the API.
- **Why the camera doesn't move but `lookAt` still works** — `lookAt` only affects rotation, not position. The camera stays put while turning to face the box. This is a useful trick for orbit-style cameras.
- **WebGPU vs WebGL** — this app uses WebGPU. Consider duplicating the experiment with `WebGLRenderer` to understand the differences in setup and performance.
- **Easing functions** — the movement here is linear (constant speed). Try adding easing (ease-in, ease-out, sinusoidal) to make the animation feel more natural.

> 💡 More up to date alternative: Use `THREE.Clock` instead of `Date.now()` for production animation loops — it handles tab backgrounding, precision, and pausing correctly.
