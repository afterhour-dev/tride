# 19.5 Real-time Environment Map

## Concept

So far (`19.0`–`19.3`) our environment maps were **static**: a pre-rendered HDR or LDR image (loaded from a file) was assigned to `scene.environment` and the GPU sampled it to compute reflections. That works, but the map is a *picture* — its light sources can't move, and nothing in it reacts to the scene.

A **real-time environment map** is the opposite: the environment map itself is a **live render of the actual 3D scene**, produced by the app every single frame. Instead of loading an image, we point a special camera at our scene, capture it into a cube texture (6 square faces, the internal format env maps use), assign that texture to `scene.environment`, and re-capture each frame. Now a glowing torus that rotates in the scene really *moves the light* across the objects that reflect it — dynamic reflections, in real time.

### The pieces

1. **An emissive light source in the scene.** A torus wraps around the scene with a `MeshBasicMaterial` whose color is `new THREE.Color(10, 4, 2)` — values **way above `1`**. Because the cube texture it gets rendered into is high-range (see below), colors can exceed the `0..1` LDR range, so the torus acts like a bright HDR light source, not a dim mesh.

2. **`CubeRenderTarget`** — the render target that captures the scene into a cube texture:
   ```ts
   const cubeRenderTarget = new THREE.CubeRenderTarget(256, {
       type: THREE.HalfFloatType,        // 16-bit per channel — wide range like HDR
       generateMipmaps: true,
       minFilter: THREE.LinearMipMapLinearFilter,
   });
   scene.environment = cubeRenderTarget.texture;
   ```
   - `256` is the resolution of **each cube face**. The type matters most: `THREE.HalfFloatType` (16 bits/channel) or `THREE.FloatType` (32 bits/channel) — both are a *wide dynamic range* like an HDR file, which a plain 8-bit LDR texture (values strictly `0..1`) is not. That wide range is exactly what lets the torus color go beyond `1` and shine. `Float` is 32 bits and stores a huge range but costs twice the memory; with `HalfFloat` the visible difference is negligible and it's noticeably faster/cheaper — it's the sweet spot.
   - `generateMipmaps: true` + `LinearMipMapLinearFilter` make the cube faces filter smoothly when sampled, so reflections don't look aliased.
   - The connection to lighting: `scene.environment = cubeRenderTarget.texture` — it's the **target's `.texture`** that becomes the environment, not the target itself.

3. **`CubeCamera`** — the camera that actually captures the scene into the target:
   ```ts
   const cubeCamera = new THREE.CubeCamera(0.1, 100, cubeRenderTarget);
   scene.add(cubeCamera);
   ```
   Parameters: `near`, `far`, and the `CubeRenderTarget`. It renders all **6 faces automatically**. (The alternative — using six `PerspectiveCamera`s, each with its FOV tuned to fill one face perfectly, one render per side, then manually combining them — *would* work, but `CubeCamera` exists precisely to do that in one object.)
   - Critically, this CubeCamera is **separate from the camera the user sees**. Your normal `PerspectiveCamera` still exists and produces the final image; the CubeCamera never touches the screen. It only fills the cube texture.

4. **Re-render the environment every frame.** Inside the animation loop:
   ```ts
   iluminatingTorus.rotation.x = Math.sin(timer.getElapsed() * 0.2) * 2; // move the light source
   cubeCamera.update(renderer, scene);   // re-capture the 6 cube faces
   renderer.render(scene, camera);       // then draw the frame the user sees
   ```
   Without `cubeCamera.update(...)` on every frame, the environment would be a single stale snapshot — *that* is what makes it "real-time".

### Why the loaded maps are only `background`, not `environment`

The AI-generated equirectangular maps (cabin, castle, japan trees, neon city, sci-fi sky) are loaded through `THREE.TextureLoader` and are **LDR, JPEG, and dark**. If you assign such a dark map to `scene.environment`, the whole scene lights up from a dim picture and looks muddy. Instead:

- `scene.environment = ...` is deliberately **not set** (and the GUI even ships the `scene.environment` dropdown *disabled*), so the loaded maps are **not responsible for lighting at all**.
- `scene.background = cabinTexture` sets them only as the visual background.
- Since we render our own environment (the torus) live, our scene brings its own lights — an LDR background is perfect for that.

Two LDR-specific settings from the previous lessons are repeated here (`19.3`-era knowledge):
```ts
cabinTexture.mapping = THREE.EquirectangularReflectionMapping; // correct mapping for reflections
cabinTexture.colorSpace = THREE.SRGBColorSpace;                // LDR maps look washed-out without this
```

### The bug and the fix — **Layers**

There is a visible bug in this app: lower the **roughness of the torus knot** in the GUI toward `0` (making it mirror-like) and the reflections glitch — you see the environment "chasing itself" with wrong, doubled reflections.

**Why:** the mirrored objects (knot, Flight Helmet, console) reflect the environment map. If those same reflective objects are *also rendered into* the environment map (because the CubeCamera captures the whole scene), the map contains the very objects that are reflecting it — a feedback loop of the scene reflecting a render of itself.

**The fix — layers.** Layers are categories on every `Object3D` (meshes, cameras…). A camera only sees objects that share **at least one layer** with it; by default everything is on layer `0`. Three methods (`layers` is an `Object3D` property):

- `object.layers.enable(1)` — **add** a layer (keeps the others)
- `object.layers.disable(1)` — remove a layer
- `object.layers.set(1)` — enable `1` and **disable all others** (replace)

Applied here:

```ts
iluminatingTorus.layers.enable(1); // torus: {0, 1} — visible to main camera (layer 0) AND cube camera (layer 1)
cubeCamera.layers.set(1);          // cube camera: {1} only — sees the torus, not the reflective meshes
```

The default camera (layer `0`) still sees the torus (it kept layer `0`), while the CubeCamera (layer `1` only) renders a clean environment containing **just the light source** — no mirrored meshes — so the feedback disappears. Note the asymmetry: `enable(1)` (add) on the object vs `set(1)` (replace) on the camera. If we had used `set(1)` on the torus, the *main* camera would stop seeing it — README warns that "we want that illuminating torus to be visible for both the default camera and the cubeCamera, since default layer is 0 we just need to add 1".

### Performance

Every frame costs **6 full renders** (one per cube face) in addition to the main render. So: use the smallest sensible `CubeRenderTarget` resolution (here `256`), keep the part of the scene captured by the CubeCamera simple (thanks to layers, that's just the torus), and watch the frame rate.

The models used to *observe* the reflections: the Flight Helmet (realistic, heavy glTF — Draco-compressed variant also shipped in the repo), a small game console modeled in Blender and Draco-compressed, and the **torus knot** (`TorusKnotGeometry` + `MeshStandardMaterial`, `metalness = 1`, `roughness = 0.1`, `castShadow = true`) — the knob you tweak in the GUI to see how env-map lighting changes with material properties.

## Code

in repo - `apps/19_5_real_time_env_map`

```ts
import * as THREE from 'three/webgpu';

const scene = new THREE.Scene();
const renderer = new THREE.WebGPURenderer({ canvas });
await renderer.init();

// 1. LDR equirectangular map — background ONLY, never the lighting environment
const cabinTexture = await new THREE.TextureLoader(loadingManager).loadAsync(
	'/textures/environmentMaps/ai-images/cabin_interior.jpg',
);
cabinTexture.mapping = THREE.EquirectangularReflectionMapping;
cabinTexture.colorSpace = THREE.SRGBColorSpace; // LDR maps look washed-out without sRGB

scene.background = cabinTexture;
// scene.environment = cabinTexture; // NOT set — we light the scene ourselves

// 2. emissive light source: a torus around the scene.
//    color > 1 works because the cube texture below is high range (HalfFloat)
const iluminatingTorus = new THREE.Mesh(
	new THREE.TorusGeometry(8, 0.4),
	new THREE.MeshBasicMaterial({ color: new THREE.Color(10, 4, 2) }),
);
iluminatingTorus.position.y = 1;

iluminatingTorus.layers.enable(1); // seen by the main camera (0) AND the cube camera (1)
scene.add(iluminatingTorus);

// 3. CubeRenderTarget → high-range cube texture = the live environment
const cubeRenderTarget = new THREE.CubeRenderTarget(256, {
	type: THREE.HalfFloatType, // 16-bit wide range, half the memory of FloatType
	generateMipmaps: true,
	minFilter: THREE.LinearMipMapLinearFilter,
});
scene.environment = cubeRenderTarget.texture;

// 4. CubeCamera captures the scene INTO the target (near, far, target)
const cubeCamera = new THREE.CubeCamera(0.1, 100, cubeRenderTarget);
cubeCamera.layers.set(1); // only "sees" the torus — reflective meshes stay out of the env map
scene.add(cubeCamera);

// 5. the user's viewing camera — completely separate from the CubeCamera
const camera = new THREE.PerspectiveCamera(75, aspect, 0.1, 100);
scene.add(camera);

// 6. per frame: move the light source → re-capture the environment → render
function tick(timestamp: number) {
	timer.update(timestamp);

	iluminatingTorus.rotation.x = Math.sin(timer.getElapsed() * 0.2) * 2;

	cubeCamera.update(renderer, scene); // re-renders the 6 cube faces
	renderer.render(scene, camera);
}
renderer.setAnimationLoop(tick);
```

## Gotchas

- **`scene.environment` needs the target's `.texture`, not the target.** `scene.environment = cubeRenderTarget.texture` — assign the texture produced by the `CubeRenderTarget`, not the `CubeRenderTarget` itself.
- **Forgetting `cubeCamera.update(renderer, scene)` per frame** makes the environment a one-time snapshot — it stays "static" no matter how much the scene moves. Re-capture every frame; that's the entire point of a real-time env map.
- **`enable` vs `set` on layers — easy to mix up and "get lost in what is being rendered".** `enable(1)` *adds* layer `1`; `set(1)` replaces the layer mask with `{1}` only. README explicitly warns to be careful here. Mistake example: `iluminatingTorus.layers.set(1)` would remove layer `0`, and the *main* camera (layer `0`) would stop rendering the torus entirely.
- **Lights are NOT affected by layers.** Layer filtering decides which objects a camera renders — it does not stop a `DirectionalLight`/`AmbientLight` from lighting objects on other layers. Keep that in mind if you expect layers to "hide" a light.
- **Wide-range requirement for emissive colors.** `new THREE.Color(10, 4, 2)` only glows because the cube texture is `HalfFloatType`/`FloatType`. Into a plain 8-bit LDR texture the values would clip at `1` and the torus would be a dim white-ish ring. High range on the target is what buys you the HDR-light behavior.
- **Skipping the LDR details makes maps look wrong.** These JPEG env maps need `.mapping = THREE.EquirectangularReflectionMapping` and `.colorSpace = THREE.SRGBColorSpace`, otherwise switching background maps looks washed out or maps reflections incorrectly.
- **Background ≠ environment.** Setting a dark LDR image as `scene.environment` makes the whole scene dim and muddy; the whole point of this setup is that *live* environment lighting comes from your own emissive objects. The GUI even disables the `scene.environment` dropdown to prevent the mistake.
- **6 renders per frame is expensive.** One render per cube face, plus the main render. Keep the capture resolution small (`256`) and the captured scene simple (torus only, thanks to layers). Watch the frame rate while dragging the GUI.
- **`directionalLight.shadow.radius` doesn't work with `PCFSoftShadowMap`** (GUI note, carried over from previous shadow lessons) — irrelevant to the env map itself, but easy to chase while testing reflections.

## Revisit

- **The roughness-`0` bug proves the env map contains the mirrored meshes.** Try it again while toggling the layers on/off (temporarily comment `cubeCamera.layers.set(1)` / `iluminatingTorus.layers.enable(1)`) — it's the clearest hands-on demonstration of what layers are protecting you from. Worth understanding *why* the feedback happens, not just the fix.
- **Commented-out floor mesh** (`PlaneGeometry` + `MeshStandardMaterial`, roughness `0.4`, metalness `0.3`): a simple reflective plane would make the moving env light very visible on a large surface — good candidate to uncomment and play with.
- **`castShadow` on all model meshes.** The commented-out `traverse()` passes over the Flight Helmet and the console show how to enable `castShadow` per-mesh across an imported model. The knot already has `castShadow = true`; the models don't.
- **Draco-compressed variants.** The repo ships the Flight Helmet in plain glTF and in `glTF-KTX2-BasisU`, and the console (Blender-built) is loaded via `DRACOLoader`. Compare load time and this lesson's env-map behavior between compressed and uncompressed — connects to `16.3` (Draco).
- **`gsap` is installed but unused** (`import gsap from 'gsap'` is commented out). Could replace the sine-based torus rotation with a tween — e.g. animate `iluminatingTorus.rotation.x` to see the env light sweep smoothly.
- **Shadow maps interplay** (`13.x`): `renderer.shadowMap.enabled`/`type` GUI switches are present but shadows are off here. Combining mirror-like materials, a moving env light, and shadow maps is a natural next experiment.
- **Layers and the Raycaster.** The docs note `Object3D.layers` also filters objects in `Raycaster` intersection tests — not used yet; could be useful to reuse the layer system for hover/click filtering (see `17.x`).

## Outdated

approach is valid

> ⚠️ **This is a WebGPU-first lesson.** `CubeRenderTarget`, `CubeCamera`, and the whole `three/webgpu` pipeline these rely on run on the `THREE.WebGPURenderer` — they do not exist on the classic WebGL renderer. If you need dynamic cube-map environments in a WebGL project you'd be hand-rolling the six-camera capture yourself (the approach the lesson explicitly avoided). Prefer the WebGPU path for real-time environment maps.
