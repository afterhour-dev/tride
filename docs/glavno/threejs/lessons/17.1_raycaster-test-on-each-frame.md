## Concept

The previous lesson ([17.0 raycaster intro](17.0_raycaster-intro.md)) cast the ray **once**, before the scene even rendered. That answers the question *"does this static ray hit anything, and where?"* — a single instant snapshot.

This app asks the harder, more realistic question: *"what does the ray hit **right now**, while things are moving?"* And the only correct answer is to **test on every frame** — inside the animation loop.

### Why per-frame?

A ray is a snapshot in time. If the spheres are bobbing up and down and you cast the ray a single time, you catch them in exactly one position. A frame later the spheres have moved and the answer is outdated. Anything animated — moving platforms, enemies, the player's own hand — has to be raycast **again each frame** if you want collision/picking to follow the motion.

Look at the sphere motion:

```ts
sphereMesh1.position.y = Math.sin(elapsedTime * 0.3) * 3;
sphereMesh2.position.y = Math.sin(elapsedTime * 0.8) * 2.5;
sphereMesh3.position.y = Math.sin(elapsedTime * 1.4) * 2;
```

Three frequencies, three amplitudes. The spheres sweep up and down through, and *past*, the ray line (ray is at `y = 0`, sphere radius `0.5`). A sphere only registers a hit while it actually crosses `y = 0`; when it's high up, the ray passes under it and the intersection disappears. Only a per-frame test can track that.

### The per-frame pattern

Each tick does the same four steps:

```ts
// 1. Set the ray fresh (origin can change, direction must stay unit-length)
raycaster.set(rayOrigin, rayDirection);

// 2. Test against the objects we care about — returns hits, nearest-first
const intersections = raycaster.intersectObjects(objectsToTest);

// 3. Reset the old state BEFORE applying new hits
for (const ob of objectsToTest) {
	ob.material.color.set('#e6cbe8');
}
for (const item of intersections) {
	if (item.object instanceof THREE.Mesh) {
		item.object.material.color.set('#344e70');
	}
}

// 4. Visualize + render
raycasterHelper.hits = intersections;
raycasterHelper.update();
renderer.render(scene, camera);
```

**Step 3 is the pattern that carries the lesson.** Every frame an object that was *not* hit must go back to its default color, and an object that *is* hit turns dark. If you only set the hit color and never reset, the first sphere to be hit stays dark forever — the set is never "released". Reset-then-apply makes the visual state mirror the ray's state on every single frame.

### The `updateMatrixWorld(true)` question

In the previous lesson we needed `scene.updateMatrixWorld(true)` before raycasting, because the ray was cast **before any render** — the spheres had been moved with `.position.set()` but their `matrixWorld` had never been recalculated, so the raycaster (which works in world space) saw every hit at `distance ≈ 2.5` as if all spheres sat at the origin.

In **this** app you do **not** need to call it, and that's the coincidence. Why? Because `renderer.render()` already calls `scene.updateMatrixWorld()` internally on every frame. Once the animation loop is running, one render always precedes the next raycast, so the world matrices are always up to date when the next tick's raycast runs. The stale-matrix problem only exists while *nothing has rendered yet*.

That's the exact answer to the niggle in the README: yes, it's correct *not* to call it, and yes, `renderer.render()` is the thing that's doing the matrix work. (Worth noting: the raycast in the loop technically runs on matrices from the *previous* frame's render — a one-frame lag — but at 60fps the motion is continuous and it doesn't matter here.)

### The visual helper

`@gsimone/three-raycaster-helper` gives us `RaycasterHelper`, which draws the ray as a line in the scene (origin → near → far points) and puts markers on the hit points:

```ts
import { RaycasterHelper } from '@gsimone/three-raycaster-helper';

const raycaster = new THREE.Raycaster();
const raycasterHelper = new RaycasterHelper(raycaster);
scene.add(raycasterHelper);

// in the loop:
raycasterHelper.hits = intersections;  // or helper.hits = hits, depending on version
raycasterHelper.update();
```

It's a scene object: add it once, feed it the current intersections every frame, call `update()`, and you can *see* the ray reaching out and tapping the spheres mid-animation — invaluable when debugging picking inside a moving scene. It's not part of core three.js (a PR to add it to core was declined) but it's available via [three-stdlib](https://github.com/pmndrs/three-stdlib) v2.35+ and the [@gsimone/things](https://github.com/gsimone/things) repo.

## Code

in repo — `apps/17_1_raycaster_test_on_each_frame`

```ts
// minimal working example: raycast every frame against three moving spheres
const scene = new THREE.Scene();
const raycaster = new THREE.Raycaster();
const rayOrigin = new THREE.Vector3(-3, 0, 0);
const rayDirection = new THREE.Vector3(1, 0, 0).normalize();

const sphereColor = '#e6cbe8';
// Each mesh gets its OWN material — we change colors per object
const sphere1 = new THREE.Mesh(geo, new THREE.MeshStandardMaterial({ color: sphereColor }));
const sphere2 = new THREE.Mesh(geo, new THREE.MeshStandardMaterial({ color: sphereColor }));
const sphere3 = new THREE.Mesh(geo, new THREE.MeshStandardMaterial({ color: sphereColor }));
sphere1.position.x = -2;
sphere3.position.x = 2;
const objectsToTest = [sphere1, sphere2, sphere3];
scene.add(...objectsToTest);

// Visual helper for the ray + hits (not core three.js)
const raycasterHelper = new RaycasterHelper(raycaster);
scene.add(raycasterHelper);

renderer.setAnimationLoop((timestamp) => {
	timer.update(timestamp);
	const elapsed = timer.getElapsed();

	sphere1.position.y = Math.sin(elapsed * 0.3) * 3;
	sphere2.position.y = Math.sin(elapsed * 0.8) * 2.5;
	sphere3.position.y = Math.sin(elapsed * 1.4) * 2;

	// 1 — set the ray fresh each frame
	raycaster.set(rayOrigin, rayDirection); // direction must be unit length

	// 2 — test against the moving objects
	const intersections = raycaster.intersectObjects(objectsToTest);

	// 3 — reset old colors, then apply new hits
	objectsToTest.forEach((ob) => ob.material.color.set(sphereColor));
	intersections.forEach((item) => {
		if (item.object instanceof THREE.Mesh) {
			item.object.material.color.set('#344e70');
		}
	});

	// 4 — helper + render
	raycasterHelper.hits = intersections;
	raycasterHelper.update();

	renderer.render(scene, camera);
});
```

## Gotchas

- **Reset before applying, or colors stick.** `intersections` only contains what's hit *this frame*. If you set the hit color but never reset the non-hits back to the default, the first object ever hit stays darkened for the whole session. Reset-all-then-apply is the order that makes the colors track the ray correctly.
- **Per-object color changes require per-object materials.** Three meshes sharing one `MeshStandardMaterial` instance means `material.color.set()` on one changes all three. That's why the app constructs a separate material for each sphere — same color *value*, three different instances. `// EXPLAIN:` comments in the code call this out directly.
- **You don't need `scene.updateMatrixWorld(true)` here** — the previous lesson did, but that was because the raycast ran before the first render. `renderer.render()` updates world matrices every frame, so inside the loop they're already fresh. Forcing matrix updates every frame just costs performance.
- **`distance` values change every frame — that's correct.** The spheres sweep in `y`, so the point where the ray first enters the sphere shifts as the sphere rises and falls, and hits vanish entirely when a sphere floats above the ray line. Don't mistake these changing values for a bug.
- **TypeScript wants a narrowing guard.** `intersection.object` is `Object3D`, which has no `.material`. `if (item.object instanceof THREE.Mesh)` narrows it to `Mesh` (which does). The code has an `// EXPLAIN:` wondering whether to just suppress the error — keep the guard, it's the honest type-check and costs nothing.
- **Direction must stay unit-length.** Even though `(1, 0, 0)` is already length 1, the code normalizes anyway — insurance for when someone later edits the value. Non-normalized direction silently scales every `distance` and `point`.
- **Raycasting has a real per-frame cost.** CPU-side math over every tested object, transformed by its world matrix. Three small spheres is trivial; do this on thousands of complex meshes every frame and you'll feel it. Use it as little as you can get away with — but for *moving* objects, per-frame is the minimum.

## Revisit

- **One-frame lag nuance:** worth meditating on the exact ordering — positions are set, then raycast, then render (which recomputes matrices). The raycast in frame N uses matrices from frame N-1's render. At 60fps this is invisible, but if you ever need *sampling-correct* "current frame" intersections, call `scene.updateMatrixWorld()` manually before the raycast.
- **`setFromCamera` / mouse picking** — the ray here is hardcoded; the natural next step (pointed at in the previous lesson too) is `raycaster.setFromCamera(pointerNDC, camera)` with the real mouse position, so the ray follows the cursor.
- **When per-frame is overkill** — for static scenes you can raycast on demand (`.onClick`), and for *many* objects consider only raycasting against an AABB / `boundingSphere` broad-phase list first, then precisely on the candidates. The three.js `Raycaster` does check bounding spheres internally, but you still control how many objects you feed it.
- **GPU-side picking** — when even a tight CPU loop is too slow for thousands of objects, GPU picking (render IDs into an offscreen render, read a pixel) is the alternative. See the linked forum thread.

## Outdated

approach is valid

> 🚀 This project already runs on the **WebGPU** renderer (`three/webgpu` + `WebGPURenderer`). The `Raycaster` itself is renderer-agnostic — it does CPU-side math against object geometries — so per-frame testing works identically on WebGL and WebGPU. If you ever need *GPU*-side picking (faster for scenes with thousands of objects), the WebGPU path offers async render-target pixel reads (`readRenderTargetPixelsAsync`), but for this scene CPU raycasting is correct, portable, and fast enough.
