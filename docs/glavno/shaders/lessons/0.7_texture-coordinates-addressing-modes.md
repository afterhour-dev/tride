## Concept

Through [[0.5_textures-and-multiplicative-blending]] and [[0.6_blending-two-textures-and-alpha-problem]] every texture sample used UVs that happened to live inside `[0, 1]` — the remembered convention: `(u: 0.0, v: 0.0)` at the bottom-left of the image, `(u: 1.0, v: 1.0)` at the top-right. This lesson asks the question hiding there all along: **what happens when texture coordinates go past 1.0 — or below 0.0?** There are no texels outside the tile, so the GPU needs a rule. That rule is the texture's **addressing mode** (a.k.a. *wrap mode*), and the app's whole job is to poke at it: scale the UVs out of range, then switch modes and see.

### The experiment: push UVs outside [0, 1]

The plane's vertex UVs still span `[0, 1]` — nothing changes in the vertex shader ([`shader.vert`](apps/21_7_shader_texture_coordinates/src/shaders/shader.vert) just forwards the built-in `uv` attribute to `vUvs`, as in every lesson since [[0.2_shader-inputs-varyings-uv]]):

```glsl
vUvs = uv;
```

The scale happens in the **fragment shader**, right before sampling ([`shader.frag`](apps/21_7_shader_texture_coordinates/src/shaders/shader.frag)):

```glsl
vec2 uvs = vUvs * 2.;
vec4 diffuseSample = texture2D(diffuse, uvs);
```

The plane still shows its full `[0, 1]` UV range, but the shader samples at coordinates in `[0, 2]` instead. The image data lives in `[0, 1]`, so the **bottom-left quarter** of the plane shows the whole image, squeezed ("bottom left our image and it is much smaller"). Everywhere else the sampler is asked *"give me the texel at u = 1.3"* — a coordinate that doesn't exist in the tile. That's the moment the addressing mode decides.

### Addressing modes: the rule for out-of-range UVs

OpenGL/WebGL give each texture a wrapping function, set **per axis**:

- `wrapS` — the **u axis** (horizontal; in GL terms the "s" texture coordinate)
- `wrapT` — the **v axis** (vertical; the "t" coordinate)

They're independent: you can mix `RepeatWrapping` on S and `ClampToEdgeWrapping` on T on the same texture, and you can also `Repeat` the S axis but scale only one axis to make the two visible separately. Three.js maps these to the `THREE.*Wrapping` constants ([Texture docs](https://threejs.org/docs/#api/en/textures/Texture)) and uploads them as `GL_TEXTURE_WRAP_S` / `GL_TEXTURE_WRAP_T`.

**`THREE.ClampToEdgeWrapping`** — this is the **default**, so it's the first thing you see. Any coordinate outside `[0,1]` is clamped to the nearest edge texel: `u < 0 → u = 0`, `u > 1 → u = 1`. The border behaves as if it were copy-pasted forever — exactly the **streaking** the README describes:

- the right edge of the image stretches horizontally all the way to the right edge of the plane,
- the top edge stretches vertically all the way up,
- the top-right corner texel fills the top-right quarter.

One image, small, in the corner; streaks radiating from its right and top edges.

**`THREE.RepeatWrapping`** — the texture tiles: `1.0` in UV space is one full period, and the sampler repeats it forever in both directions. With `uvs = vUvs * 2.` the plane covers two periods per axis, so you see **2 × 2 = 4 copies** of the image ("tiles twice in each direction"). Because the scaling happens per-component, `vec2 uvs = vUvs * vec2(2., 3.);` is a **Hadamard product** — the component-wise multiplication from [[0.5_textures-and-multiplicative-blending]] — and gives you **2 tiles in u and 3 in v**, the two axes finally visible at once.

**`THREE.MirroredRepeatWrapping`** — like Repeat, but every other copy is **mirrored**. Walking left→right you watch the image flip horizontally tile by tile; walking bottom→top it flips vertically tile by tile. The result is a checkerboard of mirrors, so the seams between tiles are invisible in a way plain Repeat's seams aren't.

### Wrap modes are just math on UVs

There's no magic — the hardware applies a per-coordinate function before looking up the texel. This is the whole lesson in three lines:

```
ClampToEdge:     u' = clamp(u, 0, 1)
Repeat:          u' = u − floor(u)          // ≡ fract(u)
MirroredRepeat:  u' = 1 − |1 − mod(u, 2)|
```

Since `u − floor(u)` is exactly GLSL's `fract`, **Repeat is `fract(u)`** — and you can emulate every one of the modes in a plain fragment shader if you ever need to. This also explains why Repeat behaves sanely at negative coordinates: `fract(−0.5) = 0.5`, the tile runs backwards but still lands inside the image. ([LearnOpenGL — Textures](https://learnopengl.com/Getting-started/Textures) has the same picture, with the classic tiling illustration.)

### Homework: why does `vUvs * (−1.)` rotate the image by π?

The app's active shader line:

```glsl
vec2 uvs = vUvs * (-1.);
```

with `RepeatWrapping` on both axes — and the README asks: *the image looks rotated by PI — am I right about noticing that?*

**Yes, you are.** Here's the mechanism. Negation maps the plane's UV range `[0, 1]` onto `[-1, 0]` — every coordinate comes out negative. With `Repeat`, the sampler wraps periodically (the `u − floor(u)` rule), and `[-1, 0]` is exactly the same tile as `[0, 1]`, just traversed **backwards**:

```
fract(−0.25) = 0.75
fract(−0.75) = 0.25
```

So the effective sample coordinate becomes `1 − u` (and `1 − v`): **both axes are reversed**.

- `u → 1 − u` mirrors the image **horizontally**,
- `v → 1 − v` mirrors it **vertically**.

A horizontal mirror followed by a vertical mirror is a **point reflection** — a 180° (π) rotation about the image's center. That's exactly the "rotated by π" look. It is *not* the texture being rotated in UV space; it's two flips compounding into a half-turn.

Two things to keep in mind:

- The result reads as a clean half-turn because the plane covers exactly **one period** of the texture. Reverse-traversing one tile = flipping it once. If the plane's UVs covered `[0, 2]` and got negated to `[-2, 0]`, both tiles would be traversed right-to-left — mirrored tiling, not a single rotation. (See Revisit.)
- Swap in `ClampToEdgeWrapping` and the same line behaves completely differently: every coordinate clamps to `u = 0, v = 0`, so the whole plane fills with a single stretched corner texel — a solid fill, no rotation at all. **The rotation is a property of the wrap mode, not of the multiplication.**

Scene setup note (identical to 0.6): `OrthographicCamera` spanning `-0.1 … 1.1`, the 1×1 plane at `(0.5, 0.5, 0)`, camera at `z = 1`, `OrbitControls` disabled, GUI hidden until you press `h`. The commented `radeDevColor` attribute block in `main.ts` is a leftover from [[0.4_shader-inputs-attributes]], and `material.wireframe = true` is commented out.

## Code

in repo - `apps/21_7_shader_texture_coordinates`

```ts
import * as THREE from 'three';

const textureLoader = new THREE.TextureLoader();
const cityTexture = textureLoader.load('/textures/city.png');

// addressing mode — set per axis (the app's active choice)
cityTexture.wrapS = THREE.RepeatWrapping;   // u axis
cityTexture.wrapT = THREE.RepeatWrapping;   // v axis
// alternatives the app keeps commented:
// cityTexture.wrapS = THREE.ClampToEdgeWrapping;     // the default
// cityTexture.wrapT = THREE.MirroredRepeatWrapping;

const planeGeometry = new THREE.PlaneGeometry(1, 1);

const material = new THREE.ShaderMaterial({
  uniforms: { diffuse: { value: cityTexture } },
  vertexShader: /* glsl */ `
    varying vec2 vUvs;
    void main() {
      gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0);
      vUvs = uv; // built-in uv attribute → varying
    }
  `,
  fragmentShader: /* glsl */ `
    uniform sampler2D diffuse;
    varying vec2 vUvs;

    void main() {
      // push UVs outside [0,1] — scaling, not shifting
      vec2 uvs = vUvs * (-1.);          // homework: why π rotation? see Concept
      // vec2 uvs = vUvs * 2.;          // uniform scale → 2×2 tiles
      // vec2 uvs = vUvs * vec2(2., 3.); // Hadamard product → 2 × 3 tiles
      vec4 diffuseSample = texture2D(diffuse, uvs);
      gl_FragColor = diffuseSample;
    }
  `,
});

const planeMesh = new THREE.Mesh(planeGeometry, material);
planeMesh.position.set(0.5, 0.5, 0);
scene.add(planeMesh);
```

The app keeps the shaders in `src/shaders/shader.vert` / `shader.frag`, imported as strings via `vite-plugin-glsl` (import types in `src/types/shaders.d.ts`), and toggles modes by uncommenting lines in `main.ts` (marked `// EXPLAIN: changing addressing modes for texture`).

## Gotchas

- **`ClampToEdgeWrapping` is the default** — the streaking (and with scaled UVs, the small corner image) is what you see *before* setting anything. If you change only one axis, the other axis still clamps.
- **`wrapS` and `wrapT` are separate switches.** `Repeat` on S and `Clamp` on T is legal and often exactly right — e.g. tiling a road horizontally but not vertically. The Hadamard scale `vUvs * vec2(2., 3.)` makes the axes visible independently.
- **The wrap mode doesn't decide how many tiles you get.** `Repeat` with UVs stuck in `[0, 1]` still shows one copy. The tile count comes from the *range* the UVs cover after scaling — ×2 → 2 periods per axis → 4 copies. Wrap mode and shader scaling are two separate pieces of the same pipeline, not interchangeable knobs.
- **Negative scale ≠ MirroredRepeat.** `vUvs * (-1.)` on a one-tile plane produces the same single flip a mirror would, but the mechanism is different: negation *reverses traversal* of the tile (`u → 1 − u` via wrapping), while `MirroredRepeatWrapping` mirrors at every integer boundary *inside* the sampler. They diverge the moment the UV range spans multiple tiles.
- **Changing wrap modes after upload** — in modern three.js (r152+) assigning `wrapS`/`wrapT` bumps the texture's internal version, forcing the GL `TEXTURE_WRAP_S/T` parameters to re-upload. Still, set them before first render (the app does, right after `load()`) — older three.js had to be told with `texture.needsUpdate = true`.
- **NPOT textures and WebGL1.** `Repeat`/`MirroredRepeat` require **power-of-two** textures on WebGL1. On WebGL2 (three.js' default renderer) and WebGPU any size works — `city.png` is 2912×1632 (non-power-of-two) and tiles fine here for exactly that reason.
- **Wrap modes are about coordinates, not filtering.** Mirrored tiles are still texture-filtered normally; the mirror is what the wrap function outputs, applied before the filter runs.
- **Dead uniforms linger.** `overlay` (a second texture that still loads, pointlessly) and `tint` were inherited from [[0.6_blending-two-textures-and-alpha-problem]]; the active shader samples only `diffuse`. Declared-but-unused uniforms are harmless — three.js just doesn't use them — but carry the cost of the extra async load.
- **`texture.colorSpace` is still unset** (the `colorSpace and stuff` placeholder) — for photographic color textures modern three.js expects `THREE.SRGBColorSpace`; same caveat as [[0.5_textures-and-multiplicative-blending]].

## Revisit

- **Live GUI test.** The app toggles modes by commenting/uncommenting constants. Upgrade it: expose `wrapS`, `wrapT` and the UV scale multiplier as lil-gui controls and flip them at runtime — the `planeTweaks` folder is already there, the wiring is the exercise.
- **Emulate the wraps by hand.** Write `fract(u)`, `clamp(u, 0., 1.)` and `1. - abs(1. - mod(u, 2.))` directly in the fragment shader with *no* wrap mode set, and confirm output matches the hardware modes. This is the "wrap functions are just UV math" insight paying off.
- **Non-uniform negative scaling.** Try `vUvs * vec2(-2., 3.)` with `Repeat` and reason about the result before running it: one axis reversed (per-tile horizontal flip), the other tiling normally — a mirror, not a rotation.
- **`texture.repeat` instead of shader scaling.** `texture.repeat.set(2, 2)` scales UVs through three.js' texture matrix before the sampler sees them — same maths, different place. Reconcile the two and the whole texture pipeline makes sense.
- **The multi-period negation case.** Re-derive why `vUvs * (-1.)` on a plane whose UVs already cover `[0, 2]` gives reversed *tiling* rather than the clean half-turn seen here.

## Outdated

The raw-GLSL `ShaderMaterial` + `texture2D()` approach is **still perfectly valid on WebGL** — that's what this app runs on (`THREE.WebGLRenderer`).

⚠️ **But the project's stated direction is WebGPU, and the shader syntax doesn't carry over.** ⚠️ The *addressing-mode concept* survives completely unchanged — `wrapS`/`wrapT` are properties of `THREE.Texture` and behave identically under `WebGPURenderer`; only the sampling syntax changes. In TSL (Three.js Shading Language) the sample is a node built in JS, not a GLSL function call:

```js
import * as TSL from 'three/tsl';
const diffuse = TSL.texture(cityTexture);   // wrapS/wrapT still set the same way
// material: MeshBasicNodeMaterial with colorNode: diffuse
```

Same texture, same wraps, different spelling. Learn the *concept* here (UVs out of range, per-axis wrap rules, tile count = UV range ÷ period); re-express it in TSL later.

> 💡 More up to date alternative: [three.js TSL specification](https://threejs.org/docs/TSL.html) — `TSL.texture()` replaces `sampler2D` + `texture2D()` on the WebGPU path; the `Texture` wrapping properties stay identical. 🤖 suggested

Also, `texture2D()` and `gl_FragColor` are WebGL 1 / GLSL 1 conventions; GLSL 3 (three.js `glslVersion: THREE.GLSL3`) uses `texture()` and `out vec4 fragColor;`.

> 💡 More up to date alternative: [three.js ShaderMaterial docs — `glslVersion`](https://threejs.org/docs/#api/en/materials/ShaderMaterial) — set `THREE.GLSL3` and use `texture()` / `out vec4 fragColor;`. 🤖 suggested
