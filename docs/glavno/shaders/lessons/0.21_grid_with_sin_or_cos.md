## Concept

The README's intent in one line: *"learning how to use sin and cos in more ways in GLSL."* The previous lesson, [[0.20_sin-and-cos]], drove `sin()` with **time** — this one drops time entirely and drives `sin()` with **texture coordinates** (`vUvs`). That one swap turns a breathing color loop into a whole family of procedural patterns. Everything here builds on `sin()` being a **bounded, repeating signal** (returns `-1..1`, period `2π`).

> **`sin(uvComponent * bigNumber)` turns space itself into an oscillator.** Multiply one UV component by a large constant, pass it to `sin()`, and you get repeating stripes. Combine several such terms with `*`, `max`, `min` and you get grids and checkerboards.

### Stripes: one component, big multiplier

`vUvs` on the `PlaneGeometry(1, 1)` spans roughly `(0,0) → (1,1)`. The shader takes a single component and multiplies it:

```glsl
float t1 = sin(vUvs.y * 100.);
```

- `vUvs.y * 100.` grows from `0.` to `100.` across the plane. Each full `sin` period is $2\pi$, so the plane holds $\frac{100}{2\pi} \approx 15.9$ full oscillations — about **16 light bands**.
- Where `sin` is positive the fragment renders light; where it's negative the channel clamps to black (see Gotchas — no remap here, deliberately). Result: alternating **light/dark stripes**.
- Orientation is just which component you feed it:
  - `sin(vUvs.x * 100.)` — the value changes with `x` → **vertical stripes**
  - `sin(vUvs.y * 100.)` — the value changes with `y` → **horizontal stripes**

The `100.` is the **frequency knob**: it's what turns "one smooth gradient" into "many stripes". That single idea — a UV component scaled big and fed to a periodic function — is the seed of most procedural textures (wood, water, scanlines, flags…), which is why the README calls it a basis for many patterns.

### Chessboard: multiply two sines

```glsl
color = vec3(t1 * t2); // sin(vUvs.y * 100.) * sin(vUvs.x * 100.)
```

Multiplying the two waves combines both frequencies. Where the product is positive the cell is light, where negative it's black — the README calls it "similar to a chess board". ⚠️ *Similar*, not exact: **negative × negative = positive**, so the cells where *both* waves are negative light up again. An exact checkerboard needs a `step()`/`sign()` hardening step (see Revisit).

### Grid: `max`, and its inversion `min`

```glsl
color = vec3(max(t1, t2)); // looks like a grid
color = vec3(min(t1, t2)); // essentially the inversion
```

- `max(t1, t2)` keeps the brighter of the two waves per fragment: bright where *either* wave approaches its peak, dark where both dip low — reads as a **grid of bright cells** with darker lines between.
- `min(t1, t2)` keeps the darker one: bright only where *both* waves are high, which visually is the inverse of the `max` image.

### The point

None of these is "the" correct pattern. `sin` of a UV component gives you a bounded, repeating signal **in space**, and composing several such signals with `*`, `max`, `min`, `mix`, … is the way procedural textures are built. The README's payoff example: drive a `sampler2D` lookup with a UV modulated by these stripes and you get an effect that looks like an **old TV screen** with recognizable scanline bands.

One quiet detail of this app: the `time` uniform **is** declared and updated every frame (via `THREE.Timer`), but this shader never reads it — the pattern is static, driven purely by UVs. Animating it is one `+ time` away (see Revisit).

## Code

in repo — `apps/21_21_sin_cos_2`

```ts
import * as THREE from 'three';
import vsh from './shaders/shader.vert';
import fsh from './shaders/shader.frag';

const material = new THREE.ShaderMaterial({
  uniforms: { time: { value: 0 } }, // written every frame, still unused by the shader
  vertexShader: vsh,
  fragmentShader: fsh,
});

const plane = new THREE.Mesh(new THREE.PlaneGeometry(1, 1), material);
plane.position.set(0.5, 0.5, 0); // ortho camera frames (0,0) → (1,1)
scene.add(plane);

// ... renderer, camera (OrthographicCamera near origin), then:

const timer = new THREE.Timer();
renderer.setAnimationLoop(tick);

function tick(timestamp: number) {
  timer.update(timestamp);
  material.uniforms.time.value = timer.getElapsed();
  renderer.render(scene, camera);
}
```

Minimal working example — the four pattern stages:

```glsl
// vertex.shader — same as always, just forwards UVs
varying vec2 vUvs;

void main() {
  vec4 localPosition = vec4(position, 1.0);
  gl_Position = projectionMatrix * modelViewMatrix * localPosition;
  vUvs = uv;
}

// fragment.shader
varying vec2 vUvs;

void main() {
  vec3 color = vec3(0.);

  float t1 = sin(vUvs.y * 100.); // horizontal stripes
  float t2 = sin(vUvs.x * 100.); // vertical stripes

  // color = vec3(t1);          // stage 1: plain stripes
  // color = vec3(t1 * t2);     // stage 2: chessboard-ish
  // color = vec3(max(t1, t2)); // stage 3: grid
  color = vec3(min(t1, t2));     // stage 4: inverted grid

  gl_FragColor = vec4(color, 1.0);
}
```

## Gotchas

- **The dark stripe is the clamp, not a remap, and it's intentional here.** `sin` is negative for half its cycle; assigning a negative channel value clamps to black in GLSL. In [[0.20_sin-and-cos]] the `remap(t, -1., 1., 0., 1.)` removed that dead zone; here there is **no remap**, so the negative half *is* the black stripe. Same wave, opposite intent — know which one you're writing.
- **`t1 * t2` is not an exact chessboard.** negative × negative = positive, so cells where both waves are negative render light again. If you need a strict checkerboard, harden the waves first: `step(0.0, sin(...))` per axis, then `xor`-combine — links back to [[0.9_step-mix-smoothstep]].
- **The `time` uniform is dead weight in this app.** It's updated every frame but never read by the shader — don't expect motion, and don't mistake "uniform is set" for "uniform is used". The `+ time` animation is the natural next step.
- **`100.` is a frequency in cycles of $2\pi$, not a stripe count.** `* 100.` ≈ 16 stripes across the plane. The stripes live in **UV space**, so they're tied to the geometry's UV unwrap, not to world units: scale the mesh and the stripes stretch with it; a non-square plane would squish them.
- **The grid look depends on the camera framing.** The app uses an `OrthographicCamera` framing `(0,0) → (1,1)` on a square `1×1` plane, so cells come out even. On a wide viewport the same shader would show stretched cells — multiply one component by an aspect ratio if you want square cells everywhere.
- **The WebGPU path is dormant — this is a WebGL app.** `main.ts` runs the plain `WebGLRenderer` + `ShaderMaterial` + raw GLSL; `WebGPURenderer`, `renderer.init()`, and the `three/webgpu` import are all commented out of the template. See Outdated for what changes on WebGPU.

## Revisit

- **Animate it — one `+ time` away.** `sin(vUvs.x * 100. + time)` makes the stripes travel; that motion is exactly what a scanline/TV effect needs. Try it with the `time` uniform that's already being fed.
- **Harden the cells.** Apply the `step()`/`smoothstep()` tools from [[0.9_step-mix-smoothstep]] and [[0.10_mix-and-smoothstep-side-by-side]] to get crisp-edged stripes/checkerboard instead of soft sine gradients, then try `mix`-ing two colors with the wave as `t` (remap from [[0.18_inverse-lerp-and-remap]] comes back into play).
- **Compose synonyms, not just products.** Try `sin(x * a) + sin(y * b)`, `length(vec2(t1, t2))`, or `abs()` on the wave — each changes the brightness map in a different, learnable way.
- **The README's old-TV effect.** Sample a `sampler2D` with `vUvs + smallOffset * pattern` to bend a texture along the stripes — the declared goal of this lesson's fun example.
- **Coordinate space matters.** This lesson works in `(0,1)` UV space. Recenter to `(-0.5, 0.5)` ([[0.16_what_is_center]]) or `fragCoord` space and the phase and tiling of every pattern shifts.
- **WebGPU toggle.** The logic here is ~4 lines — porting to `WebGPURenderer` (WGSL/TSL, see Outdated) is a short, high-value experiment to see the differences first-hand.

## Outdated

**approach is valid** — `sin()`/`cos()` are core GLSL built-ins and space-based oscillation is the foundation of procedural texturing; nothing here is obsolete.

⚡ **WebGPU note** — the app *is* a webgpu-based template, and this concept maps 1:1 to **WGSL** (`sin()`/`cos()` exist with the same semantics; only the plumbing differs: `vUvs` becomes a `@location` vertex output, `gl_FragColor` becomes the return of an `@fragment` function). With three.js's `WebGPURenderer` the more idiomatic route is TSL nodes or a WGSL module instead of a raw `ShaderMaterial`; on the WebGPU path this whole stripe/grid idea carries over unchanged. 🔄
