First contact with GLSL — the language that runs on the GPU. The app is deliberately minimal (a single red plane), because the real content of this lesson is the *language itself* and the *transformation pipeline* that every vertex goes through on its way to the screen. There are also four scratch files (`src/shaders/shader1.vert` … `shader4.vert`) that are **not loaded** by the app — they're just a playground for writing and thinking about GLSL.

> We are using the `WebGLRenderer` here on purpose. GLSL is the shading language of WebGL, and we want to learn it properly before stepping into TSL (Three Shading Language) and the `WebGPURenderer`. The commented-out `WebGPURenderer` line in `main.ts` is the future path.

## Concept

### What is GLSL

**GLSL** stands for **OpenGL Shading Language** — the programming language used to write shaders that run on the GPU. A quick way to place it:

- **Imperative** — you write a sequence of statements that execute in order, like you're used to from JavaScript/TypeScript or C.
- **C-style** — the syntax (semicolons, braces, `//` comments, `void main()`, `return`, `for`/`while` loops, `if`/`else`) will feel very familiar if you've written any C-like language.
- **Strongly typed** — every variable has a fixed type and you can't silently mix them. `float + int` won't just "work" like it does in JS; you need explicit conversions.

### Main types

| Type | Meaning |
|---|---|
| `float` | single-precision decimal number, written with a decimal point: `1.0`, `0.5`, `2.` (a trailing dot is valid GLSL!) |
| `int` | whole number: `1`, `42`, `-7` |
| `bool` | `true` / `false` |

Note the `1.` syntax — in GLSL `1` is an `int`, while `1.0` (or `1.`) is a `float`. They are **different types**, and mixing them in an operation is an error unless you convert. That's exactly why in the shaders you'll see `vec4(1., 0., 0., 1.)` — every component written as a float.

### Vector types

Vectors group several numbers of the same type into one value:

- `vec2` — two components (e.g. a UV coordinate `(u, v)`, a 2D point)
- `vec3` — three components (e.g. a position `(x, y, z)`, a normal, an RGB color)
- `vec4` — four components (e.g. a position with `w`, an RGBA color)

In this app the color `vec4(1., 0., 0., 1.)` is red with full alpha.

### Matrix types

Matrices correspond to the vector sizes:

- `mat2` — 2×2 matrix
- `mat3` — 3×3 matrix
- `mat4` — 4×4 matrix

Non-square matrices exist too, like `mat2x3` (2 columns, 3 rows — or rather, two `vec3` columns). `shader2.vert` has an example:

```glsl
mat2x3 non_square = mat2x3(
  1., 2., 3.,  // column 0 (a vec3)
  4., 5., 6.   // column 1 (a vec3)
);
```

The 4×4 matrix is the star of the show, because all the transformation pipeline (below) is built on `mat4`.

### Common mathematical operations

The operators are `+`, `-`, `*`, `/`, `=`, `+=`, `-=`, `*=`, `/=`. But **what they do depends on the operands** — this is the single most important idea of the whole lesson:

- **Scalar × scalar** — normal math: `2.0 * 3.0` → `6.0`.
- **Vector × scalar** — scales every component: `vec3(1.,2.,3.) * 2.` → `vec3(2.,4.,6.)`.
- **Vector + / − vector** — **component-wise**: `vec3(1.,2.,3.) + vec3(4.,5.,6.)` → `vec3(5.,7.,9.)`.
- **Vector × vector** — **component-wise** (called the *Hadamard product*): each component multiplies its matching component only.
  ```glsl
  vec3(1.,2.,3.) * vec3(4.,5.,6.)   // → vec3(1.*4., 2.*5., 3.*6.) = vec3(4.,10.,18.)
  ```
- **Matrix × vector** — **NOT component-wise.** This is real matrix multiplication: the vector is treated as a column vector, and the result is a new vector. This is how you *transform* a point or direction.
- **Matrix × matrix** — regular matrix multiplication (`m_result = m2 * m1`), also **not component-wise**.
- **Component-wise matrix multiplication** exists as a dedicated built-in: `matrixCompMult(m2, m1)`.

Two follow-up questions the README raised, with the answers:

- **Is a vector an *n×1* matrix when multiplied by a matrix?** Effectively yes — `matrix * vector` treats the vector as a column vector (a 4×1 matrix). The columns of the matrix (4) match the rows of the vector (4), and the result has the rows of the matrix (4) — a `vec4`.
- **Does order matter for matrix × vector?** Yes! `matrix * vec` treats `vec` as a **column** vector. `vec * matrix` treats `vec` as a **row** vector (a 1×4 matrix). They are different operations and give different (though related) results. The convention in graphics is `matrix * vector` — and that's exactly the order used in the vertex shader below: `projectionMatrix * modelViewMatrix * localPosition`.

### Type qualifiers — the pattern

The README's pattern for declaring shader variables:

```
<type qualifier> <data type> <name>
```

The three classic qualifiers (from `shader4.vert`):

```glsl
attribute vec4 my_attribute;
varying  vec4 my_varying;
uniform  vec4 my_uniform;
```

- **`attribute`** — per-vertex data coming from the geometry (positions, normals, UVs, colors). You don't usually set these yourself; the mesh provides them.
- **`varying`** — the "bridge" between vertex and fragment shader: written in the vertex shader, automatically **interpolated** across the surface, and read in the fragment shader.
- **`uniform`** — a global read-only value, the same for every vertex and every fragment in a draw call (a color, a time value, a texture).

(Note: `attribute` and `varying` are the *classic* GLSL ES 1.0 spellings — see the Gotchas section about how WebGL2/Three.js handles them.)

### The Transformation Pipeline

How does a model get onto the screen? The README lays out the full chain. Each step re-expresses the same 3D data relative to a new reference frame, and most steps are just a matrix multiply. The **vertex shader's only real job** is to run the vertex through this pipeline far enough to produce a clip-space position.

1. **Local space (a.k.a. object space)** — the model's own coordinates, as it was modeled. Imagine the world from your own point of view: everyone has their own "local space", and everyone's left/right/up/down is relative to themselves.
2. **World space** — local space is transformed into world space, so everything is now defined relative to the world. Like GPS coordinates: North/South/East/West are world-relative, not person-relative.
3. **View space** — world space is transformed into view space, relative to the camera. Like a movie set: the whole scene is re-expressed from the camera's point of view.
4. **Clip space** — the output of the vertex shader. It's the result of the World + View + Projection transformations combined. Everything that happens *after* clip space is handled by OpenGL itself, not by you.
5. **NDC space (Normalized Device Coordinates)** — clip space is transformed into NDC by the **perspective divide** (dividing by `w`), which OpenGL does for you. NDC is a standardized 3D coordinate system used across graphics pipelines (OpenGL, DirectX, WebGPU) after projection.
6. **Screen space** — resolution and depth range are applied to NDC to get the final pixel position.

That's why the vertex shader is just one line of "real" work:

```glsl
gl_Position = projectionMatrix * modelViewMatrix * localPosition;
```

`modelViewMatrix` covers local → world → view (in a single combined matrix), and `projectionMatrix` covers view → clip. Three.js provides both as built-in uniforms — you don't have to build them yourself.

### Vertex + Fragment = a shader program

A **shader program** is a vertex shader plus a fragment shader bound together. When you draw a mesh, you bind a shader program, and the GPU runs:

1. the **vertex shader** once per vertex (to place it in clip space, and to produce values that get interpolated),
2. the **fragment shader** once per pixel/fragment covered by the mesh (to decide its color).

Three.js's `ShaderMaterial` takes both shaders and bundles them into a program for you.

### Uniforms, Attributes, Varyings — the three ways to set "parameters"

Like any program, a shader can be run with different parameters. There are three channels:

- **Uniforms** — the most common way. Global, read-only values set once per draw call; every vertex and fragment reads the *same* value. Perfect for global state: textures, tinting, time, camera matrices.
- **Attributes (vertex attributes)** — the model data itself. This is *not* something you generally set by hand — it comes from the mesh's geometry, defined per vertex: positions, normals, texture coordinates, colors. (It is possible to set them yourself, e.g. when you hand-build a `BufferGeometry`.)
- **Varyings** — a one-way communication pipeline from vertex → fragment. The vertex shader writes them, the GPU **interpolates** the values across the surface (per-vertex data becomes smooth per-fragment values), and the fragment shader reads the interpolated result. Useful for sending per-vertex color, texture coordinates, or anything else the fragment shader needs. An advanced use: doing work once per vertex instead of once per fragment as an optimization.

### Summary — what shaders do

- Shaders are **small programs that run on the GPU**, one instance per vertex (vertex shader) or per fragment (fragment shader).
- The vertex shader's most common responsibilities:
  - set `gl_Position` — typically `projection * modelView * position`
  - supply varying values for the fragment shader
- The fragment shader commonly outputs `gl_FragColor` — the final color of the pixel.

### How the shaders got loaded (briefly)

The shader files are loaded with Vite's `vite-plugin-glsl` (`vite.config.js` just registers `glsl()` as a plugin). The `.glsl` files are imported as plain strings (`import vsh from './shaders/vertex-shader.glsl'`) and handed to `ShaderMaterial`. This is the easiest way to work with shaders in a Vite project; `src/types/shaders.d.ts` provides the TypeScript module declarations so the imports type-check.

## Code

in repo - `apps/21_0_shader_language_intro`

Minimal working example — a red plane using `ShaderMaterial`:

```ts
// main.ts (relevant part)
import * as THREE from 'three';
import vsh from './shaders/vertex-shader.glsl';
import fsh from './shaders/fragment-shader.glsl';

const scene = new THREE.Scene();

// deliberately WebGL — we're learning GLSL before TSL
const renderer = new THREE.WebGLRenderer({ canvas });

const geometry = new THREE.PlaneGeometry(1, 1);

const material = new THREE.ShaderMaterial({
  uniforms: {},
  vertexShader: vsh,
  fragmentShader: fsh,
});

const planeMesh = new THREE.Mesh(geometry, material);
planeMesh.position.set(0.5, 0.5, 0);
scene.add(planeMesh);
```

```glsl
// vertex-shader.glsl
void main() {
  vec4 localPosition = vec4(position, 1.0);

  gl_Position = projectionMatrix * modelViewMatrix * localPosition;
}
```

```glsl
// fragment-shader.glsl
void main() {
  gl_FragColor = vec4(1., 0., 0., 1.); // opaque red
}
```

Notes on the example:

- `position` is a built-in attribute (the vertex's local position, a `vec3` from the geometry), `projectionMatrix` and `modelViewMatrix` are built-in uniforms provided by Three.js.
- `position` is `vec3`, so it's padded to `vec4` with `w = 1.0` before the matrix multiply (affine transforms need the `w` component).
- The app uses an `OrthographicCamera` with unusual bounds (`-0.1, 1.1, 1.1, -0.1`) just to practice that API — the plane sits in a tiny slice of space near the camera.
- The four `.vert` scratch files (`shader1.vert` … `shader4.vert`) are *not* imported — they're the GLSL playground, full of the `// EXPLAIN:` questions this lesson answers.

## Gotchas

- **`vec * vec` is component-wise, but `mat * vec` is real matrix multiplication.** These look similar but are completely different operations. If you want component-wise *matrix* multiplication, use the built-in `matrixCompMult()`.
- **Order matters for matrix–vector multiplication.** `matrix * vec` treats `vec` as a column vector; `vec * matrix` treats it as a row vector. Graphics convention is `matrix * vec`, and that's the order you'll see in every vertex shader: `projectionMatrix * modelViewMatrix * position`.
- **Matrix constructors are column-major.** When you write out a `mat4` in code, each *row of source text* is actually one **column** of the matrix (each row is a column vector). `shader2.vert` marks this explicitly:
  ```glsl
  mat4 m2 = mat4(
    2., 0., 0., 0.,  // column 0
    0., 3., 0., 0.,  // column 1
    0., 0., .5, 0.,  // column 2
    0., 0., 0., 1.   // column 3
  );
  ```
  Getting this backwards means a transposed matrix and mysteriously wrong transformations.
- **GLSL is strongly typed — no implicit conversions.** `1` is an `int`, `1.0` is a `float`; `vec4(1,0,0,1)` with bare `int`s won't compile. Always write float literals with a decimal point: `1.`, `.5`, `2.0`.
- **`attribute` and `varying` are the legacy spellings.** In raw WebGL2 (GLSL ES 3.0) these keywords were replaced by `in`/`out`, and `gl_FragColor` was replaced by an `out` variable. Three.js keeps the old names working in `ShaderMaterial` by rewriting them under the hood — but be aware that if you paste your shader into a raw WebGL2 context or a tool like ShaderToy, you may need the newer syntax.
- **`gl_FragColor` in Three.js.** Even though Three.js runs WebGL2 by default now, `gl_FragColor` still works in `ShaderMaterial` because Three.js defines it as a macro pointing at its own fragment output. Don't be surprised if code elsewhere shows `out vec4 fragColor;` instead.
- **`varying` values are interpolated, and that interpolation is perspective-correct.** A value you set per-vertex becomes a smoothly changing value per-fragment — which is the whole point, but it also means you can't rely on a varying holding the exact per-vertex value inside the fragment shader.

## Revisit

Things to look into further, practice again, or decide on:

- **The open questions left in the scratch files.** `shader1.vert` asks about `in`/`out` parameter qualifiers (can you have multiple `in`/`out` values? — yes, any number, they're just parameters with direction qualifiers, GLSL passes by value-in / value-out semantics). `shader3.vert` asks whether GLSL has logical operators (`&&`, `||`, `!` — yes), bitwise operators (`&`, `|`, `^`, `<<`, `>>` — yes in GLSL ES 3.0/WebGL2), `switch` (yes), and other loop types (`for`/`while`/`do-while` are what exist; there is no `for...in`).
- **Build real matrices by hand.** Write a small translation/rotation/scale `mat4` yourself and verify what `matrix * vec` does to a point — the column-major trap only really sinks in once you've constructed one and been surprised.
- **Understand the built-in uniforms Three.js provides.** `projectionMatrix`, `modelViewMatrix`, `position`, `normal`, `uv`, `modelMatrix`, `viewMatrix`, etc. — the `WebGLProgram` docs list them all. Knowing which are attributes vs uniforms clarifies the whole pipeline.
- **Varying interpolation, and doing work per-vertex vs per-fragment.** Try moving a computation from the fragment shader into the vertex shader and passing the result through a varying — you'll see the interpolation and the performance trade-off live.
- **TSL (Three Shading Language) and WebGPU.** This is the stated destination: learn GLSL properly first, then move to `WebGPURenderer` + TSL, where the whole mental model changes again (the commented-out lines in `main.ts` are the first step).

## Outdated

The **approach is valid** — learning GLSL on WebGL is still the right foundation for understanding how GPU shading works, and the language is far from dead: WebGL remains everywhere on the web, and GLSL knowledge transfers directly to understanding any shading language.

That said, two things are moving:

1. **WebGPU + TSL is the forward direction** in Three.js. The user's own README states the plan explicitly: *"We are using here glsl, meaning we are not using WebGPU Renderer. I want to learn good glsl before stepping into TSL."* So this lesson is a deliberate stepping stone, not stale — but the WebGPU path is where the course is headed. 🚀 Once GLSL fundamentals are solid, the `WebGPURenderer` + TSL route replaces this whole setup (no `vite-plugin-glsl`, no `gl_FragColor`).
2. **The syntax is the GLSL ES 1.0 dialect.** `attribute` / `varying` / `gl_FragColor` are from WebGL1's GLSL ES 1.0. WebGL2 uses GLSL ES 3.0 with `in`/`out` and explicit fragment outputs. Three.js hides this, but learning the modern spelling is worth doing eventually.

> 💡 More up to date alternative: [Three.js TSL (node-based shading language) docs](https://threejs.org/docs/#api/en/nodes/tsl/TSL) — the WebGPU-native way to write shaders in Three.js, the stated next step. — three.js's TSL reference, where GLSL skills carry over to a node-graph style.
