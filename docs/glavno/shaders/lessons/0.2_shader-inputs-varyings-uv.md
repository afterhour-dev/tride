The vertex shader runs **per vertex**, the fragment shader runs **per pixel** — so how does information about position (or anything else computed at the vertices) reach the fragments in between? The answer is the topic of this lesson: **varyings**, demonstrated with the built-in **`uv`** attribute. The payoff is a smooth gradient drawn across a plane using nothing but interpolated vertex data.

> This is the direct follow-up to [[0.1_simple-colors]]. There we wrote our first fragment shader with a hardcoded color. Here we finally feed *real data* into the fragment shader — data that comes from the vertices.

---

## Concept

### The gap between the two shader stages

Shader programs have a fixed pipeline: the vertex shader produces a position for each vertex, then the GPU rasterizes the triangles, then the fragment shader fills each covered pixel. The problem: the vertex shader knows about vertices (a handful of them), the fragment shader deals with pixels (thousands of them). Anything you want the fragment shader to know — where along the triangle a pixel sits, a color per corner, a per-vertex normal — must be **handed across the stage boundary**.

That hand-off mechanism is the **varying**:

1. Declare `varying` with a name and a type in the **vertex shader** and **assign it a value** there (you have access to attributes and matrices here).
2. Re-declare the *same* varying, same name and type, in the **fragment shader** and **read** it there.

The GPU interpolates the value between vertices automatically, so every fragment between vertex A and vertex B gets a smoothly blended version of their values.

### `uv` — an attribute you get for free

Every standard Three.js geometry can supply a `vec2` attribute called **`uv`**, which holds per-vertex texture coordinates in the range `0.0`–`1.0`. For a `PlaneGeometry(1, 1)` the bottom-left vertex has `uv = (0.0, 0.0)` and the top-right has `uv = (1.0, 1.0)`.

Two things make `uv` special for learning:

- You **don't declare or define it** — it's a built-in attribute, already provided by the geometry. You just *use* it in the vertex shader, exactly like `position`.
- It's already normalized to `0.0`–`1.0` — the same range as GLSL colors. So `uv` maps directly onto color channels, which is exactly what this lesson does. `uv` is the coordinate system of the surface, and colors are the coordinate system's visualization.

### The vertex shader — declaring and assigning the varying

```glsl
varying vec2 vUvs;

void main(){
  vec4 localPosition = vec4(position, 1.);

  gl_Position = projectionMatrix * modelViewMatrix * localPosition;

  vUvs = uv;
}
```

- `varying vec2 vUvs;` declares the varying. The `v` prefix is just a naming habit to signal "this is a varying" (the code comment calls it a preference) — there is no syntax requirement for it.
- `vUvs = uv;` copies the vertex's uv coordinate into the varying. Each of the four vertices of the plane gets its own assigned value.
- `position`, `projectionMatrix`, `modelViewMatrix` are all provided by Three.js — same as the previous lesson.

### The fragment shader — reading the varying

```glsl
varying vec2 vUvs;

void main(){
  gl_FragColor = vec4(vec3(vUvs.x), 1.);
}
```

The first line is a copy-paste of the declaration — a varying must be declared in *both* shaders identically. Then `vUvs.x` is used as all three RGB channels, producing a **grayscale gradient from black (left) to white (right)**: at the left edge `x = 0.0`, at the right edge `x = 1.0`.

### The flip homework — why `1. - vUvs.x` works

The README's homework was *"flip the gradient so it goes right to left"*, and the naive first try was:

```glsl
gl_FragColor = vec4(vec3(1. - vUvs.x), 1.);
```

This works for a clear reason worth making explicit: since `vUvs.x` is always in `[0.0, 1.0]`, the expression `1.0 - vUvs.x` is a **reflection about 0.5**. It maps `0.0 → 1.0` and `1.0 → 0.0` — the order of values is reversed, so the gradient direction flips. It is *not* a general "invert anything" trick: if `x` were ever outside `[0, 1]` the result could go negative or above 1.0.

### Both components — the diagonal gradient and the corner reading

```glsl
gl_FragColor = vec4(vec3(vUvs.x, vUvs.y, 0.), 1.);
```

Now red comes from `x` (left to right) and green from `y` (bottom to top). The corners tell the whole story — read each `uv` at the four corners:

| Corner | `uv` | output `vec3(r, g, b)` | color |
|---|---|---|---|
| bottom-left | `(0.0, 0.0)` | `vec3(0.0, 0.0, 0.0)` | black |
| top-left | `(0.0, 1.0)` | `vec3(0.0, 1.0, 0.0)` | green |
| bottom-right | `(1.0, 0.0)` | `vec3(1.0, 0.0, 0.0)` | red |
| top-right | `(1.0, 1.0)` | `vec3(1.0, 1.0, 0.0)` | yellow |

### The interpolation insight

Here's the surprising part the code comment highlights: the plane has **only 4 vertices** (two triangles covering the whole quad), yet the gradient is smooth across *every* pixel. There is no per-pixel uv data — each fragment receives a continuously interpolated `vUvs` produced by the GPU between the two vertices of the triangle it belongs to. This is the core mental model of varyings: **vertex data in, smoothly spread over the surface out**. The fragment shader never sees the raw 4 vertex values — only the interpolated ones.

### `vec4(vUvs, 0., 1.)` — spreading a smaller vector

Since `vUvs` is a `vec2`, this also works:

```glsl
gl_FragColor = vec4(vUvs, 0., 1.);
```

GLSL vector constructors take **components**, not vectors — so a `vec2` + two floats happens to fill all four slots of the `vec4`. The comment guesses it feels like "spreading parameters"; that's a good intuition: `vec4(vUvs, 0., 1.)` is `vec4(vUvs.x, vUvs.y, 0., 1.)` spelled shorter.

### The final version — top-left red, bottom-right blue

```glsl
gl_FragColor = vec4(1.-vUvs.x, 0., 1.-vUvs.y, 1.);
```

Apply the corner-reading from above: at top-left `uv = (0.0, 1.0)` → `vec4(1., 0., 0., 1.)` (red); at bottom-right `uv = (1.0, 0.0)` → `vec4(0., 0., 1., 1.)` (blue). The `1. - v` reflections push each color to the opposite corner.

## Code

in repo - `apps/21_2_shader_inputs_varyings`

The `main.ts` setup is the standard template (WebGL renderer, orthographic camera, `ShaderMaterial` with empty uniforms, animation loop) — the whole lesson lives in the two shader files.

```glsl
// shader.vert — where the varying gets its value
varying vec2 vUvs;                    // declare the varying, "v" = it's a varying

void main(){
  vec4 localPosition = vec4(position, 1.);

  gl_Position = projectionMatrix * modelViewMatrix * localPosition;

  vUvs = uv;                          // hand the vertex's uv to the varying
}
```

```glsl
// shader.frag — where the varying gets read (interpolated)
varying vec2 vUvs;                    // same declaration, copy-pasted

void main(){
  // grayscale, left → right:                 gl_FragColor = vec4(vec3(vUvs.x), 1.);
  // flipped, right → left:                   gl_FragColor = vec4(vec3(1.-vUvs.x), 1.);
  // diagonal gradient, green-red corners:    gl_FragColor = vec4(vec3(vUvs.x, vUvs.y, 0.), 1.);
  // same, "spread" a vec2 into a vec4:       gl_FragColor = vec4(vUvs, 0., 1.);
  // final — top-left red, bottom-right blue: gl_FragColor = vec4(1.-vUvs.x, 0., 1.-vUvs.y, 1.);
}
```

## Gotchas

- **A varying must be declared in *both* shaders, with the same name *and* the same type.** `varying vec2 vUvs;` in the vertex shader and `varying vec3 vUvs;` in the fragment shader won't link. Forgetting the declaration in either shader at all is also a compile error.
- **A varying is assigned in the vertex shader and only *read* in the fragment shader.** If you never assign it in the vertex shader, the fragment shader reads garbage. (UV is assigned by the geometry, but values you declare yourself must be written manually.)
- **`uv` is an *attribute*, `vUvs` is a *varying* — they're different things.** `uv` is per-vertex input data that exists on the geometry; a varying is the stage-to-stage transport for data you want interpolated. Three.js injects the `uv` attribute for standard geometries (`PlaneGeometry`, `SphereGeometry`, …) — you don't declare it. For a **hand-built `BufferGeometry` you have to add a `uv` attribute yourself** or the shader gets nothing.
- **`1. - v` only "flips" because the value is normalized to `[0, 1]`.** It's a reflection about 0.5, guaranteed to stay in range only because `uv` is. Apply the same trick to a value outside `[0, 1]` and you'll get negative or over-one results, not a clean inversion.
- **Float literals still need the decimal point**, same as the previous lesson: `1.` not `1`, `0.` not `0`.
- **`gl_FragColor` is WebGL-1-era GLSL.** Three.js's `ShaderMaterial` lets you write it because Three.js rewrites the shader for the actual context. In raw WebGL 2 you'd have to declare an `out vec4 fragColor;` instead — a reminder that you're reading Three.js-flavored GLSL, not writing raw WebGL 2.

## Revisit

- **`vec4(vUvs, 0., 1.)` "spreading" deserves a fuller mental model.** GLSL constructors take components; any mix of scalars and vectors that adds up to the target component count compiles (e.g. `vec4(vUvs.x, vUvs.xy, 0.)` would be the two x from the first arg... — actually `vec4(vec2, vec2)` and `vec4(vec3, float)` are the two tidy cases). Also worth meeting: **swizzling** — `vUvs.xy`, `vUvs.yx`, `vUvs.xx` — which the README hints at by reordering components.
- **Uv as a mini coordinate system.** The corner-reading exercise is really "the corners are the vectors `(0,0)`, `(1,0)`, `(0,1)`, `(1,1)`". From here the natural steps are radial gradients (`length(vUvs)`) and shaping functions (`smoothstep`) to turn the linear gradient into something interesting — the Book of Shaders "shaping functions" chapter is the classic next read.
- **Make the gradient move.** This lesson has `uniforms: {}` — an empty uniforms object. Adding time-based uniforms (e.g. `uTime` updated in `tick()`) is the obvious next experiment and directly sets up the following lessons in the shader series.
- **Perspective-correct interpolation (deep rabbit hole).** Varyings are interpolated across the triangle, but there's a subtlety: interpolation is done in a perspective-correct way (hence `vUvs` divided by `w` and re-multiplied per fragment). Useful to know exists before you build closer-than-near-plane artifacts. 🐇
- **The flipped-gradient homework generalized.** Try `1. - vUvs.x`, `1. - vUvs.y`, both, then other combinations, and confirm each colored corner matches your hand-computed `uv` — that's the fastest way to *feel* how the interpolation works.

## Outdated

The **approach is valid** — varyings and the `uv` attribute are fundamental, hardware-level concepts that every shading language implements: WebGL, WebGPU, Vulkan, and Metal all interpolate per-vertex outputs across triangles. The GLSL here is written in WebGL-1-era syntax (`varying`, `gl_FragColor`) because that's what Three.js `ShaderMaterial` accepts and rewrites for its actual context.

Three.js now pushes hard toward `WebGPURenderer` + **TSL** (Three Shading Language), where varyings still exist but are expressed as nodes (`varyingFloat(...)`, `.mul()`, etc.) instead of keyword declarations. 🚀 If this app were rebuilt for WebGPU, the *concept* transfers 1:1 — only the spelling changes.

> 💡 More up to date alternative: [Three.js TSL docs](https://threejs.org/docs/#api/en/nodes/tsl/TSL) — the WebGPU-native shading language; the uv/varying concept is identical, the syntax is a node graph.
