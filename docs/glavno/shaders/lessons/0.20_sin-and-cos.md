## Concept

The README's intent in one line: *"learning how to use sin and cos in GLSL."* Both are **built-in math functions** — part of the same toolbox as the min/max/clamp stuff from [[0.13_common-math-functions]] — and the lesson is really about one insight that goes beyond trigonometry:

> **`sin()` and `cos()` map any input into the `-1..1` range, forever.** That makes them time machines for values you control.

### Radians, not degrees

`sin()` and `cos()` take their argument **in radians**:

| input | `sin()` | `cos()` |
|---|---|---|
| `0.0` | `0.0` | `1.0` |
| `PI / 2` | `1.0` | `0.0` |
| `PI` | `0.0` | `-1.0` |
| `PI * 3.0 / 2.0` | `-1.0` | `0.0` |

The two are the same wave, just shifted by a quarter period ($\frac{\pi}{2}$): `cos(x) = sin(x + PI / 2)`. Both oscillate between `-1` and `1` with period $2\pi$.

As with any GLSL built-in, `PI` is just `3.14159265...` for the compiler — you write the constant yourself (there are no built-in degree constants).

### What the lesson proves with color

The app is the familiar shader rig (a `1×1` `PlaneGeometry` + `ShaderMaterial`, orthographic camera framing roughly `(0,0) → (1,1)`, the `time` uniform driven by `THREE.Timer` every frame — same scaffold as [[0.19_derivative-functions]]). The fragment shader walks through four stages:

1. **`color = vec3(time)`** — commented out. `time` is *elapsed seconds*, an ever-growing number with no upper bound. To a color it means: almost instantly pure white. Not useful on its own inside `[0,1]`.
2. **`t = sin(time)`** — now the value is bounded to `-1..1`, oscillating about once per `2π ≈ 6.28` seconds. If you feed it directly to a color, the **negative half of the cycle renders as pure black** (GLSL clamps channel values to `[0,1]` — see Gotchas), so you get a long "dead" phase with nothing changing.
3. **`t = remap(t, -1., 1., 0., 1.)`** — the fix. Reuse the `inverseLerp`/`remap` pair from [[0.18_inverse-lerp-and-remap]] to squeeze `-1..1` into `0..1`. Now the plane smoothly fades black → white → black with **no clamped, frozen period**.
4. **`color = mix(red, blue, t)`** — the payoff. Blend two fixed colors by the oscillating `t`, and you get an infinite, perfectly smooth **red ⇄ blue breathing** loop with no visible cycle seams.

That's the whole idea: `sin/cos` give you a never-ending, smoothly-varying signal; a `remap` + `mix` turns it into exactly the interpolation you wanted.

## Code

in repo — `apps/21_20_sin_and_cos`

```ts
import * as THREE from 'three';
import vsh from './shaders/shader.vert';
import fsh from './shaders/shader.frag';

const material = new THREE.ShaderMaterial({
  uniforms: {
    time: { value: 0 }, // written every frame in tick()
  },
  vertexShader: vsh,
  fragmentShader: fsh,
});

const plane = new THREE.Mesh(new THREE.PlaneGeometry(1, 1), material);
plane.position.set(0.5, 0.5, 0);
scene.add(plane);

const timer = new THREE.Timer();
renderer.setAnimationLoop(tick);

function tick(timestamp: number) {
  timer.update(timestamp);
  material.uniforms.time.value = timer.getElapsed(); // seconds elapsed
  renderer.render(scene, camera);
}
```

Minimal working example — the four stages side by side:

```glsl
// vertex.shader
varying vec2 vUvs;

void main() {
  vec4 localPosition = vec4(position, 1.0);
  gl_Position = projectionMatrix * modelViewMatrix * localPosition;
  vUvs = uv;
}

// fragment.shader
varying vec2 vUvs;
uniform float time;

float inverseLerp(float v, float minVal, float maxVal) {
  return (v - minVal) / (maxVal - minVal);
}
float remap(float v, float inMin, float inMax, float outMin, float outMax) {
  float t = inverseLerp(v, inMin, inMax);
  return mix(outMin, outMax, t);
}

vec3 red  = vec3(1., 0., 0.);
vec3 blue = vec3(0., 0., 1.);

void main() {
  vec3 color = vec3(0.);

  // float t = time;                 // stage 1: unbounded → white in a blink
  float t = sin(time);               // stage 2: -1..1, period ~6.28 s
  t = remap(t, -1., 1., 0., 1.);     // stage 3: 0..1, no clamped black phase
  color = mix(red, blue, t);         // stage 4: red ⇄ blue forever

  gl_FragColor = vec4(color, 1.0);
}
```

## Gotchas

- **Radians or nothing.** `sin(90.0)` is *not* `1.0` — the argument is radians, so it's `sin(PI / 2.0)`. If you need degrees there are built-in `radians()` / `degrees()` converters, but the whole math-GLSL ecosystem thinks in radians.
- **Negative→black is a clamp, not a feature.** GLSL color values are clamped to `[0,1]`. So `vec3(sin(time))` over the negative half of the cycle doesn't give you "slightly darker red" — it gives you **pure black that sits frozen** while the wave is negative. This is exactly the README's *"certain moment where nothing changes from black"*. The `remap` isn't cosmetic; it eliminates a whole clamped dead zone.
- **Elapsed time is unbounded.** `THREE.Timer.getElapsed()` returns growing seconds. Feeding that straight into a color (`vec3(time)`) whips straight to white — the value is *right*, the range is *wrong*. Always think "what range is this exponential/evergreen value in?" before assigning to a color.
- **The `time` uniform starts at `0`.** The material is created with `time: { value: 0 }`, so the very first couple of frames are black until `tick()` writes a real value. The code literally asks *"is it good idea to send 0 at first for time like we did here?"* — harmless visually (one frame), but if the shader ever reads `time` for an offset or derivative, an uninitialized-feeling `0.0` first beat can produce a transient artifact. Consider seeding it with the current elapsed time on the first tick if it ever bothers you.
- **`remap` here is hand-rolled.** The shader defines its own `inverseLerp`/`remap` (see [[0.18_inverse-lerp-and-remap]]). Don't confuse this with the TSL/three.js-side `MathUtils.inverseLerp` — in raw GLSL `ShaderMaterial` code there is no built-in, you inline it per shader.
- **The WebGPU path is dormant.** The rig is a *webgpu-based template*, but `main.ts` runs the plain `WebGLRenderer` + `three` import; `WebGPURenderer`, `renderer.init()`, and the `three/webgpu` import are all commented out. `ShaderMaterial` + raw GLSL is a WebGL thing — see Outdated for what changes on WebGPU.

## Revisit

- **The next lesson continues exactly here.** The README closes with: *"we will continue with cos/sin in next lesson, I don't want to bloat my example and make it hard to understand upon revisit"* — so the deep-dive (multi-wave, uv-based sin/cos patterns, `cos` used as a second channel) is deliberately deferred. Re-read this doc when the next one lands.
- **Feel the skipped stages.** Uncomment `color = vec3(time)` and then `color = vec3(t)` (pre-remap) to see the "instant white" and "frozen black" behaviours with your own eyes — the comments in `shader.frag` walk through both.
- **Frequency and offsets.** The wave runs at 1 radian/second. Try `sin(time * uSpeed)` (a GUI-driven multiplier) and `sin(time + uOffset)` (phase shift, which also answers the uniform-init-at-0 question: seed an offset to skip the initial black beat).
- **`time * 0.0` isn't what you want to send first.** Revisit whether initializing the uniform to `0` vs. to `timer.getElapsed()` on first tick matters for a production-grade setup.
- **WebGPU toggle.** With the `WebGPURenderer` path already sitting in `main.ts`, porting this shader (its logic is 4 lines) is a short, high-value experiment to see TSL/GLSL4 differences.

## Outdated

**approach is valid** — `sin`/`cos` are core GLSL built-ins and the behaviour described is evergreen; this app's whole function (bounded oscillation → remap → mix) transfers to every shading language unchanged.

⚡ **WebGPU note** — the app *is* deliberately a webgpu-based template. The concept maps 1:1 to **WGSL**, which has built-in `sin()`, `cos()` (returning `-1..1`, same semantics) and the same waving idea — only the plumbing differs: `time` becomes a `uniform`, `gl_FragColor` becomes return of `@fragment fn`, and GLSL `mix()` → WGSL `mix()`. With three.js's `WebGPURenderer` you'd write this with TSL nodes or a WGSL `FGlSLModule` instead of a raw `ShaderMaterial`. 🔄
