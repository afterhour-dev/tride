## Concept

The last lesson filled your toolbox with `abs`, `floor`, `ceil`, `round`, `fract`, `mod` ([[0.13_common-math-functions]]). This lesson uses two of them — `fract` and `abs` — plus `max`, to build a **reference grid** out of nothing but UV coordinates. The goal (from the README): *"we want to learn how to create a grid, and manipulate with cells."* Since the upcoming lessons will **plot functions**, a reference grid is the scaffolding they'll be drawn on.

The whole trick is one sentence: **scale the UVs up, then wrap them back down with `fract`.** Everything else is decorating one cell and letting it repeat.

### Step 1 — see the UVs

```glsl
vec3 color = vec3(vUvs, 0.);
```

Scratch that in: `vUvs` maps the whole plane to `[0, 1]` in both axes, and the constructor `vec3(uv.x, uv.y, 0.0)` binds **`uv.x` → red, `uv.y` → green**, blue off. Bottom-left is black `(0,0,0)`, bottom-right is red, top-left is green, top-right is yellow.

### Step 2 — multiply by 10 and watch the clamp

```glsl
color = vec3(vUvs, 0.) * 10.;
```

Now the channels run `0 → 10` instead of `0 → 1`. But the fragment output can only hold `[0, 1]` per channel (it is clamped on write), so **everything ≥ 0.1 saturates to 1.0** and only the first tenth of each axis survives as a gradient:

| region | uv range | channel values | visible color |
| ------ | -------- | -------------- | ------------- |
| rest of the plane | `uv.x ≥ 0.1`, `uv.y ≥ 0.1` | `(1, 1, 0)` | yellow |
| bottom edge | `uv.x ≥ 0.1`, `uv.y < 0.1` | `(1, 10·uv.y, 0)` | red → yellow going up |
| left edge | `uv.x < 0.1`, `uv.y ≥ 0.1` | `(10·uv.x, 1, 0)` | green → yellow going right |
| bottom-left corner | both `< 0.1` | `(10·uv.x, 10·uv.y, 0)` | black → red/green → yellow diagonal |

This explains the picture the README describes — "a small bottom row of red blending to yellow, a small left column of green blending to yellow". Not magic: it's just **which channel each UV axis landed in** (`uv.x` is red, `uv.y` is green) plus the clamp. The two gradients overlap in the corner and mix into a diagonal blend toward yellow `(1,1,0)`.

### Step 3 — `fract` wraps the ramp into cells

```glsl
color = fract(vec3(vUvs, 0.) * 10.);
```

`fract(x) = x - floor(x)` keeps only the fractional part, always producing values in `[0, 1)` ([[0.13_common-math-functions]]). Its mental model for grids: **it wraps a linear ramp back to zero every time it crosses an integer** — like a clock that resets every 12 hours, or `mod`. Since `10·uv` crosses an integer every `0.1` in UV space, the single `0 → 1` ramp of Step 2 is chopped into **10 repeating ramps along x and 10 along y → 10 × 10 cells**, each cell running `(0,0)` at its bottom-left to `(1,1)` at its top-right.

The image the README reaches for ("fractals from 5 to 6 have the same fractions as 7 to 8") is exactly right: every full width of one cell produces an identical copy of the ramp, so you get repetition, not a single gradient.

### Step 4 — name the cell

```glsl
vec2 cell = fract(vUvs * 10.);
```

Same thing as Step 3, but the result lives in one variable. The README's reason is good engineering: **one place to change the grid density**. Want 20×20? Change the single `10.` — not two lines.

### Step 5 — distance to the cell center: `0.5 - max(d1, d2)`

![[2026-10-22_21-19.png]]
Now we want to *manipulate every single cell*: a value that is one color at the cell's edges and blends toward a different color in the middle — the "thickness" of the cell. The README gives the formula up front:

```glsl
d = 0.5 - max(d1, d2)
```

where `d1`, `d2` are the horizontal and vertical distance from the cell center to the chosen line. Deconstruct it in three moves:

```glsl
// 1. center the cell: [0,1] -> [-0.5, 0.5], zero at the center
cell = abs(cell - 0.5);

// 2. dist: 0 at center, 1 at every edge
float distToCell = 2.0 * max(cell.x, cell.y);

// 3. invert: 1 at center, 0 at edges
distToCell = 1.0 - distToCell;
```

- **`cell - 0.5`** shifts the local range from `[0, 1]` to `[-0.5, 0.5]`, so the center of the cell is now `0`.
- **`abs(...)`** — yes, it is component-wise on vectors (the README's guess is correct): each `-0.5 → 0.5` ramp is *folded* at the center into a V, giving the distance from the center per axis: `0` at the center, `0.5` at all four edges.
- **`max(cell.x, cell.y)`** picks the larger of the two folded distances. At the center both are `0` → `0`. Everywhere on the boundary at least one component reaches `0.5` → `0.5`. So the scalar is `0` precisely at the center and `0.5` on **every** edge — it is the axis-aligned "largest distance" (Chebyshev-style), which is exactly the distance to the closest *edge* in the square sense.
- **`* 2.0`** rescales `[0, 0.5]` → `[0, 1]`, and **`1.0 - ...`** inverts so the brightest value (`1`) sits in the middle of the cell and `0` at the borders.

Algebraically the code is `1 - 2·max(...) = 2·(0.5 - max(...))` — the README's `0.5 - max(d1, d2)` just rescaled and offset. The isolines are **squares** (max of two axes), not circles: the value is `1` at the center point, drops through a shrinking square, and hits `0` on the whole cell border. Every cell draws the same pattern, neighbor borders merge, and you get a **grid of bright cell centers fading to black grid lines** (the "thickness" look the deleted reference image `ticknessfract.png` was meant to show).

### Step 6 — dump the distance into the color

```glsl
color = vec3(distToCell);
```

Gray on all three channels at once: `1` (white) at each cell's center fading to `0` (black) at the shared borders — a visible reference grid, shading-free, waiting for function plots to be drawn over it.

```glsl
varying vec2 vUvs;

vec3 red   = vec3(1., 0., 0.);
vec3 blue  = vec3(0., 0., 1.);
vec3 white = vec3(1.);
vec3 black = vec3(0.);
vec3 yellow = vec3(1., 1., 0.);

void main() {
  vec3 color = vec3(.75);          // gray start

  // color = vec3(vUvs, 0.) * 10.;     // step 2: clamp -> L-shaped frame
  // color = fract(vec3(vUvs, 0.) * 10.); // step 3: 10x10 cells

  vec2 cell = fract(vUvs * 10.);   // step 4: one variable, one density

  // step 5: thickness of the cell
  cell = abs(cell - .5);
  float distToCell = 2. * max(cell.x, cell.y);
  distToCell = 1. - distToCell;

  // step 6

  gl_FragColor = vec4(color, 1.);
}
```

## Gotchas

- **The fragment output clamps to `[0, 1]` per channel.** The entire "why does `* 10.` only show a 0–0.1 frame" question is this one fact. Values are silently clamped on write; nothing errors, you just lose the gradient above `0.1`.
- **Channel order decides the picture.** `vec3(vUvs, 0.)` binds `uv.x` to red and `uv.y` to green — that's why the saturated row is red→yellow at the *bottom* and the column is green→yellow on the *left*, not the other way around. Swap the constructor to `vec3(vUvs.y, vUvs.x, 0.)` and the colors trade axes.
- **`fract` is floor-based, so it's `[0, 1)`, always.** With positive `uv` in `[0, 1]` this can't bite here, but the wrap direction matters the day you offset the grid: `fract(-0.25)` is `0.75`, not `0.25` (see [[0.13_common-math-functions]]).
- **`abs` is component-wise on vectors** — the README suspected this and it's true; no scalar-vs-vector surprise hiding in `abs(cell - 0.5)`.
- **`max` gives *square* isolines; `length` gives circles.** `max(|x|,|y|)` is the distance in the Chebyshev sense — flat along the edges, which is what "thickness of the cell" needs. Swap in `length(cell)` and each cell becomes a circular blob fading to the corners last. Both are legitimately "distance", but only `max` matches the *square* cell.
- **There are two transforms on `distToCell` — rescale (`2.0 *`) and invert (`1.0 - `).** Forgetting one gives an all-black screen (values stuck in `[0, 0.5]`), forgetting the other gives bright edges and a black center — inverted.
- **The density constant lives in one place only if you keep `fract` in a variable.** The commented experiment lines copy `10.` around; the shipped shader correctly names it `cell` so a density change stays a one-line edit.
- **The app runs WebGL, not WebGPU.** The `three/webgpu` import and `WebGPURenderer` block are commented out in `main.ts`; output is `gl_FragColor` (see Outdated).

## Revisit

- The README asked to "explain this better" for three things, all covered in Concept — now *see* them: (1) the `* 10.` clamp regions, (2) the `fract` wrap intuition, (3) the `0.5 - max(d1, d2)` thickness. Rebuild each step from memory with the comments off; that's the drill.
- **Vary the grid density** — `fract(vUvs * 5.)` and `fract(vUvs * 20.)`, and a non-uniform grid `fract(vUvs * vec2(5., 9.))` to confirm cells repeat per-axis.
- **Cell index is the other half of the idiom.** `floor(vUvs * N)` gives the (integer) cell address, `fract(vUvs * N)` the local coordinate inside it — the pair behind every tile/instancing system ([The Book of Shaders — Tiles Patterns](https://thebookofshaders.com/09/)). Use the index to paint cells individually: a checkerboard is `mod(floor(vUvs*N).x + floor(vUvs*N).y, 2.)`.
- **Outline the cells** — pass `distToCell` through `smoothstep` ([[0.9_step-mix-smoothstep]]) to get thin crisp grid lines instead of the soft star, or swap it into `step(0.98, distToCell)` for a bright crosshair in each cell.
- **The reference image `ticknessfract.png` was deleted from the app** — if you want the "expected look" back, re-screenshot the finished shader into `apps/21_14_grid_and_cell/doc_images/` and re-link it.
- **`mod` vs `fract` for the same job** — `fract(vUvs * N)` here is `mod(vUvs * N, 1.0)`; when the grid needs a phase, `fract(vUvs * N + offset)` is the cheap animation trick (`offset` driven by `THREE.Timer`).

## Outdated

**approach is valid** — `fract`-based UV tiling is the canonical grid idiom in GLSL and is unchanged since the earliest spec; nothing here is deprecated.

> 💡 **WebGPU note** — ⚡ The whole lesson ports 1:1 to WebGPU. `fract`, `abs`, `max` are WGSL built-ins with identical component-wise semantics, and the grid idea doesn't touch the renderer at all. In three.js, swap to `import * as THREE from 'three/webgpu'` + `new THREE.WebGPURenderer({ canvas })` (both already sketched in `main.ts`), and in WGSL replace `gl_FragColor = vec4(color, 1.);` with a fragment output variable: e.g. `@location(0) var<out> fragColor : vec4<f32>;`. 🔄
