First hands-on with the *fragment shader*: the fragment shader's job is to "dump out the color" of every pixel. This lesson is about **how colors are represented in GLSL** — which is different from how you're used to writing them in CSS, Photoshop, or HTML.

> This is the direct follow-up to [[0.0_shader-language-intro]]. There we learned the language itself (types, operations, the transformation pipeline). Here we actually start *writing fragment shaders* and thinking about color values.

## Concept

### What the fragment shader does

The **fragment shader** runs once per pixel (fragment) that the mesh covers on the screen, and its whole responsibility — in plain terms — is to **output a color**. That's it. In GLSL ES 1.0 that output variable is `gl_FragColor`:

```glsl
gl_FragColor = vec4(1., 0., 0., 1.); // opaque red
```

Compare that to the **vertex shader** from the previous lesson, which had to output a clip-space position (`gl_Position`). The vertex shader produces a few varying values and positions the vertex; the fragment shader decides what color each pixel becomes.

### How colors are represented in GLSL

In CSS, Photoshop, and most design tools, a color is written in one of two familiar forms:

- **HEX** — `0xFF00FF` (or `#FF00FF`)
- **RGB** — `rgb(255, 0, 255)`

Both describe each channel (red, green, blue) with an integer in the range **0–255**.

**GLSL is different.** Shaders deal with colors as **floating-point values in the range `0.0` to `1.0`**. Red is not `255`, it's `1.0`:

```glsl
// Red in CSS:
//   0xFF0000   or   rgb(255, 0, 0)
// Red in GLSL:
vec3(1.0, 0.0, 0.0)
```

So the conversion rule is simply:

$$
glslColor = rgbColor / 255.0
$$

component-wise — each channel of the 0–255 value is divided by `255.0` to land in the 0.0–1.0 range.

### Conversion examples

| HEX | RGB | GLSL |
|---|---|---|
| `0xFF0000` | `rgb(255, 0, 0)` | `vec3(1.0, 0.0, 0.0)` |
| `0x800000` | `rgb(128, 0, 0)` | `vec3(0.501, 0.0, 0.0)` — because `128 / 255 = 0.501...` |
| `0xFF8000` | `rgb(255, 128, 0)` | `vec3(1.0, 0.501, 0.0)` — a warm orange |

This is exactly what the app does — it takes the CSS-style orange `rgb(255, 128, 0)` and converts it inside the shader:

```glsl
vec3 myColor = vec3(255., 128., 0.); // CSS-style 0-255 values
myColor /= 255.;                     // component-wise division → 0.0-1.0
gl_FragColor = vec4(myColor, 1.);
```

The key operation is the `/=` — and because both operands are vectors (`vec3 / float`), GLSL applies it **component-wise**: `255./255.`, `128./255.`, `0./255.`. That's the same component-wise rule for `*`/`/` between vectors and scalars from the previous lesson.

### `vec4` — RGBA and alpha

A fragment color is a `vec4`: **r, g, b, a**. The fourth component is **alpha** (opacity):

- `gl_FragColor = vec4(1., 0., 0., 1.);` — red, fully opaque
- `gl_FragColor = vec4(vec3(1., 0., 0.), 1.);` — same thing; a `vec3` color with alpha as the second argument

Alpha is useful later for **blending** (transparency, additive effects). In this app's example it's just set to `1.0` and not used — it's there because `gl_FragColor` needs all four components.

### Why `1.` instead of `1`?

Same point as the previous lesson: in GLSL `1` is an `int` and `1.0` (or `1.`) is a `float`. Since `vec3`/`vec4` are float vectors, every literal is written with a decimal point. A trailing dot (`1.`) is valid GLSL shorthand.

## Code

in repo - `apps/21_1_simple_colors`

The app renders a single plane with a `ShaderMaterial` built from `shader.vert` + `shader.frag`. The `main.ts` setup is the standard template (WebGL renderer, orthographic camera, animation loop) — the real content of this lesson lives entirely in the shader files.

```glsl
// shader.vert — the vertex shader, unchanged from the previous lesson
void main(){
  vec4 localPosition = vec4(position, 1.);

  // the vertex shader's two responsibilities:
  //  - produce varying values (none here yet)
  //  - output gl_Position
  gl_Position = projectionMatrix * modelViewMatrix * localPosition;
}
```

`position` (an attribute from the geometry), `projectionMatrix`, and `modelViewMatrix` (built-in uniforms) are all provided by Three.js — you don't declare them.

```glsl
// shader.frag — the fragment shader, the star of this lesson
void main(){

  // rgba, and it is red:
  // gl_FragColor = vec4(1., 0., 0., 1.);

  // same thing — rgb color plus alpha as the second parameter:
  // gl_FragColor = vec4(vec3(1., 0., 0.), 1.);

  // the active version — converting a CSS-style color to 0.0-1.0:
  vec3 myColor = vec3(255., 128., 0.); // rgb(255,128,0) = 0xFF8000

  myColor /= 255.; // component-wise division → vec3(1.0, 0.501, 0.0)

  gl_FragColor = vec4(myColor, 1.);
}
```

The result is an opaque **orange** plane (`0xFF8000`), produced by dividing each CSS channel by `255.` right inside the shader.

## Gotchas

- **Don't mix the 0–255 range with the 0.0–1.0 range.** A GLSL color like `vec3(255., 128., 0.)` is *not* "orange in shader form" — it's way out of the valid color range and will render as near-white or garbage. You must normalize by dividing by `255.` (or just write the values in 0.0–1.0 directly).
- **`myColor /= 255.` is component-wise, not "whole vector" division.** Every component gets divided independently: `255./255.`, `128./255.`, `0./255.`. This is the same rule as `*` and `/` between a vector and a scalar from the previous lesson.
- **A `vec3` is not a valid `gl_FragColor`.** `gl_FragColor` expects all four components — that's why the final line always wraps in `vec4(color, 1.)`. Forgetting the alpha leaves you with a compile error.
- **`vec3(1., 0., 0.)` vs `vec4(1., 0., 0., 1.)`.** A `vec3` is just the color channels; the `vec4` adds alpha. They're different types and GLSL won't silently convert.
- **Write float literals with a decimal point.** `vec4(1, 0, 0, 1)` with bare `int`s won't compile — always `1.` / `0.` / `.5`.
- **`128 / 255` is not exactly `0.5`.** It's `0.5019...`. When you see "dark red" like `0x800000` in GLSL, it's `vec3(0.501, 0.0, 0.0)`, not a clean half.

## Revisit

- **Blending.** Alpha was mentioned but not used. The next step is `renderer` blending settings (e.g. `THREE.AdditiveBlending`, `THREE.NormalBlending`) to see what alpha actually *does* once transparency is on.
- **Playing with conversion live.** Take a few HEX colors, convert them by hand to 0.0–1.0, then swap them into `myColor` in the fragment shader and verify the plane matches your mental math. (The GUI has plane position tweaks, but no color control yet — adding a `lil-gui` color picker and wiring it to a `uniform` would be a natural next experiment.)
- **Switching the same color to `vec4(vec3(...), alpha)` form** and varying alpha between `0.` and `1.` to get a feel for how the fourth component reads.
- **A useful mental shortcut:** `rgb / 255` is *almost* "divide by 256" in your head for quick estimates (`0xFF8000` ≈ `(1.0, 0.5, 0.0)`), but the exact conversion always uses `255.0`. Knowing when the estimate is good enough and when it isn't is a small but real shader habit.

## Outdated

The **approach is valid** — color representation in GLSL as 0.0–1.0 floats is fundamental and hasn't changed; every shading language works this way. Writing colors, and the `rgb / 255.0` conversion, remain exactly the same whether you target WebGL or WebGPU.

The only forward-looking note is the same as the whole series: this app uses `WebGLRenderer` and classic GLSL ES `gl_FragColor` on purpose, as a deliberate step before moving to `WebGPURenderer` + TSL, where colors are still 0.0–1.0 floats but are expressed as nodes (`color(...)`) rather than `gl_FragColor` assignments. 🚀

> 💡 More up to date alternative: [Three.js TSL (node-based shading language) docs](https://threejs.org/docs/#api/en/nodes/tsl/TSL) — the WebGPU-native way to express fragment output in Three.js; the color concept is identical, the syntax is a node graph.
