## Concept

This lesson closes the **shader inputs trio**. A `ShaderMaterial` can get data into your shaders in exactly three ways:

| input | what it is | where it lives | accessible in |
| --- | --- | --- | --- |
| **attribute** | per-vertex data, stored on the geometry | geometry buffer | vertex shader only |
| **uniform** | one value for the whole mesh (color, time, …) | material | vertex + fragment shader |
| **varying** | output of vertex shader, input of fragment shader | the GPU pipeline | a channel, not an input |

Varyings were the topic of [[0.2_shader-inputs-varyings-uv]], uniforms of [[0.3_shader-inputs-uniforms]]. Attributes are the last piece.

### What an attribute actually is

Think of a `BufferGeometry` as a table where **every row is one vertex**. The columns are the attributes:

| position | normal | uv | radeDevColor (custom) |
| --- | --- | --- | --- |
| (x0, y0, z0) | (nx0, ny0, nz0) | (u0, v0) | (r0, g0, b0) |
| (x1, y1, z1) | (nx1, ny1, nz1) | (u1, v1) | (r1, g1, b1) |
| … | … | … | … |

Each column is a flat `Float32Array` where consecutive groups of numbers describe one vertex — 3 floats per vertex for a `vec3`, 2 for a `vec2`, 1 for a `float`.

**Three.js already fills in some attributes for you** — that's why you can write `position`, `normal`, and `uv` in a vertex shader without doing anything:

- `position` — vertex coordinates (always present)
- `normal` — vertex normal (present if the geometry computes normals)
- `uv` — texture coordinates (present only if the geometry has UVs; `PlaneGeometry` does)

**Any other attribute you define yourself.** That's the whole point of this lesson.

### The demo, step by step

```ts
// 1. a 1x1 plane → exactly 4 vertices
const planeGeometry = new THREE.PlaneGeometry(1, 1);

// 2. one color per vertex (red, green, blue, cyan)
const colors = [
  new THREE.Color(0xff0000),
  new THREE.Color(0x00ff00),
  new THREE.Color(0x0000ff),
  new THREE.Color(0x00ffff),
];

// 3. 4 colors × 3 floats = 12 flat floats
const colorFloats = colors.map((c) => c.toArray()).flat();

// 4. register it as an attribute: 3 floats per vertex (a vec3)
planeGeometry.setAttribute(
  'radeDevColor',
  new THREE.Float32BufferAttribute(colorFloats, 3),
);
```

The name `radeDevColor` is **deliberately weird** (it's the author's handle) — it proves the attribute is fully custom. If it were a built-in like `uv`, three.js would have created it for you; here you can see the exact place where a name enters the geometry in JS and has to be picked up by the same name in GLSL.

```glsl
// vertex shader
attribute vec3 radeDevColor;   // ← matches the JS name exactly
varying vec3 vRadeDevColor;

void main() {
  gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0);
  vRadeDevColor = radeDevColor;  // pack into a varying → fragment shader
}
```

```glsl
// fragment shader
varying vec3 vRadeDevColor;     // ← must be re-declared here too

void main() {
  gl_FragColor = vec4(vRadeDevColor, 1.0);
}
```

### Why you see a smooth gradient, not 4 hard squares

Attributes are **per-vertex** and only readable in the **vertex shader**. The fragment shader never sees the attribute directly — the vertex shader hands it over through a varying. The GPU then **linearly interpolates** the varying between the triangle's vertices for every pixel in between. So vertex 0 is pure red, vertex 1 pure green, and everything in between is a blend — the plane renders as a smooth color gradient with each corner locked to its own color. `vRadeDevColor` carries the color per vertex; the fragment shader just writes it out.

A small scene detail worth noting: the camera is an `OrthographicCamera` with a tiny range (`-0.1 … 1.1`) and the plane is moved to `(0.5, 0.5, 0)`, so the 1×1 plane fills most of the view — that's why the four corners and their colors are clearly visible.

## Code

in repo - `apps/21_4_shader_inputs_attributes`

```ts
import * as THREE from 'three';

// geometry with a custom per-vertex attribute
const geometry = new THREE.PlaneGeometry(1, 1); // 4 vertices

const colors = [
  new THREE.Color(0xff0000),
  new THREE.Color(0x00ff00),
  new THREE.Color(0x0000ff),
  new THREE.Color(0x00ffff),
];
const colorFloats = colors.map((c) => c.toArray()).flat(); // 12 floats

// 3 = floats per vertex, matching the vec3 in the shader
geometry.setAttribute(
  'radeDevColor',
  new THREE.Float32BufferAttribute(colorFloats, 3),
);

const material = new THREE.ShaderMaterial({
  uniforms: {
    color_1: { value: new THREE.Vector3(1, 0, 0) },
    color_2: { value: new THREE.Vector3(0, 0, 1) },
  },
  vertexShader: /* glsl */ `
    attribute vec3 radeDevColor;
    varying vec3 vRadeDevColor;
    void main() {
      gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0);
      vRadeDevColor = radeDevColor;
    }
  `,
  fragmentShader: /* glsl */ `
    varying vec3 vRadeDevColor;
    void main() {
      gl_FragColor = vec4(vRadeDevColor, 1.0);
    }
  `,
});

const mesh = new THREE.Mesh(geometry, material);
scene.add(mesh);
```

Note: the app keeps the shaders in separate `.vert` / `.frag` files and imports them as strings via `vite-plugin-glsl` (types for `*.vert` / `*.frag` imports are declared in `src/types/shaders.d.ts`).

## Gotchas

- **The name must match exactly between JS and GLSL.** `geometry.setAttribute('radeDevColor', …)` and `attribute vec3 radeDevColor;` are two sides of the same contract. There's **no compile error** if they drift apart — three.js just logs a warning and the attribute silently reads as `(0, 0, 0)` in the shader, which is miserable to debug.
- **`itemSize` must match the GLSL type.** A `vec3` needs **3** floats per vertex, a `vec2` needs 2, a `float` needs 1. The total array length has to be `vertices × itemSize` (here 4 × 3 = 12). A mismatch throws a three.js error or gives you garbage data.
- **Attributes are vertex-shader-only.** You cannot use `radeDevColor` in the fragment shader directly — it has to travel through a varying (see `// EXPLAIN:` comments in both shader files).
- **The varying must be declared in *both* shaders.** Declaring it only in the vertex shader is a GLSL compile error.
- **Built-ins are only there if the geometry has them.** `uv` and `normal` exist on `PlaneGeometry`, but a bare `BufferGeometry` built by hand may have no UVs — then reading `uv` is undefined behavior. `position` is always present.
- **Vertex order decides which corner gets which color.** `PlaneGeometry` lays out its 4 vertices in a specific order; if your colors look "rotated" between corners, it's the vertex order, not the color math.
- **`gl_FragColor` is the GLSL 1 (WebGL 1) convention** that three.js still defaults to for `ShaderMaterial`. In GLSL 3 / WebGL 2 you'd use an `out` variable instead (see Outdated).

## Revisit

- **The commented `mix()` line** in `shader.frag` — `vec3 col = mix(color_1, vRadeDevColor, vUvs.y);` — is a tiny example that combines **all three** inputs at once: a uniform (`color_1`), an attribute carried by a varying (`vRadeDevColor`), and the built-in `uv` varying. Worth uncommenting and playing with to lock in how the trio composes.
- **The reserved `color` attribute.** Three.js has a first-class path for per-vertex colors: `geometry.setAttribute('color', new THREE.BufferAttribute(rgbArray, 3))` plus `vertexColors: true` on the material. This lesson's custom attribute shows the raw mechanism; for real work with standard materials you'd use the built-in one.
- **Animating attributes** — attributes are just arrays on the GPU, so you can mutate `attribute.array[i]` per frame and set `attribute.needsUpdate = true` to re-upload. The official particles example ([link](#examples)) does exactly this — a natural next step after the static colors here.
- **Varying interpolation is more subtle than it looks** (perspective-correct interpolation, the difference between `noperspective` and `smooth`). The gradient you see here is the smooth, perspective-correct default — worth reading up on when you hit texturing artifacts later.
- **The WebGPU / TSL way** of reading custom attributes (see Outdated).

## Outdated

The raw-GLSL `ShaderMaterial` + `attribute` keyword approach is **still perfectly valid on WebGL** — that's what this app uses (`THREE.WebGLRenderer`). The `// `three/webgpu` import is commented out at the top of `main.ts`.

⚠️ **But the project's stated direction is WebGPU, and there this exact code does not work as written.** With `WebGPURenderer` / `three/webgpu`, shaders are written in **TSL (Three.js Shading Language)** and compiled to WGSL/GLSL for you. Custom attributes are not declared with the GLSL `attribute` keyword — they're read with the TSL helper:

```js
import * as TSL from 'three/tsl';

const radeDevColor = TSL.attribute('radeDevColor', 'vec3');
// use it directly in the node graph: color().toVec4(1.0)
```

The same geometry-side `setAttribute('radeDevColor', …)` still feeds it, so the JS half of this lesson carries over unchanged — only the shader syntax changes. If the aim is WebGPU fluency, don't over-invest in the raw-GLSL form; learn the concept here, then re-express it in TSL.

> 💡 More up to date alternative: [three.js TSL specification](https://threejs.org/docs/TSL.html) — the `attribute(name, type)` function replaces the raw `attribute` keyword for custom attributes in the WebGPU path. 🤖 suggested

Also, `gl_FragColor` is deprecated in GLSL 3.00 / WebGL 2 in favor of an `out` variable (`out vec4 fragColor;`). Three.js keeps writing it for you at the default GLSL 1 level, so this code runs fine — just know the newer idiom exists for when you set `glslVersion: THREE.GLSL3`.

> 💡 More up to date alternative: [three.js ShaderMaterial docs — `glslVersion`](https://threejs.org/docs/#api/en/materials/ShaderMaterial) — set `THREE.GLSL3` and use `out vec4 fragColor;` instead of `gl_FragColor`. 🤖 suggested
