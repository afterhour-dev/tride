Varyings got *per-vertex* data from the geometry into the fragment shader. But there's another kind of input, and it's the exact opposite: a value that is the **same for every vertex and every fragment** in a draw call — a **uniform**. This lesson introduces uniforms and then puts them to work with GLSL's built-in **`mix()`** function (linear interpolation / LERP), which draws a red→blue gradient across a plane — this time with the colors supplied from JavaScript, not hardcoded.

> This is the direct follow-up to [[0.2_shader-inputs-varyings-uv]]. There the gradient came from `vUvs.x` alone; here the *endpoint colors* are uniforms set from Three.js, and `vUvs.x` plays the role of the interpolation factor `t`.

---

## Concept

### Three kinds of shader input

Every value a shader reads comes from one of three places, and it's worth getting the vocabulary straight because each behaves differently:

| Input | Value of | Where it lives | Set by | Per-… |
|---|---|---|---|---|
| **attribute** | geometry data (position, uv, normal, color) | the GPU buffer for that mesh | the geometry | vertex (raw, before interpolation) |
| **varying** | values handed between shader stages | declared in *both* shaders | the vertex shader | vertex → smoothly interpolated per-fragment |
| **uniform** | a constant for the whole draw call | the material | JavaScript (each frame) | the entire mesh |

So: an attribute says "this vertex is *here*", a varying says "this fragment is *between* those vertices", and a uniform says "everything gets *this value*". A classic analogy — attributes are the coordinates of the terrain, varyings are the altitude measured at every pixel between the survey points, uniforms are the weather, which is the same everywhere for the whole scene draw.

### Declaring a uniform in GLSL — and why you can't initialize it

Declaring a uniform looks deceptively like a normal variable:

```glsl
uniform vec3 color_1;
uniform vec3 color_2;
```

The first thing the code comments document (`shader.frag` lines 4–7) is that you **cannot write a default value**:

```glsl
// ❌ compile error
uniform vec3 color_1 = vec3(1., 0., 0.);
```

This fails because the whole point of a uniform is that its value is decided *outside* the shader, by the program that calls `draw` — the GPU pins the value down just before each draw call. The shader source isn't allowed to pre-empt that. In GLSL ES 1.00 (which Three.js `ShaderMaterial` compiles) initializers on `uniform` declarations are simply forbidden by the spec. The CPU is the only owner of the value.

### Supplying uniforms from Three.js

On the JavaScript side, uniforms are an object on the `ShaderMaterial`, mapping **names to `{ value: ... }` wrappers**:

```ts
const material = new THREE.ShaderMaterial({
  uniforms: {
    color_1: { value: new THREE.Vector3(1, 0, 0) },  // red
    color_2: { value: new THREE.Vector3(0, 0, 1) },  // blue
  },
  vertexShader: vsh,
  fragmentShader: fsh,
});
```

A few mechanics worth noticing:

- **The name must match the GLSL declaration exactly** — case-sensitive. `color_1` in JS talks to `uniform vec3 color_1;` in GLSL and only that.
- **The wrapper is required.** Each entry is `{ value: ... }`; the `value` is what Three.js reads every frame and uploads to the GPU. Writing `color_1: new THREE.Vector3(1, 0, 0)` (no wrapper) uploads nothing.
- **The type must match the GLSL type.** A `vec3` needs a `THREE.Vector3` (or `THREE.Color`) — Three.js does not coerce a plain number into a vector.
- Because `value` is a live reference, **updating is done by mutating it**, e.g. `material.uniforms.color_1.value.copy(someColor)` in the animation loop — not by re-assigning the entry.
- Uniforms like this (with no `uTime` yet) are *static* — the material is created with them and the renderer uploads them on every draw. This app doesn't animate the uniform yet; that's the obvious next step (see `## Revisit`).

### `mix()` — GLSL's built-in linear interpolation

`mix(a, b, t)` returns the value `t` of the way from `a` to `b`. In one line:

$$
mix(a, b, t) = a + t \cdot (b - a)
$$

That formula deserves a derivation, because it also explains the "decimal fraction" (razlomak) intuition from the README. Multiplying the *distance* `b - a` by a fraction `t` picks out a fraction of that distance; adding it back onto `a` lands you a fraction of the way along the trip:

$$
p = a + t \cdot (b - a)
$$

$$
p = a + t \cdot b - t \cdot a
$$

$$
p = a - t \cdot a + t \cdot b
$$

$$
p = (1 - t) \cdot a + t \cdot b
$$

That last form, $p = (1 - t) \cdot a + t \cdot b$, is the symmetric "LERP" form you'll see in most texts — it makes the extremes visible at a glance: with $t = 0$ every bit of $b$ cancels and only $a$ survives; with $t = 1$ the opposite. The two forms are algebraically identical; `mix` is the shader version of exactly this.

Trying a *concrete* fraction makes it click — 25 % of the way means multiply by `0.25`, 75 % means `0.75`, halfway means `0.5`. Work one channel by hand, `a = 1` (red), `b = 0` (blue), `t = 0.5`:

$$
1 + 0.5 \cdot (0 - 1) = 0.5
$$

Now the full red→blue table, component-wise:

| `t` | red channel | green | blue | result |
|---|---|---|---|---|
| `0.0` | 1.0 | 0.0 | 0.0 | red |
| `0.25` | 0.75 | 0.0 | 0.25 | dark reddish-purple |
| `0.5` | 0.5 | 0.0 | 0.5 | muted purple |
| `0.75` | 0.25 | 0.0 | 0.75 | blue-leaning purple |
| `1.0` | 0.0 | 0.0 | 1.0 | blue |

Because red and blue only differ on the R and B channels, the green channel stays at `0.0` the whole way — each channel is interpolated **independently**.

`mix` is overloaded across all GLSL numeric types, and `t` can even be a vector: `mix(vec3, vec3, float)` interpolates all three channels with the same `t` (what this lesson uses), while `mix(vec3, vec3, vec3)` interpolates each channel with its *own* `t`. The scalar form is the workhorse.

### Putting it together — the gradient from uniforms

The final fragment shader:

```glsl
uniform vec3 color_1;
uniform vec3 color_2;
varying vec2 vUvs;

void main(){
  vec3 col = mix(color_1, color_2, vUvs.x);
  gl_FragColor = vec4(col, 1.);
}
```

Everything from the last lesson is reused: `vUvs.x` runs `0.0`→`1.0` across the plane (the plane is a `PlaneGeometry(1, 1)` at `(0.5, 0.5)`, with an orthographic camera whose frustum spans `-0.1`→`1.1`, so the plane fills the view exactly and `uv` maps 1:1 onto the screen). At the left edge `t = 0.0` → pure `color_1` (red); at the right edge `t = 1.0` → pure `color_2` (blue). In between, the GPU interpolates.

The conceptual payoff: **the shader no longer knows its own colors.** `color_1` and `color_2` are data — you can change them from JavaScript, per frame, without touching a single line of shader code. That's the division of labor uniforms exist for.

### The homework — why the middle of the gradient looks darker

The README and the comments in `shader.frag` (lines 41–60) pose a genuinely good puzzle: the *middle* of the red→blue gradient looks darker than both edges, even though "intuitively" a halfway blend should look about as bright as either end.

The answer is in the table above. At `t = 0.5` the color is `(0.5, 0, 0.5)` — **the strongest channel is only 0.5**, so the pixel can only ever be half as "full" as the endpoints:

- red has `R = 1.0` (fully bright red channel, `G = B = 0`),
- blue has `B = 1.0` (fully bright blue channel),
- the midpoint has `R = 0.5, B = 0.5` — no channel anywhere near `1.0`.

The brightness carried by red *drops* (1 → 0.5) while the brightness carried by blue *rises* (0 → 0.5). The two channels never add up — they just trade places through a valley, and at the bottom of the valley nothing is bright. Linear interpolation in RGB moves through a **dark desaturated purple** rather than a vivid one.

Two deeper reasons this feels wrong:

1. **RGB mixing is not what your eye does with pigments or light.** Physically mixing red and blue light gives a *magenta* that you'd expect to stay bright. Linear RGB interpolation instead crosses through grey-ish `(0.5,0,0.5)`.
2. **Brightness isn't linear in RGB.** Perceptually, `0.5` grey is nowhere near "half as bright as white" — the eye's response is roughly a power curve. So the midpoint's *perceived* darkness is extra strong. This is exactly the phenomenon your `pow(col, vec3(1./2.2))` experiment (next section) was poking at.

This is a well-known limitation of mixing colors in RGB. Interpolating in a *perceptual* color space (HSL/HSV, or the modern [Oklab](https://bottosson.github.io/posts/oklab/)) keeps the midpoint vivid — see `## Revisit` for links, and the [Book of Shaders "Color" chapter](https://thebookofshaders.com/06/) for a hands-on take on mixing colors in shaders.

### The commented-out `pow` experiment

`shader.frag` lines 52–60 contain a commented experiment:

```glsl
vec3 col = mix(vec3(1.,0.,0.), vec3(0.,0.,1.), vUvs.x);
col = pow(col, vec3(1./2.2));   // the "0.5 → 0.73" guess
gl_FragColor = vec4(col, 1.);
```

Your guess was exactly right: for the interpolated red channel at the middle, `pow(0.5, 1/2.2) ≈ 0.73`. But notice what `pow(x, 1/2.2)` *is*: a **gamma encode** — the classic `linear → sRGB` transfer function (0.5 grey encodes to a brighter ~0.73 value for display). It brightens the *entire* gradient, not just the middle, and it does nothing about the perceptual muddiness — it's a display-conversion step, not a fix for RGB interpolation.

Modern Three.js color management already has a proper place for this step: built-in materials run `#include <colorspace_fragment>` after `gl_FragColor` is set, converting linear output to `renderer.outputColorSpace` (sRGB by default). A hand-written `ShaderMaterial` does **not** include that chunk automatically — so this is worth a deliberate look (`## Revisit`), not a blind `pow()`.

## Gotchas

- **You cannot initialize a uniform at its GLSL declaration.** `uniform vec3 color_1 = vec3(1.,0.,0.);` is a compile error in GLSL ES 1.00 — the code comments show this exact failure. Uniforms are owned by the CPU; the shader only *reads* them.
- **Declared in GLSL but missing in `material.uniforms` → silent zeros, not an error.** The code comment says this "would throw", but in practice you most often just get black/zero values — the uniform keeps its GLSL default of 0. The reverse is also true: provide a uniform in JS that the shader never uses, and the linker drops it — no visible effect. Debug by checking the name spelling first.
- **Names must match exactly, case-sensitively.** `color_1` in JS and `uniform vec3 color_1;` in GLSL is a match; `color1` or `Color_1` is not.
- **The `{ value: ... }` wrapper is mandatory.** `uniforms.color_1` must be an object with a `value` key. And once set, update by *mutating* that value (`material.uniforms.color_1.value.copy(...)`), never by re-assigning the entry.
- **Uniform types must match shader types.** A GLSL `vec3` needs a `THREE.Vector3` or `THREE.Color`; a `vec2` needs a `THREE.Vector2`. No auto-conversion from plain numbers.
- **`mix()` does not clamp `t`.** `mix(a, b, 1.5)` returns values *past* `b`, and `mix(a, b, -1.)` values before `a` — extrapolation. For a hard clamp, wrap: `mix(a, b, clamp(t, 0., 1.))`.
- **Float literals still need the decimal point.** `mix(color_1, color_2, 0.5)` compiles; `mix(color_1, color_2, 0)` is an int literal and won't.
- **`mix` on colors is per-channel RGB LERP, not a perceptual blend.** That's exactly why the midpoint looks muddy-dark. If you want a vivid red→blue crossing, RGB is the wrong space — see `## Revisit`.
- **`gl_FragColor` is WebGL-1-era GLSL**, same as the previous two lessons. Three.js rewrites it for the actual context; raw WebGL 2 would want an `out vec4` declaration instead.

## Revisit

- **The darker-middle puzzle, generalized.** Interpolating in RGB produces desaturated midpoints. Read [Oklab — a perceptual color space for image processing](https://bottosson.github.io/posts/oklab/) (Björn Ottosson) and try interpolating the same red→blue in HSV/Oklab — vivid magenta in the middle, no dark valley. The [Book of Shaders "Color" chapter](https://thebookofshaders.com/06/) has shader-ready `mix` experiments for exactly this.
- **The `pow(col, vec3(1./2.2))` question — verify against Three.js color management.** Built-in materials get `#include <colorspace_fragment>` (linear → `outputColorSpace`) for free; `ShaderMaterial` does not. Before hand-rolling gamma math, check [Three.js color management](https://threejs.org/docs/#manual/en/introduction/Color-management) and decide whether to include the chunk yourself — double-converting is a classic mistake.
- **`mix` with a vector `t`.** `mix(a, b, vUvs)` interpolates each channel with its own factor — one step away from radial gradients (`mix(a, b, length(vUvs))`), the classic next exercise.
- **Animate the uniforms.** The uniforms here are static. Adding a `uTime` uniform updated in `tick()` (via `THREE.Timer`) is the natural bridge to the rest of the shader series — this app has the commented `gsap` import sitting there for exactly that.
- **Hook the uniforms to lil-gui.** The GUI exists but is hidden (`gui.hide()`, toggle with `H`) and only tweaks the plane's position. `gui.addColor(debugObject, 'color_1').onChange(c => material.uniforms.color_1.value.copy(c))` turns this into a live color picker.
- **`smoothstep` as the contrast to `mix`.** Linear interpolation has visible "bands" in the middle; `smoothstep` shapes the factor so the gradient feels more even to the eye.
- **The commented `WebGPURenderer` line in `main.ts`.** Porting this app to WebGPU/TSL changes the spelling: uniforms become `uniform(vec3(...))` nodes and `mix(a, b, t)` becomes the `mix()` node — the concept transfers 1:1 (see `## Outdated`).

## Outdated

The **approach is valid** — `ShaderMaterial` + GLSL uniforms + `mix()` are stable, widely-taught WebGL concepts that every shading language keeps. The GLSL here is WebGL-1-era syntax (`uniform`, `varying`, `gl_FragColor`) that Three.js accepts and rewrites for the actual context.

Three.js now pushes hard toward `WebGPURenderer` + **TSL** (Three Shading Language). 🚀 Uniforms and `mix` still exist there — as `uniform(...)` nodes and the `mix()` node — and the data-flow lesson (JS owns the values, the shader reads them) is identical. This app even has the `WebGPURenderer` construction commented out at the top of `main.ts`, so it's primed for a port.

> 💡 More up to date alternative: [Three.js TSL docs](https://threejs.org/docs/#api/en/nodes/tsl/TSL) — the WebGPU-native shading language; uniform + `mix` exist as nodes, same concept, different spelling.
