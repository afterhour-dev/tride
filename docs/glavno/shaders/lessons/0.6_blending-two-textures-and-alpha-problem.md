## Concept

[[0.5_textures-and-multiplicative-blending]] put a single texture on the plane and multiplied it by a `tint` uniform. This lesson goes one step further: **two textures at once**, both sampled in the same fragment shader and blended together. The second texture rides a second `sampler2D` uniform called `overlay` — that's the whole new mechanic, plus a detour through what went wrong with transparency while experimenting.

### Two textures in one material

The JS side now hands the material **two** textures, each in its own uniform slot:

```ts
uniforms: {
  diffuse: { value: cityTexture },      // city.png
  overlay: { value: overlayTexture },   // renocetiri.jpg
  tint:    { value: new THREE.Vector4(1.0, 0.0, 0.0, 1.0) },
}
```

The shader declares a matching uniform per texture:

```glsl
uniform sampler2D diffuse;
uniform sampler2D overlay;
```

Two `sampler2D`s are just two "textures you can sample from" — there's no limit of one per material. Each name in GLSL must match a key in the JS `uniforms` object exactly, exactly like in the previous lesson.

### Sampling both, then blending

Both textures are sampled at the *same* UV, which comes in as the `vUvs` varying (the vertex shader is identical to 0.5 — it just forwards the built-in `uv` attribute):

```glsl
vec4 diffuseSample = texture2D(diffuse, vec2(vUvs.x, vUvs.y));
vec4 overlaySample = texture2D(overlay, vUvs);
```

Each call returns a `vec4` of the texel's RGBA. Then the active line of the lesson combines them:

```glsl
gl_FragColor = diffuseSample * overlaySample;
```

That `*` is the **Hadamard product** again (component-wise multiplication, see 0.5): every channel of the city texel is multiplied by the matching channel of the overlay texel — R×R, G×G, B×B, A×A. This is *multiplicative blending* applied to two images: where both are bright the result stays bright, where either is dark the result darkens. It can only darken, never lighten. That's the classic "Multiply" blend mode from Photoshop, done on the GPU.

### The alpha problem

The workshop this app follows used an overlay texture that was *mostly transparent*, and that's where the trouble started. The README describes two versions of the same bug, and it's worth understanding both — they are **not** the same phenomenon, and the second one in this app has an extra twist.

**The author's problem — transparent parts came out black.** The author's overlay was a PNG with a transparent background. Multiplying `diffuseSample * overlaySample` turned the transparent regions **black** instead of letting the diffuse texture show through.

Why: in a *straight-alpha* PNG (the common case), the RGB values under the transparent area are almost always stored as **black** — `(0, 0, 0)` — with alpha `0`. The `w` channel says "don't show this", but the `rgb` channels are still there. `diffuseSample * overlaySample` multiplies the RGB regardless of alpha:

```
black × anything = black        // rgb = 0  ×  city texel = 0
```

So the multiply blend happily shows black where the image is "transparent", because multiplication ignores the alpha channel entirely. This is the classic **black-fringe / black-halo** artifact of straight-alpha images.

**The author's fix — drive a `mix()` with the alpha channel.** Instead of multiplying the colors, use the overlay's own alpha as the blend factor between the two textures:

```glsl
gl_FragColor = mix(diffuseSample, overlaySample, overlaySample.w);
```

`mix(a, b, t)` is GLSL's **linear interpolation** (lerp):

```
mix(a, b, t) = a × (1 − t) + b × t
```

- `t = 0` → result is `a` (the diffuse texture)
- `t = 1` → result is `b` (the overlay)
- `t = 0.5` → a 50/50 blend

With `t = overlaySample.w`, the overlay's alpha decides how much overlay shows: alpha `0` → pure diffuse (transparent area "shows through"), alpha `1` → pure overlay. Written out, that's exactly the standard **"over" compositing operator** from alpha compositing:

```
out = diffuse × (1 − α) + overlay × α
```

(The one nuance: proper "over" usually only mixes RGB and recomputes the output alpha as `α_out = α_src + α_dst(1 − α_src)`. Mixing the whole `vec4` including alpha is a slight shortcut — fine here.)

**The user's problem — the fix showed white.** The README asks why, with the author's `mix()` fix, the transparent parts came out **white** instead of black. The important finding for this doc: **the actual overlay file in this app is `renocetiri.jpg` — a JPEG, which has no alpha channel at all.** And `city.png` is `8-bit RGB` — also no alpha. (Verified with `file`/`identify`: `city.png` is `PNG image data, 2912x1632, 8-bit/color RGB`, `renocetiri.jpg` is a JPEG with `components 3`.)

A JPEG stores three components — R, G, B — and nothing else. When it's uploaded as a `sampler2D`, its alpha channel is filled with a constant `1.0`:

```
overlaySample.w == 1.0   everywhere, because the image has no alpha
```

So the author's fix degenerates:

```
mix(diffuseSample, overlaySample, 1.0) = diffuseSample × 0 + overlaySample × 1 = overlaySample
```

The `mix()` does **nothing** — the fragment shader just outputs the overlay photo in full, everywhere. The "white transparent parts" the user saw were simply the bright (white) regions of the photo being drawn at full strength, not a transparency artifact at all. And plain multiplication "just worked" for the user for the same underlying reason: with an opaque overlay, `diffuse * overlay` is just a multiply (darkening) blend of two photos, which reads as a smooth blend with no black/white seams.

So the honest answer to the README question ("is it a three.js version thing?") is: **mostly no** — the real cause is that the overlay file has no alpha to blend with. A three.js version difference might shift the *black-vs-white* look of genuine transparent PNGs (premultiplied-alpha handling, color space, the sampler's decode), but here there is no alpha in the source image, so the author's alpha-driven approach was guaranteed not to work. To actually see alpha-driven blending, the overlay needs a real alpha channel (a PNG/TGA with transparency), and then the black-vs-white question comes down to how the file stores its transparent texels: straight alpha with RGB=0 → black on multiply, RGB=white or premultiplied → white. The `mix()` fix is the robust choice for both.

### The commented experiments

The README asks to document every example in the shader, commented out or not. There are two more lines in `shader.frag`:

```glsl
// gl_FragColor = diffuseSample * tint * overlaySample;
```

This stacks the 0.5 lesson's `tint` multiply on top of the two-texture blend: the Hadamard product of all three, R×R×R, G×G×G, B×B×B, A×A×A. With the app's `tint = (1, 0, 0, 1)`, green and blue get multiplied by `0` → the two-texture result renders in shades of red. The same "multiply only darkens" rule as before.

```glsl
// gl_FragColor = vec4(vec3(vUvs.x), 1.0);
```

A diagnostic: it ignores both textures and paints the `u` coordinate as grayscale — pure black on the left edge (`u = 0`), pure white on the right (`u = 1`), a smooth gradient in between. It's the fastest way to *see* the interpolated varying working: if the gradient is reversed or stretched, your UVs are wrong. The same trick was the basis of the channel experiments in 0.5.

The vertex shader (`shader.vert`) is unchanged from 0.5 — `projectionMatrix * modelViewMatrix * vec4(position, 1.0)` and forwarding `uv` into `vUvs`. The commented-out `radeDevColor` attribute block in `main.ts` is a leftover from [[0.4_shader-inputs-attributes]], unused here. `material.wireframe = true` is commented out too.

Scene setup note: same orthographic staging as 0.5 — `OrthographicCamera` spanning `-0.1 … 1.1`, the 1×1 plane at `(0.5, 0.5, 0)`, camera at `z = 1`, `OrbitControls` disabled, press `h` to toggle the hidden GUI. The `colorSpace and stuff` comment in `main.ts` marks that `texture.colorSpace` is still unset — same caveat as 0.5.

## Code

in repo - `apps/21_6_shader_blending_textures`

```ts
import * as THREE from 'three';

// 1. two textures → two uniforms (TextureLoader is async — pixels arrive later)
const textureLoader = new THREE.TextureLoader();
const cityTexture = textureLoader.load('/textures/city.png');
const overlayTexture = textureLoader.load('/textures/renocetiri.jpg');

// 2. geometry — 1×1 plane, UVs span [0, 1]
const planeGeometry = new THREE.PlaneGeometry(1, 1);

// 3. material — one sampler2D uniform per texture
const material = new THREE.ShaderMaterial({
  uniforms: {
    diffuse: { value: cityTexture },
    overlay: { value: overlayTexture },
  },
  vertexShader: /* glsl */ `
    varying vec2 vUvs;
    void main() {
      gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0);
      vUvs = uv; // built-in uv attribute → varying
    }
  `,
  fragmentShader: /* glsl */ `
    uniform sampler2D diffuse;
    uniform sampler2D overlay;
    varying vec2 vUvs;

    void main() {
      vec4 diffuseSample = texture2D(diffuse, vUvs);
      vec4 overlaySample = texture2D(overlay, vUvs);

      // multiplicative blending of the two textures (Hadamard product)
      gl_FragColor = diffuseSample * overlaySample;

      // alpha-driven blend — the "over" operator.
      // Only meaningful if the overlay actually HAS an alpha channel:
      // gl_FragColor = mix(diffuseSample, overlaySample, overlaySample.w);
    }
  `,
});

const planeMesh = new THREE.Mesh(planeGeometry, material);
planeMesh.position.set(0.5, 0.5, 0);
scene.add(planeMesh);
```

The app keeps the shaders in `src/shaders/shader.vert` / `shader.frag`, imported as strings via `vite-plugin-glsl` (import types in `src/types/shaders.d.ts`).

## Gotchas

- **JPEG has no alpha channel — the "transparent overlay" premise doesn't hold here.** Both `city.png` (8-bit **RGB**) and `renocetiri.jpg` (3 components) are fully opaque. `overlaySample.w` is `1.0` everywhere, so `mix(diffuseSample, overlaySample, overlaySample.w)` degenerates to `mix(…, 1.0) = overlaySample` — the overlay draws at full strength and the alpha fix visibly does nothing. This, not a three.js version quirk, is why the user's "transparent" parts came out white. If you want alpha-driven blending, the overlay must be a format with an alpha channel (PNG/TGA), not a JPG.
- **Black vs white transparency is a file-format fact, not a shader bug.** A straight-alpha PNG stores transparent texels with RGB `0` (black) → multiplying them darkens to black. A texture with white or premultiplied RGB under alpha `0` → multiplication shows white. `mix(diffuse, overlay, overlay.w)` handles *both* correctly because it stops using the overlay's RGB entirely when `w = 0`. Prefer `mix()` over `*` when the overlay has real transparency.
- **`mix()` is lerp, not a blend mode.** `mix(a, b, t) = a(1−t) + b·t` needs a factor `t` that actually varies. If you hardcode or feed it a constant `1.0`, you just get `b` back — the blend silently disappears.
- **`*` between colors can only darken.** Two images multiplied never get brighter. For a transparency *crossfade* you want `mix()`; for darkening/atmosphere the multiply is right.
- **`*` multiplies the alpha channel too.** `diffuseSample * overlaySample` scales `w` as well as RGB. If either texture's alpha is less than 1, the output becomes partly transparent — which is exactly why the author's transparent PNG looked wrong with multiplication.
- **`texture2D()` and `gl_FragColor` are GLSL 1 / WebGL 1 names.** Three.js' `ShaderMaterial` accepts them by default; in GLSL 3 it's `texture()` and `out vec4`. (See Outdated.)
- **The uniform name is a two-sided contract.** `overlay` must match between the JS `uniforms` object and the GLSL declaration exactly, or the sampler stays unbound and you sample black.
- **`texture.colorSpace` is still unset here** (the `colorSpace and stuff` placeholder). For photographic color textures, modern three.js expects `texture.colorSpace = THREE.SRGBColorSpace`, so this app's colors are technically off — same caveat as [[0.5_textures-and-multiplicative-blending]].
- **Textures load async.** `load()` returns an empty `THREE.Texture` immediately; rendering before the pixels arrive samples black. The app's `LoadingManager.onLoad` log tells you when it's safe.

## Revisit

- **Prove the premultiplied-alpha theory for yourself.** Take a real transparent PNG (any PNG with alpha), load it as the overlay, and compare: (a) `diffuseSample * overlaySample`, (b) `mix(diffuseSample, overlaySample, overlaySample.w)`. Then inspect the file in an editor (Photopea) to see whether the transparent texels store black or white RGB. That observation is the whole black-vs-white story.
- **Check the three.js alpha/color knobs.** `texture.premultiplyAlpha` (default `false`) and `texture.colorSpace` change how the GPU decodes the texel before your shader ever sees it. Toggle them with the same PNG and note how `overlaySample` changes.
- **The diagnostic trick.** Re-derive `vec4(vec3(vUvs.x), 1.0)` from scratch and use it to spot-check UV orientation on any future textured mesh — cheap and always available.
- **Re-read 0.5's gotchas** — everything about UVs, `texture2D`, color space, and the Hadamard product carries over; this lesson adds only the second texture and the `mix()` operator.
- **The WebGPU / TSL way** of mixing two textures (see Outdated).

## Outdated

The raw-GLSL `ShaderMaterial` + `texture2D()` approach is **still perfectly valid on WebGL** — that's what this app runs on (`THREE.WebGLRenderer`).

⚠️ **But the project's stated direction is WebGPU, and the same shaders don't carry over.** With `WebGPURenderer` / `three/webgpu`, shaders are authored in **TSL (Three.js Shading Language)** and compiled to WGSL/GLSL. The two-texture blend survives almost verbatim as node math:

```js
import * as TSL from 'three/tsl';
const diffuse  = TSL.texture(cityTexture);
const overlay  = TSL.texture(overlayTexture);

// multiply blend:  diffuse.mul(overlay)
// alpha mix:       TSL.mix(diffuse, overlay, overlay.a)
```

The JS side (two `TextureLoader` loads, two uniforms) carries over unchanged — only the sampling syntax changes. Learn the *concept* here (two samplers, Hadamard product, `mix()` as the over-operator); re-express it in TSL later.

> 💡 More up to date alternative: [three.js TSL specification](https://threejs.org/docs/TSL.html) — `texture()` nodes and `mix()` replace `sampler2D` + `texture2D()` on the WebGPU path. 🤖 suggested

Also, `texture2D()` and `gl_FragColor` are WebGL 1 / GLSL 1 conventions; GLSL 3 (three.js `glslVersion: THREE.GLSL3`) uses `texture()` and `out vec4 fragColor;`.

> 💡 More up to date alternative: [three.js ShaderMaterial docs — `glslVersion`](https://threejs.org/docs/#api/en/materials/ShaderMaterial) — set `THREE.GLSL3` and use `texture()` / `out vec4 fragColor;`. 🤖 suggested
