## Concept

The last few lessons asked "how does a value move from 0 to 1?" (`mix`, `smoothstep`) and "how do we keep a value inside a range?" (`min`, `max`, `clamp` — see [[0.12_min-max-clamp-saturate]]). This lesson is the **reverse direction**: instead of taking a fraction `t` and producing a value, we take a value that already sits inside a range and ask **"what fraction `t` does it correspond to?"** That's **inverse lerp** — and **remap** is just inverse lerp followed by a regular lerp.

The README is explicit that this is a *concept* lesson: *"We will not code anything but look into inverse lerp function and remap"*. Not the first time the author met them — they first appeared in the math-for-game-dev course (the vault's [[6. Interpolation]] cheatsheet covers the same ground: LERP, inverse LERP, remap).

### Inverse lerp — the fraction from the value

Regular lerp (`mix` in GLSL) answers: given a fraction `t` in `[0, 1]`, what value sits between `minValue` and `maxValue`?

$$mix(minValue, maxValue, t) = minValue + t \cdot (maxValue - minValue)$$

Inverse lerp answers the **opposite** question: given a value already between `minValue` and `maxValue`, what fraction `t` does it sit at? The implementation is straightforward — solve the lerp formula for `t`:

$$t = \frac{currentValue - minValue}{maxValue - minValue}$$

```glsl
float inverseLerp(float currentValue, float minValue, float maxValue) {
  return (currentValue - minValue) / (maxValue - minValue);
}
```

The README puts it in words: *"lerp is giving us a value between `minValue` and `maxValue` based on a fraction multiplier or percent, but inverseLerp is giving us the fraction multiplier back based on a value between"*. The two are exact inverses of each other: `mix(a, b, inverseLerp(x, a, b)) == x` for any `x` inside `[a, b]`.

| call | result |
| ---- | ------ |
| `inverseLerp(0.0, 0.0, 100.0)` | `0.0` |
| `inverseLerp(25.0, 0.0, 100.0)` | `0.25` |
| `inverseLerp(75.0, 0.0, 100.0)` | `0.75` |
| `inverseLerp(100.0, 0.0, 100.0)` | `1.0` |

**It's like `smoothstep`, but linear.** `smoothstep(edge0, edge1, x)` also maps a range to `[0, 1]` — but with a soft S-curve (see [[0.9_step-mix-smoothstep]]). Inverse lerp does the same mapping with a straight line, so it's often called a **"linear step"**: `smoothstep` = eased version, `inverseLerp` = linear version.

### Remap — move a value to a different range, preserving proportion

You have a value that sits inside one range, and you want to place it in a **different** range — at the same proportion, or scale, of that first range. That's remapping. The README's recipe is two steps:

1. **Inverse lerp** the value inside the input range to get the fraction `t`,
2. **Lerp (`mix`)** that fraction between the output range to get the new value.

```glsl
float remap(float currentValue, float inMin, float inMax, float outMin, float outMax) {
  float t = inverseLerp(currentValue, inMin, inMax);
  return mix(outMin, outMax, t);
}
```

The result is the new value — call it `P'` (P prime), the README's notation: `P' = outMin + t * (outMax - outMin)`.

| call | result |
| ---- | ------ |
| `remap(0.0, 0.0, 100.0, 5.0, 10.0)` | `5.0` |
| `remap(50.0, 0.0, 100.0, 5.0, 10.0)` | `7.5` |
| `remap(100.0, 0.0, 100.0, 5.0, 10.0)` | `10.0` |

Halfway through `[0, 100]` (the `50.0`) lands halfway through `[5, 10]` (`7.5`) — the proportion is preserved, only the scale changes. Note that you never actually need the fraction `t` as an intermediate for this use — `remap` is just inverse lerp and lerp **composed** — but keeping it as a named helper makes the intent obvious.

Minimal working example — the two helpers, plus a visual proof on the plane: remap `vUvs.x` from `[0, 1]` to `[0.2, 0.8]` and the gradient starts and ends short of the edges, showing the proportion was preserved:

```glsl
// Fragment shader
varying vec2 vUvs;

// Inverse lerp — the fraction that value sits at between minValue and maxValue
float inverseLerp(float currentValue, float minValue, float maxValue) {
  return (currentValue - minValue) / (maxValue - minValue);
}

// Remap — value from [inMin, inMax] to the same proportion in [outMin, outMax]
float remap(float currentValue, float inMin, float inMax, float outMin, float outMax) {
  float t = inverseLerp(currentValue, inMin, inMax);
  return mix(outMin, outMax, t);
}

void main() {
  // vUvs.x goes 0 → 1 across the plane.
  // Remapped to [0.2, 0.8], the left edge starts at 0.2 grey
  // and the right edge stops at 0.8 — never black, never white.
  float v = remap(vUvs.x, 0.0, 1.0, 0.2, 0.8);
  gl_FragColor = vec4(vec3(v), 1.);
}
```

Try `remap(vUvs.x, 0.0, 1.0, 1.0, 0.0)` to flip the gradient's direction — remapping can also **reverse** a range by swapping the output bounds.

## Gotchas

- **`inverseLerp` and `remap` are not GLSL built-ins.** GLSL gives you `mix` (lerp) and `smoothstep`, but you hand-roll the inverse — the README's key point: *"in other libraries they are built in but not in glsl; unity for example supplies them"* (Unity's `Mathf.InverseLerp`, Three.js's `MathUtils.inverseLerp`). Don't go looking for a built-in in the GLSL spec — write the one-liner yourself.
- **Argument order.** `inverseLerp(currentValue, minValue, maxValue)` — the value comes *first*. And `remap` takes **five** arguments (`currentValue, inMin, inMax, outMin, outMax`) — swapping the two `in` bounds or the two `out` bounds is the classic silent slip: the result looks plausible but is wrong.
- **Division by zero when `minValue == maxValue`.** If the input range collapses to a point (`inMin == inMax`), `inverseLerp` divides by zero → `NaN`/`inf`, which then poisons the whole shader. Guard the degenerate range or make sure the ranges you pass are valid.
- **No clamping — this is extrapolation, not a bound.** `inverseLerp` returns values *outside* `[0, 1]` when `currentValue` is outside `[minValue, maxValue]`, and `remap` happily extrapolates outside `[outMin, outMax]` too. That's often exactly what you want (see Revisit), but if you need the result confined, clamp `t` first: `clamp(t, 0.0, 1.0)` ([[0.12_min-max-clamp-saturate]]).
- **It's linear, not eased.** Inverse lerp is the *"linear step"* — a straight ramp. `smoothstep` is the S-curved cousin. Reaching for `smoothstep` when you want a linear proportion (or vice versa) gives a subtly wrong result: `smoothstep` compresses the middle and takes the exact `t` you asked for and reshapes it.
- **The app runs WebGL, not WebGPU** — the `three/webgpu` import and `WebGPURenderer` are commented out in `main.ts`. The helpers here are plain GLSL (see Outdated).

## Revisit

- **Extrapolation is a feature.** Because inverse lerp doesn't clamp, `t` leaves `[0, 1]` when the value leaves the range — and remap follows. This is how values "overshoot" a target range, the same territory as the `## Extrapolation` section (t out of `0..1`) in the [[6. Interpolation]] cheatsheet. Practice: what does `remap(x, 0.0, 1.0, 0.0, 10.0)` return for `x = 1.5`? (Answer: `15.0`.) That's extrapolation in action.
- **They live in other libraries already.** Unity supplies `Mathf.InverseLerp` and `Mathf.Remap`, and Three.js ships `MathUtils.inverseLerp`. Reading those docs is a good way to confirm the argument order and the no-clamp behavior you just learned in GLSL.
- **Chaining remaps.** Remap is a composition — inverse lerp then lerp. You can chain them to map a value through several ranges, or "un-remap" back by reversing the two ranges. If it ever feels opaque, break it into the two explicit steps (`t`, then `mix`) instead of the one-liner.
- **Draw it.** The plane rig is a cheap way to *see* remap: keep `remap(vUvs.x, 0.0, 1.0, 0.2, 0.8)` and check the left/right edges never hit black or white; then widen the output range past `[0, 1]` (e.g. `-0.5, 1.5`) and watch the gradient exceed black and white — the extrapolation made visible.
- **Mental family.** `step`, `mix`, `smoothstep`, `clamp`, inverse lerp, remap are one family of "range thinking": map a value into `[0, 1]` (step/inverseLerp/smoothstep), blend with it (mix), or confine it (clamp). Come back to [[0.9_step-mix-smoothstep]], [[0.12_min-max-clamp-saturate]] and this lesson together whenever one of them feels isolated.

## Outdated

**approach is valid** — inverse lerp and remap are pure arithmetic that never goes stale, and they still aren't GLSL built-ins, so the hand-rolled helpers above remain the correct way to write them.

> 💡 **WebGPU note** — ⚡ The same holds in **WGSL**: no built-in `inverseLerp`/`remap`, but `mix` exists with identical semantics, so the two helpers port line-for-line. Only the surrounding shader boilerplate changes when you swap `WebGLRenderer` for `WebGPURenderer`. 🔄
