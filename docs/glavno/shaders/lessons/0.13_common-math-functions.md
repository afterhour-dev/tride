## Concept

The lessons so far shaped one value: `step` jumps it, `mix` blends it, `smoothstep` eases it, `clamp` bounds it ([[0.9_step-mix-smoothstep]], [[0.10_mix-and-smoothstep-side-by-side]], [[0.12_min-max-clamp-saturate]]). This lesson is different in spirit: not one curve to master, but a **toolbox of everyday single-number functions** that the workshop author reaches for constantly — `abs`, `floor`, `ceil`, `round`, `fract`, `mod`. The README is explicit: *we are not going to cover all of them, just ones used often* — these are the primitives the next lessons build on.

A shared question the README asks for each function: **"can *a* be a vector?"** Answer up front — **yes, every one of these is component-wise**: `fract(vec2(3.75, -0.25))` runs `fract` on each component independently and returns a `vec2`. A scalar `a` is just the case where the vector has length 1.

### `abs(a)` — strip the sign

```glsl
abs(a)  // a < 0 ? -a : a
```

Absolute value: distance from zero, always `>= 0`. The definition `a < 0 ? -a : a` is literally how you'd hand-roll it.

| call | result |
| ---- | ------ |
| `abs(3.0)` | `3.0` |
| `abs(-3.0)` | `3.0` |
| `abs(-0.75)` | `0.75` |
| `abs(0.0)` | `0.0` |

Vector: `abs(vec3(-0.2, 0.5, -1.0))` → `vec3(0.2, 0.5, 1.0)`.

In the wild, `abs` is the **folding** function: `abs(vUvs.x - 0.5)` takes a left-to-right gradient and mirrors it into a V-shape centered on `0.5` — one half of x and the other. Any time you want the two sides of something to behave the same way, `abs` is the first thing to try.

### `floor(a)` — snap down

```glsl
floor(a)  // nearest integer (as a float!) that is <= a
```

"Floor" = the integer **below or equal**. The key phrase is *less than or equal* — it steps **toward −∞**, not toward zero. That one detail is where everyone trips (see Gotchas).

| call | result |
| ---- | ------ |
| `floor(3.0)` | `3.0` |
| `floor(3.7)` | `3.0` |
| `floor(-0.2)` | `-1.0` |
| `floor(-3.2)` | `-4.0` |

Vector: component-wise. `floor` is how you **quantize**: `floor(vUvs * 10.0) / 10.0` snaps a gradient into 10 discrete steps (cheap pixelation/grid effects).

### `ceil(a)` — snap up (exact opposite of floor)

```glsl
ceil(a)  // nearest integer (as a float!) that is >= a
```

The ceiling is the **ceiling**: the integer above or equal, stepping toward **+∞**.

| call | result |
| ---- | ------ |
| `ceil(3.2)` | `4.0` |
| `ceil(3.0)` | `3.0` |
| `ceil(-3.7)` | `-3.0` |
| `ceil(0.1)` | `1.0` |

Vector: component-wise. Where floor is "snap to a darker/left slot", `ceil` is "snap to the next one up" — alternating `floor`/`ceil` is a quick way to make a value bounce between two tiers.

### `round(a)` — snap to the nearest integer

```glsl
round(a)  // nearest integer to a
```

Exactly what it says: snap to the closest integer. Works like floor and ceil, but picks whichever integer `a` is *closest to*.

| call | result |
| ---- | ------ |
| `round(3.0)` | `3.0` |
| `round(3.4)` | `3.0` |
| `round(3.7)` | `4.0` |
| `round(-2.3)` | `-2.0` |

⚠️ **The exact-tie case (`x.5`) is implementation-defined in GLSL** — most drivers round half *away* from zero (`round(3.5)` → `4.0`, `round(-3.5)` → `-4.0`), but the spec says the direction is chosen by the implementation. If you need a guaranteed tie behavior, use `roundEven` (rounds ties to the nearest *even* integer: both `3.5` and `4.5` → `4.0`).

Vector: component-wise. `ceil`/`floor`/`round` are the three "snap-to-integer" verbs — the only difference is which direction the tie-breaking leans.

### `fract(a)` — keep only the fractional part

```glsl
fract(a)  // a - floor(a)
```

`fract` discards the integer part and keeps the tail — but *not* by truncation. It's defined as `a - floor(a)`, so it follows floor's "toward −∞" direction. The result is **always in `[0.0, 1.0)`**.

| call | result |
| ---- | ------ |
| `fract(3.75)` | `0.75` |
| `fract(5.0)` | `0.0` |
| `fract(0.5)` | `0.5` |
| `fract(-0.25)` | `0.75` |

Vector: component-wise — go-to for **repeating/tiling**: `fract(vUvs.x * 5.0)` reruns the same `0 → 1` gradient 5 times across the plane, and `fract(vUvs * 10.0)` tiles both axes. Because it always lands in `[0, 1)`, it's also the classic **loop timer**: `fract(t)` wraps elapsed time into a repeating 0..1 sweep. The negative case is why it's called "interesting but a little bit weird" in the README — `fract(-0.25)` is `0.75`, *not* `0.25` (see Gotchas).

### `mod(x, y)` — the remainder

```glsl
mod(x, y)  // x - y * floor(x / y)
```

Modulo — the remainder of `x` divided by `y`. The formula is *right there in the spec*: it's floor-based, so the sign of the result follows **y and floor's direction**, not C-style truncation (see Gotchas).

| call | result |
| ---- | ------ |
| `mod(5.0, 3.0)` | `2.0` |
| `mod(4.5, 2.0)` | `0.5` |
| `mod(7.0, 2.5)` | `2.0` (7 − 2·2.5, since `floor(7/2.5) = 2`) |
| `mod(1.9, 1.0)` | `0.9` |
| `mod(-1.0, 2.0)` | `1.0` |

The README's note: **with `y = 1.0`, `mod` is the same as `fract`** — `mod(1.9, 1.0)` → `0.9` and `fract(1.9)` → `0.9` (both defined as `x - y * floor(x / y)` with `y = 1`). The general mental model: `mod(x, y)` wraps `x` into a window of length `y`, starting at `0`.

`x` and `y` can both be vectors, or **one of them a scalar** (broadcast): `mod(vUvs, 0.2)` wraps every fragment's UV into tiny 0.2-wide cells — the basis of grids, bars, and checkerboards ([The Book of Shaders — Tiles Patterns](https://thebookofshaders.com/09/)).

### The four "snap to integer" functions side by side

`floor`, `ceil`, `round` (and `trunc`, not covered here) are easy to conflate. For a **negative** input, pin one contrast to memory: `floor(-3.2) = -4.0` (down to −∞), while `trunc(-3.2) = -3.0` (toward zero). GLSL gives you `floor`/`ceil`/`round`/`roundEven` but *no* `trunc` — if you ever need truncation, that's why it isn't in this list.

The fragment shader in the repo is still the plain gray placeholder (the color constants `red`/`blue`/`white`/`black`/`yellow` are already declared, unused) — the actual exploration is meant to be written in:

```glsl
varying vec2 vUvs;

vec3 red   = vec3(1., 0., 0.);
vec3 blue  = vec3(0., 0., 1.);
vec3 white = vec3(1.);
vec3 black = vec3(0.);
vec3 yellow = vec3(1., 1., 0.);

void main() {
  vec3 color = vec3(.75);
  gl_FragColor = vec4(color, 1.);
}
```

Minimal working example — the classic first experiment: tile a gradient with `fract` and `mod`, side by side (top band `fract(vUvs.x * 5.0)`, bottom band `mod(vUvs.x * 5.0, 1.0)` — identical, because `mod(x, 1.0) == fract(x)`):

```glsl
varying vec2 vUvs;

void main() {
  vec3 color;
  if (vUvs.y > 0.5) {
    // top half: repeating 0..1 gradient, 5 tiles
    color = vec3(fract(vUvs.x * 5.0));
  } else {
    // bottom half: the same thing written with mod(y = 1.0)
    color = vec3(mod(vUvs.x * 5.0, 1.0));
  }
  gl_FragColor = vec4(color, 1.);
}
```

Swap `fract` for `floor`, `ceil`, or `round` (e.g. `vec3(floor(vUvs.x * 5.0) / 5.0)`) to see the stairs each "snap" function draws; use `abs(vUvs.x - 0.5)` for the fold.

## Gotchas

- **`floor` steps toward −∞, not toward zero.** `floor(-0.2)` is `-1.0`, not `0.0`. This is the number-one confusion here, and it's the same reason `fract(-0.25) = 0.75`: the tail is measured "after the last integer *below*", so negative fractions still land in `[0, 1)`.
- **`fract` and `mod` are floor-based, so negative inputs don't behave like C.** `mod(-1.0, 2.0)` is `1.0` in GLSL (sign follows `y`), where C's `%` would give `-1` (sign of the dividend). And the **integer `%` operator in GLSL still behaves like C** — don't expect float `mod` semantics from `%` on ints.
- **`round`'s tie at exactly `x.5` is implementation-defined** — the GLSL spec doesn't guarantee `round(3.5)` → `4.0`. `roundEven` (ties to the nearest even integer) is the guaranteed alternative. Check the [spec PDF](https://registry.khronos.org/OpenGL/specs/es/3.00/GLSL_ES_Specification_3.00.pdf) §8.2 before relying on `round` for exact ties.
- **`floor`/`ceil`/`round` return a `float`, not an `int`** — `floor(3.7)` is the float `3.0`. If you need an actual integer you cast: `int(floor(a))`. There's also no `trunc` built-in in GLSL — that's `floor` for "toward −∞" vs "toward 0" contrast isn't available without hand-rolling.
- **Everything is component-wise on vectors**, scalar broadcasts where the signature allows it (`mod(vec2, 0.2)` broadcasts the scalar `y`). There is no "vector vs scalar comparison" hidden in any of these.
- **The app is currently gray.** All the function exploration happens inside `shader.frag`; until it's rewritten you'll see the `vec3(.75)` fill and nothing else — don't be surprised, the rig below it (ortho camera, plane, GUI) is already live.
- **The app runs WebGL, not WebGPU** — the `three/webgpu` import and `WebGPURenderer` are commented out in `main.ts`. All six functions exist identically in WGSL (see Outdated).

## Revisit

- The README asked **"can `a` be a vector?"** for every function — answer it by experiment, not by nodding: pass `vUvs` itself into each function and watch the gradient respond per-axis. `fract(vUvs * vec2(3.0, 7.0))` tiles columns *and* rows at different rates.
- Draw each function's graph on the plane the way [[0.11_drawing-linear-mix-and-smoothstep]] and [[0.12_min-max-clamp-saturate]] did — plug `vUvs.x` into `floor`, `ceil`, `round`, `roundEven`, `fract`, `mod(vUvs.x, 0.3)` and connect each curve shape with the tables above. Shift first with `vUvs.x - 0.5` so you actually see the *negative* branch, where the four "snap" functions diverge.
- Keep the `mod` → cell-placement trick in your back pocket: `mod(p, size)` gives local coordinates inside a tile, and `floor(p / size)` gives the tile index — that pair is how grids, tiles, and instancing layouts are built ([The Book of Shaders — Tiles Patterns](https://thebookofshaders.com/09/)). These functions will keep showing up in the next lessons; come back here when one of them feels opaque.
- Play with `roundEven` vs `round` on a gradient of `x.5` ties to *see* the divergence on your driver — and remember the spec says it's allowed to change.

## Outdated

**approach is valid** — `abs`, `floor`, `ceil`, `round`, `fract`, `mod` are fundamental GLSL ES built-ins with the same behavior since the specification began, and still exactly what you use for single-value math in shaders.

> 💡 **WebGPU note** — ⚡ All six functions exist as **WGSL** built-ins with identical semantics — `abs`, `floor`, `ceil`, `round`, `fract`, `mod`, all component-wise on vectors. One small improvement: WGSL specifies its `round` **rounds half away from zero** (the GLSL spec leaves ties implementation-defined), and WGSL includes `trunc` natively. Porting this lesson means swapping the renderer and rewriting the shader source in WGSL — the math is unchanged. 🔄
