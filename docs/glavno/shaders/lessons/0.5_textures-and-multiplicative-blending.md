## Concept

Time to put an actual image on the plane. Up to now the fragment shader has been painting colors from math: uniforms ([[0.3_shader-inputs-uniforms]]), attributes carried through varyings ([[0.2_shader-inputs-varyings-uv]], [[0.4_shader-inputs-attributes]]). This lesson adds the last big input — a **texture** — and shows the most important way to combine two colors in a shader: **multiplicative blending**.

The whole pipeline for this app is short: the vertex shader passes the built-in `uv` attribute to the fragment shader as a varying, the fragment shader samples the texture at that position with `texture2D()`, and the resulting `vec4` is multiplied component-wise with a `tint` color.

### What UV coordinates are

A texture is an image, and a model is geometry with no idea what an image is. **UV coordinates are the bridge**: a way of mapping every point of an image onto the surface of the geometry. It's a second coordinate system that lives on the mesh, glued to its vertices.

For the corners of a 1×1 `PlaneGeometry`, the convention is:

| corner | position (XYZ) | UV coordinate |
| --- | --- | --- |
| bottom-left | (-0.5, -0.5, 0) | (0, 0) |
| bottom-right | (0.5, -0.5, 0) | (1, 0) |
| top-right | (0.5, 0.5, 0) | (1, 1) |
| top-left | (-0.5, 0.5, 0) | (0, 1) |

UVs are **normalized to [0, 1]**, independent of the image's pixel resolution — (0, 0) is always the bottom-left of the image, (1, 1) always the top-right. The axes have their own names:

- **U axis** — left to right
- **V axis** — bottom to top

That's why texture coordinates are also called **UV coordinates**, and why the geometry attribute that carries them is named `uv`.

**Why "UV" instead of "XY"?** The user's guess in the README is mostly right: you already have an XYZ space for the model itself, so reusing X and Y for texture space invites confusion. The convention descends from parametric surface math, where a surface is written as a function `P(u, v)` of two parameter variables — and in graphics the third dimension of parameter space is `W`, mirroring model space's `X, Y, Z`. So it's not arbitrary, but it's also not deep: U/V/W is *parameter space*, XYZ is *model space*.

### Getting the texture into the shader

**JS side.** Three.js loads images for you:

```ts
const loadingManager = new THREE.LoadingManager(); // tracks loading progress
const textureLoader = new THREE.TextureLoader(loadingManager);
loadingManager.onLoad = () => console.log('texture loaded'); // fires when all textures are in

const cityTexture = textureLoader.load('/textures/city.png');
```

`textureLoader.load()` returns a `THREE.Texture` immediately (still empty) and fills it with pixels asynchronously once the image finishes downloading — that's what the `onLoad` log is for, to know when it's safe to assume the texture is on the GPU.

**Shader side.** To read a texture in GLSL you need a **sampler** — an opaque built-in type that represents "a texture you can sample from." It's declared as a uniform, because it's one value for the whole mesh:

```glsl
uniform sampler2D diffuse;
```

On the three.js side, the uniform's value is simply the `THREE.Texture`:

```ts
uniforms: {
  diffuse: { value: cityTexture },
}
```

The name `diffuse` is a **convention, not a requirement** — the workshop author called it that because it holds the color (diffuse) texture. In PBR workflows people often say **albedo** or **base color** instead; whatever name you pick, it must match exactly between the JS uniforms object and the GLSL declaration.

### Texels and `texture2D()`

An image on disk is made of **pixels**; the same data in a GPU texture is made of **texels** ("texture elements") — the smallest addressable unit of a texture. The built-in GLSL function that pulls a texel out is:

```glsl
vec4 diffuseSample = texture2D(diffuse, vec2(vUvs.x, vUvs.y));
```

`texture2D(sampler, uv)` takes the sampler and a UV coordinate, and returns **one vec4** — the texel's 4 channels, red, green, blue, alpha, each in [0, 1]. The coordinate is the interpolated `vUvs` from the vertex shader; the GPU figures out which texel (and, thanks to filtering, which mix of neighboring texels) that coordinate falls on. (In GLSL 3 / WebGL 2, `texture2D` is renamed `texture` — see Outdated.)

### Playing with channels (the commented experiments)

The fragment shader has several commented experiments worth understanding — the exact sample is `vec4`, so you can swizzle it:

```glsl
// show only the red channel, broadcast to all 3 → grayscale image
gl_FragColor = vec4(vec3(diffuseSample.r), 1.0);
```

Putting `.r` on every channel collapses red intensity into gray: a red texel contributes bright gray, a blue texel contributes almost black. To keep the image red instead:

```glsl
// red channel on red, zero the others → pure red image, tinted by the original red amounts
gl_FragColor = vec4(vec3(diffuseSample.r, 0.0, 0.0), 1.0);
```

**Flipping homework (now answered in the comments).** To flip the texture, lie to `texture2D` about the coordinates. Subtracting the UV from `1.0` inverts an axis:

```glsl
// flip both axes: (u, v) → (1-u, 1-v)
texture2D(diffuse, vec2(1.0) - vUvs);
// flip vertically only
texture2D(diffuse, vec2(vUvs.x, 1.0 - vUvs.y));
// flip horizontally only
texture2D(diffuse, vec2(1.0 - vUvs.x, vUvs.y));
```

This works because at v = 1 (top of image) you now sample v' = 0 (bottom of image), and vice versa. One subtlety: three.js flips images on load (`Texture.flipY` defaults to `true`) so that v = 0 really is the bottom of the image as seen in an image editor. If the vertical flip "looks wrong", this is usually why.

### Multiplicative blending (the point of the lesson)

Multiplying every channel of one color by the corresponding channel of another:

```glsl
gl_FragColor = diffuseSample * tint;
```

This is called **multiplicative blending**, also *modulation* (a classic term from lighting hardware — "texture modulation"), and it's the *Multiply* blend mode in Photoshop. It is arguably the single most important color operation in shaders: it's how light attenuates, how shadows darken, how "color × texture" tinting works.

`vec4 * vec4` in GLSL is **component-wise** — element-by-element multiplication:

```
vec4 c1 = vec4(0.5);              // vec4(0.5, 0.5, 0.5, 0.5) — one value fills all channels
vec4 c2 = vec4(1.0, 0.5, 0.0, 0.0);

c1 * c2;
// = vec4(0.5*1.0, 0.5*0.5, 0.5*0.0, 0.5*0.0)
// = vec4(0.5, 0.25, 0.0, 0.0)
```

Each channel is multiplied by itself, in lockstep — this is the **Hadamard product** (aka Schur product). Don't confuse it with the dot product or cross product — both of those return a *scalar*; `*` between two vectors returns another vector.

**Why does the plane turn red with `tint = vec4(1, 0, 0, 1)`?** The user's own explanation in the README is exactly right. Multiplying the texel by the tint zeros out every channel whose tint component is 0: green × 0 = 0, blue × 0 = 0. Only red survives, scaled by `tint.r = 1.0` — so the texture renders in shades of red. The alpha channel participates too: `diffuseSample.w × tint.w`. If you wanted the image *lighter*, you couldn't do it with `*` alone — multiplication can only darken (values ≤ 1). Lightening needs `mix()` or `+`; tinting a texture with a color is a classic *modulate* task.

### The vertex shader half

The fragment shader can't see the geometry's `uv` attribute directly — attributes are vertex-shader-only ([[0.4_shader-inputs-attributes]]). So the vertex shader forwards it:

```glsl
varying vec2 vUvs;
void main() {
  gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0);
  vUvs = uv;   // built-in attribute on PlaneGeometry → interpolated per fragment
}
```

Between the plane's 4 corners the GPU **interpolates** `vUvs` across every pixel — that's how the fragment shader always receives a continuous UV that correctly addresses the texture even between vertices.

Scene setup note: the app uses an `OrthographicCamera` with a tiny range (`-0.1 … 1.1`) and the plane moved to `(0.5, 0.5, 0)`, so the 1×1 plane fills most of the view and you can clearly see the texture. Press `h` to toggle the hidden GUI.

## Code

in repo - `apps/21_5_shader_textures`

```ts
import * as THREE from 'three';

// 1. load the texture (async — check LoadingManager.onLoad / console for confirmation)
const loadingManager = new THREE.LoadingManager();
loadingManager.onLoad = () => console.log('texture loaded');
const textureLoader = new THREE.TextureLoader(loadingManager);
const cityTexture = textureLoader.load('/textures/city.png');

// 2. geometry — 1×1 plane, so UVs span [0, 1] across its corners
const planeGeometry = new THREE.PlaneGeometry(1, 1);

// 3. material — texture rides a sampler2D uniform, tint is a plain vec4 uniform
const material = new THREE.ShaderMaterial({
  uniforms: {
    diffuse: { value: cityTexture },
    tint: { value: new THREE.Vector4(1.0, 0.0, 0.0, 1.0) },
  },
  vertexShader: /* glsl */ `
    varying vec2 vUvs;
    void main() {
      gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0);
      vUvs = uv; // built-in uv attribute → varying → fragment shader
    }
  `,
  fragmentShader: /* glsl */ `
    uniform sampler2D diffuse;
    uniform vec4 tint;
    varying vec2 vUvs;

    void main() {
      vec4 diffuseSample = texture2D(diffuse, vec2(vUvs.x, vUvs.y));
      gl_FragColor = diffuseSample * tint; // multiplicative blending
    }
  `,
});

const planeMesh = new THREE.Mesh(planeGeometry, material);
planeMesh.position.set(0.5, 0.5, 0);
scene.add(planeMesh);
```

The app keeps the shaders in separate `shader.vert` / `shader.frag` files imported as strings via `vite-plugin-glsl` (import types declared in `src/types/shaders.d.ts`). The `radeDevColor` attribute block commented out in `main.ts` is leftovers from [[0.4_shader-inputs-attributes]] — proof that the custom-attribute path is orthogonal to texture sampling here.

## Gotchas

- **Texture colors can look washed out without `colorSpace`.** For a color texture (photos, textures meant to be seen as-is) modern three.js expects `texture.colorSpace = THREE.SRGBColorSpace` so the GPU decodes the sRGB image into linear before sampling, then re-encodes on output. This app does **not** set it (the `colorSpace and stuff` comment is a placeholder), so the rendering is technically off — compare after setting it and see the difference.
- **`texture2D` is the old name.** It's the GLSL 1 (WebGL 1) builtin that three.js' `ShaderMaterial` still accepts by default; in GLSL 3 / WebGL 2 it's plain `texture()`. Same for `gl_FragColor` → `out vec4` (see Outdated).
- **The uniform name is a two-sided contract**, same as attribute names: `diffuse` in the JS `uniforms` object must match `uniform sampler2D diffuse;` in GLSL exactly. No compile error if they drift — the sampler just stays unbound and you get empty/black samples.
- **A texture is not ready on the first frames.** `load()` returns immediately; the pixels arrive async. If you render a frame before the image finishes, the plane can sample an empty texture (black). That's what the `LoadingManager.onLoad` console log is for — render after it fires, or fade the mesh in.
- **Don't forget `flipY`.** Three.js flips images on upload by default so UV (0, 0) is the bottom-left. If you write your own loader or generate a canvas texture, you may need to toggle `texture.flipY` to match — the flip-homework experiments above assume three.js' default.
- **`*` between vectors is component-wise, and it can only darken.** New shader authors sometimes expect `colorA * colorB` to "mix"; it doesn't. Multiplicative blending is the multiply/screen logic of blend modes — for anything that should get brighter use `mix()` or `+`.
- **The alpha channel multiplies too.** `diffuseSample * tint` scales `w` as well: `tint.w = 0` would make the output fully transparent. If you're only tinting RGB, set `tint.w = 1.0`.
- **Non-power-of-two images are fine here, mostly.** `city.png` is 2912×1632 — not a power of two. WebGL2 (three.js' default these days) fully supports NPOT textures. Only in WebGL1 would NPOT textures fail (no mipmaps, `ClampToEdgeWrapping` only).
- **`diffuse` is a naming convention, not a requirement.** PBR materials call the same thing *albedo* or *base color*. Don't copy the name because it "sounds right" — pick one and be consistent between JS and GLSL.

## Revisit

- **The UV-flip homework.** The answers are now in the commented code, so re-derive them yourself from scratch: what does `vec2(1.0) - vUvs` do to the image? Which axis does `vec2(vUvs.x, 1.0 - vUvs.y)` invert? The skill is "lie to `texture2D` about coordinates", and it generalizes to scrolling textures later (`vUvs + vec2(time, 0.0)`).
- **"Why UV not XY?"** — the short version is above (parametric surface convention + avoid clashing with model XYZ). Worth reading a few minutes on parametric surfaces (a surface `P(u, v)`) to make the naming stick.
- **texel vs pixel.** The user asked whether "texel" is the right word — it is. Reading up on **mipmaps** makes it concrete: mipmaps are pre-filtered copies of the texel grid at each power-of-two resolution, which is exactly why the texture looks smooth when the plane is small (the GPU samples low-res mip levels).
- **The `colorSpace` pass.** This app deliberately skipped it; a proper pass would set `texture.colorSpace = THREE.SRGBColorSpace` and compare rendering with/without. Related: `renderer.outputColorSpace` (defaults to SRGB).
- **The commented `radeDevColor` block** in `main.ts` — a leftover from the attributes lesson; good mental exercise to spot why it's commented out here (no custom attribute is used by the texture shaders).
- **The WebGPU / TSL way** of sampling textures (see Outdated).

## Outdated

The raw-GLSL `ShaderMaterial` + `texture2D()` approach is **still perfectly valid on WebGL** — that's what this app runs on (`THREE.WebGLRenderer`).

⚠️ **But the project's stated direction is WebGPU, and the same shaders don't carry over.** With `WebGPURenderer` / `three/webgpu`, shaders are authored in **TSL (Three.js Shading Language)** and compiled to WGSL/GLSL. Textures are sampled with node helpers rather than `texture2D`:

```js
import * as TSL from 'three/tsl';
import { texture } from 'three/tsl';

const cityTex = TSL.texture(cityTexture); // a sampler node
// in the node graph: cityTex.mul(tint).toVec4(1.0) — multiplicative blending survives verbatim
```

The JS side (`TextureLoader`, the `THREE.Texture` object) carries over unchanged — only the sampling syntax changes. Learn the *concept* here (sampler, UV, texel, Hadamard product); re-express it in TSL later.

> 💡 More up to date alternative: [three.js TSL specification](https://threejs.org/docs/TSL.html) — `texture()` nodes replace `sampler2D` + `texture2D()` in the WebGPU path. 🤖 suggested

Also, `texture2D()` and `gl_FragColor` are WebGL 1 / GLSL 1 conventions; GLSL 3 (three.js `glslVersion: THREE.GLSL3`) uses `texture()` and `out vec4 fragColor;`.

> 💡 More up to date alternative: [three.js ShaderMaterial docs — `glslVersion`](https://threejs.org/docs/#api/en/materials/ShaderMaterial) — set `THREE.GLSL3` and use `texture()` / `out vec4 fragColor;`. 🤖 suggested
