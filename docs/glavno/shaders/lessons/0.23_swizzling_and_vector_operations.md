## Concept

The intent in one line: *"exploring vector operations, vector methods and functions, and swizzling."* This lesson is the **vector** counterpart of [[0.22_more-math-operations]] — that one surveyed the *scalar* built-ins (`pow`, `sqrt`, `exp`, `log`, …), this one covers the two things that make `vec2`/`vec3`/`vec4` so pleasant to work with in GLSL: **swizzling** (reading/writing components in any order and grouping) and the **common vector functions** (`length`, `normalize`, `dot`, `cross`, `reflect`, `refract`).

It's a *language anatomy* lesson again: the app's shader is the same blank plane scaffold as the last few lessons, a scratch surface you can paste any of the snippets below into.

### Two spellings for the same components

Every vector type can be addressed through **three parallel namespaces** — same storage, different names:

| Type | Position | Color | Texture coords |
|---|---|---|---|
| `vec2` | `xy` | `rg` | `st` |
| `vec3` | `xyz` | `rgb` | `stp` |
| `vec4` | `xyzw` | `rgba` | `stpq` |

So `someVector.g` and `someVector.y` are the **same component** — you pick the namespace that matches what the vector *means*:

```glsl
vec4 color = vec4(0.8, 0.3, 0.1, 1.0);
float redChannel = color.r;   // 0.8  — it's a color, so "r" reads better than "x"
vec3  position  = vec3(1., 2., 3.);
float height    = position.y; // 2.0  — it's a position, so "y"
```

`xyzw` for positions/geometry, `rgba` for colors, `stpq` for texture coordinates. That's the whole point of the aliases: **readability**.

### Reading — swizzle masks

"You can pull out individual components, and you are *not* limited to individual components" — a swizzle is any order/selection of components, and it both *reorders* and *shrinks* the type. Pulling one component gives a scalar; pulling several gives a smaller vector ("subvector"):

```glsl
vec3 v = vec3(0.5, 1.0, 2.0);

float x  = v.x;      // 0.5        — single component
float g  = v.g;      // 1.0        — same slot as v.y, color spelling
vec2  xy = v.xy;     // (0.5, 1.0) — subvector, drops z
vec3  zyx = v.zyx;   // (2.0, 1.0, 0.5) — any order you like
vec2  vv = v.xx;     // (0.5, 0.5) — repetition is fine when READING
vec2  w_only = vec4(1., 2., 3., 4.).wz; // (4.0, 3.0) — even from a vec4 to a vec2
```

The pattern `v.xy` is called a **swizzle mask**: it "masks" the vector, choosing components and how they're arranged. Note that reading can repeat components (`.xx`) and can reorder (`.zyx`) freely — that's the flexible half. Swizzles are also how you *build* vectors from parts: `vec3(v.xy, 1.0)` makes a `vec3` out of a `vec2` plus a scalar — a very common idiom.

### Writing — swizzles as targets

A swizzle can also be the **left-hand side** of an assignment:

```glsl
vec3 v = vec3(0.5, 1.0, 2.0);

v.x = 3.0;              // v == (3.0, 1.0, 2.0) — single component write
v.yx = vec2(0.0, 0.0);  // v.y = 0.0, v.x = 0.0 → v == (0.0, 0.0, 2.0) — swap in place
```

Writing a "subvector" in an order you want **is allowed** — `v.zy = vec2(1., 2.)` compiles and works just fine. But two rules constrain l-value swizzles:

- **No repeated components** — `v.xx = vec2(0.1, 0.2)` is a *compile error*. And it makes sense why: the mask on the left lists which slots to write, and `.xx` lists the same slot twice — two different incoming values could not both land in one component in a well-defined way. The README's hunch is exactly right.
- **No mixed namespaces** — `v.xr = vec2(1., 2.)` (or reading `.xr`) is also an error. Pick one namespace per mask.

And a style note: writing `.zy = …` is legal but people tend not to like it — it reads backwards. `.yz = …` says the same thing without making the reader think. Same for reading: `.yx` is occasionally genuinely useful (swapping), but use natural order by default.

### The common vector functions

Given the lesson's signature — `vec3 someVector = …; vec3 normal = …;` — GLSL gives you these built-ins (all of them exist for `vec2`/`vec3`/`vec4`, except `cross` which is `vec3`-only):

**`length(v)`** — the magnitude:
$$ \mathrm{length}(v) = \sqrt{x^2 + y^2 + z^2} $$

```glsl
float len = length(vec3(1., 2., 2.));  // sqrt(1 + 4 + 4) = 3.0
```

Distance-from-origin in one call. The variant `distance(a, b) = length(a - b)` gives the distance between two points.

**`normalize(v)`** — divide by the length, keep only the direction:
$$ \mathrm{normalize}(v) = \frac{v}{|v|} $$

```glsl
vec3 dir = normalize(vec3(1., 2., 2.));  // (1/3, 2/3, 2/3) — length exactly 1
```

The result is a **unit vector** (length 1), pointing the same way. This is the single most common vector operation in shading — directions like light rays and normals must be unit length before any `dot`. ⚠️ `normalize(vec3(0.))` is a division by zero (see Gotchas).

**`dot(a, b)`** — the scalar product:
$$ a \cdot b = a_x b_x + a_y b_y + a_z b_z = |a|\,|b|\,\cos\theta $$

```glsl
float s = dot(vec3(1., 2., 2.), vec3(0., 0., 1.));  // 2.0
```

`dot` tells you **how aligned two vectors are**: positive → same general direction, zero → perpendicular, negative → opposing. Because the normal is unit here, `s = 2.0 = |a|·cosθ`, so `cosθ = 2/3` → θ ≈ 48°. This is the engine of **diffuse lighting**: `max(dot(normal, lightDir), 0.)` is "how directly does the light hit this surface".

**`cross(a, b)`** — the vector product (only `vec3`):
$$ a \times b = \begin{pmatrix} a_y b_z - a_z b_y \\ a_z b_x - a_x b_z \\ a_x b_y - a_y b_x \end{pmatrix}, \qquad |a \times b| = |a|\,|b|\,\sin\theta $$

```glsl
vec3 perp = cross(vec3(1., 2., 2.), vec3(0., 0., 1.));  // (2., -1., 0.)
```

The result is **perpendicular to both inputs** — check it: `(2,-1,0)·(1,2,2) = 0` and `(2,-1,0)·(0,0,1) = 0`. Direction follows the right-hand rule. This is how you get a surface normal from two triangle edges, or the camera's "right" vector from forward and up.

**`reflect(i, n)`** — bounce a direction off a surface:
$$ \mathrm{reflect}(i, n) = i - 2\,(n \cdot i)\,n $$

```glsl
vec3 mir = reflect(vec3(1., 2., 2.), vec3(0., 0., 1.));  // (1., 2., -2.)
```

`i` (incident) comes in, `n` is the surface normal, and you get the mirrored direction out — the `z` flips sign here because the normal points along `z`. This drives specular highlights, planar mirror tricks, and environment-map lookups.

**`refract(i, n, eta)`** — bend a direction through a material boundary (Snell's law):
$$ \mathrm{refract}(i, n, \eta) = \eta\,i - \left(\eta\,(n \cdot i) + \sqrt{k}\right) n, \qquad k = 1 - \eta^2\,(1 - (n\cdot i)^2) $$

```glsl
vec3 bent = refract(normalize(vec3(1., 2., 2.)), vec3(0., 0., 1.), 0.75);
```

`eta` is the ratio of indices of refraction (e.g. air→water is `1.0 / 1.333 ≈ 0.75`). If the angle is too steep and the square root `k` goes negative, total internal reflection occurs — **GLSL returns `vec3(0.)`** in that case, which you must check for (see Gotchas). `refract` expects unit-length `i` and `n`.

### Why the second vector is called `normal`

The README's own question: *"why is the second vector called `normal`? For dot product it doesn't make sense — if it were a normal, wouldn't the dot product be 0?"*

This confuses *perpendicularity* with *normals*. `dot(a, b) = 0` happens when the two vectors are **perpendicular** — it says nothing about whether `b` is "a normal". A genuine surface normal `n` dotted with a light direction `l` gives `cos(angle)`: `1` when light hits dead-on, `0` only at a grazing 90°. That nonzero value is *exactly* what diffuse lighting wants — so the name `normal` is not wrong there.

The more accurate read: the workshop author reused one signature (`someVector`, `normal`) for all six functions. For `reflect`/`refract` the second argument **is** the surface normal, literally. For `dot` it's just "the reference direction you're measuring against" — a normal, a light ray, a view vector, anything. Call it `referenceDirection` if the name bugs you; the math doesn't care. (Real cottage fact: a `normal` dotted with the *tangent* of its own surface *is* 0 — see Revisit.)

### Check the built-ins before you hand-roll

The closing point of the README: *"GLSL offers a lot of these as built-in functions — your first instinct shouldn't be to go implement it; check if the function already exists."* The [Khronos GLSL common-functions list](https://registry.khronos.org/OpenGL-Refpages/gl4/html/length.xhtml) has dozens of these (`length`, `normalize`, `dot`, `cross`, `reflect`, `refract`, `faceforward`, `distance`, `clamp`, `mix`, `smoothstep`, …). GPU drivers ship dedicated implementations — hand-rolled versions are usually slower and occasionally subtly wrong on edge cases (e.g. `normalize` of a near-zero vector).

The *language* being learned here is best read as a self-contained snippet:

```glsl
// fragment shader scratch — swizzling and vector functions
varying vec2 vUvs;

void main() {
  // ---- swizzling: read ----
  vec3 v = vec3(0.5, 1.0, 2.0);

  float x   = v.x;      // 0.5        — single component
  float g   = v.g;      // 1.0        — color alias of v.y
  vec2  xy  = v.xy;     // (0.5, 1.0) — subvector
  vec3  zyx = v.zyx;    // (2.0, 1.0, 0.5) — any order
  vec2  vv  = v.xx;     // (0.5, 0.5) — repetition OK when reading

  // ---- swizzling: write ----
  v.x = 3.0;              // (3.0, 1.0, 2.0)
  v.yx = vec2(0.0, 0.0);  // v.y = 0.0, v.x = 0.0 → (0.0, 0.0, 2.0)
  // v.xx = vec2(0.1, 0.2); // ERROR: repeated component as a write target

  // ---- vector functions ----
  vec3 someVector = vec3(1., 2., 2.);
  vec3 normal     = vec3(0., 0., 1.);

  float len = length(someVector);          // 3.0
  vec3  dir = normalize(someVector);       // (1/3, 2/3, 2/3)
  float s   = dot(someVector, normal);     // 2.0
  vec3  perp = cross(someVector, normal);  // (2., -1., 0.) — perpendicular to both
  vec3  mir  = reflect(someVector, normal); // (1., 2., -2.) — z flipped
  vec3  bent = refract(normalize(someVector), normal, .75); // needs unit i

  gl_FragColor = vec4(perp, 1.);
}
```

…and the idiom that uses all of it at once, straight out of real lighting code:

```glsl
vec3 n = normalize(vNormal);
vec3 l = normalize(lightPosition - vWorldPosition);
float diffuse = max(dot(n, l), 0.0);
```

## Gotchas

- **An l-value (write) swizzle can't repeat components** — `v.xx = vec2(0.1, 0.2)` and `v.zz = …` are compile errors. Reading `.xx` is fine; writing it is nonsense (two values into one slot). This is the README's "makes sense why" — it's exactly the case they guessed is invalid.
- **A swizzle can't mix namespaces** — `.xy` + `.r` in the same mask (e.g. `v.xr`, `v.rgbw`) is an error in every position, read or write. `vec4(x, y, z, w).rgba` is fine; `v.xyzw` is fine; `v.xrgb` is not.
- **Reversed l-value swizzles are legal but confusing** — `v.zy = vec2(1., 2.)` compiles and swaps, but reads backwards. Prefer `v.yz`. Same spirit for reading: `.yx` is a legit swap trick, don't overuse it.
- **`dot` doesn't return 0 *because* one input is "a normal"** — it's 0 only when the vectors are *perpendicular*. A light direction dotted with a surface normal is `cos(θ)`, which is exactly the diffuse term. The name "normal" is just the reference direction (see Concept).
- **`normalize(vec3(0.))` is a division by zero** — `length` of the zero vector is 0, so the result is `NaN`/garbage. Guard real code: `normalize(max(v, vec3(1e-5)))` or check the length first.
- **`cross` takes exactly two `vec3`s** — no `vec2` version; for 2D "perpendicular" you use the scalar trick `vec2(-v.y, v.x)`.
- **`refract` needs unit-length inputs and can return `vec3(0.)`** — steep angles trigger total internal reflection (`k < 0` in the formula), and GLSL signals that by returning a zero vector. If you feed non-normalized vectors you'll silently get a wrong bend, so check the result: `vec3 r = refract(i, n, eta); if (length(r) < 1e-5) …`.
- **`reflect` is also defined on non-unit `n`** — it still "works" but reflects around a scaled-up normal, giving a wrong (scaled) result. Normalize your normals.
- **Swizzles are for vectors, not matrices** — `mat4` doesn't take `.xyzw` masks (matrix components are accessed via `[row][col]`).
- **WebGL, not WebGPU** — `main.ts` runs `WebGLRenderer` + `ShaderMaterial`; the `WebGPURenderer`/`renderer.init()` path is commented out of the template. Same as the rest of this series (see Outdated for the WebGPU story).

## Revisit

- **The `normal` naming question — close the loop.** The README asks it and this doc gives a reading ("reference direction"), but it's worth proving to yourself: pick a surface normal `n`, a tangent `t` in the same surface, and check that `dot(n, t) == 0` (there's the "0" the README expected!) while `dot(n, lightDir)` is anything but 0 unless the light grazes the surface. The confusion dissolves once you see perpendicularity ≠ normal-hood.
- **The app's shader doesn't practice any of this yet.** The six functions and swizzling are documented but the live fragment still shows the old gradient/line rig. High-value exercise: genuinely *use* one — e.g. a radial gradient with `length(vUvs - vec2(.5))`, a brightness falloff with `1. - dot(...)`, or a UV mirrored with `v.xy` swapping — and watch the plane change.
- **Play with `refract`'s `eta`.** Air→water ≈ `0.75`, air→glass ≈ `0.67`. Find where the `vec3(0.)` (total internal reflection) kicks in by raising the incidence angle — understand *why* the square root in the formula going negative means "the ray can't leave the medium".
- **Verify against the spec.** Check each of the six functions in the [Khronos GLSL refpages](https://registry.khronos.org/OpenGL-Refpages/gl4/html/refract.xhtml) and confirm the exact formulas match what you think they are — spec-reading is a skill on its own.
- **Tie `dot`/`cross` to the math vault.** The same two products appear in `docs/math-for-game-dev` concepts: [[3. Dot Product]] and [[4. Cross Product]] (normalized vectors, direction vectors, scaling, dot and cross) — worth re-reading now that you've seen the GPU versions.
- **`reflect`/`refract` are where "unit vectors matter" bites.** Compare passing the raw (non-normalized) `i` into both — `reflect` keeps working by accident because the `n·i` term scales along with it, `refract` doesn't. That asymmetry is a good mental anchor.
- **WGSL translation.** Swizzles and all six functions exist 1:1 in [WGSL](https://www.w3.org/TR/WGSL/#float-builtin-functions) (`length`, `normalize`, `dot`, `cross`, `reflect`, `refract`), so this exact lesson survives the WebGPU move verbatim at the math level.

## Outdated

**approach is valid** — swizzling is core GLSL (and every shading language worth learning), and `length`/`normalize`/`dot`/`cross`/`reflect`/`refract` are stable built-ins in GLSL ES 3.0 with identical behavior in WGSL. Nothing here is stale.

⚡ **WebGPU note** — this lesson is *fully* doable with `WebGPURenderer` instead of `WebGLRenderer`: WGSL has the same swizzle syntax and the exact same vector built-ins, so the math carries 1:1 and only the plumbing differs (`vUvs` becomes a `@location(0)` vertex output, `gl_FragColor` becomes the return value of an `@fragment` fn). With three.js the idiomatic WebGPU route is TSL rather than a raw `ShaderMaterial`. 🚀
